# T-033 decisions: journal entries and lines, posted through one service

Autonomous team-mode decisions by `ba` for `docs/specs/T-033-journal-entries.md`. Each is the most conventional, safest, reversible choice. Format: `D-n | Question | Decision | Reason | Reversible: yes/no`. Spec-ahead: documents only, no code and no gate run until T-032 is DONE and merged in.

D-1 | What does FP-261 build? | Two tables, `journal_entries` and `journal_lines`; one published posting contract with a reversal operation; four thin permission-checked handlers (get, list, post manual, reverse); the three T-032 ports rebound to the journal; the two foreign keys T-032 owes (`journal_entries.period_id` onto `fiscal_periods`, `fiscal_years.retained_earnings_entry_id` onto `journal_entries`); one seeded number sequence row. Not built: `account_balances` (D-11), `account_mappings` (FP-262), `financial_accounts` (FP-263), `currencies` and `exchange_rates`, HTTP routes, any screen. | The backlog row names entries, lines and one service; the neighbouring rows own the rest. | Reversible: yes, every omission is additive.

D-2 | Name and shape of the published contract. | Contract `PostingService` in `packages/contracts/src/Finance` (name follows `docs/database.md` section 7), with `post(PostingRequest): PostedEntry` and `reverse(ReversalRequest): PostedEntry`; immutable value objects `PostingRequest`, `PostingLine`, `ReversalRequest`, `PostedEntry`; a closed `PostingRefusal` enum and a `PostingRefused` exception carrying the code and the offending field path. Both operations require an open transaction and throw `LogicException` without one, exactly as `PeriodGate::clear` does. | Mirrors the shape T-032 already established for `PeriodGate` and `ChartOfAccounts`, so reviewers and the boundary check see one idiom. `docs/database.md` section 7 says the document and its entry are written in one transaction. | Reversible: yes before FP-262 consumes it.

D-3 | How are amounts carried and validated? | Strict decimal strings matching `^(0|[1-9][0-9]{0,13})(\.[0-9]{1,4})?$`, at most 4 decimal places, at most 14 integer digits (`DECIMAL(18,4)`, T-028 D-14). Integers, floats, null, negatives, exponents, a leading `+`, whitespace and leading zeros are refused, never coerced. Over-precise input is refused, never rounded. All arithmetic is exact string decimal arithmetic. Output is always four decimal places. | `docs/database.md` section 3.2 calls a bare DECIMAL a bug; rounding inside the service would change what a document says it posted and break balance proofs. Refusing is strictly safer than rounding. | Reversible: yes, loosening is additive.

D-4 | Currency columns. | `journal_entries.currency`, `exchange_rate` and `journal_lines.currency`, `exchange_rate`, `base_debit`, `base_credit` are NOT built. All amounts are in the company currency. | `currencies` and `exchange_rates` do not exist (T-032 D-1, D-9); a base column with no rate source would be two numbers that must always be equal. | Reversible: yes, additive expand migration later.

D-5 | Entry statuses, and does this task create drafts? | The status vocabulary is the documented `draft`, `posted`, `reversed`, stored as VARCHAR with an application enum. Every entry the service writes is `posted` on insert. No operation in this task creates a `draft`. The `PeriodCloseBlockers` port still counts drafts (it will report 0 until something creates one). | The documented table has the three states and T-032 AC-41 names draft entries as a blocker. A draft door needs an approval flow nobody has specified. | Reversible: yes.

D-6 | What is the idempotency key and what is compared on replay? | The documented key `(source_type, source_id, source_purpose)`. A replay with the same key and the same payload fingerprint returns the stored entry with `replayed = true` and writes nothing, takes no number. The fingerprint is a SHA-256 of a canonical form of entry date, branch, description, and the ordered lines (account, debit, credit, memo, dimensions); actor and clock are excluded. Same key with a different fingerprint is refused `idempotency_conflict`. A replay is detected before the period gate and the account checks, so a replay of an already-posted entry still succeeds after its period has since closed. A null `source_purpose` must still be unique per `(source_type, source_id)`, so uniqueness cannot rest on a nullable column. `manual` entries may omit `source_id` and then have no idempotency; every other source type must supply one. | The design states the key; the fingerprint is the conventional way to tell a replay from a conflicting reuse (T-028 D-21 class). Returning the stored entry is read-only and cannot change the books. NULLs are distinct in a unique index in both engines (the `number_sequences` migration documents the same trap). | Reversible: yes.

D-7 | Source type vocabulary and `plugin`. | The service accepts the documented closed list (manual, opening, sale, sale_refund, sale_void, grn, purchase_return, supplier_invoice, supplier_payment, customer_payment, expense, expense_payment, payroll_run, payroll_payment, commission_payout, stock_adjustment, stock_transfer, stock_count, stock_production, cash_movement, bank_transaction, revaluation, period_close, year_close, reversal, plugin). Stored as VARCHAR(30) with an application enum (list grows). `plugin_name` is not built (no plugin module). `is_auto` is built: true when the entry was posted with no human actor. | The list is documented; stored as the number-sequence migration stored its own growing list (AC-35(b) there). A type with no module yet is harmless; an unknown type is refused. | Reversible: yes.

D-8 | Document numbering. | One company-wide sequence, `document_type = journal_entry`, prefix `JE-`, padding 6, no reset, seeded by a backfill-phase tenant migration (idempotent, no audit row), the same mechanism as T-032 D-27. Allocated inside the posting transaction with the existing `number_sequences` row-increment pattern, after every validation and after the replay check, so a refusal, a replay or a rollback consumes no number and committed entries are gap-free. A reversal entry takes its own number from the same sequence. A missing sequence row is a deployment fault that fails closed, never silently created. | `docs/database.md` section 6.1 numbers per branch or company-wide and says `journal_entries.number` is unique. One company-wide sequence is the safest reading: an auditor expects one ledger numbering. Seeding avoids a creation race between two first postings. | Reversible: yes (per-branch sequences are additive; numbers already issued never change).

D-9 | Reversal rules. | `reverse` creates a new entry (`source_type = reversal`, `source_id` = the original entry id, `reversal_of_id` = the original) with each line's debit and credit swapped, same accounts, dimensions and memo; and in the same transaction sets the original's `status = reversed` and `reversed_by_id`. These two columns plus `updated_at` are the only columns of a posted entry that ever change, enforced by a static rule. The reversal date is required (no default), must not be earlier than the original's date, and is cleared through the period gate like any posting. A reason of 1 to 500 characters is required. A reversal entry itself is not reversible (`not_reversible`), and an entry already reversed is refused `already_reversed`. Two concurrent reversals of one entry leave exactly one. | `docs/database.md` section 7: nothing is edited after posting, a correction is `reversal_of_id` plus a new entry. The table carries `status` and `reversed_by_id` so those two updates are the documented design. Reversing a reversal is a fresh entry, not a toggle. | Reversible: yes.

D-10 | Who checks permissions? | The posting service performs no permission check (callers are modules that have checked their own actions; T-032 D-28: the gate answers only the period question). Four thin handlers check permission themselves, first, before any transaction or read, refusing `not_permitted`: `finance.journal.view` (get, list), `finance.journal.post_manual` (manual entry), `finance.journal.reverse` (reversal). The soft-closed allowance stays `finance.periods.post_adjustment` (T-032 AC-64). `docs/database.md` section 7 names a `finance.post_closed_period` key; T-032's built key supersedes it. The permission rows are declared through the existing permission declaration mechanism; roles are seeded by the roles task. | Matches T-032 D-24 (handlers check, no route layer). A cashier completing a sale must not need `finance.journal.*`; the human doors do. | Reversible: yes (a key can be merged later).

D-11 | Maintain `account_balances` in this task? | No. Not built, not written. | `docs/patterns.md` section 5 allows the projection but requires a measured slow query before adding one; none exists, and the first consumer (trial balance, FP-268) does not exist. Maintaining it now adds a second source of truth and a write on every posting with no reader. The journal stays the only truth, so a later projection is rebuildable by construction. | Reversible: yes, additive and rebuildable from `journal_lines`.

D-12 | What do the three T-032 ports answer? | `AccountUsage::hasPostings`: any `journal_lines` row names the account, whatever the entry's status (a reversed entry is still history). `FiscalYearUsage::hasEntries`: any entry whose `entry_date` lies in the year's date range, any status. `PeriodCloseBlockers::blockersFor`: one blocker `draft_journal_entries` with the count of entries in status `draft` dated in the range, or an empty list when zero. All three read only the journal and are bound to replace the "none" defaults. | Ports were written for exactly these questions (T-032 D-7). Counting reversed entries is the conservative reading of "has postings". | Reversible: yes.

D-13 | A document dated in a period that closed before its queued posting ran (handed to FP-261 by T-032 D-28). | The service never moves a date. It refuses with the gate's refusal (`period_closed` or `period_soft_closed`) and writes nothing. Parking, alerting or choosing a different open date is the caller's decision (FP-262's queued job), not the ledger's. | Silently re-dating would put revenue in a month the document does not belong to, with no human decision. Refusing keeps the books honest and is the only choice that cannot be wrong. | Reversible: yes. FP-262 owes the park-and-alert rule.

D-14 | Reversal and inactive accounts. | A reversal needs every account on the original's lines to pass `ChartOfAccounts::postable` now. If an account has since been deactivated, the reversal is refused with the account refusal and the accountant reactivates the account first. | One rule for every posting; a special exception for reversals would let inactive accounts take postings by a back door. | Reversible: yes.

D-15 | Entry size and line limits. | At least 2 and at most 200 lines per entry; memo 0 to 255 characters; description null or 1 to 500 characters; the entry total must fit `DECIMAL(18,4)`. | The documented tables imply none of these; a bound is needed to stop unbounded requests, and 200 is far above any documented posting (sale: under 10 lines). | Reversible: yes, raising a limit is additive.

D-16 | Dimensions that have no target table yet. | `journal_lines` carries the dimension columns `branch_id`, `location_id`, `department_id`, `employee_id`, `customer_id`, `supplier_id`, `product_id` as nullable CHAR(26) ULID columns. A foreign key is added (contract phase) only where the target table already exists in the tenant schema; for any other the column stays unguarded and is listed as owed to the owning module, following the `number_sequences.branch_id` precedent. `project_ref`, `tax_id` and `tax_base` are NOT built (no tax tables until FP-267; no project concept). | Foreign keys everywhere inside a database is the rule, but a key onto a missing table cannot exist. Building the tax columns early would invent their meaning. | Reversible: yes.

D-17 | Static proof that nothing else writes the ledger. | A mechanical test fails the build if any code outside the posting service writes `journal_entries` or `journal_lines`, and carries a planted-violation control proving the scan sees real source (it names the directories it scans). | `docs/patterns.md` rule 5 states the rule; a convention without a check decays (the T-032 and earlier tasks' static-rule precedent). | Reversible: yes.

D-18 | Outbox events. | No outbox event is emitted by posting. | `docs/database.md`: the outbox only feeds outward edges; none is named for the journal. Adding one later is additive. | Reversible: yes.

D-19 | Audit volume. | One audit row per entry written (posting or reversal), in the same transaction, summary only (number, source, totals, line count); lines are in `journal_lines`. A replay, a refusal and a read write none. | `Refference/ERP.md` section 24 and `docs/database.md` make journal entries mandatory audit coverage; the line detail already lives in the append-only table. | Reversible: yes.

D-20 | Nightly integrity job and trigger. | Not built. `CHECK (total_debit = total_credit)` on the entry and `CHECK (debit = 0 OR credit = 0)` plus non-negative checks on lines are built; no trigger. The nightly re-check job named in `docs/database.md` is filed as a follow-up (see Questions for the owner). | Checks are cheap and engine-neutral; a job needs a scheduler contract not specified here. | Reversible: yes.

D-21 | Ordering of validations. | Fixed so refusals are deterministic: shape of every field (first failing field in request order, line index ascending), then amounts, then balance, then replay lookup, then period gate, then accounts (ascending account id), then number allocation, then write. | Two simultaneously wrong requests must give one answer in every run (T-032 D-25 precedent for parent checks). | Reversible: yes.

D-22 | Future-dated and backdated entries. | An entry date is accepted if the gate clears it; there is no "not in the future" rule. | The request states no such rule; accruals legitimately post ahead within an open period. Any extra restriction would be an invented business rule. | Reversible: yes.

D-23 | Reversal replay fingerprint. | Reversal idempotency key is `(reversal, original entry id, null purpose)`; the fingerprint covers reversal date and reason. | Same machinery as D-6; a retry returns the same reversal, a retry with a different date is refused `already_reversed` (corrected by D-28; it was worded "conflict"). | Reversible: yes.
