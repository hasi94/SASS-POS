# T-011: Planner fixture baseline and the settings.updated_by contract migration - decisions

Format: `D-n | Question | Decision | Reason | Reversible: yes/no`. Taken by `ba` without the human, under the TEAM PROTOCOL. No escalation trigger applied: no real data is deleted or migrated, no payment, message, paid API or credential, no legal choice. Technical points are marked **-> architect** in the spec.

D-1 | Where does the fixture baseline tree live? | In the test-support tree beside the FX directories (`modules/host/tests/Fixtures/TenantMigrations/`, as a sibling directory to FX1 to FX6), never under the product tree. | The FX sets already live there and are composed by position; a baseline beside them is the same mechanism with one more directory, and no product code can read it. Anything under the product tree is shipped and is what the corpus must stop depending on. | Reversible: yes (a directory move).

D-2 | A frozen copy of today's baseline, or a minimal synthetic baseline? | **Minimal and synthetic**: a few hand-written expand-only files with their own numbering, no contract or destructive step, nothing copied from the product tree. | A frozen copy is drift with a delay: it would need re-freezing at every product file, and it would still be tested as if it were the product. What the corpus needs from a baseline is a plausible starting version and tables to build FX on, not fidelity. Fidelity to the real tree is deliberately carried elsewhere: by the one named shipped-tree case (D-3) and by the product-tree tests (baseline build, catalogue, discipline), which are unchanged. The cost accepted is that a runner test asserting a real table's shape through the baseline must move to that named case or to the product tests (spec E3). | Reversible: yes (the baseline can be swapped for a copy without touching the corpus, since composition is by directory).

D-3 | Which named case keeps measuring the shipped tree, and what does it assert? | One named case (one group, one entry point) that reads the shipped catalogue, derives V from its highest contract step, and asserts: it fails (never skips) if there is no contract step; a fleet at 0 is refused naming the shipped step with zero rows and zero tenant connections; a fleet at V - 1 plans (and a `provisioning` tenant does not block); and the printed remedy is run (D-5). A sweep ensures it is the only reader of the shipped tree in the corpus. | FP-304's own "done when" asks for one named case. These are the assertions the shipped tree could silently stop satisfying, and each has a positive control, so the case measures the product rather than the fixture. Failing instead of skipping when no contract step exists keeps "coverage named, not lost" true; a developer who removes the last contract step must decide knowingly. | Reversible: yes.

D-4 | How do the command-level tests, which build their set from the shipped path, get the fixture baseline? | Through the existing single authority for that path, set in the test, not by editing the command or the kernel. **-> architect** to confirm and name it. | T-010's rejected option was a kernel source change made to let tests pass. The path is already a single configuration key read by one authority. | Reversible: yes.

D-5 | Is the migration driver-gated, as the T-010 plan first prescribed? | **No gate.** One code path on every driver: data-clean pre-check first, then the key. | T-010 step 3b measured all five rebuild properties green on a populated table with Laravel 12's SQLite grammar, and the gate's sibling case (no ALTER that adds a CHECK) is a different fact about a different statement. Carrying the measurement into AC-15 keeps it from being re-derived. | Reversible: yes (a gate is additive).

D-6 | What is the migration's version number? | Not written anywhere. It is one above the previous highest version, derived from the shipped catalogue; the printed remedy is `--to=<V-1>` with V derived. Today's value is not stated in prose or tests. | FP-181 (one authority per number) and the T-010 plan's own correction that "version 15 / `--to=14`" holds only if this key is the next shipped. Any intervening migration would make a literal false silently. | Reversible: yes.

D-7 | What happens to a tenant whose `settings.updated_by` holds an unknown id? | The migration **fails for that tenant**: `settings` is unchanged, no key is added, no rebuild leftovers, its version stays V - 1, the failure is recorded against it, and the other tenants proceed (T-008 isolation). Re-running after the data is fixed succeeds. The migration never deletes, nulls or repairs the value. | Silently clearing an audit-trail value is a data change nobody asked for and cannot be undone; failing closed is the safest and is what T-010 AC-10 already said. | Reversible: yes (an operator-approved repair path could be added later).

D-8 | Does a soft-deleted employee count as an existing employee for the key? | Yes: the key refers to the row. Letter-case differences count as unknown (ids are compared exactly). | A foreign key cannot see `deleted_at`; a rule that treated soft-deleted employees as unknown would be stricter than the key it adds and would make the pre-check disagree with the engine. | Reversible: yes.

D-9 | Does this task turn foreign-key enforcement on in the tenant stanza (FP-305)? | No. The liveness criterion turns it on in the test's own stand-in and shows the off-state control; the dirty-data criterion holds with enforcement off and on. | FP-305 is a connection-factory change every tenant test would inherit and was deliberately kept out of T-010 for that reason; it is no more in scope here. The pre-check is the real guard where enforcement is off. | Reversible: yes.

D-10 | May the failure message carry the offending values? | The count of offending rows and the migration are named; no `updated_by` value from the data. **-> architect** to confirm what the runner's error recording stores. | A message may reach logs; an id from tenant data is not the operator's to read there, and the count is enough to act on (the pre-check can be re-run by hand). | Reversible: yes.

D-11 | Which pre-existing tests may be edited, and how is a sanctioned edit told from a weakening? | Spec AC-24 lists categories E1 to E5 and a "not sanctioned" list, and states no count (the diff derives it). A fleet that starts at 0 still starts at 0. | The T-010 AC-12b pattern: a stated list is checkable; an unstated one makes every edit look like a weakening or none. | Reversible: yes.

D-12 | Are the engine-only tests and `ThreeTenantFixture` re-pointed at the fixture baseline here? | No. They keep the shipped path, are skipped under the engine hold, are named in AC-8's sweep exclusions, and a follow-up is filed by the lead. | They share the defect (a real-engine fleet at 0 against a shipped contract step is refused), but editing a test that cannot be run is an unverified change to the one evidence base the engine hold protects. Naming it avoids the silent loss FP-304 exists to prevent. | Reversible: yes.

D-13 | Is the printed remedy exercised by running it? | Yes, in the named shipped-tree case (AC-11): the message's own remedy is executed against stand-in tenants with the real applier, then the plan to the top succeeds. The existing argument-guard test keeps its own subject. If **-> architect** finds the shipped tree cannot be applied to the stand-in in reasonable time, the criterion degrades to the guard plus the plan to V - 1 and records the application as NOT VERIFIED rather than disappearing. | T-010 plan section 7's standing rule: a printed instruction must be runnable, and the test must run the command it names. Matching the text proved only that the text existed (the T-008 round-3 defect). | Reversible: yes.
