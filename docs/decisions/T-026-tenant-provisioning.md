# T-026 decisions

Format: `D-n | Question | Decision | Reason | Reversible: yes/no`. Autonomous/team-mode work: every
question below was decided rather than left for the human, per the standing protocol. Cross-references
to other tasks' decisions are cited as "T-n D-n".

D-1 | Where does `tenants.code` come from — derived from `--name`, or operator-supplied? | **Operator-supplied, required `--code`**, normalised by trim-then-uppercase (mirroring `OrgCode::normalise()`, T-014) and validated against `ActivationCodeFormat::TENANT_PART_PATTERN`. No slugify-from-name algorithm is built. | Deriving a short code from free text means inventing a slugification policy (truncation length, collision suffixing, transliteration) nobody specified. `OrgCode`'s own precedent for branches/locations/terminals is an explicit, required code, not a derived one. | Reversible: yes — a later task can add a `--code` auto-suggestion on top without changing the stored format.

D-2 | Where does `tenants.slug` come from? | Defaults to the lower-cased `code` when `--slug` is not separately supplied; `--slug` overrides it. | `slug` has no other consumer in the shipped codebase today (measured: no feature reads it); a mechanical, deterministic default avoids inventing a second naming policy while leaving the door open to a real one later. | Reversible: yes.

D-3 | Build the `import_template` fast-path (`docs/database.md` §8 step 7) now, or defer it? | **Defer.** `migrate_remainder` always runs the full migration set from version 0 via the existing runner; no template-dump generation, no CI step to keep it in sync, filed as a follow-up. | The backlog's own line is "run migrations", which the full-set path satisfies. Building template generation and its CI drift-check (`docs/database.md` §9.5) first would smuggle a second, larger task into this one, and nothing about resumability or correctness depends on it — only provisioning speed. | Reversible: yes — adding the fast path later changes nothing about `migrate_remainder`'s observable contract, only its running time.

D-4 | How does provisioning avoid re-implementing T-008's migration runner? | `migrate_remainder` calls the existing `PlanMigrationRunHandler`/`ClaimMigrationJobHandler`/`MigrateTenantHandler` machinery with a **named** selector for the one tenant being provisioned, never a bulk run. | `TenantStatusPolicy::NAMED_ONLY_STATUSES` already exists specifically so a `provisioning`-status tenant is enterable by a named run and invisible to a bulk one; this task is the first real caller of that exact seam, and T-008's `MigrateTenantHandler` docblock states outright that FP-206 owns the `provisioning → active` transition — confirming the runner was built anticipating this task reusing it rather than being extended by it. | Reversible: yes — the call shape can change without touching the runner itself.

D-5 | What exactly does `seed_core` seed, given `docs/database.md` §8 step 9 lists tables (chart of accounts, pay components, payment methods, print templates, `company_profile`) that do not exist in the shipped tree? | **Scope to what already has a working, idempotent, per-tenant seed mechanism today**: `SyncPermissionRegistry` (permissions + the system `owner` role, T-010) and `CreateBranch` (one default branch + its `branch_store` location, T-014). Everything else `docs/database.md` §8 step 9 lists is explicitly out of scope, to be seeded by whichever future task ships its owning module, following the same idempotent-sync shape. | Seeding rows into tables/modules that do not exist would mean this task first inventing the Finance, Payroll and Printing schemas — well beyond FP-206's one-line scope and a decision this role cannot make (chart-of-accounts structure, pay-component rates and print-template content are real business rules nobody has specified yet). | Reversible: yes — later modules add their own seed step without changing this one's contract.

D-6 | `SecretResolver` is read-only (T-003/T-008) — how does `store_credentials` persist two brand-new passwords? | **Revised after architect review round 1 (B-3): the earlier version of this decision was wrong about what already exists.** Measured directly against `TenancyServiceProvider`: only `env://` is registered (`SchemeSecretResolver([EnvSecretResolver::SCHEME => new EnvSecretResolver($app)])`), and `env://` cannot be written (a process environment is not something this task's own process can durably persist into for a *different*, later process to read). **No `file://` driver exists at all** — not read, not write — despite `docs/database.md` §4.4 documenting it as "the default for this project today". So this task builds a brand-new `file://` driver, for **both** reading and writing, confined to one configured directory (a path, not hard-coded — see D-29 for where that directory actually lives). The cloud drivers (`vault://`, `awssm://`, `azkv://`) stay unbuilt, exactly as today. | Writing is new ground regardless of driver, and so — it turns out — is reading via `file://`, which `docs/database.md` describes but nothing has ever implemented. Building exactly the one driver this environment actually uses (local XAMPP / future VPS) avoids building and testing three cloud SDK integrations nobody can exercise here, while finally shipping the driver the design doc already named but nobody had built. | Reversible: yes — the cloud drivers gain read/write support later without changing this task's own contract.

D-7 | Does `activate` write `tenants.status` itself, or rely on `TenantStatusSync`? | **Writes it directly, once**, immediately after starting the subscription, in the same transaction. | `TenantCommercialStatus::PROTECTED` (T-016) explicitly excludes `pending` and `provisioning` from `TenantStatusSync`'s reach, with a comment citing FP-206 by number as the reason — the shipped code already anticipates this task making the one explicit transition out of `provisioning`, rather than extending the reconciler's own protected set. | Reversible: yes, in the sense that a later task could move this write into a shared helper, but the fact that something outside `TenantStatusSync` must make this transition is load-bearing and not meant to be reversed.

D-8 | Does starting a subscription (`StartSubscriptionHandler`, T-016) promote `tenants.status` on its own? | **No** — its internal `TenantStatusSync::reconcile()` call is a no-op while the tenant is still `provisioning` (protected status), so `activate` must make the transition itself (D-7) in the same step, after the subscription row exists. | Measured directly from `CommercialStatus::target()`'s row 0 (protected statuses return unchanged) — relying on the subscription start to flip the status would silently leave every provisioned tenant stuck at `provisioning` forever. | Reversible: yes.

D-9 | `activate`'s subscription-starting status — always `trial`? | Defaults to `trial`; an `--active` flag starts it `active` instead (for an operator provisioning an already-paid account). `StartSubscriptionHandler` itself only accepts these two values. | Matches `docs/database.md` §8 step 12's own "`tenants.status = trial|active`" and gives the common case (a new, unpaid signup) a sensible default without guessing a paid status nobody asked for. | Reversible: yes — the default can change without touching the mechanism.

D-10 | Build the real MySQL/MariaDB `CREATE DATABASE`/`CREATE USER`/`GRANT` driver now, under `ENGINE_HOLD`? | **Build the contract and both implementations** (the real MySQL/MariaDB driver and a recording stand-in), but the real driver is never invoked against a live server in this environment, and the criterion that it actually works is marked `[ENGINE]`/NOT VERIFIED until gate G-1. | Exactly the precedent T-008 (AC-22), T-009 (AC-22/AC-50) and T-023 (AC-18/AC-19) already set: build and prove the real logic, fence the one fact only a live engine can prove, never fake a green result and never skip the design because the engine is unreachable. | Reversible: n/a — this is a verification-timing decision, not a design one; nothing about it needs reversing once G-1 lifts.

D-11 | Does a failed step auto-rollback (compensate) immediately, or stay resumable? | **Stays resumable by default.** Compensation (`docs/database.md` §8's per-step compensation column) only runs on an explicit `tenant:provision --abandon=<run_id>`, never automatically on failure. | The backlog's own framing is "resumable", which implies retry-first; an automatic rollback on every transient failure (a dropped connection, a momentarily-full server) would discard real progress (a created database, written secrets) for a condition that might clear on retry. An explicit abandon command is the deliberate, auditable alternative. | Reversible: yes — an auto-compensate-after-N-failures policy could be layered on later without changing the abandon path's own behaviour.

D-12 | Two concurrent `tenant:provision` invocations for the same `--code` — what happens? | The second is refused at `reserve_identity` once it loses the race on `tenants.code`'s unique index, with a message naming the winning run's id so the operator can `--resume` it instead of starting a parallel, conflicting run. | `tenants.code` is already unique (T-008); relying on that existing constraint as the concurrency backstop avoids building a second, bespoke locking mechanism for a race this task's own schema already prevents. | Reversible: yes.

D-13 | Does `migrate_remainder` plan a fresh migration run every time it is (re-)entered? | No — it records the migration run id on its own step's `output` the first time it plans one, and a re-entry (resumed run) checks for that id first, continuing/claiming the existing run rather than planning a second one. | Planning a second run for a tenant that already has one in flight would race against itself inside T-008's own runner (two `tenant_migration_jobs` rows claiming the same tenant) — avoidable entirely by recording and reusing the first run's id. | Reversible: yes.

D-14 | Does this task cover suspend/deprovision/move/clone (`docs/database.md` §8's "related lifecycles, same machinery")? | **No** — only the `create` provisioning type. The other four are explicitly out of scope, each its own future backlog row. | `docs/database.md` itself presents them as a separate table from the twelve-step `create` sequence FP-206 names, and none of the backlog text for FP-206 mentions them. Building all five would multiply this task's scope well past "create database, record mapping, run migrations, seed defaults, activate". | Reversible: yes.

D-15 | Is `--plan` required, with what default if omitted? | **Required, no default.** A missing `--plan` refuses at input validation, before any row is written. | Which commercial plan a new paying customer starts on is a business decision with real pricing consequences; silently defaulting to some plan would be inventing a business rule, exactly what this role must not do. | Reversible: yes — a default could be added later under a configuration key, itself a reviewed decision.

D-16 | What are the owner employee's and master user's default field values when only `--owner-email` is given? | Employee display name defaults to the local part of the email unless `--owner-name` is supplied; the master `users` row gets a random password with `must_change_password = true`; no welcome-email is sent (no notification module exists yet). | The conventional, safest shape for a login nobody has used: a credential nobody could have guessed, forced to be changed, with no secret transmitted insecurely by this task inventing its own email-sending path. | Reversible: yes.

D-17 | Does `verify` trust `seed_core`'s/`create_owner`'s own reported success, or re-check? | **Re-checks**, reading the tenant connection and the master directly for each postcondition (migrations list, `owner` role's keys, the branch, the owner employee and its master link) rather than trusting the prior steps' own `output` payloads. | Mirrors `docs/database.md` §8 step 11's own description ("assert... assert... run a smoke transaction") and the general project convention (FP-182, "a claim that names its own evidence is checked by opening what it names") rather than compounding an earlier step's possible false-positive. | Reversible: yes.

D-18 | Does `activate` run a smoke transaction (`docs/database.md` §8 step 11's "open a shift, post a 1.00 sale, reverse it") as part of `verify`? | **No** — no `shifts`/`sales` tables exist yet (Sales module unbuilt), so there is nothing to smoke-test. `verify`'s checks are scoped to what this task actually created (AC-32). | Same reasoning as D-5: a step cannot smoke-test a document type that does not exist in the shipped schema yet. | Reversible: yes — add the smoke transaction once Sales exists, as a non-breaking addition to `verify`.

D-19 | Required inputs beyond the backlog's literal `tenant:provision` signature (`docs/database.md` §8's header line names only `--name --plan --owner-email --server --resume`) | Adds `--code`, `--country`, `--timezone`, `--currency`, `--business-type` as required, because `tenants`' own non-nullable columns and `CreateBranch`'s own "no default, inventing one would be a guess" rule both need values from somewhere, and an operator is the only source for them. | The one-line header in `docs/database.md` §8 is illustrative, not an exhaustive CLI contract; the master schema it is built against already requires these fields to be non-null. | Reversible: yes — options can gain defaults later without changing the underlying requirement that the fields exist.

## Architect review round 1 (B-1 to B-11) — `ba`'s own resolutions

D-20 | B-1: AC-2 and AC-17 contradicted each other on step order (`create_users` before `store_credentials`, or the reverse) — which is correct? | **`store_credentials` runs before `create_users`.** The step sequence becomes `create_database, store_credentials, create_users, write_mapping, ...`. `store_credentials` generates both passwords and durably writes them through the new `file://` driver (D-6) before anything reads them back; `create_users` then reads them and calls the engine contract's `createUser()`. | The reverse order loses a password irrecoverably if the process dies between creating a user on the server and writing that user's password down anywhere — leaving a real, created database user with no way to authenticate as it, ever, without a second, separate password-reset operation this task does not otherwise need. Storing first means the only failure mode is "password written, user not yet created", which is a normal, idempotent retry. | Reversible: yes — this is a step-ordering fix with no effect on either step's own external contract.

D-21 | B-2: `abandon` cannot `DROP DATABASE` (the gate forbids any file but `EngineDatabase`, test-only code, from issuing one — a rule from a real incident) and cannot delete the `tenants` row (freeing `sequence` for reuse could collide with the still-existing orphaned database on the server) — what does `abandon` do instead? | `abandon` marks `tenants.status` and `tenant_databases.status` both `archived` (already-designed, otherwise-unused statuses) rather than deleting either row, issues `DROP USER` for the two created database users (a user-level statement, outside the gate's database-drop restriction) and deletes the stored secrets, and **prints the database name and server for the operator to drop by hand**, with an explicit "not dropped automatically" message. | Measured directly: `DestructiveStatementContainmentTest` scans the whole repository for `DROP DATABASE`/`DROP SCHEMA` and fails the gate if any file other than `packages/testing/src/Engine/EngineDatabase.php` (test-only) contains one — written after a real incident (2026-10-14, sixteen databases dropped by a permissively-stubbed guard). A production `abandon` path cannot pass the gate while issuing one. Archiving rather than deleting the `tenants` row also sidesteps the sequence-reuse collision entirely, at the cost of a manual step an operator who chose to abandon a run is already expecting to do some cleanup. | Reversible: yes — a future task could add a *reviewed*, engine-gated, human-triggered drop utility living in production code's own equivalent of `EngineDatabase` if the operational cost of manual drops ever justifies it; nothing here forecloses that, it simply isn't built now.

D-22 | B-4: T-008 left `schema_meta`'s tenant-identity row unwritten, naming FP-206 as its owner (`SchemaMetaIdentity`'s own docblock) — where does this task write it? | `seed_core` writes it (one row, key `tenant_id`, value the tenant's master id), immediately alongside the other seeding it already does; `verify` reads it back through the existing `SchemaMetaIdentity::of()` rather than re-deriving the check. | `seed_core` is already the step that writes the tenant's first real rows after the schema exists, and `SchemaMetaIdentity`/`TenantIdentityMismatch` already exist as the reader/refusal half — adding the one missing write here closes the loop T-008 explicitly left open rather than inventing a thirteenth step for one row. | Reversible: yes.

D-23 | B-5: granting the very first `owner` role in a tenant cannot go through `AssignRoleHandler` (`Escalation::requireRoleHeld()` demands the actor already hold every key `owner` holds, which is unsatisfiable for the first grant, and a `null` actor is refused outright with a message naming FP-206 as the expected caller) — what does `create_owner` call instead? | A new, narrowly-scoped access-bootstrap operation, added to `packages/access` and reached only through a published contract (never `AssignRoleHandler`'s internals): it writes the `employee_roles` row directly, skipping `Escalation::requireRoleHeld()`, but **only when a precondition holds, checked inside the same transaction**: no live (non-soft-deleted) employee in this tenant currently holds a system role keyed `owner`. Any other caller — including a second attempt once an owner already exists — is refused, so this is not a general bypass of the escalation guard, only the one case it cannot otherwise answer. | This is exactly the shape `Escalation`'s own docblock anticipates ("Provisioning is expected to supply a named system actor, not a null one") without widening the guard itself or creating a standing way to skip it for anything but the one chicken-and-egg case that has no other answer. Gating on "no live owner yet" rather than on a caller identity keeps the exception self-limiting and auditable by its own precondition rather than by trust in who calls it. | Reversible: yes — if a future task adds a real platform-level "system actor" identity, this bootstrap operation can be retired in favour of a named actor without changing what `create_owner` observably does.

D-24 | B-6: AC-29 assumed `employees.branch_id` and an invented "provisioning-run reference" for finding the owner on resume — neither exists in the real schema (`employees` has no `branch_id` at all, branch membership is `employee_branches`; the resume key must be a real column) | Branch attachment goes through the existing, unchanged `AttachBranchHandler` (`employee_branches`, `is_default = true`). The resume key is `employees.code = 'OWNER'` — a fixed literal this step always uses, never operator-supplied, which doubles as both the one value this tenant's owner-employee row is always found by and a value `employees.code`'s own uniqueness already protects. | `code` is already `NOT NULL` and unique on `employees`; using the fixed literal `OWNER` for the one employee this step ever creates needs no new column and no new lookup mechanism — the schema already carries exactly what a resume needs. | Reversible: yes.

D-25 | B-8: AC-1 checked only that required fields were present, not that their values were valid — a bad `--timezone`/`--currency`/`--business-type`, an over-length `--branch-name`, or an inactive `--plan` would only surface after a database and two users already existed (steps 3-8), not before step 1 | AC-1 now validates format and existence up front, before `reserve_identity` runs: `--country` (two upper-case letters), `--currency` (three upper-case letters), `--timezone` (a value `DateTimeZone::listIdentifiers()` recognises), `--business-type` (one of `retail`/`restaurant`/`both`, the enum `docs/database.md` §4.1 already names), `--plan` (exists, not soft-deleted, `is_active = true` — the identical lookup `StartSubscriptionHandler` already performs), `--branch-name`/`--branch-code` (`branches`' own column length / `OrgCode::normalise()`). | Every one of these is a mechanical format or existence check against a rule the schema or an existing handler already states — not a new business rule invented by this task — and checking it before any write avoids leaving a real database and two real users behind a validation failure that could have been caught for free. | Reversible: yes — more validations can be added later without changing this one's shape.

## `ba`'s own resolution of the AC-31 / `docs/database.md` conflict the architect flagged

D-30 | The spec's own AC-31 originally refused attaching an existing master `users` row as the owner of a second tenant, but `docs/database.md` §8 step 10 says "insert/attach `users` and `tenant_users`" — attaching an existing user is clearly contemplated, not an oversight. Which reading is correct? | **Attach, not refuse** — `docs/architecture.md` §5 states the capability as an explicit, deliberate design goal ("One person, several shops ... signs in once and switches between them without separate accounts"), so refusing would contradict documented, intended behaviour rather than fill an unspecified gap. `create_owner`'s master-side write now: inserts a new `users` row only when the email is genuinely new; attaches the existing `users` row — unmodified, no new password, no status change — when it already exists, adding only a new `tenant_users` row for the new tenant (`unique(tenant_id, user_id)` already permits the same user across many tenants). The tenant-side `employees` row is still created fresh either way, because an employee identity is per-tenant data even when the login is shared. | The "more conventional" reading is the one the architecture document itself names as a deliberate goal; inventing a refusal the design never asked for would be a second, silent business rule laid on top of a capability the product owner's own authoritative document already describes. | Reversible: yes — if a real need for refusing cross-tenant attachment ever surfaces (fraud, support escalation), it can be added as an explicit, separate refusal rule without changing the schema or the happy path this decision establishes.
