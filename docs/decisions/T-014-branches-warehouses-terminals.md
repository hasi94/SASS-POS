D-4 | What happens to a branch that a foreign key points at when someone tries to delete it? | The keys use the engine default (restrict: the delete is refused). **No operation in T-014 hard-deletes or soft-deletes a branch, location or terminal.** A branch is deactivated, not removed. The `deleted_at` column of the design is created and unused. | History (assignments, numbering, later documents) must keep resolving; the design marks these tables `[SOFT]`, which is what the column is for when a delete rule is eventually decided. Deactivation is reversible, deletion is not. | Reversible: yes (a delete operation can be added; removing a column cannot be done cheaply).

D-5 | What if a tenant already holds a branch id that names no branch (T-010 AC-31 allowed that)? | Each key migration runs a **data-clean pre-check first** (T-011 pattern): count rows with a non-null `branch_id` matching no `branches.id`; if above zero, refuse before altering anything, naming table, column and the **count** (never a value), never delete, null or repair; that tenant fails alone and succeeds on re-run after the data is fixed. Comparison is exact (case matters). | Identical to T-011 D-7 and D-10; a migration that repairs data silently is a data-loss risk. No real tenant exists yet, so the check is expected to pass everywhere; it is there because the stand-in's table rebuild never re-checks data. | Reversible: yes.

D-6 | T-010 AC-31, AC-32 and AC-35 say a well-formed unknown branch id is accepted. After the keys exist that is false. What replaces it? | An unknown branch id is refused `validation` with reason `unknown_branch`; a deactivated branch is refused `branch_inactive` for **attaching and for new assignments or grants only**. Detaching, removing and clearing are never blocked by deactivation. T-010 AC-31 sentence "a well-formed id for which no branch exists is accepted", the matching clauses of AC-32 and AC-35, and the QA test that asserts acceptance are superseded by AC-52. | The database would refuse the row anyway; the application should say why. Blocking removal on an inactive branch would trap rights that must be revocable. | Reversible: yes.

D-7 | FP-309: normalise branch ids to upper case. In T-014 or separately? | **In T-014**, because T-014 is the task that starts generating real branch ids (the backlog row says "before FP-209 starts generating"). Every branch id entering the system (path, body, scope) is folded to upper case at the boundary; generated ids are upper-case ULIDs. The backlog row's remaining work is then the lead's to close. | Under `ascii_bin` a lower- and an upper-case spelling are two different branches; the fold is cheap now and a corrupting mismatch later. | Reversible: yes.

D-8 | Exact semantics of the T-010 D-39 rule (setting another employee's PIN). | Refused `no_escalation`, nothing written, when the target is another employee **and** holds at least one system role **and** the actor does not hold, at each scope concerned, every key the target's grants confer (T-010 AC-36's test). "Holds" counts the target's grants whatever the target's status (a suspended person's rights return on reactivation, T-010 D-38). "System role" means `roles.is_system = true`. A target with no system role is unrestricted by this rule. Self-reset is always allowed (T-010 AC-47). No actor is `actor_required`. The authorization refusals come **before** PIN-value validation. | The rule text is the owner-approved wording in T-010 D-39 and the backlog. Authorization before validation so a weak PIN cannot be used to probe whether a target is protected. Counting status-independent grants is the conservative reading. | Reversible: yes.

D-9 | Does T-014 add a till route that verifies a PIN? Does it settle FP-310 (whitespace around a PIN)? | **No route verifies a PIN** (T-010 AC-49 stays true; the till is later). FP-310 is therefore **not settled here and stays open**; the rule recommended for when the till route is built: the PIN policy sees the raw value and refuses surrounding whitespace as `validation`. | D-39 only blocks routes that verify; with none, the prerequisite is met by the rule alone. Deciding FP-310 without the route that exposes it repeats the mistake T-010 D-39 avoided. | Reversible: yes.

D-10 | Which design-document columns are not created? | Omitted: `branches.cost_centre_account_id` (no `accounts` table), `branches` and other `[CF]` custom fields, `terminals.default_price_list_id` (no price lists), `terminals.invoice_prefix` (document numbering owns it), `terminals.settings` JSON (see D-24), `terminals.last_sync_at`, `offline_since`, `app_version`, `agent_version` (sync and heartbeat tasks own them), `terminal_credentials.secret_hash` and `rotated_at` (D-20), and the `company_profile` table (nothing in FP-209 reads it). `terminals.activation_code` is created as `activation_code_hash` (D-17). All are additive later. | Creating a column nobody writes is a promise nobody keeps (the T-010 D-13 argument); each omitted column is nullable-additive, so adding it later is an expand step. | Reversible: yes.

D-11 | Which location types can be created, and with what defaults? | Types stored: `branch_store`, `warehouse`, `transit`, `consignment`, `damaged`, `virtual` as a validated closed set. T-014 creates `branch_store` **only** as part of branch creation (one per branch, atomically) and `warehouse` by hand; the other four are refused `validation` (their rules belong to FP-251 and later). Defaults when not supplied: `branch_store`: sellable true, purchasable true, negative stock **false**; `warehouse`: sellable false, purchasable true, negative stock **false**. A warehouse may belong to a branch or to none (`branch_id` null, central warehouse). | The design says every branch gets one `branch_store` and a warehouse may belong to no branch. Negative stock off is the safe default; the flag exists and stock itself is FP-250 and FP-251. Sellable false for a warehouse matches "what a terminal sells from". | Reversible: yes.

D-12 | Which permission keys, and branch-scoped or not? | Eight keys: `branches.view`, `branches.manage`, `locations.view`, `locations.manage`, `terminals.view`, `terminals.manage`, `settings.view`, `settings.manage`. All `is_branch_scoped = false`. Revoking a terminal and issuing an activation code are under `terminals.manage`. | Same reasoning as T-010 D-13: no document gives the rule for a person attached to two branches. Company-wide is least surprising and later narrowing is a rule change someone must decide, not a default. | Reversible: partly (making a key branch-scoped later changes who is allowed; it is a deliberate migration of grants).

D-13 | Code and field rules for branches, locations and terminals. | `code`: required, 1 to 10 characters from `A-Z`, `0-9` and `-`, **folded to upper case on input**, unique (branch codes tenant-wide, location codes tenant-wide, terminal codes per branch, soft-deleted rows included), **immutable** after creation. `name` required, 1 to 100 characters, trimmed. `timezone` required, must be a valid IANA zone. `currency` required, three upper-case letters. `email`, if given, a valid address. `phone`, `address` optional. No defaults for timezone or currency. Branch `sort_order` defaults to 0. | Mirrors T-010 AC-25's code rules and the 10-character columns of the design. Timezone and currency are required because inventing a default (or reading a company profile that does not exist yet) would be a guess about the business. Immutable code follows T-010 D-14. | Reversible: yes.

D-14 | When may a branch or location be deactivated? | A branch: refused `has_active_terminals` while any of its terminals is `pending` or `active` (an `inactive` or `revoked` terminal does not block); refused `last_branch` if it is the only active branch. A location: refused `location_in_use` if it is the `default_location_id` of an active branch or the selling location of a `pending` or `active` terminal. Stock-on-hand is **not** checked (no stock exists; FP-251 owns it and must add its own refusal). Deactivating a branch does not change any employee's `perm_version` or token claims. | Same family as `last_owner` (T-010 AC-37): a tenant with no active branch cannot sell. The stock rule cannot be written before stock exists. Deactivation takes effect where branches are used (attach, assign, create terminal, write settings). | Reversible: yes.

D-15 | Terminal states and transitions. | `pending` (created, never activated) -> `active` (activated) <-> `inactive` (administratively paused, reversible) ; `pending`, `active` or `inactive` -> `revoked`. **`revoked` is final**: it cannot be reactivated, re-issued a code or re-enrolled; a replacement tablet is a new terminal with a new code. | Revocation is the response to a lost or stolen device; a path back to life is a path for the thief. A new terminal is cheap, a resurrected compromised one is not. | Reversible: yes (a deliberate re-enrol route can be added; un-revoking is the thing that cannot be taken back once data exists).

D-16 | One device per terminal? Separate device routes? | A terminal has **at most one non-revoked device** at a time and in T-014 exactly one ever (the one it was activated from). Devices are listed read-only; **no device mutation route exists**: a device is revoked only as part of revoking its terminal. A device fingerprint that is the non-revoked device of another terminal cannot activate a second one. The `devices` table keeps the history shape of the design. | Smallest surface that satisfies "devices" in FP-209; replacing a device on a live terminal is a feature nobody asked for. | Reversible: yes.

D-17 | Activation code: format, storage, lifetime. | Format `<TENANT CODE>-XXXX-XXXX` as `docs/database.md` prints (`TEN000123-XXXX-XXXX`), the last two groups drawn from an unambiguous alphabet (no `0`, `O`, `1`, `I`, `L`; **31 characters, amended by D-33**, not 32), generated from a cryptographically secure source. **Only a SHA-256 hash of the secret part is stored** (`activation_code_hash`, indexed); the plaintext is shown **once**, in the response that creates or re-issues it, and is never readable again. Valid **24 hours** from issue (configurable). **Single use**: consumed (hash cleared) on successful activation. Re-issuing for a `pending` terminal replaces it and invalidates the previous one. | The design stores `activation_code` plain; a stored plaintext credential is the conventional thing to avoid, and a high-entropy random code needs no slow hash. 24 hours covers "set up the till tomorrow morning" without leaving a long-lived secret. The tenant part makes first contact resolvable, as the design says. | Reversible: yes.

D-18 | The activation route is public and a code is about 40 bits (39.6, D-33). What stops guessing? | Every failure of every kind (unknown tenant part, unknown or expired or used code, revoked terminal, bad fingerprint, device in use, tenant not active) returns **one identical refusal**. Failures are counted **per tenant part and per caller address** in a fixed window: after **10 failures in 15 minutes** for either, further attempts for that tenant part (or from that address) are refused with the same refusal **even with a correct code** until the window passes. All numbers configurable. The code is never written to a log. | A single refusal and a lockout bound online guessing: 10 tries per 15 minutes against 2^40 is negligible, at the cost that an attacker can briefly block activation for one tenant; the owner can re-try after the window and issue a new code. Per-IP throttling for login is FP-199 and is not a dependency. | Reversible: yes.

D-19 | Terminal token: which claims, and which authority? | Minted at activation and at every terminal refresh: `tenant` claim as for tenant tokens, `terminal_id`, `branch_ids` containing **exactly the one branch of the terminal** (plural form, T-010 D-2), token type/principal `terminal`, access lifetime and refresh rotation **as T-009** (15 minutes access; single-use refresh rotation within a family; replay revokes the family). **No employee claims** (`employee`, `all_branches`, `perm_version`, `perm_hash` are absent). The tenant database is the authority on **every request**: a terminal token is refused when the terminal is not `active`, its credential is not `active`, or its branch is missing. | The two design documents disagree (`branch_id` against `branch_ids`); the plural keeps one claim shape across token kinds. Request-time authority is T-010 D-4's reasoning: the tenant connection is already open, and "revoked" must mean now, not in 15 minutes. | Reversible: yes while no terminal exists in the field.

D-20 | `terminal_credentials.secret_hash` and rotation. | Not built. The terminal's credential is its **refresh-token family** (master `refresh_tokens`, principal type `terminal`) plus the tenant-side `terminal_credentials.status`. The table keeps `device_fingerprint`, `status`, `activated_at`, `activated_by`, `revoked_at`, `revoked_by`. `activated_by` is the employee who issued the activation code in force (read from the issuing audit row, D-34). | A second secret with no route that checks it would be an unchecked credential; the design's purpose (a revocable per-terminal credential) is met by status plus the family. | Reversible: yes.

D-21 | Revocation spans two databases. What if the master step fails? | Tenant side first, in one transaction: terminal `revoked`, credential `revoked`, devices revoked, code cleared; effective immediately because of D-19. Then master side: every refresh family for that terminal (`principal_type = terminal`, that `principal_id`, that tenant) revoked. If the master step fails, the tenant side **stays revoked**, the response says the sessions step did not complete, and **repeating the revoke is a success that retries the master step** and writes no second audit row. | A distributed transaction between a tenant database and the master is not available and not wanted; because the tenant side is authoritative, a failed master step leaves a revoked terminal that merely cannot refresh anyway. Idempotence makes the retry safe. | Reversible: yes.

D-22 | What can a terminal token do in T-014? | Refresh itself, and read the **effective settings for its own terminal** (AC-50). It satisfies **no** employee-permission route; employee tokens satisfy no terminal-only route. No PIN login, no sync, no sales (later tasks). | Smallest useful surface; proves the token and the hierarchy end to end without inventing the till. | Reversible: yes.

D-23 | Settings hierarchy details. | Effective value = terminal -> branch -> company -> registry default, exactly as `docs/database.md`. Scope `employee` exists in the schema but is **not part of the resolution chain and cannot be written** in T-014 (`scope_not_supported`). A setting value may not be JSON null: "clear" removes the override row and is how a value reverts. Writes validate the key is registered, the value against the registry's `type` and `validation`, and the scope (company: `scope_id` null; branch: an active branch; terminal: a non-revoked terminal). `updated_by` is the actor. Keys whose registry row has `is_secret` are never returned, audited in clear, logged or published (AC-47). | The unique key already makes one value per scope; refusing null removes the ambiguity between "no row" and "row with null". The employee layer has no consumer. | Reversible: yes.

D-24 | `terminals.settings` JSON in the design duplicates the `settings` table's terminal scope. | The JSON column is **not created**: terminal settings live only in `settings` with `scope_type = terminal`. | Two stores for one fact is the defect class FP-281 and the authority audit exist to catch. | Reversible: yes.

D-25 | Are plan limits (`plan_limits` for branches, locations, terminals) enforced? | **No.** T-014 neither reads nor enforces them; the lead should file the follow-up. | The limits live in the master database and enforcement belongs with subscriptions and licensing (FP-210 area); inventing an enforcement point here would also make branch creation depend on master availability. | Reversible: yes.

D-26 | Suspension reaching an offline till (FP-241). | Out of scope, unchanged. T-014 supplies the 15-minute access lifetime, the refresh family and request-time terminal checks; the local expiry the till enforces is FP-241. | The backlog row is separate and tied to the sync design. | Reversible: yes.

D-27 | Audit and events. | Every mutating operation (branch, location, terminal, setting, PIN reset refusal excluded) writes exactly one `audit_logs` row with actor, `branch_id` where one applies, before and after, and no secret. Activation writes one `access_log` row of type `terminal_login` with `terminal_id` and the caller address. **No outbox event is published** by T-014. | Matches T-010's "one audit row" convention. No consumer of branch or terminal events exists (the replica is later), and an event nobody reads fixes a payload shape too early. | Reversible: yes.

D-28 | List and read conventions. | As T-010 AC-29: list ordered (branches by `sort_order` then `code`; locations and terminals by `code`), soft-deleted excluded, inactive included with their flag, page size clamped to a configured maximum, never any secret or hash. | One convention across the tenant API. | Reversible: yes.

D-29 | Who may create the first branch, and how does a tenant get one? | Creating the first branch is the same operation as any other, by an owner. **Seeding a default branch and its store at provisioning is FP-206**, not this task. | FP-206 is blocked by the engine hold and owns seeding; T-014 supplies the operation FP-206 will call. | Reversible: yes.

D-30 | Terminal location rule. | A terminal's `location_id` must be an active location whose `branch_id` equals the terminal's branch and whose `is_sellable_from` is true; a central warehouse (null branch) cannot be a terminal's selling location. | "What it sells from" must be a place in its own shop; the design gives no cross-branch selling. | Reversible: yes.
