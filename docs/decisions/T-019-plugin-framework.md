# T-019 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-019-plugin-framework.md`, per
the TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most
reversible option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | What exactly are "the five modes" the backlog row (FP-213) names for the hook gateway? | **Already defined, not invented here.** `docs/architecture.md` §13: "a hook gateway with named extension points, each declaring its mode: **add**, **before** which may veto, **after** which is queued, **filter** which transforms, and **override** which is permitted only on points explicitly marked overridable." Five modes: `add`, `before`, `after`, `filter`, `override`. | The vocabulary is settled architecture, not a gap. Inventing a different set would contradict a document the backlog row itself cites. | Yes — additive if a sixth mode is ever justified. |
| D-2 | Does `after` reuse the EventBus/Outbox T-018 just shipped, or does the gateway invent a second async mechanism? | **Reuses it.** `after` hooks are dispatched by writing to the tenant's `outbox_events` (via T-018's one outbox writer) and relayed/consumed exactly like any other event; `docs/database.md` line 1736 already lists "plugin AFTER hooks" among the async-afterwards items drained from the outbox. `add`, `before`, `filter`, `override` are synchronous, in-process hook-gateway calls — a different mechanism, confirmed by T-018's own spec (D-15/AC-35, Users affected note): "FP-213's hook gateway... is a different mechanism (in-process, synchronous, vetoable) layered on top of module contracts, not on the event bus." | Avoids a second dispatch mechanism for the one mode (`after`) that is genuinely async-fire-and-forget; avoids reinventing retry/dead-letter for it when T-018 already built that. The other four modes cannot be async by definition (`before` vetoes synchronously, `filter` must return a transformed value inline, `override` replaces the call inline, `add` augments inline). | Yes |
| D-3 | Does plugin licensing need a new mechanism, or does it reuse T-016's `FeatureFlags`/`PlanLimits`? | **Neither reused as-is; the already-documented dedicated schema is used.** `docs/database.md` §4.3 already specifies `plugins`, `plugin_versions`, `plugin_dependencies`, `plugin_tenant_access`, `tenant_plugins`, plus `licences` (`type=plugin`) — a richer model (versioning, dependency constraints, per-tenant private-plugin grants, per-tenant migration `schema_version`) than a boolean feature flag can express. `feature_flags.is_plugin_flag` exists for a different, narrower purpose (gating a plugin-*adjacent* behaviour toggle, not plugin install/enable/licence state) and is not repurposed here. None of these tables has a migration in the repo yet (measured: no `create_plugins_table`/`create_tenant_plugins_table`/etc. found under `modules/host/database`), so this task writes the migrations the architecture document already designed rather than inventing a third licensing concept. | `docs/database.md` is the authoritative schema document; it already answered this question for a future task, and that task is this one. Reusing `FeatureFlags` for plugin enablement would duplicate `tenant_plugins.status`/`licence_id` with a second, weaker authority — the FP-184 "one authority per fact" family this project already follows (T-016, T-017, T-018). | Yes — `FeatureFlags` can still gate an individual plugin *capability* later without touching enablement. |
| D-4 | `docs/database.md` line 1439's `plugin_execution_logs.mode` enum lists only `(before, after, filter, override)` — missing `add`, one of the five modes D-1 confirms. Does this task carry that gap forward? | **No — corrected before the first migration ships it.** This task's migration for `plugin_execution_logs` uses the full five-value enum `(add, before, after, filter, override)`. | No migration for this table exists anywhere in the repo yet (measured), so this is filling in an undelivered design to match the document's own §13 narrative, not an expand-and-contract change against live data. Shipping a logging table that cannot record one of the five documented modes would silently under-report `add` hook activity from day one. | Yes — logged here for `architect`/the doc owner to reconcile `docs/database.md`'s own text in a later pass. |
| D-5 | What counts as a plugin hook "failing," for the circuit breaker? | **Any exception/error thrown by the hook handler, or exceeding a configured per-call timeout** (default reversible value, no stated business rule exists). Both count identically as one failure. | `docs/architecture.md` §13: "A plugin failure is caught, timed, logged and circuit-broken" — explicitly names both catching (exceptions) and timing (duration) as inputs, not just one. | Yes |
| D-6 | What does the breaker do when open, and how does it reset? | **Per tenant, per plugin** (matching `tenant_plugins`' own grain, which already carries `failure_count`, `tripped_at`, `last_error` columns — no new table needed). On reaching a configured consecutive-failure threshold (default **5**, mirroring T-018 D-8's precedent default), the gateway sets that tenant's `tenant_plugins.status='error'`, stamps `tripped_at`/`last_error`, and from then on **refuses to dispatch any hook to that plugin for that tenant** without invoking it — it logs the refusal and continues normally for every other plugin and every other hook point (isolation, matching §13's "one badly behaved plugin cannot take down a till"). A successful invocation resets `failure_count` to 0 (consecutive-failure semantics, standard breaker behaviour). Reset out of the tripped state is a **deliberate operator console action** only (sets `status='enabled'`, `failure_count=0`, clears `tripped_at`/`last_error`) — no automatic time-based reset by default. | Reuses columns `docs/database.md` §4.3 already designed for exactly this purpose rather than adding new ones. "Operator decides, never automatic" mirrors T-018 AC-31's dead-letter/failed-row retry precedent (D-9's "console commands only" convention) and is the safer default — an automatic cool-down can reopen a breaker onto a plugin that is still broken. | Yes — a time-based auto-reset/cool-down can be added later as a configurable option without a schema change. |
| D-7 | What does "the runtime" mean concretely, given no real plugin exists yet (FP-296 is Phase 6)? | A **manifest loader + hook registry**: given an enabled `tenant_plugins` row, the runtime loads that plugin version's manifest (the `plugin_versions.manifest` JSON column), validates it, and resolves the PHP handler classes it declares for each named extension point, registering them in-process against the hook gateway. Plugin code runs **in-process, in the same PHP request/worker**, matching §13's explicit statement — no separate process, container or sandbox is built. Proven with one or two **test-fixture plugins** living under `packages/plugin-sdk/tests/Fixtures`, mirroring T-018's `fixture.pinged`/`demo` proof-of-pipeline discipline — not a real business plugin (that is FP-296) and not `modules/demo` (a different module's scaffold). | Keeps this task's economy of change to "framework, proven on a fixture" exactly as T-016/T-017/T-018 did for their own mechanisms; avoids speculative sandboxing/process-isolation work the architecture document never asks for. | Yes — process isolation is a strictly additive hardening step later if a real plugin ever needs it. |
| D-8 | Minimum manifest fields? | `name`, `version`, `core_constraint`, `hooks: [{point, mode, handler}]`, `permissions: [...]`, `requires_licence: bool`. A manifest failing validation (missing required field, unknown mode, a `handler` class that cannot be resolved, an `override` declared against a point not marked overridable) is refused **before** registration — never partially registered. | Mirrors exactly the columns `plugin_versions.manifest` (JSON) and `plugins.requires_licence` already name in `docs/database.md`, plus §13's "override... permitted only on points explicitly marked overridable" and §17's "plugin permissions declared in the manifest... never implicit" — nothing here is invented past what the architecture document already requires the manifest to carry. | Yes |
| D-9 | Does this task build the per-tenant plugin migration runner `docs/database.md` §9.6 describes (`tenant:migrate --plugin=<name>`)? | **Yes**, as a capability (the command, the `plugin_migrations` tenant table migration, the `tenant_plugins.schema_version` mirror write in master) — but ships and proves it with **fixture plugin migrations only**, never a real plugin's migrations (none exist; FP-296 is Phase 6). | §9.6 names this mechanism as part of what "the same runner" already does for core and explicitly ties it to `tenant_plugins.schema_version`, a column this task's own enablement model (D-3) already builds on — leaving it out would make enabling a fixture plugin for a tenant untestable end-to-end. | Yes |
| D-10 | Does this task add an HTTP route or admin UI for any registry/enablement/breaker-reset operation? | **No.** Console/internal commands only. | Same precedent as T-016 D-21, T-017 D-7, T-018 D-9: no platform-admin authorization model or HTTP surface exists anywhere in this codebase yet; inventing a one-off model to gate a route that would otherwise have none is out of this task's scope. | Yes — additive once such a surface exists for any reason. |
| D-11 | Does this task build the frontend plugin-remote-loading mechanism `docs/architecture.md` §15 describes ("plugins ship as separately built remotes the shell loads at runtime")? | **No.** FP-213's backlog row is explicitly `BE`. This spec covers the backend framework (manifest, registry, licensing/enablement, hook gateway, runtime, circuit breaker) only. | The frontend remote-loading mechanism is a distinct, frontend-scoped concern with its own likely backlog row; conflating it here would exceed FP-213's stated column (`BE`) and this task's own economy-of-change discipline. | Yes — tracked as a gap for whoever scopes the matching frontend row. |
| D-12 | Does this task special-case the workflow engine (FP-214), which will run as a `before`-mode hook handler per §14? | **No special-casing.** The `before` mode's documented semantics ("may veto") already give FP-214 what it needs; this task does not add workflow-specific hook points, approval tables or conditions. | Avoids designing FP-214 by proxy, per the orchestrator's explicit instruction not to design for FP-214/FP-296 while not painting the gateway into a corner — `before`'s existing veto semantics are sufficient and already generic. | Yes |
| D-13 | What proves the pipeline end-to-end? | One minimal fixture plugin (e.g. `fixture-echo`) exercising all five modes in tests — add, before (veto and allow), after (via outbox), filter (transform), override (on a point marked overridable) — explicitly labelled a proof-of-pipeline fixture, not a reference plugin. | Mirrors T-018's own `demo.pinged` discipline (D-10) and the orchestrator's explicit instruction to produce, at most, "one minimal proof-of-pipeline example," not FP-296's reference plugins. | Yes |

| D-14 | AC-48, as first drafted, asked for a migration `down()` ("reversible... `down()` undoes exactly what `up()` did"). `architect`'s plan follows T-008 D-8 (tenant migrations are forward-only, no rollback) instead and flagged the conflict rather than silently overriding the spec (plan Ruling 14). Does this task's plugin migrations get an exception to D-8, or does AC-48 get amended? | **AC-48 amended, no exception to D-8.** Confirmed D-8 is a standing, project-wide, enforced convention — `docs/decisions/T-008-master-schema-and-tenant-baseline.md` D-8 states it in exactly those terms ("No. Forward-only. The runner has no rollback."), no shipped migration anywhere in the repository (master or tenant, across T-008/T-016/T-017/T-018) has a `down()`, and `BranchForeignKeysMigrationTest` asserts the convention holds project-wide, not per-task. AC-48 now asks for: no `down()` method (matching the convention), clean forward application against a real engine, and a double-apply being a safe no-op — not reversibility via `down()`. | Plugin install/uninstall looked, at first glance, like a plausible place to want rollback (installing and uninstalling a plugin is inherently more symmetric than a core schema change), but that symmetry is already delivered by AC-20's export-then-drop uninstall path, not by a migration `down()` — a plugin's own tables are owned entirely by that plugin's migrations, so "undo what this plugin's schema change did" is "uninstall this plugin," a feature this spec already requires, not a second, parallel reversal mechanism bolted onto the migration runner. Carving a one-task exception into D-8 for a framework whose own spec already provides the equivalent capability by a different, already-reviewed route would fragment a convention a project-wide test enforces, for no capability gained. | Reversible: yes — a future task could still add `down()` broadly if D-8 itself is ever revisited; nothing here forecloses that, it only declines to make plugin migrations the first one-off exception. |
| D-15 | AC-27, as first drafted, asked for the outbox `type` column to name both the hook point and the plugin. `architect`'s plan instead uses a fixed `type` of `plugin.<point>` and carries plugin identity in `aggregate_id`/`actor`/`payload`, flagging that the literal wording is structurally incompatible with two measured facts: T-018's `ConsumeEventsHandler` matches `type` against an exact declared list (`ConsumeEventsHandler.php:126`), and `outbox_events.type` is capped at 80 characters, which a composite `<point>.<plugin>` string can exceed for real names. Does AC-27 get amended to describe the mechanism correctly? | **AC-27 amended.** `type` is a fixed, catalogue-derived string naming only the hook point (`plugin.<point>`); the plugin's identity travels in `aggregate_id`, `actor` (`actor_type='plugin'`), and `payload`. The criterion still requires that the row unambiguously identify both the firing hook point and the firing plugin — that traceability goal is unchanged — but the mechanism by which it is satisfied is now stated correctly instead of requiring something that cannot coexist with the outbox this task is built on. | A `type` that varied per plugin would force every `after` consumer to read a per-plugin subscription list from the master on every delivery instead of matching a small, static, declared list — the exact mechanism T-018 already built and this task is instructed to reuse (D-2), not redesign. The 80-character cap is a measured, already-shipped column limit, not a convention this task could reasonably ask T-018 to widen retroactively for a framework that does not need a composite string to prove its own traceability — `aggregate_id`/`actor`/`payload` already carry the plugin identity exactly as unambiguously as a composite `type` would, without colliding with either constraint. | Reversible: yes — if T-018's matching or the column width ever change, `type` could later carry more without this task's gateway or consumer code needing to change shape. |

Every decision above is reversible; none forecloses FP-214 or FP-296.
