# T-009: Authentication - decisions

Format: `D-n | Question | Decision | Reason | Reversible: yes/no`. These are T-009's own; T-008's D-1 to D-56 are in `T-008-master-schema-and-tenant-baseline.md`.

Taken by `ba` without the human, under the TEAM PROTOCOL. `architect` has no messaging tool reachable from `ba`, so the questions that are really technical are marked **-> architect** and are routed through the lead in `ba`'s report.

D-1 | What is a "token"? | Two signed JWTs plus one opaque refresh token. A **platform access token** (`token_type=platform`, opens no tenant database) is issued by login. A **tenant access token** (`token_type=tenant`, carries the tenant id) is issued by tenant selection. A **refresh token** is an opaque random string, stored only as a SHA-256 hash in `refresh_tokens`. Signing is asymmetric, by a key recorded in `signing_keys` (`kid` in the header). | This is what `docs/database.md` section 5 and `docs/architecture.md` sections 5 and 17 already describe; the only choice made is to take the database.md claim names. The exact algorithm and JWT library are **-> architect**. | Reversible: yes while no token has been issued to a real user.

D-2 | How long does an access token live? | 15 minutes, both types. | Architecture section 17 says "short lifetimes for people" without a number; 15 minutes is the conventional figure and bounds how long a disabled user or a suspended tenant keeps access (see D-9). Held in configuration, not code. | Reversible: yes.

D-3 | How long does a refresh token live, and what happens when one is replayed? | 14 days from the moment it is issued (sliding: each rotation issues a fresh 14 days; **no absolute session cap**, see D-21). Single use: every refresh rotates it within a `family_id`. Presenting a token already marked used revokes the **whole family** and writes a `token_reuse` row to `security_events`. | `refresh_tokens` already has `family_id`, `used_at`, `revoked_at` and `security_events` already has `token_reuse`; the schema was designed for exactly this. | Reversible: yes.

D-4 | Does switching tenant re-authenticate? | No password is asked again. Switching needs a valid **platform** access token (so the client holds a platform refresh token and refreshes it if expired) and issues a new tenant token plus a new tenant-scoped refresh token. The current token is never mutated and is not revoked; it simply expires. A tenant token alone cannot be used to switch. | Architecture section 5: "Switching tenant means issuing a new token, not mutating the current one." ARCH.md section 6: switch "without creating a completely separate platform account". Re-entering a password per shop would defeat the one-login-many-shops point. Revoking the old token on switch is not required by any document and would break a user with two browser tabs. | Reversible: yes.

D-5 | What does lockout count, for how long, and against what? | Consecutive wrong passwords for an **existing** account: **5** failures lock it for **15 minutes** (`users.locked_until = now + 15 min`). `failed_attempts` resets to 0 on a successful login **and** at the moment the lock is applied. Failures while locked are not counted and do not extend the lock. `users.status` stays `active`; the `locked` status value is reserved for an administrative lock with no expiry (nothing in T-009 sets it). A `lockout` row goes to `security_events`. Unknown emails have no counter. | Five and fifteen are the conventional figures. Self-expiring beats a permanent lock for a POS counter where nobody can phone a support desk at 7am; not extending the lock stops an attacker keeping a victim out indefinitely by hammering. | Reversible: yes, numbers in configuration.

D-6 | Is login history in the master or the tenant? | **The master**, table `login_history`. The tenant's `access_log` records PIN and terminal events and is a different thing (database.md section 6 says so in terms). | A login happens before any tenant is chosen, and a failed login for an unknown email has no tenant at all. | Reversible: no (the table is already in the master design).

D-7 | What happens when a user's only tenant is suspended? | Login **succeeds** (the credentials are valid and the person is a real user); the tenant list contains the tenant with its status and `selectable=false`; `default_tenant_id` is null; selecting it is refused with a `tenant_not_servable` reason that names the tenant status. No tenant token is issued. | Hiding it would leave a paying customer with an empty list and no idea why. Telling a member their own shop is suspended discloses nothing they should not know. Refusal at **selection** is architecture section 5 "refused at resolution". | Reversible: yes.

D-8 | Which `tenants.status` values may be selected? | `trial`, `active`, `past_due`. Everything else (`pending`, `provisioning`, `suspended`, `read_only`, `closed`, `archived`) is listed but not selectable. | Taken verbatim from `docs/database.md` section 5. **`read_only` and `suspended` are in tension with database.md section 8, the Suspend row ("The tenant can still log in and read and export") - see the report's contradictions list.** Refusing is the safer reading and can be loosened once the owner rules. | Reversible: yes.

D-9 | Does authentication run the tenant serving gate? | **No.** Issuing a tenant token reads only `users`, `tenant_users` and `tenants`. It does not call `Tenancy::enter()` and does not read `tenant_databases`. The serving gate (`tenant_databases.status = active`, schema floor) runs on **every later request**, when the verified token's tenant is entered through the existing `Tenancy`. So a member of a tenant whose database is `read_only` can hold a tenant token and be refused on the first request. | The brief: "Authentication resolves which tenant; the existing gate decides whether it may be served. Do not duplicate that gate." Calling `enter()` at issue time would also need a tenant database, which the engine hold prevents. ARCH.md section 5 lists "approved database mapping exists" among the checks; that check is the gate's, applied one step later. **-> architect to confirm**; the alternative is a mapping-exists probe at selection, rejected here as a second copy of the gate's first rule. **Confirmed by `architect` (plan section 0, Ruling 2).** A third document, `docs/database.md` section 5's tenant-token flow, does read the mapping, open the tenant database and read the tenant's employees; it does so to produce the employee and permission claims that D-10 already defers, so D-9 and D-10 are one deferral seen twice. Selection opens no tenant database *while the token carries no tenant-local claim*; when FP-208 adds such claims the right answer is still the existing `Tenancy::enter()`, not a mapping probe. D-9 is only safe because the middleware that verifies the token and the call that enters the tenant live in **one class**, so a route cannot be authenticated without being gated (AC-45 to AC-47). | Reversible: yes.

D-10 | What goes in the tenant token? | `sub` (user id), `tenant` (tenants.id, ULID), `employee` (from `tenant_users.employee_id`, omitted when null), `token_type`, `iat`, `exp`, `jti`. **No** `branch`, **no** `perm_hash`. | database.md section 5 and architecture section 5 list *different* claim sets, and both include data (`branch_ids`, `perm_hash`/`perm_version`) that comes from the tenant's `employees` table, which does not exist until FP-208. Tenant token claims for branch and permissions are FP-208's to add. `employee` is **not verified** against the tenant database (that is the nightly consistency check's job). | Reversible: yes (additive claims).

D-11 | Which tables does T-009 add? | A new master migration for `refresh_tokens`, `signing_keys`, `login_history`, `security_events`, as specified in database.md section 4.1. **Not** `mfa_factors` or `service_clients`. T-008 built none of these (checked against `modules/host/database/migrations/`). | T-008's spec only required the five identity/licensing tables. MFA and service clients have no consumer in this task. | Reversible: yes.

D-12 | What does a failed login say? | One response for every credential failure: unknown email, wrong password, locked, user not `active`, soft-deleted. Same status, same body, same headers that vary with the case. The *reason* is recorded in `login_history.failure_reason`, never returned. For an unknown email the hasher is still run once against a fixed dummy hash. | Conventional anti-enumeration. Costs the legitimate user a less specific message while locked; accepted. | Reversible: yes.

D-13 | Which users may log in? | Only `users.status = active` and `deleted_at IS NULL`. `invited`, `disabled`, `locked` and soft-deleted all fail as in D-12. | No invitation-acceptance feature exists yet, so `invited` cannot be a valid login state. | Reversible: yes.

D-14 | Is logout in scope? | Yes, minimally: presenting a refresh token revokes its family; idempotent and non-revealing. | FP-207 says "revocable" nowhere explicitly, but architecture section 17 does, and a refresh token that cannot be revoked cannot be tested for revocation. | Reversible: yes.

D-15 | Is tenant selection recorded in login history? | Yes: one `login_history` row per selection attempt with `tenant_id` set, success or failure. | The table has a `tenant_id` column that otherwise has no writer. | Reversible: yes.

D-16 | What does `must_change_password` do at login? | Login succeeds and the response carries `must_change_password: true`. **Enforcement is out of scope** (no change-password feature exists). | Refusing the login would lock the user out of a flow that does not exist. | Reversible: yes.

D-17 | What is out of scope? | MFA, password reset, password change, invitation acceptance, impersonation, terminal and service tokens, per-IP rate limiting, retention pruning of `login_history`, `subscriptions`/`licences` checks (FP-210), `tenant_domains` host-based resolution, branch and permission claims (FP-208/209). | None is named by FP-207. | Reversible: yes.

D-18 | Do platform staff bypass tenant membership? | No. Staff log in like anyone and need a `tenant_users` row to select a tenant. | Architecture section 17: "no bypass flag". Impersonation is a later, audited feature. | Reversible: yes.

D-19 | Input limits. | `email` required string, trimmed, at most 191 characters (the column width). `password` required non-empty string, at most 1024 characters, rejected **before** hashing. No minimum length at login (that is a creation-time rule). Tenant code: required, trimmed, non-empty. Invalid input is a validation failure (422), is **not** a login attempt, writes no `login_history` row and does not touch `failed_attempts`. | The upper bound stops a multi-megabyte password becoming a hashing denial of service. 1024 is a round assumption. | Reversible: yes.

D-20 | What does the client send to pick a tenant? | The tenant `code` (database.md section 5: `{tenant_code}`), not the ULID. ARCH.md's `TEN001` example is a code, not a database name. | Codes are the human-facing identifier; the token carries the ULID. | Reversible: yes.

D-21 | Absolute cap on a refresh family? | None in T-009. A family can live as long as it is used within 14 days. Raised as a non-blocking question. | Not specified; adding an arbitrary cap would be an invented rule. | Reversible: yes.

D-22 | How do tests control time? | All expiry and lockout logic reads an injectable clock (the kernel already has `RunnerClock`; `architect` decides whether to reuse it). No criterion may rely on sleeping. | Boundaries ("exactly at `exp`", "exactly at `locked_until`") are unprovable otherwise. | Reversible: yes.

D-23 | Signing keys in tests, and secrets generally. | Tests generate ephemeral key pairs at run time. No private key or secret is committed. `signing_keys.private_key_ref` holds a reference only. A production key is a deployment matter (docs/deployment-vps.md), not a T-009 deliverable. | Team protocol forbids committing secrets. This is not an escalation: no real credential is needed to build or test. | Reversible: yes.

D-24 | A refused tenant refresh: is the token consumed? | No. If a tenant-scoped refresh is refused because the tenant is not servable or the membership is no longer active, the refresh token is left unused and unrevoked. | A tenant that is suspended on Monday and reinstated on Tuesday should not log every user out for good. Disabling the *user* is different: that revokes the family (spec AC-36; this row previously cited AC-31 in error). | Reversible: yes.

D-25 | JWT library and algorithm? | `firebase/php-jwt` ^6.10 in `packages/auth/composer.json`; ES256. Decided by the machine, not preference: `ext-sodium` is absent so EdDSA was never available; EC P-256 works through openssl. The caller names the algorithm at decode, so `alg=none` and algorithm mismatch are refused by the library (AC-29). | `architect` plan section 0, Ruling 1 (measurements are `architect`'s and the lead's, not re-derived by `ba`). **Needs the branch:** the dependency must actually install; the composer cache has no entry for it, and if install fails dev stops and reports (plan section 10). | Reversible: yes while no real token exists.

D-26 | Case-insensitive email on the stand-in? | A stored generated `email_lower` column on `users` with a unique index; lookup uses it. This upgrades `ba`'s lookup-only remedy: it also gives the stand-in the uniqueness half and keeps an index on the real engine. Consistent with T-008's stored-sentinel convention. Side effect: T-008's AC-8(a) becomes provable on the stand-in; that is **not** a re-proof, and AC-2's `[ENGINE]` marker stands. | `architect` plan section 9 finding 2; verified on raw SQLite 3.39.2 by `architect`. **Needs the branch:** Laravel's SQLite grammar is unproven for the generated column (plan step 2 spikes it; fallback is `LOWER(email) = ?` plus a backlog row, which would reopen this row). | Reversible: yes.

D-27 | AC-47: how is "no copy of the tenant-database status list" proved? | Replaced as in the spec: refusal by `TenantDatabaseNotActive` (never constructed by auth) plus handler spy for behaviour; deptrac layer `Package_Kernel_TenancyStatus` deliberately not granted to `Package_Auth`, with a scratch-import negative control. The old "move the other list" proof is dropped because the serving list is deliberately not injectable, and the fallback text search is the proof T-008 refused. The criterion states its evidence and its limit. | Plan section 9. **AMENDED in place (see D-33):** my earlier correction here said deptrac "would catch the double-quoted second literal only if that literal is a class reference". That was itself an overclaim: measured, a string FQCN (double-quoted, single-quoted, or in a `[FQCN, 'method']` callable) is not reported at all, because every collector is `classLike`. Deptrac reports type references only; it is blind to value copying, including a string that spells a class name. The copied-list residual is carried by the behavioural half, the moved-value shape of plan step 6, and diff review, and by nothing else. Negative control (a scratch `use` of `TenantConnectionPurpose` fails the check) was verified by `dev`; QA re-runs it. | Reversible: yes.

D-28 | `login_history.id` and `security_events.id` as BIGINT AUTO? | Consistent; no amendment to database.md or the rule. The identifier convention governs references to another row's identity, not a log's own surrogate key. Their `user_id` and `tenant_id` are references and use the ULID identifier column. | Precedent: `platform_audit_logs` migration (`$table->id()`, reasoning in its docblock) from T-008. Plan Ruling 3. | Reversible: yes.

D-29 | Per-IP throttling and the exposure of per-account lockout? | Filed as FP-199, marked as blocking public launch. Nothing built in T-009. Closes spec open question 6. D-5's rule of not extending a live lock stays as the mitigation. | Plan section 9 finding 3; per the lead's brief the row is filed (`ba` has not seen the backlog row text). | Reversible: yes.

D-30 | Argon2id in tests and CI? | Tests hash with real Argon2id at reduced work factors set in `phpunit.xml`; the algorithm is unchanged, no test asserts a duration. Availability in CI becomes an acceptance item on the CI row (FP-218), because no CI exists today. Not a T-009 criterion. | `architect`'s measurements (0.232 s vs 0.0015 s) and the lead's check that no workflow directory exists; not re-derived by `ba`. | Reversible: yes.

D-31 | D-23 given the openssl hazard? | D-23 stands: tests still generate ephemeral keys and nothing is committed. Generation goes behind a resolver (`KeyPairGenerator`) that finds an OpenSSL config (env var, then beside the PHP binary, then none) because `openssl_pkey_new()` with no arguments fails on this machine. My original D-23 would have failed on first run; I did not know the environment. | `architect`, Ruling 1; verified by the lead. **Needs the branch:** the resolver must work on this machine and on a config-less Linux runner. | Reversible: yes.

D-32 | Longer claim set in design documents? | Not mine to edit. `docs/database.md` section 5 and `docs/architecture.md` section 5 print the longer claim set (branch, permissions, terminal) from a tenant table that does not exist until FP-208. Both need an "added by FP-208" annotation, plus a note against `docs/database.md` section 5's tenant-token flow (see D-9). The lead should file this, and FP-208's row should name the claims it owes. Rule recorded: a claim we cannot populate must not be minted, or a later task changes a claim's meaning instead of adding one (D-10 confirmed). | Plan section 9 finding 1. | Reversible: yes.

D-33 | What exactly does the deptrac rule prove for AC-47? | That authentication holds no **type reference** (`use`, type hint) to `TenantConnectionPurpose`, `TenantDatabase`, `TenantStatusPolicy`. It is strictly stronger than a text search for symbol reuse and completely blind to value copying. Measured by `dev` with probe files under `packages/auth/src`: type reference reported; FQCN as double-quoted string, single-quoted string, and `[FQCN, 'method']` callable all not reported (zero violations); a class holding `['active', 'read_only']` with `in_array()` not reported (zero violations). Cause: every collector in `modules/host/deptrac.yaml` is `type: classLike`. The criterion may say "no reference to the status types" and may never say "no copy of the serving list". The copied-list residual is carried only by the behavioural half of AC-47 (kernel refuses a `suspended` mapping with `TenantDatabaseNotActive`, which auth never constructs; never-called handler spy), the moved-value shape of plan step 6 for `TenantSelectionPolicy`, and diff review. | `dev` measurement, relayed by the lead. The clause "a double-quoted reference is still reported" came from the lead's brief to `ba` and was written into the spec unmeasured. Negative control verified by `dev`: a scratch class importing `TenantConnectionPurpose` gave exit 1 with 3 violations; removed, 0 violations and exit 0. D-27 amended in place. | Reversible: yes.

D-34 | Rule on describing what a tool proves. | A criterion may not describe what a tool proves until someone has run the tool on the evading shape. Where the evading shape has not been run, the criterion states only what was measured and names the unmeasured shapes as unproven. | Second time on this task a proof's strength was asserted and then measured smaller: first the plan's "the boundary check still reports the double-quoted copy" (corrected by `ba` on reasoning, D-27), then `ba`'s own partial correction that still held a string-FQCN overclaim (measured false, D-33). Reasoning about a tool is not evidence about it. | Reversible: yes.

D-35 | Should AC-47's evidence statement be re-checked if the deptrac configuration changes? | Yes. The four measurements in D-33 are a property of `deptrac.yaml` as it stands (all collectors `classLike`). If a collector type is added or changed, QA must re-run the four probe shapes before relying on any wider claim. | Prevents the measured limit from silently becoming stale in either direction. QA to confirm against the committed config, which `ba` cannot read history for. | Reversible: yes.

D-36 | AC-23 says every login attempt that passes validation writes a `login_history` row; AC-31 (no active signing key) writes none, because the signing key is resolved before the user lookup and `RecordLoginAttempt::REASONS` has only the six credential/tenant reasons. Which governs? | **AC-23 is narrowed** to attempts whose credentials were evaluated (the user lookup has run). An operational failure before that point writes no `login_history` row and no seventh reason is added. No code change. `login_history` means "a credential was judged"; it is not a request log. AC-23 and AC-31 are reworded in the spec, and AC-23 tells QA the positive control (add a key, repeat, one row appears) and not to file the absence as a defect. | The failed request told us nothing about the credentials, so a row would have to invent a `failure_reason` that is neither a credential outcome nor true of the user; a row with `user_id` null would also be indistinguishable from `unknown_user` to anyone investigating abuse, polluting the very table used to detect guessing. A closed reason set that cannot express an operational failure is a safer shape than one that can. The cost is real and accepted: `login_history` is silent about a misconfigured deployment (see D-37). Option 3 (a `security_events` row) was rejected for now: `security_events.type` is a closed enum in database.md section 4.1 with no operational value, so it would need a schema change and a per-request write on a path that, in the failure case, is hit by every login. | Reversible: yes (a seventh reason or an event type can be added later without changing existing rows).

D-37 | If every signing key is retired, every login fails with a 5xx and `login_history` is silent. Is that acceptable, and what records it? | Acceptable for T-009 only on the condition stated here. **The honest answer is that nothing built by T-009 records or alerts on it, except whatever the framework's exception handling writes to the application log when the 5xx is raised.** `ba` cannot verify that from the specs; `qa` must confirm by test that the failure reaches the application log at error level with no password or token in it (AC-26 still applies), and report if it does not. No alerting, no health check and no `security_events` type exists for it. **A backlog row is needed** (for `lead`): detect and alert on "no active signing key" (a health or readiness check plus an operator alert), and decide whether `security_events` gains an operational type such as `signing_unavailable`. It is a launch-readiness item, not a T-009 blocker, because production keys are a deployment matter (D-23) and no real user exists yet. | The alternative of blocking T-009 on monitoring would invent a platform-wide observability requirement nobody asked for. Naming the gap in writing prevents it being accepted by default. | Reversible: yes.
