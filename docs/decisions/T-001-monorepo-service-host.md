# T-001 decisions — monorepo, backend toolchain and service host skeleton

Decisions made autonomously by `ba` while writing `docs/specs/T-001-monorepo-service-host.md`,
per the TEAM PROTOCOL (no blocking questions to the human).

D-1 | What happens when `SERVICES` lists a service package that does not exist under `services/`? | Host boot fails fast with a clear error naming the missing service; nothing is silently skipped. | Misconfigured deployments (e.g. a typo in `SERVICES`) must be caught immediately, not discovered later as a missing route; matches the "fail fast on bad config" pattern used elsewhere in the architecture. | Reversible: yes

D-2 | Is an empty/unset `SERVICES` a valid configuration? | Yes — the host boots successfully with zero service packages registered. | A host with no services booted is a legitimate minimal state (e.g. first boot, or a future gateway-only host per architecture.md §4 stage 2); rejecting it would block trivial smoke tests. | Reversible: yes

D-3 | Backlog FP-004 asks for "PHP 8.2+ (XAMPP) and 8.3 (Docker) verified", but Docker compose (FP-015) does not exist yet within T-001's scope. | T-001 verifies PHP 8.2 via the documented XAMPP path only (`CLAUDE.md`); `composer.json` declares `"php": "^8.2"` so 8.3 compatibility is not blocked. Docker-based 8.3 verification is deferred to FP-015/FP-019, where Docker compose and CI exist. | Cannot verify against infrastructure (Docker compose) that is explicitly out of scope for T-001 and not yet built; deferring avoids scope creep while the version constraint keeps the door open. | Reversible: yes

D-4 | Should `svc:make` allow a service to be named `host` or another reserved word? | No — `host` is rejected as a reserved name. | `services/host` is the host application itself, not a service package; allowing the name would create an ambiguous/colliding directory. | Reversible: yes

D-5 | What naming pattern must a service name satisfy? | Lowercase kebab-case: `^[a-z][a-z0-9-]*$`. | Matches Composer package naming (`flexipos/service-<name>`) and PHP namespace/folder conventions used elsewhere in the architecture; simplest, safest convention for a generator. | Reversible: yes
&gt; **Superseded by D-12.** QA (BUG-2) proved this pattern accepts a trailing hyphen and consecutive/doubled hyphens (e.g. `billing-`, `bad--name`), producing a Composer package name (`flexipos/service-billing-`) that fails Composer's own schema and a PHP namespace that collides with a validly-named service. The pattern in D-12 replaces this one; the rest of D-5's reasoning (lowercase kebab-case, no leading digit) still stands.

D-6 | Should the demonstration service package be a throwaway example or a committed part of the skeleton? | Committed: `services/demo` is generated via `svc:make`, kept in the repository, and included by default in the example environment file (`SERVICES=demo`) so it is exercised by the test suite and serves as a living template. | The task explicitly asks for "at least one demonstration service package proving the mechanism works" as an in-scope deliverable; a throwaway example proves nothing once deleted, and future developers benefit from a working reference. | Reversible: yes

D-7 | Which health endpoint(s) does T-001 implement, and how much do they check? | Implement `GET /health/live` (basic liveness) and `GET /health/ready` (lists booted services), per architecture.md §18. `/health/ready` in T-001 checks only which services are booted, not DB/Redis/consumer health. | Matches architecture §18 naming; deeper checks require infrastructure (database bootstrap FP-012, event bus FP-008) that is explicitly out of scope for T-001 and would be misleading if added prematurely (always reporting unhealthy). | Reversible: yes

D-8 | How should `SERVICES` be parsed (whitespace, duplicates)? | Split on commas, trim whitespace from each name, and de-duplicate before registering providers. | Env files commonly have spaces after commas; failing to trim/dedupe would cause confusing boot errors or duplicate route registration over a trivial formatting difference. | Reversible: yes

D-9 | What default route prefix does `svc:make` give a generated service? | `/api/v1/<name>` by default (e.g. `/api/v1/billing`), overridable by the developer after generation. | Real business services get purpose-specific public prefixes decided per architecture.md §7.1 when they are built (Phase 1+); the generic template needs one sane, predictable default. | Reversible: yes

D-10 | How much content do the seven `packages/*` placeholder directories need in T-001? | Each gets a minimal `composer.json` stub (package name + empty `src/` autoload) so the Composer workspace and Deptrac layer definitions can reference all seven from day one; no business logic. | FP-006 through FP-011 own the real content, but Deptrac's ruleset and the Composer workspace (both FP-004) need the layers/packages to exist structurally now to be testable, avoiding rework when each package lands later. | Reversible: yes

D-11 | How much content do the out-of-scope top-level folders (`gateway/`, `frontend/`, `print-agent/`, `plugins/`, `infra/`) get in T-001? | Empty directories with a `.gitkeep` placeholder only, per architecture.md §5's layout; no functional content. | FP-003's deliverable is "folders per architecture §5"; their real contents are separate, later-scheduled backlog rows (FP-014, FP-015/016, FP-017, FP-018) and must not creep into T-001. | Reversible: yes

D-12 | BUG-2 (QA, run 1): D-5's pattern `^[a-z][a-z0-9-]*$` accepts a trailing hyphen and consecutive hyphens. QA proved the consequence is real: `svc:make billing-` writes `"name": "flexipos/service-billing-"`, which fails Composer's own name schema, and produces namespace `Flexipos\Service\Billing\` — identical to (colliding with) what `svc:make billing` produces. Booting both then makes `/health/ready` report a service that has no working routes. What pattern should `svc:make` (and `ServiceRegistry`'s validation of each `SERVICES` entry, per BUG-3) enforce instead? | Tighten to `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` — still lowercase, still forbids a leading digit, but now requires every hyphen to separate two non-empty alphanumeric segments. This rejects a trailing hyphen (`billing-`) and doubled/repeated hyphens (`bad--name`) while still allowing multi-word names such as `http-client`. `dev` applies this in `SvcMakeCommand`'s `NAME_PATTERN` and in `ServiceRegistry`'s parsing of `SERVICES`, so generation-time and boot-time validation use the identical rule. | This is QA's own proposed pattern, accepted as-is: it is the minimal, targeted fix that excludes only the exact invalid shapes QA demonstrated, changes nothing else about the naming convention D-5 already established, and keeps the two validation points (generator and registry) consistent with each other, which is also what closes BUG-3's namespace/collision angle. | Reversible: yes
