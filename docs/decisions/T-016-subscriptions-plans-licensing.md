# T-016 decisions: Subscriptions, plans and licensing

Logged by `ba` under the TEAM PROTOCOL: every open business question below was resolved to the most conventional, safest, most reversible option rather than left for the human, and is cited in `docs/specs/T-016-subscriptions-plans-licensing.md`.

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | `tenants.status` already gates login/tenant-selection (T-009 AC-12, D-8). `subscriptions.status` is a separate enum. Does this task add a second, independent gate read from `subscriptions.status`? | **No.** `tenants.status` stays the sole runtime gate T-009 built. This task's job is to keep it in agreement with the subscription's billing state by writing it when the subscription changes, not to add a parallel check. | Two sources of truth checked independently at the same gate is exactly the shape FP-184/FP-186 warn about on this project. Re-opening T-009's reviewed, shipped gate inside an unrelated task also risks a regression nobody asked for. | Yes |
| D-2 | Given D-1, what does "subscription status gating access" (FP-210's own wording) concretely mean? | This task defines and enforces the transition rules from `subscriptions.status` to `tenants.status` (AC-9 to AC-12 of the spec), written in the same transaction as the subscription change, so `tenants.status` is never stale by more than that one write. | Matches FP-210's wording without duplicating T-009's mechanism. | Yes |
| D-3 | Where does plan-limit enforcement read the current count and the limit value from — live tenant query, master join, or the nightly `tenant_usage_metrics`? | Live `COUNT(*)` on the tenant's own table (no cross-database query) for the count; the limit value is resolved from master once (at tenant selection or from a bounded-TTL cache) and carried forward, never re-fetched live on the write path. | T-014 D-25 explicitly rejected making branch creation depend on live master availability for this exact reason. `tenant_usage_metrics` is documented as a reporting/nightly collector, not an enforcement source, and is stale by up to a day. | Yes |
| D-4 | Which `plan_limits.limit_key` values are hard-enforced in this task? | `branches`, `locations`, `terminals`, `employees`, `users` (master-side `tenant_users` count) are hard-enforced. `products`, `monthly_sales`, `storage_mb`, `api_calls_per_day` are not — `products` has no catalog table yet (Phase 1), and the other three are continuous metrics with no realtime metering path built; they stay reporting-only via `tenant_usage_metrics`. | Enforce exactly the limits that already have a tenant-local, discrete, countable table to enforce against; inventing metering infrastructure for the rest is a bigger undertaking than this backlog row describes. | Yes — enforcement can be added for the rest later without a schema change. |
| D-5 | What is the feature-flag precedence when a tenant override, a plan value and a global default can all exist for one flag? | `tenant_feature_flags` row (if any) overrides `plan_features` row (if any) overrides `feature_flags.default_enabled`. | Not invented: `docs/database.md` §4.2 already annotates `tenant_feature_flags` as "Overrides the plan." This task is the first to implement the ladder the schema already states. | Yes |
| D-6 | `licences` covers `type` in (`platform`, `plugin`, `module`). Does this task enforce all three? | Only `type = 'platform'` is enforced. `plugin`/`module` licences are deferred. | No plugin or module install/enable mechanism exists yet (the plugin framework is an unbuilt Phase 0 roadmap item); a licence for something that cannot yet be installed has nothing to attach to or gate. | Yes — narrowing scope now, widening later, is cheap. |
| D-7 | Should the absence of a `platform` licence row for a tenant fail closed (treated as unlicensed) or open (treated as licensed)? | Fail **open**: no row means no extra restriction beyond the subscription. | No provisioning step exists yet (FP-206 is still blocked by the engine hold) to seed a licence row for every tenant; failing closed with no seed path would lock out every tenant that exists today, which is a worse and less reversible mistake than failing open until licences are deliberately issued. | Yes — flipping the default once a seeding step exists is a one-line change. |
| D-8 | `Refference/ARCH.md`'s Suspend row says a suspended tenant "can still log in and read and export"; T-009 D-8 shipped "no" (not selectable at all). Does T-016 resolve this conflict? | **No.** T-016 inherits T-009's shipped, reviewed behaviour unchanged. The conflict is already filed and open as FP-301, a pending owner decision named explicitly in the backlog as unresolved across three documents. | Re-litigating an already-reviewed, approved, shipped acceptance criterion inside a different task, without the owner input FP-301 is waiting on, is a worse outcome than leaving a known, tracked conflict open one more task. | Yes, once FP-301 closes. |
| D-9 | Does this task build route/feature-level gating for specific modules using the new feature-flag resolver? | No. It builds one resolver call (the three-layer precedence) that any module can call, and gates nothing itself. | No shipped feature today is named by any module as flag-gated, so there is nothing concrete to gate; building speculative gates for features that do not exist would be invented scope. | Yes — gating individual routes is additive later. |
| D-10 | Who seeds the actual rows in `plans` and `feature_flags` (commercial content vs technical catalogue)? | This task may seed the **technical** `feature_flags` catalogue if/when a flag key is needed by its own tests, but does **not** seed commercial `plans` rows (names, prices, limit values) — that is flagged to the lead as a non-blocking open item. | T-008 AC-11 notes seeding plans/flags belongs partly to FP-206/207/210 but names no actual content; plan pricing and limits are business decisions `ba` has no authority to invent. | Yes |
| D-11 | `tenants.plan_id` and `subscriptions.plan_id` both exist and can disagree. Which is authoritative? | `subscriptions` is the authority. `tenants.plan_id` is a denormalised mirror of the **current** subscription's plan, written only by the code path that changes the current subscription, in the same transaction (spec AC-15). | This is exactly the "name the authority wherever two columns hold the same information" convention this project already named as FP-184, found and fixed the same way three times on T-006. | Yes |
| D-12 | How long may a `past_due` subscription/tenant stay selectable before being auto-suspended? No figure is specified anywhere in the design documents. | 7 days, stored as a configurable `platform_settings` key (`billing.past_due_grace_days`), not a hard-coded constant. | No owner figure exists; 7 days is a conventional billing-grace default (matches common SaaS practice), and making it configurable from day one is the reversible choice given it is a guess. | Yes |

The entries below were raised by `architect` while writing `docs/plans/T-016-subscriptions-plans-licensing.md` and relayed to `ba` by the lead (architect has no direct channel to `ba`). Confirmed or adjusted here, each cited in the spec revision.

| D-13 | AC-16 needs to know when a subscription became `past_due`; no existing column records it, and `platform_audit_logs.before`/`after` (JSON) was considered and rejected as a source. | **Confirmed.** Add a nullable `subscriptions.past_due_at` column in one master migration. Reading it back out of a JSON audit column was rejected because SQLite and MySQL/MariaDB disagree on JSON query behaviour, which would make the stand-in and the engine answer differently to the same question. | A single-purpose nullable timestamp column is the smallest, most conventional fix; relying on an audit log's JSON payload as a queryable fact would be using a log as a data store, the opposite of what an audit log is for. | Yes — the column can be widened or the mechanism changed without touching anything else. |
| D-14 | How are the grace-period deadline (AC-11) and licence `valid_until` (AC-25) checked — inline at login, or otherwise? Editing T-009's three reviewed handlers was rejected by `architect`. | **Confirmed.** A scheduled job runs every minute and performs both checks, writing `tenants.status`/`suspension_reason` itself; login/selection/refresh stay untouched. Accepted consequence: a tenant can stay selectable up to one minute past its deadline. **Follow-up needed:** `docs/deployment-vps.md` does not run Laravel's scheduler today, so this job would never fire in a deployed environment without a devops task adding it — flagged to the lead as a new backlog row, `ba` has no write access to `docs/backlog.md`. | Editing T-009's already-reviewed, approved handlers to add a time check is exactly the kind of change D-8/D-1 already decided against for a different reason (re-opening shipped, reviewed work); a scheduled job is the conventional mechanism for a deadline nothing else naturally re-checks. A one-minute lag is an acceptable trade for not touching three handlers three separate reviews already passed. | Yes — moving the check inline later is additive, not a rollback. |
| D-15 | Does a single cached snapshot (300s TTL, cleared on this task's own writes, via the existing tenant-mapping cache pattern) satisfy D-3's "no live cross-database query" rule? | **Confirmed.** This is exactly the mechanism D-3 asked for; `architect`'s choice to mirror the existing `tenant:conn:<tenant_id>` cache pattern (T-008 §4.4) rather than invent a new one is accepted, including testing it through the same stand-in config switch used for the tenant-mapping cache. | Reusing an already-reviewed pattern for the same shape of problem (a master-resolved value a tenant request needs without a live join) is lower-risk than a second, bespoke cache. | Yes |
| D-16 | Who may write `tenants.status` / `tenants.plan_id`, and may the subscription/licence reconciler ever lift a suspension an operator imposed by hand? | **Confirmed, with the added rule stated explicitly:** one class is the sole writer of `tenants.status`, a separate class the sole writer of `tenants.plan_id`, both called inside the triggering write's own transaction. The reconciler never touches `pending`/`provisioning` in either direction (extending AC-10's existing `closed`/`archived` exclusion) and **never lifts a suspension whose `suspension_reason` is not one of its own sentinel values** (`subscription_lapsed`, `licence_lapsed`, `past_due_grace_expired`). A manual suspension is reversed only by an operator, never automatically by a later subscription/licence change. | An automatic reconciler silently undoing a human operator's deliberate suspension the moment billing happens to look fine again is a worse failure mode than leaving it suspended one extra manual step — it is the same "who gets the last word" question T-010's FP-307 (a lesser administrator overriding the owner) already raised on this project in a different shape. | Yes — the sentinel list can grow or the rule can be relaxed later without a schema change. |
| D-17 | AC-6's own worked example was arithmetically inconsistent with AC-1's rule (a limit of 5 with 7 existing, deactivate 2 to reach exactly 5, call that "accepted" when AC-1 already refuses a 6th at a count of 5). | **Confirmed as a wording bug, fixed.** AC-6 now reads "strictly below the limit", and its example deactivates three (down to 4) rather than two (down to 5). | `architect` caught a genuine self-contradiction in the original spec text; the fix makes AC-6 consistent with AC-1 rather than introducing a second boundary rule. | Yes |
| D-18 | `tenant_usage_metrics`, cited in AC-4's original wording as the thing enforcement must never read from, does not exist — `architect` found T-008 never migrated it despite `docs/database.md` §4.2 describing it. | **Confirmed and AC-4 reworded.** Proof that a refusal is never sourced from a usage-metrics table is now a source scan (no handler in this task's diff reads any such table) plus a live-count control, rather than a "stale metrics row" fixture that would require a table that does not exist. | Writing a test fixture against a table that was never built would either fail to compile against the schema or silently test nothing; naming the gap and adjusting the proof is cheaper and more honest than leaving the original wording to rot (this project's own FP-171/FP-176 pattern: a stale fact stated as current). | Yes — if `tenant_usage_metrics` is built later, the richer fixture becomes possible again. |
| D-19 | AC-8 (seat/`users` limit) assumed an invite or access-grant flow exists to test it end-to-end; none does. | **Confirmed, scope narrowed.** AC-8 is proved at whatever single path creates a `tenant_users` row today, not end-to-end through an invite flow that does not exist. QA must not file the missing invite handler as a defect against this task. | The business rule (a seat limit exists and is checked) is unchanged; only the depth of the proof is bounded by what else has been built, which is honest rather than inventing an invite flow as a side effect of this task. | Yes — once an invite flow exists, the same check gets a second, fuller test for free. |
| D-20 | What exactly counts toward a limit — creation only, or also reactivation and the side-effects of one action creating two resources? | **Confirmed.** Reactivating a deactivated/soft-deleted row counts the same as creating a new one (mirrors AC-6's "deactivating frees quota" in reverse). Creating a branch also checks the `locations` limit, because branch creation creates that branch's default location in the same operation (`docs/database.md` §6.1). | Both are the conventional, safe reading of "a plan limit is actually enforced" — a limit that reactivation or an implicit side-resource could silently bypass would not actually be enforced. | Yes |
| D-21 | Does changing a subscription/licence/flag-override need an HTTP route and an authorization model for platform operators, or is an internal/console surface acceptable for this task? | **Confirmed as acceptable scope.** These ship as internal handlers plus one console command each; no HTTP route, no platform-admin authorization model — none exists anywhere in the codebase yet. A follow-up backlog row for a platform-admin model and its routes is needed once more than one task wants this surface; flagged to the lead, `ba` has no write access to `docs/backlog.md`. | Building a one-off authorization model and routes for this task alone, when no other master-side operation has either, would be scope invented beyond what FP-210 asks for. | Yes — routes and authorization are additive once the model exists. |
