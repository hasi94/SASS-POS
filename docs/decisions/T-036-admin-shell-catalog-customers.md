# T-036 decisions: Admin shell, navigation and the catalog screens

Made by `ba` in autonomous/team mode. Format: `D-n | Question | Decision | Reason | Reversible`.
Spec: `docs/specs/T-036-admin-shell-catalog-customers.md`.

| ID | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | FP-240 names a shell, navigation, permission-aware menus, six catalog areas and four customer areas. One task or more? | **Split.** T-036 = shell, login-aware and permission-aware navigation, the shared CRUD building blocks, and the **catalog** screens (categories, brands, units and unit conversions, products with variants, barcodes, modifier groups and modifiers). The **customer** screens (customers, groups, credit ledger view, loyalty view) become a follow-up frontend row (proposed F-2 below). | Measured against T-027/T-028: catalog is 8 entities with tree, dimension and variant rules; customers is 8 more with a ledger and loyalty. Together that is well over 100 testable behaviours for one dev and one QA round, and the customer screens would reuse the building blocks T-036 creates, so doing the shell and catalog first removes risk from the second task. FP-240 stays open (split, not DONE) until both rows finish. | yes |
| D-2 | Which backend does T-036 build against? | The **mock API only** (the existing mock-backend interceptor, extended). No PHP is touched. T-036's gate is `cd frontend && npm test`, plus `ng build admin` and the mock-exclusion grep. | The Get/List HTTP surface and permission keys do not exist (FP-240 note, T-027 D-2). Building them is backend work with its own gate. | yes |
| D-3 | Who builds the missing catalog Get/List endpoints and permission keys? | A separate **backend follow-up row** (proposed B-1 below). T-036 neither builds nor assumes their exact final shape: it ships **typed contracts derived from T-027's field lists** and a mock that implements them. When B-1 lands, a reconciliation step (like T-025) checks the contracts against the real responses. | Same pattern T-025 used. Contract drift is expected and is cheap to fix when the contracts live in one place (D-8). | yes |
| D-4 | What are the catalog permission keys? | Proposed naming `catalog.<resource>.view` and `catalog.<resource>.manage` for resource in `categories`, `brands`, `units`, `products`, `barcodes`, `modifiers`. `view` allows list and read; `manage` allows create, update and delete and implies nothing else (a person with `manage` but not `view` sees no menu entry; `manage` UI is only reachable with `view`). Final names are B-1's to confirm; the frontend keeps them in **one constants file** so a rename is a one-file change. | No keys exist yet. Two verbs per resource is the conventional minimum and maps to the "permission-aware menu" requirement. Existing tables (`permissions`, `role_permissions`) store a free-text `permission_key`, so dotted keys fit. | yes |
| D-5 | How does the frontend learn the signed-in person's permissions? | The session carries a **set of permission keys**. Today no real endpoint returns it (T-025 found there is not even a "who am I" endpoint). T-036 defines the typed contract it needs (proposed in B-1: the permission set for the current employee, for the current tenant) and the mock supplies it. With a real backend that does not return it, the set is empty. | The menu cannot be permission-aware without a source. Inventing the endpoint is backend scope; stating the contract needed is BA scope. | yes |
| D-6 | What happens when the permission set is empty or unknown? | **Deny by default**: no catalog menu entry, direct URL goes to the forbidden page. The client check is a convenience; the server is the only authority and every 403 is shown as a permission message, never as a crash. | Safest default; a missing permission list must never grant access. | yes |
| D-7 | List responses carry pagination how? | T-021 explicitly left pagination conventions to the first list endpoint. T-036 proposes `meta.pagination = {page, per_page, total}` (offset style) next to the existing `meta.request_id`, and `?page=&per_page=&search=` query parameters, and defines the shared list component around them. B-1 confirms or replaces. `ApiClient` gains a read that returns `data` and `meta` together. | The screens need a page-by-page list; T-028 D-17 already requires pagination on day one. Offset is the simplest convention a table UI can use. | yes |
| D-8 | Where do the typed API contracts live? | In `@flexipos/shared` (a `contracts/catalog` area), not inside the admin app. | The till (`pos`) will read the same catalog later; one source of truth avoids two copies drifting. | yes |
| D-9 | Do the contracts cover T-027's deferred columns (tax group, accounts, kitchen station, custom fields)? | **No.** Those columns do not exist (T-027 AC-6/AC-27/AC-27a). The UI shows no field for them, and the contract types omit them. | Do not build a form field the backend cannot store. | yes |
| D-10 | Which T-027 entities are NOT given screens? | `product_locations`, `product_branches`, `product_components` (bundle/kit/recipe lines), `product_modifier_groups` attachment, and `barcode_rules`. These move to the proposed catalog-extras frontend follow-up (F-3). T-036 does still show the product's `type` and lets a user pick any of the six types. | FP-240 lists "products/variants, barcodes, modifiers". Components, per-location and per-branch settings each need pickers over other lists and cycle rules; they would push the row over the size limit. `barcode_rules` is FP-423 and not built. The attachment of modifier groups to a product is also F-3. | yes |
| D-11 | Soft-deleted rows: shown or hidden? Can they be edited? | Lists show **active rows only**; no "show deleted" toggle; no screen offers to edit a soft-deleted row. If a read by id returns a soft-deleted row (T-027 AC-5 says it stays readable by id), the screen opens it **read-only with a "deleted" badge** and no save button. | FP-428 (update handlers do not filter soft-deleted rows) is an open backend policy question. The UI must not depend on its outcome and must not be the thing that makes it editable. | yes |
| D-12 | Concurrency on edit | Products carry a `version` token (T-027, `products.version`). The edit form sends the version it loaded; a stale-version refusal is shown as "changed by someone else, reload" with a reload action that does not discard the user's typed values until they choose. Other entities with no documented token are last-write-wins and the spec says so. | Avoids silent overwrite where the backend offers a guard; does not invent a guard where none is documented. | yes |
| D-13 | New runtime dependencies (component library, table library, state library)? | **None.** Angular 21, `@angular/forms` (reactive forms), the existing CSS custom properties, signals. | The workspace has none today; adding a UI kit is a design decision the owner did not ask for and it enlarges the supply chain. | yes |
| D-14 | Mock exclusion for the catalog mock | The extended mock must stay out of production bundles. The existing check greps for `demo@flexipos.test`; the catalog mock gets its **own distinctive sentinel string** that the same grep step also checks. | The existing grep would not detect a catalog mock leaking if the demo string stayed in a separate file. | yes |
| D-15 | Idempotency keys on create | Not sent by the screens in T-036. The submit button is disabled while a request is in flight so a double click cannot send twice. | T-021 made idempotency opt-in per route and no catalog route exists, so there is nothing to opt into. Revisit in the reconciliation step after B-1. | yes |
| D-16 | Language | English strings only, in templates. | Translations are listed "not built yet" in the frontend README. | yes |
| D-17 | Client-side validation depth | Mirror only rules that need no data from elsewhere (required, max length, numeric range, "supplied together", min <= max, immutable field read-only). Everything else (uniqueness, existence, dimension compatibility, cycles, depth limit, delete guards) is **decided by the server** and shown from its refusal; the mock implements a subset so the display path is tested. | Duplicating server-only rules in the browser would drift. | yes |
| D-18 | Is the existing "branch" context in the header kept? | Unchanged (T-025 D-5: mock-only). The shell keeps showing it when present and tolerates its absence. | Out of this task's concern; avoiding a regression. | yes |

## Proposed follow-up rows (for the lead to number and add to the backlog)

- **B-1 (BE): Catalog read surface and permission keys.** Get and List HTTP endpoints for categories, brands, units, unit conversions, products, product barcodes, modifier groups, modifiers (T-027 owes this per D-2/Ruling 11), write endpoints (create/update/delete) for each existing handler, the `catalog.<resource>.view|manage` permission keys seeded and enforced, the current-employee permission-set endpoint (D-5), the list pagination convention (D-7), and the FP-428/FP-429 policy decisions before exposure. Depends on T-027, T-021. Exit: Pest feature tests per route including a 403 per permission.
- **B-2 (BE): Customers read and write surface and permission keys.** `GetCustomer`, `ListLoyaltyPrograms`, a delete slice for notes, list endpoints for customers, groups, ledger and loyalty transactions, `customers.*` permission keys, and the merged-history view (T-028 AC-14 and the FP-240 note). Depends on T-028, B-1's conventions.
- **F-2 (FE): Customer screens.** Customers, groups, credit ledger view (read only), loyalty view (programs and transactions, read only), notes and communications lists, built on T-036's building blocks. Depends on T-036; mock first, real surface via B-2.
- **F-3 (FE): Catalog extras.** Product components (bundle/kit/recipe), per-location and per-branch product settings, modifier-group attachment, and barcode rules once FP-423 exists. Depends on T-036.
- **F-4 (FE): Contract reconciliation.** After B-1 lands, reconcile the typed catalog contracts and mock against the real responses (same shape as T-025). Depends on B-1.
- Row FP-240 itself: mark "split into T-036 (shell + catalog), F-2 (customers)"; do not mark DONE until F-2 is done.

## Questions for the owner (each has a built-in default, work proceeds on the default)

1. **Is splitting customers into a follow-up acceptable?** Default: yes (D-1).
2. **Permission key names** (`catalog.<resource>.view|manage`). Default: as D-4; changeable in one constants file.
3. **Should "manage" users also see the page without "view"?** Default: no, `view` is the gate to the page (D-4).
4. **List style: offset pages with a search box.** Default: yes (D-7); owner may prefer infinite scroll or cursor paging.
5. **Should deleted rows be viewable anywhere (an "archive" view)?** Default: no (D-11).
