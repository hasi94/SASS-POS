# T-017 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-017-audit-framework.md`, per the
TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most reversible
option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | Does FP-211 rebuild the audit tables or the base writers T-008/T-010/T-016 already shipped? | **No.** This task extends `AuditWriter`/`AuditTrail` (tenant) and `PlatformAudit` (master) and closes the four gaps those tasks named by name (request id, search, retention, export); it duplicates neither the schema nor the existing call sites. | T-010 D-20 and T-016 already decided the tables and the minimal writers exist; redoing them has no backlog justification and would risk the transactional guarantee (T-014 AC-71) those writers already proved. | Yes |
| D-2 | How should the missing `request_id` be sourced on both writers? | A `RequestId` support value mirroring the existing `ClientIp` pattern exactly: lazy, resolved from whatever the container currently holds, null outside a request (console, queued job, test), never fabricated. | `ClientIp` already solves the identical shape of problem for `ip` and is explicitly documented as reusable; inventing a second resolution strategy for `request_id` would be a second answer to one question. Closes `docs/architecture.md` §17's stated requirement and FP-323. | Yes |
| D-3 | Should `PlatformAudit.actor_email` stay null, or be populated? | Populated as a snapshot of the acting user's email at write time, taken once and never joined later. | Mirrors `AuditWriter::actorName()`'s own reasoning: a row whose meaning changes when a user later edits their email is not an audit row. Makes `platform_audit_logs` readable without a join to a `users` row that may since have changed. | Yes |
| D-4 | Does the per-tenant migration runner get a platform-audit row? | Yes — exactly one `platform_audit_logs` row per run, action `migration.run`, written through the extended `PlatformAudit`, at run-creation time. | `docs/database.md` §4.9 already names `migration.run` as a worked example action; `tenant_migration_runs.initiated_by` already exists to source the actor from. This is the one master-level write path that already exists today and has no audit row — closing it needs no new feature invented. | Yes |
| D-5 | What about the other example actions `docs/database.md` §4.9 names (`tenant.created`, `mapping.updated`, `credential.rotated`, `impersonation.started`, `plugin.enabled`)? | Stay unaudited by this task. | None has a write path yet: provisioning (FP-206), credential rotation, impersonation and the plugin framework (FP-213) are all unbuilt. Auditing a write path that does not exist is not buildable or testable. | Yes — each becomes auditable the moment its owning task builds the write path, through this task's same extended mechanism. |
| D-6 | Does FP-211 build the tenant `security_events` table `docs/database.md` §6.21 designs? | No. | It is a different concern from `audit_logs` (security incidents, not change history), was not shipped in T-008's baseline (its AC-23 table list omits it), and every one of its seven event types (`pin_bruteforce`, `permission_denied`, `override_used`, `after_hours_access`, `bulk_export`, `mass_delete`, `negative_stock_forced`) has no producer today — most need modules (workflow engine, bulk export, stock) that do not exist yet, and `pin_bruteforce`/`permission_denied` already have an equivalent record in `access_log` (T-010 D-21), so a second table recording the same fact would be the duplication FP-184 warns against. | Yes — a later row, once the producing features exist. |
| D-7 | Does reading audit records get an HTTP route or an admin UI? | No. Internal handler/console command only, for both the tenant and the master side. | No platform-admin authorization model or HTTP surface exists anywhere in the codebase (T-016 D-21's own precedent, made for the same reason: building a one-off model for this task alone, when nothing else has one either, is scope invented beyond what the backlog row asks for). | Yes — additive once such a surface exists for any reason. |
| D-8 | How is reading tenant audit records permissioned? | A new, dedicated permission key, named `audit.read` in the spec, defaulting closed like every one of the six existing keys in `AccessPermissions` (no automatic grant to any role). Proved against the resolver and fixture roles, not a production seeding flow. | Mirrors the existing `employees.set_pin` precedent (D-13 of T-010: a capability kept separate from general management specifically so it can be withheld); a shop may want a supervisor to manage staff without reading the full change history. No production seeding flow exists yet because tenant provisioning (FP-206) is unbuilt, so the proof is bounded the same way T-016 D-19/AC-8 already accepted. | Yes |
| D-9 | How is reading master audit records gated? | Restricted to platform staff (`users.is_platform_staff`). | The only distinction the master schema already draws between a platform operator and a tenant-side user (T-008 AC-2); inventing a finer-grained model is exactly the HTTP/authorization surface D-7 defers. | Yes |
| D-10 | `docs/database.md` §9 says tenant audit retention is "archived to `audit_logs_archive_<year>` yearly" — a table created at runtime, per year. Build it literally? | No. One permanent `audit_logs_archive` table, same shape as `audit_logs`, created by an ordinary per-tenant migration. The year-suffixed wording is recorded here as the document line to correct, not the thing to match. | Creating a table outside the per-tenant migration runner would break the standing rule that every schema change runs through the runner (`CLAUDE.md`; `docs/patterns.md` §4.6) — a scheduled job cannot run DDL against 200+ shop databases safely or reviewably. A single archive table is the safer, reversible default; true yearly partitioning is available later if query volume on the archive ever earns it (`docs/patterns.md` §5's measured-only rule). Same project convention as FP-171/176/186: a stale or unbuildable document fact is named, not silently worked around. | Yes |
| D-11 | What retention threshold, and whose decision is it (tenant-configurable or not)? | 365 days (matching §9's "yearly"), as one application-wide configuration value, not a per-tenant setting. | An operational/engineering parameter, not a business rule a shop owner would tune — consistent with T-008's own `schema.backups.available`-style config gate rather than a `settings` row. | Yes — becomes tenant-configurable later if a reason appears. |
| D-12 | Does this task build a pruning (hard-delete) job for either table? | No, for `audit_logs`, `audit_logs_archive` and `platform_audit_logs` alike. | The business has stated a floor (platform: never below 7 years) and an archive (tenant: move, not delete), never a ceiling. Building an unasked-for destructive capability is exactly the caution T-008's `is_destructive` gate (its D-10) already exists to enforce elsewhere in this codebase. | Yes |
| D-13 | What satisfies "export" (named explicitly, alongside search and retention, as owed by FP-211 — T-010 D-20)? | A console command that writes a query's result set to a local file (JSON or CSV). No object storage, email or delivery integration. | No such integration exists in this codebase for any table yet — `tenant_backups.location` is a designed column with nothing shipped behind it. Matching that existing level of ambition is safer than inventing infrastructure this task was not asked to build. | Yes |
| D-14 | The archival job needs a scheduler. Does this task wire one into deployment? | No — it depends on the same scheduler FP-319 already names as unwired in production, exactly as T-016's grace-period job does (that task's own D-14). | Duplicating a named, already-tracked gap is more honest than inventing a second cron mechanism to work around it, or silently declaring it this task's job to fix a deployment gap FP-319 already owns. | N/A — pre-existing gap, named not re-solved. |
| D-15 | Does this task pre-build audit hooks for modules that do not exist yet (sales, stock, payroll, journal, plugins)? | No. Each owning module calls the one shared writer when it ships. | Hooks for code that does not exist cannot be tested and would guess at a shape (`before`/`after` of what, exactly) nobody has designed yet. | Yes |
| D-16 | Does this task take on `audit_logs.branch_id`'s missing foreign key (FP-313)? | No — unchanged, left exactly where FP-313 already assigned it (the branches/organization module, with the data-clean pre-check pattern). | FP-211 is about who-changed-what and the request identifier, not about the branch-reference integrity FP-313 already owns; picking it up here would duplicate an existing, differently-scoped backlog row. | Yes |
