# T-018 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-018-event-bus-outbox.md`, per
the TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most
reversible option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | Does the MySQL/MariaDB `ENGINE_HOLD` (G-1) govern Redis connections too? | **No.** A separate, narrower condition governs Redis: any **[ENGINE]** criterion needing a real Redis connection is NOT VERIFIED until Redis infrastructure actually exists in this environment — measured today as absent (no Docker Compose service; `infra/` is an empty placeholder; no `predis`/`phpredis` dependency in `modules/host/composer.json`; `.env.example` defaults `QUEUE_CONNECTION=database` and `CACHE_STORE=database`, not `redis`). This condition is not owner-gated like `ENGINE_HOLD`: it lifts automatically the moment the infrastructure is wired up, with no sign-off required, because no incident and no data-loss risk is involved. | `Flexipos\Testing\Engine\EngineOnHold`/`EngineConnection` (`packages/testing/src/Engine`) are explicitly scoped to "the test engine" that suffered the 2026-10-14 MySQL/MariaDB data-loss incident (`ENGINE_DRIVER` defaults `mariadb`, the class docblock names that incident by date). Nothing in that mechanism extends to Redis, and conflating the two would wrongly make every Redis-dependent criterion wait on a MySQL dump-verification gate that has nothing to do with it. | Yes |
| D-2 | Does T-018 need a real Redis Streams implementation behind the interface, or only a stand-in? | **Both, structurally.** The interface, a deterministic in-memory/array stand-in, and a real Redis Streams adapter are all in scope; only the stand-in's behaviour is provable without **[ENGINE]** today. The real adapter ships as code whose correctness is asserted only by **[ENGINE]** criteria (NOT VERIFIED per D-1). | Mirrors the `TenantFleet`/`InMemoryTenantFleet`/`MasterTenantFleet` precedent T-017 just built: one contract, a config-selected stand-in and a config-selected real implementation, so the day Redis is reachable the same tests start proving the real adapter with no spec change. | Yes |
| D-3 | What exactly writes to `outbox_events`, and when? | Exactly **one** outbox-writing capability. Any module wanting an event published calls it; it writes the row **inside the same database transaction** as the business change that caused it. No module's diff inserts into `outbox_events` directly outside that one writer. | Matches `docs/architecture.md` §9 ("every event is written to an outbox... inside the same transaction") and `docs/patterns.md` §6 checklist item 4 ("cross-module or external effect? then through the outbox"). Mirrors the exact "one writer" rule T-017 enforced for `audit_logs` (its AC-19), which the project has now used twice. | Yes |
| D-4 | How does the relay claim rows, given `docs/patterns.md` §5 names an id-cursor over `outbox_events.id` as unsafe? | The relay selects rows where `status='pending'` ordered by `occurred_at` — exactly the access pattern the shipped `(status, occurred_at)` index already serves — never a cursor on `id`. T-018 assumes **exactly one active relay worker per tenant at a time**; concurrent relay workers racing on the same tenant's outbox, and the claim-mark column that would then be needed, are explicitly out of scope. | This is not a new design: the shipped T-008 migration's own docblock says it in so many words — *"the relay FP-212 ships first needs no mark either, because it selects `status = 'pending'` ordered by `occurred_at`... when a mark is eventually needed - several relay workers - it is a claim mark... never a cursor"*. T-018 is the relay that comment names, so it follows the plan already written for it rather than re-deciding the question. | Yes — the claim-mark column and multi-worker support are additive later, as the same comment anticipates. |
| D-5 | Does the spec mandate the relay's process model (queued job, scheduled command, or a long-running worker loop)? | No. The spec states only the observable behaviour (claims pending rows in bounded batches, publishes, marks, retries with back-off). Exact process shape is `architect`'s/`dev`'s technical design choice. | `docs/deployment-vps.md` already names `pos-worker` as "queues + stream consumers + outbox relay" at the infrastructure level; a specific implementation (cron-triggered command vs. daemon loop) is a technical decision T-003 D-33 already set the precedent for `ba` not making. | Yes |
| D-6 | Is consumer-group-plus-ack sufficient, or does the outbox also need its own dedup key, and does this task build the "inbox dedupe" the `packages/eventbus` scaffold's own description names? | Consumer group + explicit ack, plus a consumer that is **idempotent by the event's own identifier** (`outbox_events.id`, carried into the envelope), is sufficient. No new outbox-side dedup column is added, and **no generic shared "inbox dedupe" cache/table is built** by this task. | `docs/architecture.md` §9 already states the design: *"consumers are idempotent by event identifier."* Redis Streams' consumer-group + `XACK` already prevents one group from double-processing under normal operation; the remaining case (crash after acting, before acking) is exactly what identifier-based idempotency exists to cover. Building a second, outbox-side dedup key would duplicate that without a new case driving it (the FP-184 family: no second authority for one fact). The scaffold package's description phrase ("inbox dedupe") is read as aspirational packaging text, not a requirement — `docs/database.md` explicitly **deleted** `inbox_events` as a v0.3 relic ("there are no inter-module events to consume"), so resurrecting an inbox table or store on that phrase's authority alone would contradict the authoritative schema document. If a second consumer later genuinely needs a shared dedup helper, it is promoted then, under `docs/patterns.md` §3's three-use rule. | Yes |
| D-7 | What does "dead letter" mean concretely, given `outbox_events.status` only has three legal values (`pending, published, failed`) and no fourth `dead_letter` value? | **Two distinct failure paths**, matching `docs/architecture.md` §9's own wording ("failures retry with back-off and then move to a dead-letter stream with an alert"): (a) **relay-side** — the relay could never reach the bus at all; after exhausting its publish attempts the outbox row stays `status='failed'` (already a legal value, no migration needed); (b) **consumer-side** — the bus delivered the message, but no consumer in the group ever finished it; after exhausting delivery attempts it is moved to a dedicated **dead-letter stream**, never a new tenant-database table. | A new table would duplicate what the stream already tracks (per-message delivery count) and what `outbox_events.status` already offers (`failed`) — the architecture document's own words name a dead-letter **stream**, not a table, which also keeps this task's tenant-schema footprint at zero new migrations. | Yes — a dead-letter table could be added later if an operator view needs to outlive stream trimming (`docs/deployment-vps.md` already caps streams by `MAXLEN`). |
| D-8 | What retry/back-off defaults, in the absence of a stated business rule? | A reversible default: **5 attempts** before a row is marked `failed` (relay-publish side) or a message is moved to the dead-letter stream (consumer-delivery side), with **exponential back-off** between attempts (configurable base and cap), both overridable by configuration. Provable with an injectable clock, never a real wait. | No business rule exists for this; project convention (T-016 D-11, T-017 D-11) is to pick one concrete, reversible default rather than leave it an open question for the human. | Yes |
| D-9 | How does an operator see failed outbox rows and dead-lettered events? | Console commands only — no HTTP route, no admin UI. One command lists `outbox_events` rows with `status='failed'`; a second lists the dead-letter stream's entries; a third lets an operator move a chosen failed/dead-lettered item back to a retryable state. | Same precedent as T-016 D-21 and T-017 D-7: no platform-admin authorization model or HTTP surface exists anywhere in this codebase yet, so this task does not invent a one-off model to gate a route that would otherwise have none. | Yes — additive once such a surface exists for any reason. |
| D-10 | Does this task invent a business event to publish? | **No.** Exactly one example event proves the pipeline end-to-end and is explicitly a proof-of-pipeline fixture, not new business scope — named here for concreteness as something like `demo.pinged`, and a natural (not mandated) home is the already-scaffolded `modules/demo` package, which already carries an empty `src/Consumers/` directory and is this project's standing, no-business-meaning, "replace with real endpoints" module. No other event (a sale, a subscription change, a stock movement, …) is designed, named, or given a producer. | Direct instruction from the orchestrator's framing of this task; also the same "no hooks for modules that don't exist" convention T-017 D-15 already used. `modules/demo`'s `Consumers/.gitkeep` is a pre-existing signal, not an invention. Exact event name and file placement are `dev`'s/`architect`'s call. | Yes |
| D-11 | Does this task guard `outbox_events.branch_id`'s missing foreign key? | No — left exactly where **FP-313** already assigned it. | FP-313 already names `outbox_events.branch_id` by column, with its own planned fix (a contract-phase migration, per-tenant, with the data-clean pre-check pattern). This task is event-bus/outbox **behaviour**, not referential-integrity cleanup; picking it up here would duplicate an existing, differently-scoped row — the same reasoning T-017 D-16 already applied to `audit_logs.branch_id`. | Yes |
| D-12 | Does the envelope need new `outbox_events` columns? | No. The shipped columns (`type`, `version`, `branch_id`, `aggregate_type`, `aggregate_id`, `payload`, `occurred_at`, `correlation_id`, `causation_id`, `actor`, `status`, `published_at`, `attempts`, `last_error`) already carry everything `docs/architecture.md` §9's envelope asks for — tenant is implicit (no tenant table column exists anywhere in a tenant database, `docs/database.md` §2), branch/actor/correlation/causation are already named columns. | T-008 already shipped this table to the exact shape the architecture document describes; redesigning it without a found gap is outside this task's economy-of-change scope, and none was found. | Yes |
| D-13 | Does this task build retention/archival for `outbox_events` (the existing 30-day note in `docs/database.md` §6.21)? | No. | Not asked for by FP-212's own wording ("relay, consumers, retries, dead letter" — no mention of retention), and building an unasked-for job is the same caution T-017 D-12 already applied to the audit tables. | Yes — a follow-up row (candidate: next number after FP-328), not this task. |
| D-14 | Must consumers process events in strict per-aggregate order, requiring a partitioning scheme (one stream per aggregate, or similar)? | No. Only "append order within one stream" is guaranteed; no per-aggregate or cross-stream ordering mechanism is built. | No business rule requires it (no real business event is in scope per D-10), and inventing a partitioning scheme for an unstated requirement would be speculative. Added later, by whichever task first needs it. | Yes |
| D-15 | Is the event bus the same mechanism as the named Laravel job queues `docs/architecture.md` §9 lists (`default, sync, print, reports, notifications, plugins, imports, migrations`)? | No — they are two different mechanisms sharing one Redis instance per `docs/eventbus.md`. This task's event bus/outbox/relay is distinct from `config/queue.php`'s queue names, which this task does not add to or rename. | Avoids a reader conflating "which queue" with "which stream" — §9's named list is about Laravel's job-queue feature, already configured, not about Redis Streams. | Yes |
| D-16 | How does the outbox writer populate `actor` (JSON, no fixed shape in the shipped schema) and default `correlation_id`? | `actor` reuses the **same actor-type vocabulary** `AuditWriter` already uses (`employee, terminal, system, plugin, platform_staff`), with `actor_id`/`actor_name` snapshotted the same way (never re-joined later). `correlation_id` defaults via the **same lazy, per-current-request, null-outside-a-request resolver** T-017 built for audit's `request_id` (`RequestId`, mirroring `ClientIp`), reused rather than reinvented. | Avoids the tenant database growing two different "who did this" vocabularies for the same concept (the FP-184 family: name one authority). T-017's `RequestId` already solves the identical shape of problem for "which request caused this write," one task after it solved it for audit. | Yes |
| D-17 | Does this task wire the master-side `tenant.mapping.changed` event T-003 D-32 deferred pending FP-212's existence? | No. | `tenant.mapping.changed` (`docs/database.md` §4.4) is a **master**-connection cache-invalidation concern, not a tenant-database outbox event — a different domain from everything this task builds (which lives entirely in the tenant database, per topology rule, `docs/database.md` §2: no cross-database event plumbing). Wiring it is a follow-up for whoever next revisits that cache, once this task's mechanism exists to be wired to. | Yes |
