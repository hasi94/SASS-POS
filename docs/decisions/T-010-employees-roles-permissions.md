# T-010: Employees, roles and branch-scoped permissions - decisions

Format: `D-n | Question | Decision | Reason | Reversible: yes/no`. These are T-010's own; T-009's D-1 to D-38 are in `T-009-authentication.md` (cited here as "T-009 D-n"), T-008's D-1 to D-56 in `T-008-master-schema-and-tenant-baseline.md`.

D-1 | FP-208 promises *branch-scoped* permissions, but branches are FP-209 and not yet a table. Build the scoping mechanism now, or ship role-level permissions and leave scoping to FP-209? | **Build the mechanism now**, against branch ids that are opaque `CHAR(26)` values with no foreign key. `employee_roles.branch_id` and `employee_permissions.branch_id` (nullable, null = all branches) and `employee_branches.branch_id` exist from the first migration; the resolver takes an optional branch; `permissions.is_branch_scoped` is honoured; the hash covers scope. FP-209 adds the three foreign keys as a contract-phase step after proving the columns clean (the T-008 D-5 route, which the `settings` and `audit_logs` migrations already follow). Mechanism proved with fixture-registered branch-scoped keys because no production key is branch-scoped yet. | **T-009 D-10's rule cuts differently for a claim and for a column, and that difference decides this.** D-10: minting a claim you cannot populate is worse than omitting it, because a claim is a published contract inside tokens already in the wild, so adding is cheap and redefining is not. A *column* is private storage in a tenant database: adding it early costs a nullable unguarded identifier whose only risk is a bad id, which T-008 D-5 already accepted four times and a contract-phase foreign key closes. What is **not** cheap to add later is the *shape of the answer*: a resolver that returns "a set of keys" cannot become "a set of keys per branch" without changing every caller written in between; `employee_permissions`' key includes the branch; and a `perm_hash` computed over scope-less sets would be a different function afterwards, so every token issued in the window would carry a hash with a meaning that later changes. So the storage, the resolver's signature and the hash are final now, and the one thing deferred is existence checking of branch ids. The omit-until-populatable rule does still apply to the **claims**: see D-2, where `branch_ids` is minted only in a form whose meaning cannot change when branches arrive. Cost accepted: a grant can name a branch that does not exist (D-30). | Reversible: partly. The columns, the resolver shape and the hash are hard to un-make once a module codes against them; that is exactly why they are fixed now rather than later. The branch-id existence gap closes when FP-209 lands.

D-2 | Which claims does the tenant token gain, with what meaning, and when? | `branch_ids`, `all_branches`, `perm_version`, `perm_hash`, minted at tenant selection and at every tenant-scoped refresh, only for memberships with a linked employee, and then **all five employee-derived claims together or none** (`employee` is the fifth, already minted by T-009). `branch_ids` = the employee's explicit `employee_branches` ids, distinct, sorted, possibly empty, **never expanded**. `all_branches` (new, not printed by either design document) = true when the employee holds at least one *allowing* null-scope role assignment or per-person grant. A platform token and a token without an employee gain nothing. Not minted: `branch` (singular), `terminal_id`. | The two design documents contradict each other: `docs/architecture.md` section 5 prints `branch_ids[]`, `docs/database.md` section 5 prints `branch` (one id). The plural is chosen because one token must serve a person who works at several branches and a per-branch token would force re-issue on every branch switch. **`branch_ids` alone cannot be populated truthfully for an owner whose role is "all branches"**: enumerating all branches needs a `branches` table that does not exist, and defining the empty list as "all" would later *redefine* the claim when branches arrive. So `branch_ids` is defined as explicit attachments only (meaning fixed forever) and a boolean carries the "all" case; adding a claim is cheap, redefining one is not. | Reversible: yes while no token has reached a real user (additive claims; `all_branches` can be dropped).

D-3 | FP-200 and the FP-208 backlog row say T-010 owes "the full `employee` object". Mint an object? | **No.** `employee` stays a string id, as T-009 minted it. Anything else about the employee is read by a query, not carried in a token. | Neither design document prints an object: `docs/database.md` section 5 prints `employee: employee_id` and `docs/architecture.md` prints `employee_id?`. The backlog paraphrase is wrong. Turning the existing scalar into an object would change a claim's meaning after tokens exist, which is the failure T-009 D-10 was written to prevent. A name in a token also goes stale on rename. | Reversible: yes (an extra claim can be added later; the scalar cannot be turned into an object).

D-4 | Permissions change while a token is live. Inherit T-009 D-2 (valid until `exp`, 15 minutes), or something stronger? | **Stronger.** The tenant database is the authority on every request: the resolver reads it and never trusts claims. In addition a tenant token whose `perm_version` is behind `employees.perm_version` is refused with 401 `permissions_changed` until the client refreshes, and refresh re-reads everything (D-7). | The reasons differ from T-009 D-2's. (1) D-2 accepted a disabled *user* passing for 15 minutes because verifying that cheaply meant no master query per request; here the tenant database is **already open** for the request, so the check is one primary-key read on an open connection, no master round-trip. (2) The harm is asymmetric: a removed permission usually means a dismissed or misbehaving person acting for up to 15 minutes. (3) `docs/database.md` section 5 already promises it ("invalidates every issued token for that employee at the next request without a master round-trip"), as does `architecture.md` section 6 ("authorization is evaluated against the tenant database"). (4) With live resolution authoritative, the version check is also what tells a client its cached menu is stale, rather than letting it act on rights it no longer has. Not decided here and not invented: a cost figure (none measured; `docs/patterns.md` wants measurement before a read model). The design documents leave open **who compares**; this decision answers it: the request path, in the tenant connection. | Reversible: yes (the version check can be relaxed to claims-only without schema change).

D-5 | Selection used not to open the tenant database (T-009 D-9, AC-39). With tenant-local claims it must. How? | For a membership with a non-null `employee_id`, selection (and tenant refresh) enters the tenant through the existing `Tenancy::enter()`, reads the employee, and so the existing serving gate runs at selection as well as on later requests. A gate refusal at selection is the existing `tenant_not_servable`, with no token and no refresh row. A null `employee_id` keeps T-009's behaviour exactly. T-009 D-9's first clause and the last sentence of its AC-39 are superseded for employee-bearing memberships only; the one test pinning them is narrowed, not deleted. | T-009 D-9 itself predicted this: "when FP-208 adds such claims the right answer is still the existing `Tenancy::enter()`, not a mapping probe." A mapping probe would be a second copy of the gate's first rule. This is a deliberate change to a recorded T-009 decision, stated here so nobody reads it as a regression; T-009's record is not rewritten. | Reversible: yes.

D-6 | Mint-time checks on the master-to-tenant link. | At selection and at tenant refresh, with `tenant_users.employee_id` non-null, mint only if all hold: the employee row exists, is not soft-deleted, has an **acting** status (D-15), and `employees.user_id` equals the token's user id. Otherwise refuse 403 `employee_unavailable`, no token, a `login_history` failure row, one indistinguishable body; at refresh the refresh token is **not** consumed (T-009 D-24). | `docs/database.md` section 5 says the link is "checked, not enforced", by a nightly job. At mint the check is a handful of cheap column comparisons on a row already being read, and it blocks a confused-deputy case: a wrong `tenant_users.employee_id` would otherwise hand one person another's permissions for the rest of the session. Failing closed is safer than minting a token with empty rights, which would hide a data fault. | Reversible: yes.

D-7 | What exactly does the per-request check compare, and what does the client see? | `employee` present in the token: read that employee's row (`perm_version`, `deleted_at`); if the row is missing, soft-deleted, or `perm_version` differs from the claim, 401 `permissions_changed`, no handler, no `access_log` row (a stale credential is not a denial). No `employee` claim: no check; guarded routes refuse `not_permitted`. The employee's status is **not** a separate check: a status change crossing the acting boundary bumps the version (AC-27), so one mechanism covers it and the refresh then fails with `employee_unavailable`. | One comparison is easier to prove, and a second status check would be a second source for the same fact (FP-184). 401 (not 403) because the credential, not the caller's rights, is what is out of date, and the cure is a refresh. | Reversible: yes.

D-8 | Resolver semantics the documents leave open. | (a) **Deny wins**: a per-person deny at any scope covering the asked branch refuses, whatever else allows; there is no "more specific allow beats general deny". (b) A grant covers a branch when its scope is null or equal. (c) A key with `is_branch_scoped = false` is allowed only through a **null-scope** contribution; a role assigned at a branch does not confer it. (d) A branch-scoped key asked with no branch is `branch_required`; an unregistered key is `unknown_permission`; both distinct from `not_permitted`. (e) A per-person row for a non-scoped key at a specific branch is refused at write (`scope_not_applicable`). (f) Platform staff and owners get no bypass; `owner` holds every key by data, not by code. | `docs/database.md` 6.2 says only "per-person grant or explicit deny on top of roles". Deny-wins and least-privilege are the conventional, safest, readings and are the ones whose mistake fails closed. Distinct refusal reasons (d) exist so a typo in a guard does not silently deny everyone forever. | Reversible: yes before modules code against the resolver; costly after.

D-9 | Branch-related columns beyond the three scoping columns. | `employees.branch_id` (design: `NOT NULL` foreign key, "based at") is **omitted**. The authority for "which branches this person works at, and which is default" is `employee_branches` alone. Unguarded branch columns are exactly three: `employee_roles.branch_id`, `employee_permissions.branch_id`, `employee_branches.branch_id`. | A `NOT NULL` foreign key to a table that does not exist cannot be created in an expand migration, and carrying a nullable duplicate of `employee_branches.is_default` would give two columns holding one fact (FP-184). HR's "based at" is a different meaning and can be added later, additively. Fewer unguarded columns means fewer for FP-209 to clean. | Reversible: yes (a column is additive).

D-10 | Nullable keys. `docs/database.md` 6.2 prints `employee_roles` unique over (employee, role, branch) and `employee_permissions` PK (employee, key, branch), both with `branch_id` NULL meaning all branches. | Both keys are built on the §3.3 stored sentinel over the null-safe branch (`COALESCE(branch_id, '-')`, correct because the column is `CHAR(26)`; T-008's helper is declared over ULID columns only). **`employee_permissions` gets a surrogate `id` primary key** because MySQL and MariaDB make every primary-key column `NOT NULL`, so the printed composite key cannot store the "all branches" row it exists for. | The unique case is the exact defect `docs/qa/T-006-unit-of-measure.md` BUG-9 and FP-180 name (`employee_roles` is one of the eleven). The primary-key case is **not** on FP-180's list and is the same bug in a stronger form: on MySQL the row is unrepresentable, on SQLite a non-integer primary key silently accepts NULL, so the stand-in and the real engine would disagree. Stated to `architect` as Open question 6. | Reversible: yes.

D-11 | How does `employee_branches` relate to scoped grants? Neither document says. | A role assignment or per-person row scoped to branch X requires the employee to be attached to X at write (`not_attached`); detaching X is refused while any such row exists (`has_scoped_grants`). A null scope needs no attachment. | It makes `branch_ids` a truthful superset of every branch the person holds a scoped grant for, and gives referential integrity inside the tenant database even though no `branches` table exists. Read-time intersection was the alternative and was rejected: a detach would silently disable grants. | Reversible: yes.

D-12 | Which roles exist, and who holds every permission? | One system role, `owner`, holds **every** registered key by data; the registry sync adds each newly declared key to it and bumps every holder. System roles cannot be renamed, edited or deleted through any operation. A custom role in use cannot be deleted. Manager, cashier, waiter and other catalogues are **not** seeded (Open question 1). | Nothing in the documents names default roles beyond "the owner role" (`docs/database.md` provisioning step 10) and "seed defaults (roles)". Inventing a catalogue invents business rules. An owner role that does not follow new keys would lock the owner out of every later feature. | Reversible: yes (more roles are additive).

D-13 | Where are permission keys declared, and which does this task add? | In code, per module, synced idempotently into `permissions` (design: "seeded at provisioning from the application's registry"). This task declares `employees.view`, `employees.manage`, `employees.set_pin`, `roles.view`, `roles.manage`, `access.assign`, all company-wide, one per capability this task itself guards. Sync never deletes a key (reports orphans), never flips `is_branch_scoped` of an existing key (reports it). | The task's own operations are the first guarded operations and need keys. None is branch-scoped: making "manage employees" branch-scoped needs a rule for an employee attached to two branches, which is not given. The branch mechanism is therefore proved with fixture keys (AC-39, AC-41), and a reader should not take the absence of a branch-scoped production key for absence of the feature. Flipping the scope flag of a key with live grants would silently change what those grants mean. | Reversible: yes.

D-14 | How much of the design's `employees` row is built? | Identity and access only: `code`, `user_id`, names, `status`, the PIN columns, `perm_version`, timestamps, soft delete, `created_by`/`updated_by`. HR and payroll columns, `custom_fields` and the branch column are later, additive. `code` is immutable after creation and unique across soft-deleted rows, compared exactly as stored (case-sensitive). Any status may be set to any other. | The brief is "employees, roles, permissions, PINs". Salary, NIC and bank details belong to payroll and would pull in tables (departments, salary structures, accounts) that do not exist. Immutable code and no reuse keep audit and payroll history unambiguous. Case sensitivity and free status transitions are the least invented rules; both are put to the owner (Open questions 4 and 5). | Reversible: yes.

D-15 | Which employee statuses may act? | `active` and `probation` act. `on_leave`, `suspended`, `resigned`, `terminated` do not (no token mint, no PIN, every resolver question `employee_unavailable`). The set lives in one place. | The safest reading; an employee on leave signing in to ring sales is the surprising case, an owner marked on leave locking themselves out is the recoverable one (another owner changes the status, and `last_owner` stops the last owner being locked out by accident). Open question 2. | Reversible: yes.

D-16 | Cashier PIN shape, and does this task expose PIN login? | PIN is 4 to 8 digits (configuration), rejecting repeated digits and strictly ascending or descending runs, in one list. Not unique across employees; the employee is identified by `code`, then the PIN is checked, so there is no "that PIN is taken" oracle (and a salted hash could not support one). Argon2id (`docs/database.md`). **There is no network route that verifies a PIN**: the verify operation is in-process only, for the future till/terminal task. Set-PIN by an actor with `employees.set_pin`, also on oneself. | A till identifies a terminal first (FP-209); without terminal identity a public endpoint over at most 10^4 to 10^8 values, with per-IP throttling not built (FP-199 covers login only), is an avoidable guessing surface. T-009 D-17 already excluded employee/PIN login for the same reason. Digit-length and weak-PIN rules are conventional, not owner-given. | Reversible: yes.

D-17 | PIN lockout. | 5 consecutive failures lock the employee's PIN for 15 minutes; the counter resets at the lock and on success; failures while locked are not counted and do not extend the lock; setting a new PIN unlocks. Two columns, `pin_failed_attempts` and `pin_locked_until`, are added although `docs/database.md` lists none. Figures configurable. | Mirrors T-009 D-5 so there is one rule to learn. A reset-by-setting-a-PIN path is the only unlock; without it an attacker-locked cashier would be stuck. A deliberate lock-out of a known employee is possible (as T-009 acknowledged for accounts) and is bounded by the no-extension rule. | Reversible: yes.

D-18 | What must a PIN never reach? | Every column of every table in both databases (enumerated live), the application log, exception messages, every HTTP response and header, token claims, and the URL/query/path channel. A PIN is accepted only in the body; one in the query string or path is refused before any read or write and not echoed. The harness uses an unambiguous sentinel and a no-sentinel baseline run. | T-009's AC-26 scanned four sinks; QA's taxonomy added an adjacent check and an out-of-application ingress channel, and the ingress channel caught a real defect there (passwords readable from the query string). A digit-only secret is also easy to confuse with unrelated digits, hence the baseline run. The application cannot erase what a web server logs on its own; the criterion says it proves only that the application neither accepts nor re-emits the URL form. | Reversible: yes.

D-19 | Rules that stop the permission system being used to defeat itself. | (a) The last acting `owner` at a null scope cannot be removed, made non-acting or deleted (`last_owner`). (b) Nobody changes their own roles, per-person permissions or branch attachments (`self_change`). (c) Nobody can grant what they do not hold at that scope; a deny needs no check (`no_escalation`). | Conventional safeguards; without (c) any holder of `access.assign` is an owner; without (b) one is trivially so; without (a) a mistake locks a shop out with no way back before provisioning exists. None is in the documents, so each is a stated decision, and each has a positive control in the spec. | Reversible: yes.

D-20 | Does this task audit its changes? | Yes, minimally. Every successful administrative operation writes one `audit_logs` row (the baseline table, built by T-008) through one small writer; a refusal writes none. FP-211 later replaces the writer. | Who changed whose permissions is the canonical audit event; leaving it for FP-211 would make this task's own security feature untraceable. The table exists and has no writer; a minimal one is smaller than the gap. Not asked: search, retention, export. | Reversible: yes.

D-21 | What goes in `access_log`? | Only `pin_login`, `pin_failed`, `permission_denied`. A stale token (D-7), validation failure or authentication failure writes nothing. | `terminal_login` and `override_used` have no producer yet. A stale token is neither an access decision nor an attack. | Reversible: yes.

D-22 | Who adds the foreign key `settings.updated_by` to `employees`? | This task, as a contract-phase migration after proving the column holds only null or valid ids; a fixture with a dangling id fails that tenant alone and changes nothing. | T-008 D-5 and the `settings` migration's docblock assign it to "the module that creates `employees`". If the runner's contract rule (refuse a contract step while an active tenant is below the expand version) makes it impossible in one task, `architect` says so and it becomes a filed row, not a silent drop. | Reversible: yes.

D-23 | What is `perm_hash` a hash of, and what is NOT claimed? | A fingerprint of `perm_version` plus the employee's *contributing* grants and denials (role-derived allows and per-person rows with their scopes), canonical and order-independent. Proved: same contributions give the same hash; any one change changes it. **Not claimed:** that two configurations resolving identically hash equally. | Hashing the *resolved* set would need enumerating every branch ("all except Y" has no finite form without a branch list). Hashing contributions is exact, finite and available now. The non-claim is stated because T-009 D-34 (a criterion may not describe what an instrument proves until it has been run on the evading shape) applies: "equal hash iff equal rights" is the natural overclaim. Verification uses only `perm_version`; the hash is for clients and the future replica. | Reversible: yes while no real token exists.

D-24 | Who creates the first owner? | Provisioning (FP-206, `create_owner` step). Until FP-206 no tenant has an owner; tests use the internal operations. | `docs/database.md` lists it as provisioning step 10. | Reversible: yes.

D-25 | Does this task write the master side of the employee/login link? | No. `tenant_users.employee_id` and `employees.user_id` are written by nobody here. The nightly consistency job is not built. D-26 | Refusal vocabulary and what a caller sees. | Closed set: `not_permitted`, `branch_required`, `unknown_permission`, `permissions_changed`, `employee_unavailable`, `last_owner`, `self_change`, `no_escalation`, `role_in_use`, `system_role`, `scope_not_applicable`, `not_attached`, `has_scoped_grants`, `validation`, and (added by D-36) `actor_required`. Not telling a caller whether a deny exists discloses nothing useful and costs nothing; the operator still sees it. | Reversible: yes.

D-27 | How are enumerating criteria to be written? | Any criterion that sweeps a set (registry keys, routes, version-bumping operations, PIN sinks, resolver truth table) enumerates it from the source of truth, not from a list in the test; prints the items it examined; asserts the list is non-empty; and names a mutation that must turn it red, including an item nobody listed. | Shape 7 of the T-009 mask taxonomy: an instrument that discriminates perfectly over the wrong domain is invisible to mutation by construction. A test that enumerates the permissions it knows cannot see the one nobody listed. | Reversible: yes.

D-28 | When is `perm_version` bumped? | In the same transaction and by a single atomic increment, for every change to what an employee can do or to the `branch_ids` / `all_branches` claims, including a role's permission change (fanned out to every holder, bounded by one shop's staff). Not for name, PIN, lockout, role rename. A rolled-back change bumps nothing. | `docs/database.md` stores the version per employee, so a role edit cannot bump "the role". The fan-out in one transaction keeps "every change implies a bump" true, and it is the property the sweep (AC-53) checks. | Reversible: yes.

D-30 | Is a branch id validated? | Shape only: a 26-character ULID. D-32 | Employee update that includes a disallowed field (`code`, `user_id`, `pin_hash`, `perm_version`, `status`): ignore it or refuse it? A refusal is observable and cheap to assert. | Reversible: yes.

D-33 | In what order does the resolver refuse? (AC-42; settled by `architect`, shipped by `dev`) | `unknown_permission`, then `branch_required`, then `employee_unavailable`, then `not_permitted`. | The first two are properties of the question, the third of the subject; a malformed question has no answer about any subject (the HTTP layer does the same one level up: 422 before 401/403). Decisive: `unknown_permission` is a server defect logged at error level (D-26); after the employee check, a typo'd guard on a route only non-acting employees reach would deny everyone forever and log nothing. Cost of the chosen order: a non-acting employee can tell a registered key from an unregistered one, a list that ships in the application's own source, through an in-process resolver that is not a public oracle. Cited as a principle, not as T-009 D-36, which relies on this ordering without prescribing it. | Reversible: yes.

D-34 | What is the role-key format (AC-19)? No document defines it. | `^[a-z][a-z0-9_]*$`, at most 60 characters (the column width). Deliberately **not** the dotted permission-key pattern and not sharing its validator. | Narrowest shape consistent with the only role key that exists, `owner`; widening later is the reversible direction. A role key and a permission key are different namespaces, and one shared validator would make them one fact with two meanings (the FP-184 shape through a regex). | Reversible: yes (widen only).

D-35 | Smaller calls endorsed by `architect`. | (a) Setting an employee to the status they already hold is a no-op, not a refusal. (b) Setting a role's permissions to the set it already holds still bumps holders' `perm_version`; AC-53 asserts change-implies-bump, not the converse, so a spare bump is allowed and a missed one is not. (c) Guards not yet buildable are named where they will go, not stubbed to permit. (d) Fixtures use `AccessTenantFixture::switchTo()`; `Tenancy::enter()` is not relaxed, because its refusal is T-003's criterion. | (a) a refusal would be an invented rule; (b) over-bumping costs a refresh, under-bumping is a security fault; (c) a guard written to permit is worse than none; (d) relaxing another task's criterion to ease a fixture erodes it. | Reversible: yes.

D-36 | AC-36 is about an actor and silent about an operation with none. What happens, and under which reason? (found by `dev`, ruled by `architect`) | Refused, nothing written, under a new closed-set reason **`actor_required`** (added to D-26). It is a **question-level** refusal in the D-33 sense (a required input is missing, the same species as `branch_required`), so it is checked with the question-level refusals, **before** the escalation check, which cannot run without an actor. It fails closed and logs at **error** level like `unknown_permission`, because no end user can produce it: over HTTP the actor comes from the token and the tenant-token middleware guarantees one. It is not `validation` and not `no_escalation`. **FP-206's expectation:** provisioning creates the first owner with no human actor (D-24) and must supply a **named system actor, not a null one**, so the guard never needs a hole and the audit row names who acted. | `no_escalation` is a proposition about rights; "there is no actor" is a proposition about the command. One code carrying two unrelated causes is mask shape 3 inside the one vocabulary D-26 closed so a criterion could assert the cause: a test asserting `no_escalation` could not tell AC-36's real subject (the actor lacked a key) from a defect at an internal call site. A separate case rather than `validation` because the actorless case is not hypothetical and not always an error (provisioning is a real coming consumer); calling that refusal `no_escalation` would tell FP-206's author that provisioning tried to escalate, and the plausible response to a nonsense refusal is to bypass the guard. Folding "no actor" into "no guard" would be a guard that permits whenever its input is missing. The behaviour was already a refusal; only the word changes. Fixtures that granted without naming an actor now seed a privileged one: the test relied on the absence the guard now refuses, so saying who acted is the test becoming honest (not a weakening; the edit's extent is for `qa` from history). | Reversible: yes.
