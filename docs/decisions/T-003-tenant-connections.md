# T-003 decisions — master plus tenant connections

Decisions made autonomously by `ba` while writing
`docs/specs/T-003-tenant-connections.md`, per the TEAM PROTOCOL (no blocking questions to
the human). D-1 to D-24 belong to T-001 and T-002 and are unchanged; this file continues
the numbering at D-25.

D-25 | What does the resolver accept as "tenant identifier"? | The resolver's canonical input is the tenant mapping's own opaque identifier (the primary key of `tenant_databases`, a ULID per `docs/database.md` §4.4), not the human-readable tenant code (`tenants.code`, e.g. `TEN000123`). | Translating a human-readable code (or a JWT claim) into that identifier is part of authentication and tenant resolution at login (FP-207), which is explicitly out of scope for T-003; the connection resolver's job starts one step after that translation. | Reversible: yes

D-26 | Which mapping statuses permit the resolver to build a tenant connection? | Only `active`. Every other status (`provisioning`, `migrating`, `read_only`, `suspended`, `moving`, `restoring`, `archived`, `failed`, or any unrecognised value) is refused outright by the resolver in T-003. | Deny-by-default is the safe, conventional choice for a security boundary. `docs/database.md` §4.4 differentiates `read_only`/`archived` (served read-only) from the rest (refused with HTTP 503), but that distinction is an HTTP/repository-layer behaviour belonging to FP-207/FP-215; T-003 only has to decide "connect or refuse," and refusing every non-active status is the safest default a later task can loosen. | Reversible: yes

D-27 | Is `TenantContext` reset automatically per HTTP request, or does T-003 manage it explicitly? | T-003 scopes `TenantContext` to the running process (a request, a job, or a console command) and provides an explicit resolve/forget operation; there is no automatic per-request reset middleware. | Automatic per-request resolution belongs to the login/tenant-resolution flow (FP-207), which reads the tenant out of a verified JWT — explicitly out of scope here. The task's own queued-job scenario (two tenants in turn, one worker process) is a process-level concern, not a request-level one, so process-scoped context with an explicit API is the minimum that satisfies it. | Reversible: yes

D-28 | Does the resolver/`TenantContext` need an explicit "forget" operation, or is resolving a new tenant the only mutation? | Yes, an explicit forget/reset operation is required. | A long-lived queue worker that finishes tenant A's job and then picks up an unrelated, tenant-less job needs a way back to the "no tenant resolved" state without resolving a replacement tenant; without it, the only way to reach that state would be a process restart, which does not fit a queue worker. | Reversible: yes

D-29 | What fields must the mapping-source contract expose, given no real master schema exists yet (FP-203)? | The contract's one mapping record mirrors the subset of `docs/database.md` §4.4's `tenant_databases`/`database_servers` columns the connection plumbing actually needs: tenant identifier, host, port, database name, app username, app credential reference, and status. Operational columns (`schema_version`, `size_bytes`, `profile`, migration/provisioning bookkeeping, credential rotation timestamps, etc.) are left out. | Those other columns belong to later tasks (FP-205 migration runner, FP-206 provisioning, FP-210 plan/subscription enforcement) that do not exist yet; including them now would make T-003 guess at a shape those tasks haven't designed. The chosen subset is exactly what "build a connection and gate it on status" requires. | Reversible: yes

D-30 | Should T-003 add real `master`/`tenant` entries to `services/host/config/database.php` even though the master schema (FP-203) does not exist yet? | Yes. `master` is configured from environment variables the same way the stock `mysql` connection already is; `tenant` is declared with no usable database configuration until the resolver populates it. | The task explicitly requires both named connections to exist now; `master` having nothing to query yet (no migrations until FP-203) is the same situation `packages/*` was already in during T-001 (structural placeholder ahead of its real content, decision D-10) and is not a reason to delay the connection itself. | Reversible: yes

D-31 | Does T-003 need to implement every credential-reference scheme `docs/database.md` §4.4 lists (`vault://`, `awssm://`, `azkv://`, `file://`, `env://`, `enc://`)? | No. T-003 only needs the resolver to accept an opaque credential-reference string and dereference it through a pluggable step; for local development and for every test it implements only the `env://` scheme, which `docs/database.md` §4.4 already documents as "local XAMPP development only." | The other schemes need real secret-store infrastructure (Vault, AWS/Azure Secrets Manager, or the `enc://` encrypted-blob table) that nothing in the backlog builds yet; inventing a driver for infrastructure that does not exist would be speculative. Whichever later task first needs a real secret store adds the matching driver behind the same contract. | Reversible: yes

D-32 | Does T-003 add Redis-backed caching of the resolved mapping (`docs/database.md` §4.4's 300s cache and `tenant.mapping.changed` invalidation)? | No. The resolver reads the mapping source fresh on every resolution in T-003. | That caching exists to avoid a master-database round trip on every request at production scale, and its invalidation depends on the event bus (FP-212) publishing `tenant.mapping.changed` — neither the real master schema nor the event bus exist yet. Adding an uninvalidated cache now would be a correctness risk (a status change or credential rotation silently not taking effect) for a performance problem T-003 does not yet have. | Reversible: yes

D-33 | Does the spec mandate where `TenantContext`, the resolver, and the mapping-source contract live in the current (pre-rename) repository layout — `packages/kernel`, `services/host/app/Support/...`, or elsewhere? | No. The spec states only the observable behaviour each must have; file placement is the architect's technical design choice. | `docs/architecture.md` §4's target layout names `packages/kernel` as the home for "TenantContext, connection switching, ..." but that layout describes the post-rename (`modules/`) structure T-004 delivers; forcing a specific path now risks being redone by the rename task for no business reason. `ba` does not design technical solutions. | Reversible: yes
