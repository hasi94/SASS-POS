# T-020 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-020-workflow-engine.md`, per the
TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most reversible
option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | What exactly is in scope for FP-214? | **The generic engine only**: the already-designed schema (`docs/database.md` §6.15 — `workflow_definitions`, `workflow_steps`, `workflow_instances`, `workflow_tasks`, `workflow_events`), an evaluation mechanism that decides whether a given entity+context needs approval and runs its step chain, and a way to record approve/reject decisions — proven with **one** minimal fixture scenario (`entity_type='custom'`), not any real business workflow. | Matches the backlog row's own "configurable trigger, condition and steps; approval records" wording exactly, and follows the T-018/T-019 precedent (generic infrastructure, proven on one fixture, real wiring deferred) the orchestrator named explicitly. | Yes |
| D-2 | Does the workflow engine dispatch through the plugin gateway's `before`/veto mechanism (T-019), or is it a standalone mechanism modules call directly? | **Standalone.** A new contract, `WorkflowGate` (`packages/contracts/src/Workflow`), with `evaluate(entityType, context): WorkflowDecision`, called **directly and synchronously** by whichever module later owns the gated entity, inside that module's own transaction. It does **not** register as a plugin hook handler, does not run through `HookGateway::dispatch()`, and is not keyed by the plugin catalogue. `workflow_definitions.plugin_name` stays as a documented column (a plugin *may* author a definition) but authorship is unrelated to dispatch. | Two measured facts rule out reusing the plugin veto: (1) T-019's `before` mode is **fail-open** by design (`Gateway::runBefore()` — a `before` handler that throws or times out is recorded in `$failed` and the dispatch proceeds anyway; T-019's own plan Ruling 4/Risk 4 and backlog row FP-338 both flag this as wrong for approvals, because a crashing check must not silently approve a large discount or expense); approval is exactly the case where a check failing must **block**, not pass through. (2) A plugin is optional, licensed, third-party extension code a tenant can disable; a workflow rule is tenant-configured core business process logic every tenant has, named by `docs/database.md`'s own `entity_type` enum directly against core entities (expense, purchase_request, leave_request, ...), not against a plugin-scoped hook point. Conflating the two would also force a tenant to "install a plugin" merely to get approvals, which nothing in the architecture or database documents asks for. | Yes — `WorkflowGate` is a plain contract; nothing prevents a later task from also exposing a `before`-mode adapter over it if a real need appears, without changing this contract's shape. |
| D-3 | Given D-2, what is `WorkflowGate`'s failure behaviour? | **Fail closed.** If evaluation cannot complete (the definition cannot be loaded, a condition cannot be evaluated, the tenant connection errors), `evaluate()` throws rather than returning "no approval needed." The caller's gated action must not proceed past an engine error. | The deliberate opposite of T-019's `before`-mode fail-open, and the reason D-2 does not reuse that mode: an approval engine that fails open defeats its own purpose (FP-338's concern, resolved here by not inheriting the mechanism that causes it). | Yes — a per-definition "fail open" override could be added later as an explicit, named, audited exception if a real business case ever asks for one; nothing here forecloses it, it is simply not the default. |
| D-4 | Does this resolve backlog debt row FP-338 ("no fail-closed option per hook point... FP-214 will likely need it")? | **Yes, by not needing it.** Because the workflow engine never dispatches through the plugin gateway (D-2), FP-338's scenario (a `before`-mode hook point needing to fail closed for FP-214's sake) does not arise. `ba` cannot edit `docs/backlog.md` (owned by lead/orchestrator); this decision is logged here for `lead` to retire or reword FP-338 against this task. | Keeps the plugin gateway's documented fail-open semantics unchanged and un-special-cased (matching T-019 D-12's own promise not to special-case FP-214), while still giving FP-214 the fail-closed behaviour it actually needs, by a different, better-fitted route. | Yes |
| D-5 | How configurable does "condition" need to be? | **A small conjunction-only predicate DSL**: an ordered list of simple comparisons (`field`, `operator` from `=, !=, >, >=, <, <=, in, not_in`, `value`), ANDed together — matching `docs/database.md`'s own description ("a small predicate DSL") and its own literal examples (`amount > 100000 AND branch_id IN (...)`). No OR, no nested groups, no arbitrary expression language, no function calls or cross-row lookups. | A full expression/scripting language is a large, unscoped undertaking nothing in the backlog row or the architecture document asks for; every example given anywhere in the documents is a flat AND of simple comparisons on the frozen `context` snapshot (`workflow_instances.context`). Building more than that would be speculative. | Yes — OR/nested groups are an additive grammar extension later if a real business rule needs them; the stored `conditions` JSON shape does not need to change to add it. |
| D-6 | Who can approve, and are multi-step/multi-approver chains in scope? | **Yes, multi-step chains are in scope**, exactly as `docs/database.md` §6.15 already models: `workflow_steps.approver_type` (`role, employee, manager_of_requester, department_head, branch_manager, any_of, all_of`) and `quorum` (`any, all, majority`) are both implemented as documented. The backlog row's own examples ("manager, then finance", "manager, then director") are two-step chains, not single-approval. **Amended by D-13**: only four of the seven `approver_type` values (`role`, `employee`, `any_of`, `all_of`) actually resolve against real data today; the other three are refused at definition-write time, not silently resolved against an invented source. | The schema already exists for exactly this; building only single-step approval would under-deliver against both the backlog row's own examples and the already-designed table, and would need an expand migration later for no reason. | Yes |
| D-7 | What happens on reject? | **The instance's status becomes `rejected` and nothing else is undone by this engine.** `workflow_definitions.on_reject` (`stop`, `return_to_requester`) is recorded and reported back to the caller on the resulting `WorkflowDecision`/instance read, but this task does not implement "return to requester" as a workflow-engine-driven action (there is no "returned" status in the documented `workflow_instances.status` enum) — it is a signal a future consuming module may act on (e.g. letting the requester edit and resubmit, which creates a new instance). Undoing or compensating whatever the business action was (e.g. reversing a posted discount) is explicitly the calling module's responsibility, never this engine's. | Matches `docs/database.md`'s own documented enum exactly (no status for "returned" exists to invent), and keeps the same "generic engine does not own business rollback" discipline T-019's `after` hooks already established (the gateway writes the fact, never the business consequence). | Yes |
| D-8 | Does this task wire any real business entity (expense, purchase order, leave, payroll, discount) into the engine? | **No.** The `entity_type` enum ships exactly as `docs/database.md` already documents it (so a future module adding its own value is additive, not an expand migration onto a wrong shape), but **zero call sites** exist anywhere in `modules/` for any of those entity types — the only caller this task ships is its own fixture's test harness, using `entity_type='custom'`. | Explicit instruction from the orchestrator and backlog FP-214's dependency chain: none of expenses (FP-266), purchase orders (FP-254), payroll (FP-280s), leave (FP-272) or discounts (FP-231) exist yet. Designing their approval logic here would be inventing business rules no document states. | Yes — each future task wires in its own entity type without touching this engine's contract. |
| D-9 | Does this task build escalation/SLA execution (reminders, auto-escalation on breach)? | **No.** The documented columns ship (`workflow_steps.sla_hours`, `escalate_to`, `can_skip_if`; `workflow_instances.sla_due_at`; `workflow_tasks.notified_at`, `reminded_at`), but no scheduled job reads or acts on them in this task. | No document states a cadence, channel, or escalation business rule (who gets escalated to beyond the column's own JSON, what a breach actually triggers) — building a scheduler against unstated rules would be inventing them. Mirrors T-017/T-018/T-019's recurring "ships the signal, not the alerting/scheduling mechanism" convention. | Yes — a scheduled command can read these same columns later without a schema change. |
| D-10 | Does this task add an HTTP route or admin UI for creating definitions, or deciding tasks? | **No.** Console commands only (define/list a fixture definition, decide a task) for operator/test use; no HTTP route, same precedent as T-016 D-21/T-017 D-7/T-018 D-9/T-019 D-10 — no platform-admin authorization model or HTTP surface exists anywhere in this codebase yet. | Consistent project-wide convention; inventing a one-off authorization model to gate a route that would otherwise have none exceeds this task's scope. | Yes — additive once such a surface exists. |
| D-11 | What proves the pipeline end-to-end? | **One fixture scenario**, explicitly labelled proof-of-pipeline, not a real business workflow: a definition on `entity_type='custom'` with one condition (`amount > threshold`) and two ordered steps (step 1: role, quorum `any`; step 2: role, quorum `all`), exercised through `WorkflowGate::evaluate()` returning "no instance needed" when the condition does not match and creating/progressing an instance when it does, through both an approve path (reaching `status='approved'` once the final step's quorum is satisfied) and a reject path (`status='rejected'`, matching `on_reject`). | Mirrors T-018's `demo.pinged`/T-019's `fixture-echo` discipline exactly: one minimal, clearly-labelled fixture, never a named business scenario. | Yes |
| D-12 | Who is the "actor" recorded against a decision? | **The deciding employee** — `workflow_tasks.decided_by`/`workflow_events.actor_employee_id` are employee foreign keys, matching the documented schema; this engine does not introduce a `plugin` or `system` actor type for its own decisions (unlike T-019's `after` hooks, which legitimately act as the `plugin` actor). | The schema already states this; a human always makes the approve/reject decision, never the engine itself or a plugin on its behalf. | Yes |

| D-13 | `architect`'s plan (committed `e903228`) flagged a conflict: AC-9/D-6 say all seven `approver_type` values must be resolvable, but `architect` measured that three (`manager_of_requester`, `department_head`, `branch_manager`) have no data source anywhere in the shipped schema — `employees` carries no manager column (T-014 D-14 trimmed the table to identity/access only), no `departments` table exists (HR is FP-270, Phase 4, unbuilt), and `branches` carries no manager column (`locations.manager_employee_id` is a different entity; using it would invent an unstated rule). Does `ba` confirm, revise, or supply a different data source? | **Confirmed: `architect`'s resolution as planned.** `ba` independently re-read `docs/database.md`'s own `employees`/`departments`/`branches` row definitions (not just `architect`'s summary) and the as-built T-014 migrations (`2026_10_20_000304_create_employees_table.php`, `2026_10_22_000501_create_branches_table.php`) and confirms the measurement: `docs/database.md`'s *full future design* does name `employees.reports_to_employee_id` and `departments.manager_employee_id`, but neither table/column is migrated in this codebase today — T-014 deliberately deferred them (D-14) and `departments` has no migration at all. So "no data source in the shipped schema" is correct, and there is truly no way to express "the requester's manager" or "the branch's manager" with what is actually built today (option (c) in the brief — checked and ruled out). **Decision: keep all seven `approver_type` enum values in the schema/documentation shape (AC-1/AC-9's own column-for-column convention), resolve only `role`, `employee`, `any_of`, `all_of` against real data, and refuse the other three at definition-write time with a named error (`approverTypeUnavailable`), with the engine also failing closed if one is ever reached at step-activation time.** AC-9 and D-6 are amended in `docs/specs/T-020-workflow-engine.md` and above to say this explicitly rather than claim all seven work. | This is option (a) from the brief: it matches the project's own established convention for a documented-but-not-yet-wired column or enum value (T-014's own `branches` migration deferred `cost_centre_account_id` the same way, unguarded-then-keyed; `employees` deferred department/designation/salary columns entirely) — ship the documented shape forward-compatibly, refuse what cannot yet be delivered with a clear, named error rather than silently approving or stalling, and let a future HR task (FP-270) add only a resolver, never an expand migration onto a wrong shape. Option (b) (dropping the three from AC-9 and the enum) would require a later expand migration to widen the enum again and contradicts AC-1's own "match `docs/database.md` column-for-column" convention this spec already committed to. | Yes — reversible by a future task simply adding an `ApproverResolver` branch once HR/departments data exists; no schema change needed. |
