D-1 | Does the tenant baseline carry CQRS projection infrastructure (a projection-state table, claim-mark columns) or only the outbox? | **Only the outbox**, with exactly the `outbox_events` columns `docs/database.md` section 6.21 lists. No projection-state table and no claim-mark columns. The first module that needs a read model adds what it needs. The owner chose level 2 (separate read models fed by projections) on 2026-10-06; this does not contradict it, because the outbox is the seam and the seam is present. `Refference/ARCH.md` does not settle the question: it never mentions CQRS, projections or an outbox, and its section 16 says "normal business reports should run against the tenant database", which sits in tension with level 2 and is the owner's own text, so it is flagged rather than resolved here. | **Cost of reversal, stated both ways.** Deferring: a projection-state table is a new table, which is the cheapest class of change there is (expand only, online, no backfill), applied to every tenant by the runner this task builds; at 200 tenants that is 200 runner jobs and no downtime, and AC-38 proves the runner can do exactly that with a fixture. Adding it now: nobody has pinned the shape (where read models live, what a checkpoint is, whether a rebuild marker is a column or a row), so a guess is likely wrong, and fixing a wrong table is a contract change across every tenant, which is the expensive class. The asymmetry favours waiting. **One honest cost of waiting:** adding columns to `outbox_events` later is an `ALTER` on the busiest append-only table in each tenant, and a relay that needs claim marks (several workers) will need them. That is an expand-only nullable add, and the table's 30-day retention bounds any backfill, so the cost is real but small. The one thing that is cheap only today is that no tenant database exists yet, so a baseline edit now touches zero databases; after FP-206 provisions one, every edit is a runner migration. That argues for getting the **outbox's own columns** right now, which AC-27 does by pinning them. | Reversible: yes, at a cost that grows with tenant count; see the reason.

Deferred to the row that uses them: `tenant_domains`, `mfa_factors`, `refresh_tokens`, `signing_keys`, `service_clients`, `login_history`, `security_events` (FP-207 authentication); `billing_invoices`, `billing_invoice_lines`, `billing_payments`, `tenant_usage_metrics` (FP-210); the five plugin tables (FP-213); `tenant_credential_blobs` (the `enc://` driver, which T-003 did not build); `tenant_backfill_jobs`, `tenant_provisioning_runs`, `tenant_provisioning_steps` (FP-206), `tenant_backups`, `consistency_checks`. | The backlog row names the first eleven; `database_servers` is required because `tenant_databases` has a foreign key to it and T-003 already reads host, port and engine from it; the catalogue and the two run tables are what FP-205 cannot work without. Everything else is a new table added later, which is the cheap class of change (D-1). | Reversible: yes, and cheap: master is one database, so adding a table is one migration, not N.

D-3 | `Refference/ARCH.md` section 2 lists host and port on `tenant_databases`; `docs/database.md` puts them on `database_servers` (its Q-1). Which? | **Keep the normalisation.** `tenant_databases.server_id` references `database_servers`, which holds host, port and engine. The owner has not answered Q-1, so this is the design's own proposal carried forward and is flagged in the spec. | Reversible: yes while no master database holds real data.

D-4 | Which tenant tables are in the baseline? | **Six**, plus Laravel's own `migrations`: `schema_meta`, `settings_registry`, `settings`, `number_sequences`, `audit_logs`, `outbox_events`. The queue tables exist "only for the database-queue fallback" and the queue is Redis. `idempotency_keys` and `security_events` are written by features that do not exist yet. | Reversible: yes for everything except that `schema_meta` is cheaper now; see the reason.

D-5 | `settings.updated_by`, `number_sequences.branch_id`, `audit_logs.branch_id`, `outbox_events.branch_id` and the `[BY]` columns have foreign keys in the design to `branches` and `employees`, which do not exist yet. | The columns exist in the baseline with the documented type and nullability and **no foreign key**. The module that creates `branches` or `employees` adds the foreign key, as a contract-phase step, after proving the column holds only valid ids or NULL. | A foreign key to a table that does not exist cannot be created, and `docs/database.md` section 9.4 already says a foreign key is added in a contract step after the data is shown clean. The risk is real: until then, nothing in the database stops a bad id. It is stated here so the later task cannot assume the key exists. | Reversible: yes.

D-6 | Which sites does FP-180's nullable-unique-key convention (`docs/database.md` section 3.3) bite in this task? | Two: `settings` (unique over `scope_type`, `scope_id`, `key`, where `scope_id` is NULL for company scope) and `number_sequences` (unique over `branch_id`, `document_type`, where a NULL branch means company-wide). Both are applied with a stored generated sentinel `COALESCE(<col>, '-')` on `CHAR(26)` columns, which is the correct sentinel for a ULID column. The backlog says FP-180 must land "before the first per-tenant migration", and this is it. The master's `tenant_users (tenant_id, employee_id)` is the **mirror case** (NULL rows should escape the key) and needs no sentinel. | The design's own rule, applied at the first opportunity. The `number_sequences` case is one of the two FP-180 calls correctness, not hygiene: without it two company-wide sequences for `sale` can exist and two sales get the same number. | Reversible: no once a tenant holds duplicates, which is why it is done first.

D-7 | How do engine-dependent criteria run, given the host's tests run on in-memory SQLite (`modules/host/phpunit.xml`)? | Engine tests are part of `composer check`, run against whichever real engine the environment names (MariaDB 10.4 under XAMPP, MySQL 8.4 in Docker and CI), and **fail, not skip,** when the named engine is unreachable. They use only databases whose names carry a reserved test prefix and refuse to run against any other name. A criterion verified on one engine is recorded as verified on that engine only. | A skipped test is a green gate that proved nothing, and SQLite cannot represent stored generated columns in keys, `GET_LOCK`, `information_schema` or the JSON column differences, so a criterion checked there is checked against the wrong artefact. The name guard exists because `docs/database.md` section 14 puts real `flexipos_master` and `flx_t_000001` databases on this machine, and a test that migrates fresh against the wrong name destroys them. | Reversible: yes (an opt-out could be added), but an opt-out reintroduces the hollow green.

D-8 | Do tenant migrations have a `down()` and does the runner roll back? | No. **Forward-only.** The runner has no rollback. A mistake is corrected by a new migration. | Rolling back a DDL change across hundreds of databases, some of which have taken writes in the new shape, is the more dangerous operation, and expand-and-contract exists precisely so that old and new code coexist instead. | Reversible: yes.

D-9 | Which parts of `docs/database.md` section 9.3 are in scope? | Only what the FP-205 row names: planning one job per tenant, ordering by size, queued execution, claiming, the per-tenant lock, failure isolation, resumability, retry of failed jobs, concurrency caps, the maintenance status for offline migrations, recording the version, the behind report, the drift check and refusing to serve. **Out:** `--canary`, `--pretend`, `--abort`, run `mode` values other than all, selected and retry, pre-migration backups, plugin migrations (section 9.6), template import (section 8 step 7, section 9.5), `tenant:doctor`, `tenant_backfill_jobs`, and notifications. | The row is the scope; the rest is design for later rows. Template import is an optimisation that matters when a baseline is 400 migrations, and this one is a handful. | Reversible: yes, each is additive.

D-10 | What happens to a migration flagged `is_destructive` when there is no backup mechanism? | The runner **refuses** to apply it to any tenant and says why. `is_destructive` means data loss (a drop), and is independent of the contract phase: a contract step that adds a NOT NULL is not destructive. | Section 9.3 requires a pre-migration backup and refusal if it fails; the backup catalogue is deferred (D-2). Running a drop with no backup would silently break a design rule, and refusing is fail-closed. It means no destructive migration can run until a later row ships backups, which is the correct pressure. | Reversible: yes.

D-11 | Which tenant statuses may the runner touch? | A bulk run selects `active` and `read_only` (section 9.2's own query). A run that **explicitly names one tenant** additionally accepts `provisioning`, because FP-206's `migrate_remainder` step needs it, and `failed`, so an operator can retry after fixing the cause. Every other status (`migrating`, `suspended`, `moving`, `restoring`, `archived`) and every unrecognised value is refused. | Deny by default, the same rule T-003 D-26 applied to connecting. Migrating a database that is being moved or restored is how a restore is silently corrupted. **Authority (added under D-44): every status in this list is a value of `tenant_databases.status`, not `tenants.status`.** | Reversible: yes.

D-12 | What is a tenant's status after a failed migration? | An ordinary (expand-only) migration that fails leaves the status **unchanged**: expand-only changes are compatible with the old code by definition. A migration flagged `requires_offline` that fails sets the status to **`failed`**, not back to `active` and not left at `migrating`. | After an offline migration fails the schema may be half-applied, so serving it would be unsafe, and leaving `migrating` would look like work in progress forever. `failed` already exists in the enumeration and already means 503 for that tenant alone. | Reversible: yes.

D-13 | Does a failure on an early (small) tenant stop the run? | No. The run continues and ends `completed_with_failures`, exactly as section 9.3 says. | The design is explicit. This is flagged in the spec as a risk, because a structural migration bug will be applied to every tenant before anyone reads the first failure; a canary halt would be the mitigation and is out of scope (D-9). | Reversible: yes.

D-14 | `schema_meta` is listed in section 6.21 as holding a `schema_version` row, but section 9.1 says the tenant's `migrations` table is the authority and master the mirror. Three copies, or two? | **Two.** `schema_meta` is created empty by the baseline and the runner does not write a version into it. The runner does **read** `schema_meta.tenant_id`, when the table and the row exist, and refuses to migrate a database whose recorded tenant is not the mapped tenant. | A third copy of a counter is a third place to drift, and the drift check would need a third comparison. The document's own text names two stores. The identity check is the part of `schema_meta` that carries a safety property. This is a contradiction in the design and is reported to `architect`. | Reversible: yes (a writer is code only).

D-15 | Where does the tenant migration tree live, and can modules contribute to it? | One tree, in the host, separate from the master tree. **Module-contributed tenant migrations are not built here.** | Modules do not yet have any schema. The first one that does will need an ordering rule across modules (a foreign key from one module's table to another's), and designing that with no module in hand would be guessing. | Reversible: yes.

D-16 | Is the catalogue compared against the migration directory on every boot (section 4.5)? | No. It is compared by a test and **by the runner before it runs**, not on every application boot. | A boot-time directory scan on every request worker is cost without a caller; the failure it prevents (a rewritten migration) is caught before any tenant is touched by the runner and before merge by the test. | Reversible: yes.

D-17 | Are emails that differ only in letter case the same login identity? | Yes: `users.email` uniqueness is case-insensitive. | Both engines' default collations compare case-insensitively, and two accounts that differ in case is a standing support problem and a way to hold a second identity. This is the conventional and safer default; the owner may reverse it. | Reversible: yes while no real users exist.

D-18 | What becomes of the stock Laravel `users` migration and the tables beside it? | The stock integer-id `users` table is **replaced** by the design's master `users`. `sessions` and `password_reset_tokens` stay exactly as shipped (the shipped `.env.example` sets `SESSION_DRIVER=database` and a test pins that). `App\Models\User`, its factory and the seeder are not rewritten here; the gate must still pass with them. | The stock table is scaffolding with no consumer, and `docs/database.md` section 5 makes `users` the one login table. `sessions.user_id` is a bigint and the new `users.id` is a ULID, a mismatch that only matters once authenticated sessions exist, so it is recorded for FP-207 rather than solved here. | Reversible: yes while no real master database exists.

D-19 | A cached mapping can serve a stale status or version for up to its time-to-live. | **The runner evicts the tenant's cached mapping in the same step in which it changes that tenant's status or version.** There is no event bus yet, so the `tenant.mapping.changed` event of section 4.4 is out of scope; a plain eviction call is what exists. | Without it, a tenant set to `migrating` would still be served for up to 300 seconds and a freshly migrated one refused for as long. That would make the maintenance status and the version gate unreliable in exactly the case they exist for. | Reversible: yes.

D-20 | How many attempts does a failed job get? | A configured maximum, **default 3**. Section 9.3 writes `attempts < :max` and gives no number. | A bounded retry is conventional; the number is configuration and is not a business rule. | Reversible: yes.
