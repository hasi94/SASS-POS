| D-7 | Does the real failure-body shape (`{error:'<token>'}` / `{error:'invalid_request',reason:'...'}`) let the frontend's `ApiError`/`isEnvelope()` parsing work unchanged for auth calls — and does the same mechanism also need to cover the success path? | **No — this is the most consequential finding, and it has two halves.** (1) Failure path: `isEnvelope()` checks for `'success' in body && 'meta' in body`; the real auth failure body has neither, so `toApiError()`'s `isEnvelope(err.error)` branch is never taken for a real auth failure, and the client falls through to the generic `err.statusText \|\| 'The request failed.'` branch, silently losing the real `error` token (`invalid_credentials`, `wrong_token_type`, `no_access`, `tenant_not_servable`, `employee_unavailable`, `signing_unavailable`, `invalid_request`+`reason` — seven shapes in total; see AC-3). (2) Success path: `ApiClient.unwrap()` throws "not an API envelope" on *any* 2xx body lacking `success`/`meta` keys, and every real auth success body (login, tenant selection, logout) is also raw and non-enveloped, so a real auth success cannot come back through `api.post()` at all — this is not covered by fixing the failure path alone. **Decision: logged as a gap `dev` should close in this task** by (a) adding a legacy-body fallback path to `toApiError()` (or a small `AuthRefusalError` parse step ahead of the envelope check) that reads `err.error.error`/`err.error.reason` when `isEnvelope()` is false and the body looks like one of the seven known legacy shapes, and (b) adding a separate `ApiClient.postRaw()` for these pre-envelope endpoints that skips the `unwrap()` step entirely but still maps errors through the same `toApiError()`. Both are additive to `api-client.ts`, not a rewrite of the envelope path (which stays correct, unchanged, for future envelope-native endpoints) — `postRaw()` is deleted and callers switch back to `post()` once FP-369 lands. | Direct comparison of `isEnvelope()`/`ApiClient.unwrap()` (`envelope.ts`/`api-client.ts`) against `AuthRefusals.php`'s seven body shapes and every real auth success body. | Yes — additive parsing branch and additive method, no behaviour change for any endpoint that does send a real envelope. |
