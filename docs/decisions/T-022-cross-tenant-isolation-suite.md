# T-022 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-022-cross-tenant-isolation-suite.md`,
per the TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most
reversible option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | What does "generated" mean in the backlog row ("Generated attempts across routes, jobs, cache keys and plugin hooks")? | **A programmatically-generated test matrix**: each category enumerates its real surfaces at test-run time from the actual registries/sources (route list, the `ShouldQueue` job inventory, cache-key construction sites found by source scan, the `HookPointCatalogue`) and runs the same generic attack against every enumerated surface, so a route/hook/cache-site added later is covered automatically with no new test case written by hand. | This project's own idiom for a cross-cutting property is exactly this shape: `DeptracBoundaryEnforcementTest`, `QaPluginSourceRulesTest`, `QaWorkflowSourceRulesTest`, `QaEventbusSourceRulesTest`, `QaAuditSourceRulesTest` all scan real directories/registries rather than hardcoding a case list, each with a planted-file negative control proving the scan can fail. A hand-written list of "specific attack scenarios" is the alternative read, but it silently stops covering new code, which a backlog row saying "must pass to merge" cannot accept. | Yes — additional hand-written scenario tests can supplement the generated sweep later without removing it |
| D-2 | Where does this suite live, and is it a one-off audit or a permanent gate? | **Permanent, CI-gate-enforced.** Corrected 2026-11-06 (D-9): every **Feature-level** sweep (routes, cache keys, hooks, and the deterministic variant of the job sweep) lives under `modules/host/tests/Feature/`, following the `Qa*` naming and the single-exported-function-per-file discipline FP-164 established. The **one** genuinely engine-gated case — AC-9's real-migration proof — is the single exception and lives under `modules/host/tests/Engine/` instead, this repository's established home for `ENGINE_HOLD`-gated tests, not the `toolchain` group: `ToolchainGroupCoverageTest` enforces that the `toolchain` group's registry equals exactly the set of files that spawn a child process, and AC-9's engine case spawns none (it needs a real MySQL/MariaDB connection, not a subprocess), so placing it under the `toolchain` group would make that registry-equality check fail. No new test-class hierarchy otherwise: the existing `Qa*` sweep pattern covers everything else. | Backlog row says "must pass to merge", matching every other `Qa*` sweep already in `composer check`. `modules/host/tests/Feature/` is where every other cross-cutting Qa test lives; `modules/host/tests/Engine/` is where every other `ENGINE_HOLD` test already lives (`WorkflowSchemaEngineTest.php`, `MigrateTenantEngineTest.php`), so AC-9's case follows existing precedent rather than inventing a third location. | Yes — files can be moved; the location is not load-bearing |
| D-3 | What fixture backs the generated attempts — the engine-gated `ThreeTenantFixture` or a lighter stand-in? | **`AccessTenantFixture`-style two-SQLite-tenant fixture** (already used by T-010/T-014/T-016/T-021 isolation tests: `AccessTenantFixture::boot()`/`switchTo()`/`forget()`) for every route/cache-key/hook check, because none of those need a real MySQL/MariaDB server, only two real, separately-connected tenant databases. Corrected 2026-11-06 (D-10): AC-9's **deterministic** job-sweep variant is the one exception within the non-engine checks — it needs `packages/kernel/tests/Support/migrate-tenant-fixture.php` instead, because `MigrateTenantQueueJob`'s handler reads its own tenant id and the tenant-to-database mapping from the **master** database (`database_servers`/`tenant_databases` rows), which `AccessTenantFixture` does not provide (it is tenant-side only, mapped via `tenancy.databases` config). `ThreeTenantFixture` (engine-gated, `ENGINE_HOLD`) remains reserved only for the one check that is inherently about the real engine: that `MigrateTenantQueueJob`'s queued payload, run by a worker whose active tenant is a *third*, different tenant, still resolves and writes to the job's own tenant against a real MySQL/MariaDB server. | Matches the project's stated testing philosophy (fixture-based, not mocking, real stand-ins) and its own practice of using the cheapest fixture that is still real for a given claim; a SQLite stand-in is "real" in the sense that matters (separate connections, separate rows, and for AC-9's deterministic case, separate master-side mapping rows too), and running everything through `ThreeTenantFixture` would make every route/cache/hook/job case `[ENGINE]`-gated for no reason, defeating `composer test:fast`. | Yes |
| D-4 | What concretely does one generated "attempt" do, per category? | **Routes**: for every registered `api/v1` route gated by a tenant-identifying token middleware (`RequireTenantToken`/`RequireTerminalToken`), seed a distinguishing row in tenant A, request the same route/shape with tenant B's token, assert tenant B's response contains none of tenant A's distinguishing value and (for a by-id route) answers not-found/refused rather than tenant A's record; then the reverse. Platform/master-only routes (login, activation, platform audit) and the two always-open probes are excluded by construction (no tenant token exists to swap). **Jobs**: dispatch `MigrateTenantQueueJob` for tenant A, have the worker's ambient/active tenant be a different tenant (B) when the job runs, assert the job's own write lands in A's database and B's is untouched — proving the job resolves the tenant it carries, never the one ambient at pop time. **Cache keys**: scan the repository for every call site constructing a cache key or `RateLimiter` bucket name (`Cache::`, `CacheRepository`, `RateLimiter`), and assert each known site's key format embeds a tenant-distinguishing token (`{tenant_id}`/`t:`/`u:`/`d:` prefix) or is on an explicit allow-list of documented tenant-agnostic keys; a new, unlisted construction site is a failure naming the file. **Plugin hooks**: with the same plugin manifest enabled for tenant A only, dispatch a hook point for tenant B and assert `HookInvoker` never calls into A's handler and never runs under A's tenant connection; then the reverse with both tenants enabling the plugin and recording which connection name/tenant id the handler observed. | Grounds "attempt" in what the actually-built infrastructure makes checkable today, per category, instead of inventing attacks against machinery that does not exist. | Yes |
| D-5 | "Jobs" — the backlog text implies real queued business-logic jobs exist; do they? | **No.** The only `ShouldQueue` class in the repository is `MigrateTenantQueueJob` (T-008, tenant schema migration). No business-domain module (sales, inventory, etc.) has shipped a queued job yet. The event bus (T-018) is a separate mechanism — Redis Streams relayed/consumed by artisan commands (`RelayOutboxCommand`, consumers), not Laravel's queue — and its own tenant-scoping is already proven by T-018's tests reading/writing each tenant's own outbox table; duplicating that here would test the same property through a different door for no new information. **Scope "jobs" to `MigrateTenantQueueJob` only**, and record the event-bus gap explicitly rather than silently covering nothing under the word "jobs". | Testing an empty category would either be vacuous (an AC that always trivially passes) or invent a job that does not exist and ship test-only production code, which is out of role for a QA-stream task. The one real job is exactly the kind of "resolves the tenant it carries, not the one active in the worker" hazard the backlog row is pointing at. | Yes — when a business module ships its first queued job, this suite's job category gains a second generated case with no change to this task's scope statement |
| D-6 | Does this task change any production code? | **No**, except where the generated sweep finds a genuine gap, which is then a defect to log and hand to `developer`, not something `ba`/this spec authorizes fixing silently. Every category inventoried in reconnaissance (routes, the one job, two cache-key sites, hook dispatch) already resolves the tenant explicitly rather than ambiently, so none is expected to fail; the spec's acceptance criteria are written to prove that, and a found gap becomes a QA defect against the AC it violates. | FP-216 is a QA-stream row ("proving an existing property… not adding new production features"), matching the task brief. If `developer` needs to add a case (e.g. a new allow-list entry or a found bug fix), that is the plan/dev stage's job. | Yes |
| D-7 | How does the cache-key scan stay generated rather than a hardcoded pass/fail on two known files? | The scan enumerates **every** `*.php` under every `packages/*/src` and `modules/*/src` (and `modules/host/app`) for the patterns `Cache::`, `CacheRepository`, `RateLimiter` (constructor-injected), and for each matched file requires either a tenant-token literal/interpolation in the nearest key-building expression or an entry in a small, named allow-list of tenant-agnostic keys. Corrected 2026-11-06 (D-8): the allow-list is **not** empty on day one — it starts with exactly one entry, `ApiActor`'s `u:platform:{platformUserId}` bucket, which is deliberately tenant-agnostic by design (a platform token carries no tenant). `CachingTenantDatabaseRepository`'s `tenant:conn:<id>`, `ApiActor`'s `t:`/`d:`/`ip:` buckets and its `u:{tenantId}:{userId}` bucket, `CachingEntitlementSource`'s `platform:entitlements:<id>`, and `ActivationThrottle`'s `terminal-activation:tenant:<id>`/`terminal-activation:ip:<sha256>` pair all already embed a tenant/terminal/IP token, so none of those needs the allow-list. A planted file without a tenant token and not on the allow-list is the negative control. | Matches the `Qa*SourceRulesTest` idiom exactly (scan real directories, planted-file control) and the architect's own instruction to decide concretely what "every cache key construction site…includes a tenant-distinguishing component" means as code. | Yes |
| D-8 | The cache-key inventory in D-7/the spec said exactly two construction sites; architect's review found four — what is the corrected inventory? | **Four construction sites, not two**: `CachingTenantDatabaseRepository::keyFor()`, `ApiActor`'s five bucket builders (not four — `u:platform:{id}` was also missed), `Flexipos\Platform\Support\CachingEntitlementSource::keyFor()` (`packages/platform/src/Support/CachingEntitlementSource.php`), and `Flexipos\Auth\Support\ActivationThrottle` (`packages/auth/src/Support/ActivationThrottle.php`, two keys per call site: `tenantKey()`/`addressKey()`). Confirmed by reading both missed files directly: both already embed a tenant id or an IP hash in every key they build, so no production gap, only a reconnaissance gap. The spec's AC-12/AC-13 and the "Current behaviour" cache-keys bullet are corrected to this count. | Architect's review is a second, independent pass over the same `packages/*/src`/`modules/*/src` tree the spec claims to scan exhaustively; missing two of four real sites in the hand-written reconnaissance is exactly the failure mode AC-12's "scan, don't hand-maintain a list" exists to catch in the shipped code, so the spec itself has to not repeat it. | Yes — the count is a fact about the current tree, re-derivable by running the sweep once built |
| D-9 | D-2 said every new file for this suite lives in `modules/host/tests/Feature/`; architect found this cannot hold for AC-9's engine-only case — where does it go? | **`modules/host/tests/Feature/` for every Feature-level sweep (routes, cache keys, hooks, the deterministic job variant); `modules/host/tests/Engine/` for the one genuinely engine-gated case (AC-9's real-migration proof) only.** Confirmed by reading `ToolchainGroupCoverageTest.php`: the `toolchain` group's registry (`toolchainGroupFiles()`) is lint-checked to equal exactly the set of files that spawn a child process (`filesSpawningChildProcesses()`); a file that is in the registry but spawns nothing is reported as "stale" and fails that test. AC-9's engine case needs a real MySQL/MariaDB connection, not a subprocess, so it cannot be registered into `toolchain` without breaking that existing guard. `modules/host/tests/Engine/` already holds every other `ENGINE_HOLD`-gated test in this repository (`WorkflowSchemaEngineTest.php`, `MigrateTenantEngineTest.php`, `PerTenantLockEngineTest.php`, etc.), so this is precedent, not a new location. | D-2's underlying intent — one well-known home per test shape, following existing discipline rather than inventing a new one — is preserved; only the specific directory for the one case that does not fit `toolchain`'s own rule is corrected. | Yes — files can be moved; the location is not load-bearing |
| D-10 | D-3 said `AccessTenantFixture` backs every non-engine check; architect found AC-9's deterministic job variant cannot use it — what fixture does? | **`packages/kernel/tests/Support/migrate-tenant-fixture.php`** for AC-9's deterministic variant specifically; `AccessTenantFixture` remains correct for every route/cache-key/hook check. Confirmed by reading both fixture files: `AccessTenantFixture::boot()`/`mapAt()` configure tenant databases entirely through `tenancy.databases` **config**, never a master `tenant_databases`/`database_servers` table row, while `MigrateTenantQueueJob`'s handler (via `MigrateTenantHandler`) reads its own tenant id and resolves its connection from exactly those master tables. `migrate-tenant-fixture.php` (T-008) already builds both: two SQLite tenant files **and** real master-side `database_servers`/`tenant_databases`/`tenant_migration_jobs`/`tenant_migration_runs` rows (via `masterMappingServer()`/`masterMappingDatabase()`/`migrateFixtureClaimedJob()`), with `TenantMigrationApplier` faked so no real migration runs — exactly the shape AC-9's deterministic case needs, with no real engine. | D-3's underlying principle — the cheapest fixture that is still real for the claim under test — is unchanged; only the specific fixture named for this one AC is corrected, because the claim here is specifically about master-mapping resolution, which only this fixture provides. | Yes |
