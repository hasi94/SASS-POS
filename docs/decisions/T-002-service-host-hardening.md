# T-002 decisions — service host hardening from the T-001 review

Decisions made autonomously by `ba` while writing
`docs/specs/T-002-service-host-hardening.md`, per the TEAM PROTOCOL (no blocking
questions to the human). D-1 to D-12 are T-001's and are unchanged; this file continues
the numbering at D-13 and does not renumber them.

D-13 | What exact namespace and provider-prefix rule does `ServiceRegistry` enforce for FP-146 (M-1/M-2)? | The declared PSR-4 namespace must equal exactly `Flexipos\Service\<Studly(name)>\` (Studly derived the same way `svc:make` derives it, i.e. `Str::studly($name)`), and the declared provider class string must start with that exact namespace. Both are pure string comparisons that run before the namespace is ever registered with the class loader. | This is the minimal rule that ties the manifest to the one namespace a service is actually entitled to, matching exactly what `svc:make` itself generates, so a legitimately-generated service always passes and only a copy-pasted or malicious manifest is rejected. | Reversible: yes

D-14 | Does the `is_a($provider, ServiceProvider::class, true)` check (M-1) run before or after the existing `class_exists()` check? | After. `class_exists()` still answers "is anything autoloadable at all"; only once that is true does the registry ask "is it the right kind of thing". | Preserves T-001's already-QA-proven "provider missing" error path unchanged (AC-19's malformed-manifest tests) and adds exactly one new, narrower failure mode instead of restructuring the whole validation sequence. | Reversible: yes

D-15 | Does the namespace/provider-prefix validation (D-13) run before or after `addPsr4()`? | Before. `addPsr4()` is called only once the namespace-equals-expected and provider-starts-with-namespace checks have both passed. | This is the specific fix M-2 asks for: a rejected package must never have its mismatched, untrustworthy namespace registered with the class loader, even transiently. | Reversible: yes

D-16 | Should the trailing-newline fix (M-3) be a new, second pattern constant or an edit to the existing shared one? | Add the `D` modifier to the existing `ServiceRegistry::NAME_PATTERN` constant in place; `SvcMakeCommand::NAME_PATTERN` continues to alias it. | D-12 already established one pattern shared by both call sites specifically so they cannot drift apart; a second constant for this fix would reintroduce that exact risk for no benefit. | Reversible: yes

D-17 | Does the spec mandate a specific atomic-generation mechanism for FP-147 (delete-on-throwable vs. render-to-temp-then-move)? | No — the spec states only the observable outcome (no partial package survives a failed generation; a retry after such a failure succeeds). The mechanism is left to the architect's plan. | Both mechanisms in the review's own "Fix" column satisfy the outcome; picking one is a technical design decision, not a business rule for `ba` to make. | Reversible: yes

D-18 | For FP-148, which health route(s) move out of the `web` middleware group, and is any other route touched? | Only `/health/live` and `/health/ready`. No other route (in particular the stock `/` welcome route) is touched. | Decision D-7 already scoped these two endpoints as the only ones T-001 implements; only they need to survive a database outage. Matches M-5's fix exactly and avoids the explicit "no cleanup creep" instruction from spreading into unrelated routes. | Reversible: yes

D-19 | For FP-149's boot-time guard (AC-9/AC-10), what exactly does it compare? | Only the `SERVICES` value: the value baked into the cached configuration against the ambient `SERVICES` environment variable read directly at boot. A mismatch throws; a match (or no cache present) boots normally. | `SERVICES` is the "one guarantee the host exists for" the review calls out by name (M-6). Extending the guard to every cached configuration key is a larger, undefined-scope change the review does not ask for. | Reversible: yes
