# T-039 decisions

Team-mode decisions `ba` made while writing `docs/specs/T-039-goods-receipts-supplier-invoices.md`, per the TEAM PROTOCOL (no question left for the human; the most conventional, safest, most reversible option is picked and logged). `ba` has no shell and no git and claims nothing about history or any gate. Nothing here is an escalation: no irreversible or external action, no legal or compliance choice, no contradictory requirement. Owner-visible questions with their built defaults are in the spec's "Open questions".

D-n | Question | Decision | Reason | Reversible

D-1 | Is the row too large? | **Split.** T-039 builds goods receipts (GRN) and purchase returns, with the order rollup, ledger cost, price history and events. **Supplier invoices (with the three-way match) and supplier payments are two proposed follow-up rows.** Invoices need the match rules (pinned in D-14) and are the first consumer of AP; payments need `ap_documents` (FP-265, the allocation table has `ap_document_id` as a required key) and `financial_accounts` (FP-263), neither of which exists. Building them now would mean tables with foreign keys to tables that do not exist. | Smallest slice that is complete, testable and unblocks FP-262's receipt posting; the rest has hard dependencies elsewhere. | yes (rows can be merged back by the lead)

D-2 | `grn_return`: give it a document or drop it? (FP-255 text) | **Drop it.** No producer, no document, no table. A return of received goods is the `purchase_return` movement against a purchase return document (`docs/database.md` section 6.5 already defines `purchase_return` with `purchase_return_items.id` as its line). The stock ledger already refuses `grn_return` as `type_has_no_document` (T-031 AC-12), so nothing needs to change there. The enum member stays in the schema (T-031 owns it); this task adds a static test that nothing writes it (AC-48). A docs-only correction row is proposed. | Two documents for one physical event (return of goods) would double every rule; `purchase_returns` already carries `grn_id` for "returned against a receipt". | yes (a later `grn_return` would be an expand: a new document and a ledger pairing)

D-3 | Partial receipts and over-receipt policy; what counts toward the order. | Partial receipts: any number of receipts per order; the order status follows T-034's base-to-base rollup. **Over-receipt accepted freely and flagged** (`over_received`), no tolerance, no refusal, no approval (T-034 Q-1's built default; refusing goods physically on the dock is the unsafe choice). Receiving against a `received` order is allowed; against `closed`, `cancelled`, `draft`, `pending_approval` or `sent` it is `order_not_open`. Only **paid** base quantity counts against the order (`received_base_delta = base_quantity`); **free units do not**, because bonus goods were not ordered and counting them could mark a half-delivered line complete. Several lines of one receipt may name one order line. No workflow gate on a receipt. | Conventional ERP behaviour; matches T-034 AC-73 and AC-75. | yes

D-4 | Receiving unit versus order unit: fresh or inherited factor? | A line in the **same unit as its order line** uses `snapshotInherited()` against the order line, so the receipt compares to the order with the same frozen factor even if the ladder moved; a line in **any other unit** (or with no order) is a fresh `snapshot()`. Receiving in the product's stock unit is therefore always possible. Purchasing never multiplies by a factor; the base equivalent of `free_quantity` and the order-unit display delta come from the unit code (dependency for the architect). | T-034's received rollup compares base to base; inherited factor keeps same-unit receipts consistent; this is the usage FP-254 and T-027 reserved `snapshotInherited()` for. | yes

D-5 | Idempotency. | Caller-supplied ULIDs on documents and lines, as T-034 D-21: identical replay returns the original, different payload is `replay_conflict`. Posting is idempotent by outcome (already posted returns the document with `replayed = true`). Downstream keys: ledger idempotency is `(reference_line_id = receipt or return line id, product, type)` (T-031 AC-4); order application id = the receipt line id (one application per line, replay-safe via T-034 AC-76); event is written only on a real post. A ledger `replayed = true` for a document that was `draft` is `ledger_inconsistent` (rolls back), never silently accepted (T-031 AC-49). | House pattern. | yes

D-6 | Which location may a receipt use when it names an order? | **The order's delivery location**; otherwise any eligible location of a branch (live, `is_purchasable_to`, with a branch). A branch-less central warehouse is refused as T-034 D-40. | The order event feeds `quantity_incoming` per (location, product); receiving elsewhere would leave incoming stuck at the wrong place. Loosening later is a rule change, no schema change. | yes (owner Q-5)

D-7 | Returns: against a receipt or direct; effect on the order; correction of a posted receipt; cap. | A return may name a receipt (must be posted, same supplier, same location) or be **direct** (no receipt). A return line inherits the receipt line's frozen factor (T-034 FP-254 owes `snapshotInherited()` for exactly this) and may be in the receipt line's unit or the stock unit. **Over-return cap** for receipt-linked lines: cumulative posted returned base may not exceed that receipt line's `base_quantity + base_free`; draft returns reserve nothing; direct returns have no cap beyond the ledger's insufficient-stock guard. **A return does not touch the purchase order** (no negative `ApplyReceivedQuantity`): returned goods were received; reversing would reopen orders and leave a trail T-034 D-45 deliberately keeps. A posted receipt is **never edited, cancelled or reversed**; only drafts are cancelled; correction is a return (or a stock adjustment, FP-253). The return leaves stock at the location's average cost (ledger rule, section 6.5 note 6); the difference to the credit price is the purchase price variance FP-262 posts, so the event carries both. | Immutable posted documents are the house rule (T-030, T-033); no `grn` reversal movement type exists. | yes (owner Q-3)

D-8 | Document numbers. | Types `grn` and `purchase_return`, one sequence each, branch row preferred, allocated at creation inside the creating transaction, last among the locks (T-034 D-10, D-22); drafts are cancelled, never deleted, so sequences stay gapless. Default prefixes `GRN` and `PRN` are added to the numbering contract's defaults (`PR` is already the purchase request, `PO` the order), the same cross-package edit T-034 D-53 made for its two types. Failure names as T-034 AC-52. | `PR` is taken; `RTN` and `PRN` are both free; `PRN` follows the table name. | yes

D-9 | `received_date` and the posting date. | The receipt date is **client-supplied** (a delivery is often keyed the next day), not in the future by the branch's business clock, not before the order date. Back-dating beyond that is not limited by this task; fiscal-period control belongs to the posting gate (T-032/T-033), and the event carries `received_date` so FP-262 posts on it. `posted_at` is server time. | A server-set date would make late data entry post in the wrong day; the period gate already refuses closed periods. | yes (owner Q-2)

D-10 | Money model: tax, landed cost, currency, ledger value. | (a) Lines are priced by `PurchaseLinePricing` with discount 0 on **paid quantity only**; free units carry no price. (b) Inventory is valued **ex-tax** (`line_total - tax_amount` in both exclusive and inclusive groups); input tax is recoverable (design section 7.2); non-recoverable tax not modelled. (c) `other_charges` is **tax-free** (no column for its tax) and is apportioned **pro rata to ex-tax line amount**, half-up at four decimals, remainder to the largest line, so shares sum exactly; **all lines zero with charges > 0 is refused** (`charges_unapportionable`) rather than inventing a second basis. (d) `landed_cost` per **line unit** = inventory money / paid quantity (design: per line unit, section 6.5 D-72), stored at post; the ledger is fed the **line money** times `exchange_rate`, rounded once, **not** a re-multiplied rounded per-unit cost (T-031 AC-26). (e) The ledger holds company currency (section 6.5); `exchange_rate` converts document to company currency (section 6.5 money axis); no rate lookup. | Each step is the written design or the least-inventive reading; the exact-money rule is T-031's own. | yes (owner Q-4)

D-11 | Zero-price lines and all-free lines. | A zero `unit_cost` is accepted (free goods, T-034 D-28). A line with paid quantity 0 and free quantity > 0 is accepted; it moves quantity at no money, applies nothing to the order and writes no price history. A line with both zero is `validation`. | Free goods exist; refusing is an unstated rule. | yes

D-12 | Batch, serial and expiry fields on a receipt line. | **Not accepted and not built.** `batches` and `serials` are FP-252; T-031 refuses `batch_id` and any `tracking_mode` other than `quantity`. The documented `grn_items.batch_no`, `expiry_date`, `mfg_date`, `serial_numbers` columns are deferred to FP-252 by expand migration (T-034 D-3 precedent); a request carrying them is `validation`, and a product with batch or serial tracking is `tracking_not_supported`. | A column with no writer or reader is a trap; the ledger would refuse the movement anyway. | yes

D-13 | `purchase_price_history`. | Built here (the database document assigns it to FP-255; T-034 put it out of scope for itself). One row per posted receipt line with paid base > 0: `unit_cost` per **stock unit** = ex-tax line amount / paid base quantity (supplier price, excludes landed charges), `quantity` = paid base, `source = grn`, **no unit column**. The `invoice`, `quote` and `manual` sources are for later rows. | Normalising on write is what makes the price-change report comparable across a supplier who switched units. | yes

D-14 | Three-way match rules (PO -> GRN -> invoice). **Normative for follow-up row FP-NEW-A; only the receipt-versus-order half is built here (AC-32).** | (1) The match key is the receipt **line**, not the order: an invoice line names a `grn_item_id`; a non-stock line (no product) has none and is outside the match. (2) **Quantity**: invoiced base quantity (cumulative over non-cancelled invoice lines against that receipt line) may not exceed the line's received **paid** `base_quantity` (free units are not invoiced) minus the cumulative posted-return base for that line, floored at zero; over-invoicing is blocked and puts the invoice `disputed`. Under-invoicing is allowed and reported (goods received not invoiced). (3) **Price**: compared **per base unit on both sides**, each side `net amount / base_quantity` rounded half-up at four decimals before subtraction (never per document unit); any difference is allowed, recorded as the line's variance, never blocks, **zero tolerance flagged** (no tolerance percent exists in the design; an owner setting would be an additive column). (4) The variance is the figure FP-262 posts to purchase price variance (invoice side minus receipt side, per base unit times invoiced base). (5) A return after invoicing is credited through a debit note against the same receipt line (FP-265). (6) The order is not a match key: it is the cross-check only (receipt per order line and per-base price against the order line, as AC-32). | Fixes the match so the follow-up does not re-decide it, and uses the one normalisation the design states (section 7.2). | yes (all)

D-15 | Does this task post to the ledger (journal)? | No. It emits `goods_receipt.posted` and `purchase_return.posted`, carrying the stock ledger's actual value per line and the document money, and does not call T-033's `PostingService`. FP-262 consumes them idempotently by source document. A journal link column (`[GL]`) is deferred. | The backlog assigns receipt posting to FP-262; calling a service from a task that precedes the accounts is a dependency inversion. The event is the hook the lead asked for. | yes

D-16 | Permission keys. | `purchasing.receipts.view|manage|post`, `purchasing.returns.view|manage|post`, branch-scoped via the **location's branch** (no branch column on `grns`), every slice checks its own key, reads included (T-034 D-36). Posting is a separate key from editing (stock and money change on post). Approval by workflow is not used for receipts: a receipt records a physical fact. | T-034 D-26 naming; segregation of duties is the safe default. | yes

D-17 | Reading the T-034 and T-031 contracts from sibling worktrees. | Nothing in this spec assumes those branches have merged; each fact used is listed under "Dependencies the architect must verify". In particular: the exact-money quoted-price shape for the ledger (cost quantity 1), a unit-code operation for "base amount in an order unit" and "base free", and FP-179 gating the ledger DDL. | `ba` read specs and plans only; not code. | yes
