# T-021 decisions

Autonomous/team-mode decisions `ba` made while writing `docs/specs/T-021-api-foundation.md`, per the
TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most reversible
option is picked and logged here).

| D-n | Question | Decision | Reason | Reversible |
|---|---|---|---|---|
| D-1 | Do existing endpoint bodies (auth, access, organization, platform, terminal, the two 503 renders) move to the envelope in this task? | **No.** The envelope, helper and a generic `api/*` renderer are built and applied to failures no existing renderer handles, to the demo ping and to the new refusals. Existing explicit bodies keep their exact status and bytes; migration is a proposed follow-up row (FP-369) for `lead`, best done with the first frontend consumer. | T-009 D-12 makes the uniform credential refusal byte-identical by design and many tests pin the current shapes; rewriting them mixes a wire-contract change into a foundation slice and nothing consumes them yet (no frontend exists). Keeps the task proportionate. | Yes |
| D-2 | Where do health endpoints sit relative to the envelope? | **Outside it.** `/health/live`, `/health/ready` and `/up` keep a flat body (`status`, `modules`, new `checks`). They are not throttled and not session-bound. | Orchestrators and monitors parse status codes and a flat word; the existing tests and `routes/health.php` already pin this placement; the envelope is for API clients. | Yes |
| D-3 | Error-code format and namespace rule | `<module>.<snake_case>`, exactly one dot, prefix equals the registering module's name, kernel-wide codes use `kernel.`; duplicates refused; unknown code throws in dev/test and degrades to `kernel.server_error` in production. | architecture.md section 8 says "namespaced by module and catalogued centrally"; the strict registration rules make a typo fail loud and keep frontend mapping total. | Yes (codes are additive; renaming a shipped code is breaking) |
| D-4 | Is the English `message`/`detail` a contract? | **No.** The code is the contract; text is a stable default for logs and humans, translated by the frontend by code. | Section 8: "the frontend maps codes to translated messages". | Yes |
| D-5 | Is idempotency applied to every POST or opt-in per route? | **Opt-in per route** by a middleware declaration; an opted-in route makes the key mandatory. | Section 8 limits it to "state-changing requests that create a financial record"; forcing keys on login or settings would break existing clients and tests. | Yes |
| D-6 | Which responses are stored and replayed? | **Only 2xx.** 4xx, 5xx, 429 and thrown exceptions store nothing, so a retry runs the handler again. | Replaying a transient failure (503, schema-behind, lock timeout) would trap the client in the failure for 24 hours; a 4xx is cheap to recompute and may be fixed by the client with the same key. | Yes |
| D-7 | Where is the idempotency store, and does it serve master (platform) routes? | **Tenant database only**, table `idempotency_keys` exactly as `docs/database.md` designs it (24h retention); a tenant-less request on an idempotent route is a logged configuration error. No master store. | database.md already places it in the tenant schema ("one database per shop, no tenant column"); the only financial records are tenant-side; a master store would be speculative and a second schema. | Yes (a master table is additive) |
| D-8 | How is cross-user key reuse prevented, given the documented table has key as the sole primary key? | The stored `request_hash` covers method, path, actor id and body; a matching key with a different hash is 422 `kernel.idempotency_key_reused` and the stored body is never shown. No schema change to the documented columns. | Prevents a user in the same shop replaying another's response by guessing a key, without altering the designed table. | Yes |
| D-9 | Default limits and the unauthenticated key | Configurable, defaults per minute: **tenant 1200, user 120, terminal 300, unauthenticated per IP 30**. Fixed window or sliding is the architect's choice. Authenticated requests are not also counted per IP. | Section 8 requires the three buckets but gives no numbers; these are conservative placeholders sized well above a till's real rate and are configuration, not contract. Unauthenticated routes are credential endpoints, so a tighter IP bucket is the safe default. Account lockout already exists separately in T-009. | Yes |
| D-10 | When the limiter store is down, fail open or closed? | **Fail open** with a logged warning. | A cache outage must not stop a shop selling; the limiter protects capacity, not security (credential lockout is separate and keeps its own store). Security-relevant limiting is a different task. | Yes |
| D-11 | Is the OpenAPI document served publicly? | **Off by default**; command `api:openapi` always works; `GET /api/v1/openapi.json` only when `API_DOCS_ENABLED=true`, answering 404 otherwise. | A production API map is reconnaissance for an attacker and has no end-user value. Safest default; enabling is one setting. | Yes |
| D-12 | How detailed must the OpenAPI document be? | **Every `api/v1` route is listed** with method, tag, security, standard errors and envelope shape, enforced by a completeness test in `composer check`. Per-endpoint request/response schemas are declared incrementally by each feature. | "Generated from code" and "cannot drift" are achievable now for the route list; inventing schemas for ~50 existing endpoints is large, error-prone and not asked for. | Yes |
| D-13 | What does readiness check, and what if Redis is absent? | Master database connectivity (always) and Redis (only when configured as cache/queue/bus driver, else `skipped`). Missing Redis in XAMPP mode never fails readiness. Both bounded by a 2-second timeout. | The existing docblock deferred exactly "database, event bus"; CLAUDE.md says XAMPP mode has no Redis (and Redis is `ENGINE_HOLD`-gated here). Consumer-lag and outbox-age checks need infrastructure not yet built. | Yes |
| D-14 | Does one tenant being schema-behind fail readiness? | **No.** It stays a per-request 503 (T-003) and a `tenant:schema-status` report. | A whole host drained for one lagging shop turns a single-tenant incident into a full outage. | Yes |
| D-15 | Does the envelope renderer cover non-API paths? | **No, `api/*` only.** | Web and console behaviour must not change (AC-49). | Yes |
| D-16 | D-1 said existing endpoints do not change, yet the limiter must cover them (AC-28/30/32). | D-1 is read as **no existing body or status changes below the limit**. Every existing `api/*` route gains `X-RateLimit-*` headers and can answer 429 above the limit. `TerminalActivationHttpTest` ignores `x-ratelimit-remaining` in its byte-identical header comparison. | A limiter that skips existing routes (login especially) would defeat its purpose; headers are additive, like `x-request-id` in T-017. | Yes |
| D-17 | Readiness gains `checks` but nine exact-JSON assertions in six files pin the old body (AC-47). | Update those expectations to include `checks`; `status` and `modules` unchanged. | Additive body change on a probe; the tests pinned the shape, not a requirement against extension. | Yes |
| D-18 | The ping body is pinned by more than its own test (AC-50). | Update the ping's test, four module tests and the two `module:make` stubs together. | `ModuleMakeDemoRegenerationTest` requires the stubs to match the demo; leaving any stale would fail the gate. | Yes |
| D-19 | `QaActivationCodeSecrecyTest` pins the framework 404 `message`, which echoes the path and so the activation code. | Strengthen it to "body contains no copy of the code"; the envelope 404 never echoes the path. | A security improvement the envelope delivers for free. | Yes |
| D-20 | The OpenAPI document would claim the legacy endpoints return the envelope (AC-40 vs D-1). | Mark them `x-flexipos-legacy-body: true`; tag = first URI segment after `api/v1`; docs route tagged `kernel`. | Keeps the document truthful until FP-369. | Yes |
| D-21 | Small rulings from the architect. | Module list env var is `MODULES` (old word never quoted in code or docs); one error item per invalid field with first message; empty success is 200 with `data: null`; extra codes `kernel.bad_request` 400 and `kernel.payload_too_large` 413 (other 4xx to 400, other 5xx except 503 to 500). | Conventional and simplest; the vocabulary sweep test forbids the old word. | Yes |
| D-22 | Bucket and idempotency details. | Terminal token: tenant and terminal buckets, no user bucket; platform token: user bucket only. Idempotency hash excludes the query string; a null-status in-flight claim is takeable after 120 s. | Matches what each token actually identifies; a crashed worker must not block a key forever. | Yes |
