# T-034 decisions

Team-mode decisions `ba` made while writing `docs/specs/T-034-suppliers-purchase-orders.md`, per the
TEAM PROTOCOL (no question left open for the human; the most conventional, safest, most reversible
option is picked and logged here). `ba` has no shell and no git, so nothing below claims anything about
history. Nothing here is an escalation: no irreversible or external action, no legal or compliance
choice, no contradictory requirement. Items that are truly owner product decisions are also listed under
"Questions for the owner" in the spec, each with the default built.

D-n | Question | Decision | Reason | Reversible

D-1 | Where does the code live, and are there HTTP routes? | A new purchasing module (name and package layout are the architect's), vertical slices per `docs/patterns.md` section 3. **No HTTP routes**: slices are called by handler, the precedent set by T-016 D-21, T-020 D-10 and T-030 (no routes). FP-256 and the route layer own HTTP and must assert permission and branch scope themselves. | The request says routes only if the existing pattern demands them; the pattern for every backend business task so far is slices without routes. | yes

D-2 | The request names the lifecycle `draft / submitted / approved / partially received / received / closed / cancelled`; `docs/database.md` section 6.6 names `draft, pending_approval, approved, sent, partially_received, received, closed, cancelled`. Which wins? | The database document, column for column. "Submitted" in the request is the stored value `pending_approval`. `sent` ships in the enum (so adding it later is not a schema change) but **no feature in this task moves an order into or out of it**, the T-030 treatment of `failed` and `exchange`. Receiving works from `approved`. Purchase request statuses ship exactly as documented (`draft, pending_approval, approved, rejected, converted, cancelled`). | The database document is the design of record, and `Refference/ARCH.md` does not contradict it. Inventing a business meaning for `sent` (emailing? printing? locking?) is a rule nobody stated. | yes

D-3 | Which documented supplier columns are not built? | `payable_account_id` and `default_expense_account_id` (the `accounts` table does not exist; Finance is FP-262 onward) and `opening_balance` (an AP figure; its owner is FP-265) are **deferred, not shipped**, to be added by expand migrations by the tasks that own them, the T-028 D-6 convention. `credit_limit` and `payment_terms_days` ship as plain data. `[CF]` custom-field storage ships only if the Customers task shipped it for `customers`; the architect verifies and mirrors that choice exactly. | A foreign key to a missing table cannot be created, and an unkeyed column with no writer is a trap. Deferral by expand migration is additive. | yes

D-4 | Are suppliers branch-scoped or tenant-wide? | **Tenant-wide** (no `branch_id` in the documented table), so supplier permissions are not branch-scoped. Purchase requests and orders are branch documents (`branch_id` is documented), so their permissions are branch-scoped. | Matches the documented tables and T-028 D-5 for customers. | yes

D-5 | Supplier code rules. | Required on create, 1 to 30 characters, folded to upper case, letters, digits, `.`, `_`, `-`, first character a letter or digit. Unique across **all** rows including soft-deleted ones (the documented plain `unique` index), so a deleted supplier's code is never reused. **Immutable after create.** No code generator; the caller names the code. | Plain uniqueness is what the schema says. Immutability is the safest start: the code appears on supplier-facing paper and in reports, and unlocking it later is additive while locking it later breaks data. Auto-generation would need a numbering rule nobody stated. | yes

D-6 | Are `tax_no` and `name` unique? | **No.** Only `code` is unique. `tax_no` is stored as given (trimmed, upper-cased), no format validation, because tax-id formats differ by country and no rule is stated. | The schema declares only `code` unique; two legal entities can share a trading name, and a wrong uniqueness rule blocks real suppliers. | yes

D-7 | Deactivate versus delete. | `is_active = false` blocks the supplier from **new** requests and orders (and from submitting a draft), and changes nothing on existing documents. Soft delete (`deleted_at`) is refused with `supplier_in_use` while any purchase request is not in a terminal status (`draft`, `pending_approval`, `approved`) or any purchase order is not terminal (`draft`, `pending_approval`, `approved`, `sent`, `partially_received`). A deleted supplier is invisible to get and list, and existing documents still show its snapshotted name. **No restore feature** in this task. | The safest reading: never orphan live work, never destroy history. Restore is a convenience nobody asked for. | yes

D-8 | Credit terms. | `payment_terms_days` (integer 0 to 3650, default 0) and `credit_limit` (nullable `DECIMAL(18,4)` string, not negative) are **data only**: nothing in this task checks a limit, computes a due date or blocks an order. `payment_terms_days` is copied onto an order at creation as a snapshot, to be read by FP-255 when it computes a due date. | The request says "credit terms as data only". Enforcing a limit needs the AP balance, which is FP-265. | yes

D-9 | `bank_details` is sensitive. | It is stored as supplied (a JSON object), returned **only** to a caller holding `purchasing.suppliers.manage`, and **replaced by a fixed marker in every audit row and log line** (the audit row records only that it changed). | Bank account numbers are payment-fraud material; an audit table is read by more people than a manager screen. The marker is cheap and reversible. | yes

D-10 | When is a document number allocated, given the sequence is gapless? | **At creation**, inside the creating transaction, through `DocumentNumbers::next()`, taken last among the locks. A draft is **never hard-deleted**, only cancelled, so a number is never lost to a deleted draft and the sequence stays gapless. Types are `purchase_request` and `purchase_order`, each its own sequence, branch row preferred. A number longer than 30 characters is `number_too_long`, a numbering failure is `numbering_refused`, both carrying the foreign refusal as cause. | Allocating at submit would leave drafts unnumbered, which breaks the documented `number unique` header. Allocating at creation is safe only because drafts are cancelled, not deleted. | yes

D-11 | How does the approval hook behave? | `SubmitPurchaseOrder` and `SubmitPurchaseRequest` call `WorkflowGate::evaluate()` (entity types `purchase_order`, `purchase_request`) **inside the submit transaction**, **fail closed** (a `WorkflowEvaluationFailed` leaves the document in `draft` and writes nothing). `NotRequired` approves at once (the submitter is recorded as the approving actor with an audit action saying "no approval required"). `Pending` stores the instance id and sets `pending_approval`. The module is told the outcome by a pull feature, `SyncOrderApproval` and `SyncRequestApproval`, which reads `WorkflowGate::instance()` and applies it; **how the engine triggers that call** (an event, a console command, a direct call from the deciding feature) is for the architect to verify against the built engine. On `approved` the document becomes `approved`. On `rejected`: an order goes to `draft` when the instance's `on_reject` is `return_to_requester` and to `cancelled` when it is `stop`; a request becomes `rejected` in both cases (that status exists for it). `cancelled` or `expired` instance: the document returns to `draft`. | The T-020 contract (D-2, D-3, D-7) is exactly this: standalone, fail-closed, rejection reported not enforced. Mapping rejection to the documented statuses is the least invention possible. | yes

D-12 | What may be amended after approval? | See AC-60 to AC-66. In short, after approval only `notes`, `terms`, and `expected_date` (header and line) change in place. Anything financial (supplier, lines, quantities, units, prices, discounts, tax groups, shipping, currency, rate) is changed by **reopening** an approved order that has **nothing received** back to `draft` (permission `purchasing.orders.reopen`, a reason recorded in the audit row, the approval instance abandoned) and **submitting it again**, which starts a new approval. | A silent financial edit to an approved order defeats the approval, and a "change order" document is a design nobody asked for. Reopen-and-resubmit reuses the engine and is reversible. | yes

D-13 | Cancel and close. | **Cancel**: from `draft`, `pending_approval` (also cancels the workflow instance through `WorkflowGate::cancel()`) and `approved` with nothing received. Refused once anything is received. **Close**: from `partially_received` (the remaining quantity is abandoned, a short close) and from `received`. A reason (1 to 500 characters) is required to cancel an `approved` order and to close one, and lives in the audit row because the documented header has no reason column. `closed` and `cancelled` are terminal. Cancelling a request is allowed from `draft`, `pending_approval`, `approved`. | Conventional and the smallest set that lets every state end. | yes

D-14 | Where do `UnitResolver::snapshot()` and `snapshotInherited()` each apply? | `snapshot()` for a line that is **new or edited while the order is a draft**. `snapshotInherited()` in two places: (a) **converting an approved request line to an order line**, with the request line as the referenced line, so the quantity that was approved is the quantity ordered even if the ladder has moved since, and (b) **changing the quantity of an approved line in place is not allowed (D-12)**, so there is no second use; reopened lines are re-snapshotted fresh because the approval is being redone. A request line converts only in its own unit or the product's stock unit; a different unit is `InheritedUnitMismatch`, surfaced as `unit_refused`. | FP-254 explicitly owes the use of `snapshotInherited()`; conversion is the one place where "this line continues a prior line" is true in this task. | yes

D-15 | Request to order conversion semantics. | `ConvertRequestToOrder` takes the request id and **one** supplier id, and creates **one** draft order with **every** request line. A line that names a different supplier is refused `supplier_mismatch`; a line with no supplier is accepted. The order takes the request's branch, delivery location and `required_date` as its `expected_date`, sets `request_id`, and each request line gets `purchase_order_item_id`. The request becomes `converted` and **stays converted if the order is later cancelled** (the user raises a new request). A second convert of a converted request with the same supplier returns the existing order (replay); with a different supplier it is `invalid_transition`. | Splitting a request across suppliers needs a partial-conversion status the enum does not have. One supplier per conversion is the documented shape (one `purchase_orders.supplier_id`). | yes

D-16 | Money arithmetic and tax. | All money is a `DECIMAL(18,4)` string, never a float, computed with an exact decimal type and rounded **half-up at four decimals at each named step**: line subtotal = quantity x unit_cost; line discount = subtotal x discount_percent / 100; net = subtotal - discount; tax by `PricingEngine::computeTax()` (net for an exclusive group, gross for an inclusive one, base quantity for a fixed tax, context purchase, document date = `order_date`); line_total = net + exclusive tax (or net, where the group is inclusive). Header: subtotal = sum of line subtotals, discount_total = sum of line discounts, tax_total = sum of line tax, total = sum of line_total + shipping. Tax is never recomputed after submit. **Tax group resolution** for a line: the line's explicit group, else the product's `purchase_tax_group_id`, else the tenant default group (`TaxGroupDirectory::defaultGroupId()`), else refused `no_default_tax_group`. | One engine does tax arithmetic (the `PricingEngine` docblock). The resolution chain mirrors Catalog's own sales rule for the purchase side. | yes

D-17 | What is snapshotted on the order header? | `supplier_name`, `supplier_tax_no` and `payment_terms_days` are copied from the supplier at creation and are **not** re-read afterwards, so a supplier edit never changes an issued order. Lines snapshot the unit quad (`unit_id`, `quantity`, `unit_factor`, `base_quantity`), `description`, `unit_cost`, `discount_percent`, `tax_group_id`, `tax_amount`, `line_total`. The architect decides the exact column shape of the three header snapshots. | Snapshot-not-recompute, `docs/patterns.md` section 5 and `docs/database.md` section 6.5. A supplier-facing printed order must reprint identically. | yes

D-18 | The received rollup. | This task ships the **columns** (`received_quantity`, `received_base_quantity`, both default `0.0000`, and the header `received_value`, default `0.0000`) **and one operation, `ApplyReceivedQuantity`**, because without it the base-to-base transition cannot be built or tested here. It takes the order line id, a **caller-supplied application id** (ULID, the idempotency key), `received_base_delta` (the authority) and `received_quantity_delta` (in the order line's unit, **supplied by the caller**, who got it from a resolver snapshot; this module never multiplies or divides by a factor). It stores both, and recomputes the order status from **base only**. A delta may be negative (a receipt cancelled) but never takes a line below zero (`out_of_range`). **Over-receipt is accepted** (physical reality is recorded, the line simply counts as complete), and the owner is asked. `received_value` is **not** maintained here: it is FP-255's money figure. | The database document says FP-255 "maintains" the columns; the status rule belongs to the order. Putting the rule where the data lives keeps it in one place. An applications table makes the operation replay-safe without a second idempotency mechanism. | yes

D-19 | Dates. | `order_date` (and a request's creation date) is **set by the server** to today at creation and is never accepted from a client, T-030 D-70. `expected_date` and `required_date` are client-supplied dates and must not be earlier than `order_date`. The tax effective date is `order_date`. The clock and timezone source is the architect's to verify. | A client-supplied document date is a back-dating hole. | yes

D-20 | Currency and exchange rate. | Header `currency` is the explicit one, else the supplier's, else refused `currency_required`. `exchange_rate` is a positive `DECIMAL(18,6)` string, default `1.000000`. Both are **data**: no conversion happens in this task, and no total is expressed in a base currency. The workflow `amount` is the document-currency `total` and the `currency` is passed as a context field, so a rule may condition on it. | Posting and base-currency translation are FP-262. A threshold in base currency is an owner decision. | yes

D-21 | Idempotent replay. | Every create takes a **caller-supplied ULID** as the new row's id, doubling as the idempotency key (T-030 D-50): replay with an identical payload returns the original row and changes nothing; the same id with a different payload is `replay_conflict` naming the existing id. State changes are idempotent by outcome: submit on an already-submitted document returns it (no second workflow instance), cancel on a cancelled document returns it, convert on a converted request replays (D-15), `ApplyReceivedQuantity` replays by application id. A replay writes no audit row and sends no event. | The T-028 D-21 rule (an unlike replay is a refusal, never a silent success) is the only precedent in the codebase. The HTTP `Idempotency-Key` middleware belongs to the route layer, which does not exist here. | yes

D-22 | Lock order. | `UnitResolver`, `PricingEngine`, `TaxGroupDirectory` and permission reads happen **before** any lock; then the document header row is locked `FOR UPDATE`; `DocumentNumbers::next()` is taken **last**. Creation has no row to lock, so it locks the supplier row `FOR SHARE` (the T-029 `lock: true` shape) so a concurrent deactivation cannot interleave. | The ordering `docs/database.md` section 12.1 and T-030 D-50 already state. | yes

D-23 | Audit. | One `AuditTrail::record()` row per write, module `purchasing`, inside the writing transaction, with `branch_id` for branch documents, before and after images (D-9 redaction applies). Action names are declared through `DeclaresAuditActions`. A refusal writes no row. Line edits write one row each, against the order. | T-017 and the T-030 invariant "one audit row per write". | yes

D-24 | Cross-module effects. | Through the outbox, ids and base figures only: `purchase_order.approved`, `purchase_order.reopened`, `purchase_order.cancelled` (only when it had been approved), `purchase_order.closed`, `purchase_order.received_applied`. These carry exactly what FP-250 needs to maintain `quantity_incoming` (location, product, base ordered, base received), so FP-250 reads the event, not this module's tables. `purchase.approved` is the `event_key` already named for notification rules; the architect decides whether it is the same event or a second one. | `docs/patterns.md` checklist item 4. `docs/database.md` section 6.5 says `quantity_incoming` is maintained on approve, receive and close. If the architect prefers a published read contract to events, the data above is what it must expose. | yes

D-25 | Limits. | At most **200 lines** per order or request (`too_many_lines`); list reads default 25, maximum 100 per page; a quantity must be greater than zero and fit `DECIMAL(18,4)`; every rollup that cannot fit is `out_of_range`; `discount_percent` 0.00 to 100.00 with two decimals. | No limit is stated. 200 sits above any real purchase document and under the point where FP-426's per-line resolver cost (5 queries a line, 1000 for 200) becomes a problem. Raising it is a constant. | yes

D-26 | Permission keys. | Declared through `DeclaresPermissions`: `purchasing.suppliers.view`, `purchasing.suppliers.manage` (tenant-wide); `purchasing.requests.view`, `purchasing.requests.manage` (create, edit, submit, cancel, convert), `purchasing.orders.view`, `purchasing.orders.manage` (create, edit, submit, cancel), `purchasing.orders.close`, `purchasing.orders.reopen` (all branch-scoped, asked with the document's own `branch_id`). Every slice asserts its permission itself (the FP-452 lesson: a write slice that trusts the route layer is the defect). Approving is the workflow engine's own approver rule, not a purchasing key. | Follows `sales.approvals.decide` naming and T-030 D-69. | yes

D-27 | Does an order line carry `unit_code`? | **No.** The documented print-bearing list is exactly `sale_items`, `quotation_items` and `order_items` (D-66). A printed purchase order reads the code by joining `units`; a later rename of a unit code changes a reprint, which is a known limit and is recorded as a follow-up for the lead, not decided here. | The documentation is explicit and `ba` does not widen it. | yes

D-28 | Is a zero unit cost allowed? | Yes, `0.0000` is accepted (free-of-charge goods, samples). Negative is `validation`. A converted request line with no `estimated_cost` becomes `0.0000`. Asked of the owner as Q-2. | Refusing zero is a business rule nobody stated, and free goods exist. | yes

D-29 | Product eligibility on a line. | The product must exist, be active, not soft-deleted, and be one the catalogue says can be bought; a service or non-stock product, if the catalogue distinguishes them, is `product_not_purchasable`. The architect verifies which product fields express this. Non-stock lines (freight, services) are a supplier-invoice matter (FP-255), not order lines. | `docs/database.md` section 3 allows `product_id` NULL only on a supplier-invoice line. | yes

D-30 | ENGINE_HOLD. | Following the standing instruction for this stream: every engine-touching test (migrations, tenant database, models, concurrency, the cross-tenant suite) is **written but not run**; pure-logic tests (state machine, arithmetic, validation) are written and may be run only when the single gate is free. The spec states this as a delivery rule (AC-98) and does not claim a green gate. | The lead's instruction; `ba` cannot run anything. | yes
