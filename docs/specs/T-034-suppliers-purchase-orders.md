# T-034: Suppliers, purchase requests and purchase orders

Backlog row FP-254. Branch `ai/T-034-suppliers-purchase-orders`. Decisions: `docs/decisions/T-034-suppliers-purchase-orders.md` (D-1 to D-30, cited below as D-n). Written spec-ahead, documents only: `ba` has no shell and no git and claims nothing about history or about any gate.

## Problem / goal

A shop can sell (T-030) but cannot yet say who it buys from, ask for goods to be bought, or commit to buying them. This task builds the buying side up to and including the committed order: the **supplier master**, the **purchase request** (an internal ask, approved, then turned into an order) and the **purchase order** (a numbered, approved, supplier-facing commitment with exact money and a frozen unit quad on every line).

It also builds the one thing the next task needs from an order: the **received-quantity rollup**, where the order learns how much of each line has arrived, comparing **base to base** so a delivery in a different unit cannot close a half-empty order (`docs/database.md` section 6.6). Receiving itself, invoices, returns, payments and stock movements belong to other tasks.

## Users affected

- **Purchasing clerk / branch buyer**: keeps suppliers, raises requests and orders for their branch.
- **Approver** (manager, finance, owner): approves or rejects through the workflow engine (T-020); this task only calls the hook and obeys the outcome.
- **Branch / warehouse staff**: will receive against orders (FP-255, FP-256); this task gives them the order and the rollup.
- **Owner / accountant**: needs exact totals, a gapless numbered trail, an audit of every change, and supplier credit terms held as data for AP later.
- **Developers of FP-250, FP-255, FP-256, FP-262, FP-265**: consume the columns, the rollup operation and the events.

## Current behaviour

Nothing exists. `docs/database.md` section 6.6 designs `suppliers`, `purchase_requests`/`purchase_request_items`, `purchase_orders`/`purchase_order_items`. Built and reusable: `UnitResolver` (`snapshot()`, `snapshotInherited()`), `PricingEngine::computeTax()`, `TaxGroupDirectory`, `DocumentNumbers`, `PermissionResolver`, `AuditTrail`, `Outbox`, `WorkflowGate` (entity types `purchase_request` and `purchase_order` already exist in its enum), `BranchDirectory`. No supplier, request or order table, feature, permission key, number sequence or route exists. `WorkflowGate` has zero call sites for these entity types (T-020 D-8).

## User stories

- As a buyer, I want to create, edit, deactivate and delete suppliers with a unique code, contact details, tax id and payment terms, so that orders name a real, current counterparty.
- As a buyer, I want to record a supplier's credit terms and limit as plain data, so that AP work later has them without anyone re-keying.
- As a branch buyer, I want to raise a purchase request with lines in the unit I think in (a case, a carton, a kilo), so that what I ask for is what I mean.
- As an approver, I want requests and orders above a threshold to wait for approval, so that spending is controlled by the workflow rules the owner configured.
- As a buyer, I want to convert an approved request into a draft order for one supplier, so that I do not retype it, and so that the approved quantity is the ordered quantity.
- As a buyer, I want an order with exact totals (never rounded floats), tax by the purchase tax group, and a gapless number, so that the paper I send and the books agree to the cent.
- As an approver, I want an approved order not to change silently, so that approval means something.
- As a receiving clerk (via FP-255), I want the order to track how much has arrived in base units, so that receiving in a different unit from the order closes it correctly.
- As an owner, I want every change audited and a user to act only inside their branches, so that I can answer who did what where.

## Acceptance criteria

Working names for refusals (`validation`, `not_found`, `duplicate_code`, `invalid_transition`, `locked`, `replay_conflict`, and so on) are the closed vocabulary; the architect fixes the spelling. A foreign refusal (unit, pricing, numbering, workflow, access) is carried as the **cause** on a purchasing refusal that names the reason (T-030 D-67). Every refusal leaves the database, the audit trail and the outbox exactly as they were.

### Suppliers

- AC-1: Given an employee with `purchasing.suppliers.manage`, When they create a supplier with a caller-supplied ULID id, a code, and a name, Then one row exists with the code folded to upper case, `is_active = true`, `payment_terms_days = 0`, `created_by` and `updated_by` set to the actor, the row is returned, and exactly one audit row `supplier.created` exists.
- AC-2: Given a create, When the code is missing, empty, 31 or more characters, starts with a character other than a letter or digit, or contains a character outside letters, digits, `.`, `_`, `-`, Then it is refused `validation` and nothing is written. A 30-character code is accepted.
- AC-3: Given a supplier with code `ACME-1` exists (active, inactive or **soft-deleted**), When a create supplies `acme-1` or `ACME-1`, Then it is refused `duplicate_code` naming the existing supplier's id, and nothing is written.
- AC-4: Given a create or update, When `name` is empty or over 150 characters, `legal_name` over 150, `contact_name` over 100, `phone` over 30, `email` is not a well-formed address or over 190, `tax_no` over 50, `currency` is not three letters, `notes` over 2000, or `address` or `bank_details` is not a JSON object, Then it is refused `validation` naming the field. Valid values are stored; `email` is folded to lower case, `currency` and `tax_no` to upper case, text fields trimmed.
- AC-5: Given a create or update, When `payment_terms_days` is not an integer from 0 to 3650 (a decimal, a string of letters, -1, 3651), Then it is refused `validation`. When omitted on create it is stored as 0.
- AC-6: Given a create or update, When `credit_limit` is a non-negative decimal string with at most 4 decimals it is stored as `DECIMAL(18,4)` (for example `"2500"` is returned `"2500.0000"`); null is accepted and means "unspecified"; a JSON float, a negative, five decimals, or a value over 14 integer digits is refused `validation` or `out_of_range`.
- AC-7: Given a supplier with credit terms and a `credit_limit`, When an order for that supplier totals more than the limit, Then the order is created and submitted normally. Credit terms are **data only**: no limit check, no due date and no block exists in this task (D-8).
- AC-8: Given two suppliers, When they share a `name` or a `tax_no`, Then both are accepted (D-6). Only `code` is unique.
- AC-9: Given a create with id X that already exists with an **identical** payload, When it is replayed, Then the original row is returned, nothing changes and no second audit row is written. When the payload differs in any field, it is refused `replay_conflict` naming X, and the stored row is unchanged (D-21).
- AC-10: Given an existing supplier, When an update supplies a subset of fields, Then only those fields change, `updated_by` and `updated_at` move, and exactly one audit row `supplier.updated` records the before and after images and the list of changed fields. An update that changes nothing writes no audit row. An unknown, malformed or soft-deleted id is `not_found` or `validation`, never an unhandled error.
- AC-11: Given an existing supplier, When an update supplies a `code` different from the stored one, Then it is refused `code_immutable` (D-5). Supplying the same code is accepted.
- AC-12: Given a supplier edit, When any order already exists for that supplier, Then that order's stored `supplier_name`, `supplier_tax_no` and `payment_terms_days` are unchanged (snapshot, D-17).
- AC-13: Given a supplier, When it is deactivated, Then `is_active = false` and one audit row `supplier.deactivated` exists; deactivating an already inactive supplier is a no-op with no audit row (idempotent). While inactive, creating a request line, creating an order, converting a request to it, and **submitting a draft order** for it are refused `supplier_inactive`. Existing orders for it can still be received, closed, cancelled and have their `notes`, `terms` and `expected_date` amended. Reactivating restores everything.
- AC-14: Given a supplier with any purchase request in `draft`, `pending_approval` or `approved`, or any order in `draft`, `pending_approval`, `approved`, `sent` or `partially_received`, When it is soft-deleted, Then it is refused `supplier_in_use`. When every such document is terminal (`rejected`, `converted`, `cancelled`, `received`, `closed`), the delete succeeds: `deleted_at` is set, the row is **retained**, the code stays reserved (AC-3), `get` returns `not_found`, `list` omits it, and one audit row `supplier.deleted` exists. Deleting an already deleted supplier is a no-op success with no audit row. There is no restore (D-7).
- AC-15: Given `get supplier`, When the caller holds `purchasing.suppliers.view` only, Then every column is returned **except** `bank_details`; When they hold `purchasing.suppliers.manage` it is included. A caller with neither is refused.
- AC-16: Given `list suppliers`, When called with no filter, Then non-deleted suppliers are returned ordered by `code`, 25 per page; `page_size` above 100 is `validation`; filters `is_active` and a case-insensitive `q` matched against code and name work, and they combine; a page past the end, or no match, is an empty list, not an error. Soft-deleted suppliers never appear.
- AC-17: Given any supplier write, When `bank_details` is part of the before or after image, Then the audit row and every log line carry the fixed marker instead of the content, and record only that the field changed (D-9).
- AC-18: Given the supplier permissions, When a caller lacks the needed key, Then **each** supplier slice (create, update, activate/deactivate, delete, get, list) refuses with the access refusal reason carried as cause, and writes nothing. Supplier keys are tenant-wide: they are asked with no branch and are **not** refused `BranchRequired`.

### Purchase requests

- AC-19: Given an employee with `purchasing.requests.manage` at branch B, When they create a request for branch B, a delivery location L and an optional `required_date`, Then a row exists in `draft` with `requested_by` = the actor (never a caller-supplied value), a number from `DocumentNumbers::next('purchase_request', B)`, and one audit row `purchase_request.created` carrying `branch_id` B. The creation date is the server's today and is not accepted from the caller (D-19).
- AC-20: Given a create, When branch B is unknown or not active, or L is unknown, inactive, or does not belong to B, or `required_date` is earlier than today or not a real calendar date, Then it is refused (`unknown_branch`, `unknown_location`, `validation`) and no number is consumed. A request may carry no `required_date`.
- AC-21: Given an employee whose grant of `purchasing.requests.manage` is scoped to branch A only, When they create or edit a request for branch B, Then it is refused with the access reason; a company-wide grant is accepted; a branch-scoped key asked with no branch is refused `BranchRequired`.
- AC-22: Given a draft request, When a line is added with a product, a `unit_id`, a `quantity`, an optional `estimated_cost` (a non-negative decimal string, per line unit) and an optional `supplier_id`, Then the line stores the unit quad from `UnitResolver::snapshot()` (`unit_id`, `quantity` rounded to the unit's precision, `unit_factor`, `base_quantity`), the line count is one more, and one audit row `purchase_request.line_added` exists.
- AC-23: Given a line add or edit, When `quantity` is zero, negative, not a decimal string or int, a float, or does not fit `DECIMAL(18,4)` (`validation`, `out_of_range`), or the unit is unknown or not convertible for that product (`unit_refused` carrying the resolver's refusal), or the product is unknown, inactive, soft-deleted or not purchasable (`unknown_product`, `product_not_purchasable`, D-29), or `supplier_id` is unknown, inactive or deleted, Then it is refused and the request is unchanged.
- AC-24: Given a stored line, When the unit ladder or a product's conversion is later changed, Then the stored `unit_factor` and `base_quantity` of that line are unchanged and a read returns the stored values (snapshot, not recompute).
- AC-25: Given a request that is not `draft`, When a line is added, edited or removed, or the header is edited, Then it is refused `locked`. In `draft`, edit and remove work (a removed draft line is deleted and its before-image is in the audit row); the same product may appear on two lines; a request with 200 lines refuses the 201st with `too_many_lines`.
- AC-26: Given a draft request with at least one line, When it is submitted, Then `WorkflowGate::evaluate()` is called once with entity type `purchase_request`, the request id, the requester, the branch, `amount` = sum over lines of quantity x `estimated_cost` (a line with no estimate adds zero) as an exact string, and context fields `location_id` and `line_count`. A request with no lines is refused `no_lines` and the gate is not called.
- AC-27: Given `evaluate()` returns `NotRequired`, When submit completes, Then the request is `approved` immediately, with one audit row `purchase_request.approved` whose note says approval was not required. Given it returns `Pending`, Then the request is `pending_approval`, `workflow_instance_id` is stored, and it is locked (AC-25). Given `evaluate()` throws `WorkflowEvaluationFailed`, Then the request remains `draft`, no instance id is stored, nothing is audited, and the failure is surfaced `workflow_failed` (fail closed, D-11). A second submit of an already submitted request returns it and opens no second instance (D-21).
- AC-28: Given a `pending_approval` request, When its workflow instance is read as approved, rejected, cancelled, expired or still pending (`SyncRequestApproval`), Then the request becomes respectively `approved`, `rejected` (for either `on_reject` value), `draft` with the instance id cleared, `draft` with the instance id cleared, or is left unchanged. Applying an outcome the request already reflects is a no-op with no audit row. One audit row per real change.
- AC-29: Given a request in `draft`, `pending_approval` or `approved`, When it is cancelled, Then it is `cancelled`, a pending instance is cancelled through `WorkflowGate::cancel()`, and one audit row exists. Given `rejected`, `converted` or `cancelled`, a cancel is refused `invalid_transition` (a second cancel of a cancelled request is a no-op success).
- AC-30: Given an `approved` request and an employee holding both `purchasing.requests.manage` and `purchasing.orders.manage` at its branch, When they convert it for supplier S (active, not deleted), Then in **one transaction** one draft order exists with a number from `DocumentNumbers::next('purchase_order', B)`, `request_id` set, branch, location and `expected_date` (= the request's `required_date`) taken from the request, supplier snapshots taken from S, and one line per request line; each request line has `purchase_order_item_id` set; the request is `converted`; two audit rows exist (`purchase_request.converted`, `purchase_order.created`).
- AC-31: Given a conversion, When each order line is built, Then its unit quad comes from `UnitResolver::snapshotInherited()` with the request line as the referenced line, so `unit_factor` equals the request line's stored factor even if the ladder has since moved (D-14); `unit_cost` = the request line's `estimated_cost` (or `0.0000` if none); the tax group follows the chain in AC-44; and the line is re-quoted exactly as AC-43 states. A request line whose unit is neither its own stored unit nor the product's stock unit cannot arise (a line only ever carries its own unit), but a resolver refusal at any line aborts the whole conversion.
- AC-32: Given a conversion, When a request line names a supplier different from S, or S is inactive or deleted, or the request is not `approved`, or any line is refused by the resolver, the pricing engine or the tax-group lookup, Then it is refused (`supplier_mismatch`, `supplier_inactive`, `invalid_transition`, `unit_refused`, `pricing_refused`) and **nothing** is written: no order, no number consumed, request unchanged.
- AC-33: Given a request already `converted` to order O for supplier S, When convert is called again for S, Then O is returned and nothing changes (replay); for a different supplier it is refused `invalid_transition`. Cancelling O afterwards does **not** change the request, which stays `converted` (D-15).
- AC-34: Given `get request`, Then header, lines (stored unit quads and `estimated_cost` strings), status, number and `workflow_instance_id` are returned to a holder of `purchasing.requests.view` at the request's branch; any other caller is refused; an unknown id is `not_found`.
- AC-35: Given `list requests`, When called, Then results contain only requests in branches where the caller holds `purchasing.requests.view` (all branches for a company-wide grant), ordered newest first, 25 per page, maximum 100, filterable by status, branch and number; no match is an empty list.
- AC-36: Given any request create with a caller-supplied id, When replayed identically, Then the original is returned with no second number consumed and no second audit row; a differing payload is `replay_conflict` (D-21).
- AC-37: Given the request lifecycle, When any transition outside this set is attempted, Then it is refused `invalid_transition` naming the current status, with no change and no audit row: `draft -> pending_approval | approved | cancelled`; `pending_approval -> approved | rejected | draft | cancelled`; `approved -> converted | cancelled`.
- AC-38: Given any request slice (create, edit header, add/edit/remove line, submit, sync, cancel, convert, get, list), When the caller lacks the key at the request's branch, Then that slice itself refuses (FP-452: no slice relies on its route layer).
- AC-39: Given a request write, Then exactly one audit row per write exists with module `purchasing`, the actor, the request's `branch_id`, and before and after images.

### Purchase orders: header, lines, money

- AC-40: Given an employee with `purchasing.orders.manage` at branch B, When they create an order with a caller-supplied id, an active supplier S, branch B, location L, an optional `expected_date`, an optional `currency`, `exchange_rate` and `shipping`, `terms` and `notes`, Then a `draft` order exists with a number from `DocumentNumbers::next('purchase_order', B)`, `order_date` = server today, `request_id` null, `supplier_name`, `supplier_tax_no` and `payment_terms_days` copied from S, `currency` (explicit, else S's, else refused `currency_required`), `exchange_rate` default `1.000000`, `shipping` default `0.0000`, every total `0.0000`, `received_value` `0.0000`, and one audit row `purchase_order.created` with `branch_id` B.
- AC-41: Given an order create or header edit, When S is unknown, inactive or soft-deleted (`unknown_supplier`, `supplier_inactive`), the branch or location is unknown, inactive or mismatched, `exchange_rate` is not a positive `DECIMAL(18,6)` string, `shipping` is negative, a float or over `DECIMAL(18,4)`, `expected_date` is before `order_date` or not a real date, `terms` is over 1000 characters or `notes` over 2000, Then it is refused and no number is consumed.
- AC-42: Given a draft order, When a line is added with product, `unit_id`, `quantity`, `unit_cost` (non-negative decimal string, per line unit; zero is accepted, D-28), optional `discount_percent` (0.00 to 100.00, two decimals), optional explicit `tax_group_id`, optional `description` (default: the product's name at that moment, stored) and optional line `expected_date` (not before `order_date`), Then the line stores the unit quad from `UnitResolver::snapshot()` and the order's totals are re-quoted in the same transaction. Quantity, unit and product refusals are exactly AC-23's.
- AC-43: Given a line, Then the money is exact decimal arithmetic, half-up at four decimals at each step (D-16): `subtotal = quantity x unit_cost`; `discount = subtotal x discount_percent / 100`; `net = subtotal - discount`; tax from `PricingEngine::computeTax()` on `net`; `line_total = net + tax` for an exclusive group and `net` for an inclusive one. Worked example, with a 10% exclusive percentage group: quantity `12.0000`, unit_cost `3.3333`, discount 10.00 gives subtotal `39.9996`, discount `4.0000`, net `35.9996`, tax `3.6000`, line_total `39.5996`. Every amount is stored `DECIMAL(18,4)` and returned as a four-decimal **string**, never a JSON number.
- AC-44: Given a line with no explicit `tax_group_id`, When it is added, Then its group is the product's `purchase_tax_group_id`, else `TaxGroupDirectory::defaultGroupId()`, else it is refused `no_default_tax_group`. An explicit or resolved group that is unknown, inactive, or not applicable to purchases is refused `pricing_refused` carrying the engine's refusal. The group id used is stored on the line.
- AC-45: Given an order with lines, Then header `subtotal` = the sum of line subtotals, `discount_total` = the sum of line discounts, `tax_total` = the sum of line `tax_amount`, and `total` = the sum of `line_total` plus `shipping`. Worked example: two lines with line_totals `39.5996` and `10.0000`, shipping `2.5000` gives total `52.0996`. An order with no lines has every total `0.0000` plus shipping.
- AC-46: Given any quantity, money or rate in or out, Then it is a string (or an integer on input) and never a float: a JSON float in a money, quantity, percent or rate field is refused `validation`, and a source scan of the module finds no float cast, `floatval`, or float arithmetic on money.
- AC-47: Given a line or total that cannot fit `DECIMAL(18,4)`, or a `base_quantity` that cannot, Then it is refused `out_of_range` and nothing is written. A rollup that overflows (header total) refuses the line that caused it.
- AC-48: Given an order in any status, When the tax rate, tax group membership, product price, unit factor or supplier changes elsewhere, Then reading the order returns the stored `unit_factor`, `base_quantity`, `tax_amount`, `line_total` and totals unchanged. Nothing recomputes a stored order on read (snapshot, not recompute).
- AC-49: Given a draft order, When a line is edited (quantity, unit, cost, discount, tax group, description, expected date) or removed, Then the line is re-snapshotted fresh through `snapshot()` where the unit or quantity changed (D-14), the totals are re-quoted in the same transaction, and one audit row records it. A removed line's row is deleted and its before-image is in the audit row. Removing the last line leaves a valid draft with zero totals.
- AC-50: Given a draft, When a header field is edited (supplier, location, `expected_date`, `currency`, `exchange_rate`, `shipping`, `terms`, `notes`), Then it is validated as AC-41; a supplier change re-copies the three supplier snapshots and leaves currency as stored unless supplied; a change of `shipping` re-totals.
- AC-51: Given an order with 200 lines, When a 201st is added, Then it is refused `too_many_lines`.
- AC-52: Given any refusal from `UnitResolver`, `PricingEngine`, `TaxGroupDirectory`, `DocumentNumbers`, `WorkflowGate` or `PermissionResolver`, Then it surfaces as a purchasing refusal that names the reason and carries the foreign refusal and its enum type as cause (T-030 D-67); a numbering refusal over 30 characters is `number_too_long`.
- AC-53: Given an order create with a caller-supplied id, When replayed with an identical payload, Then the original is returned with no second number consumed and no audit row; a differing payload is `replay_conflict` (D-21). The same rule holds for adding a line with a caller-supplied line id.

### Purchase orders: submit and approval

- AC-54: Given a draft order, When it is submitted, Then it is refused `no_lines` with zero lines, `supplier_inactive` if S is now inactive or deleted, `unknown_location` if its location is no longer active, and otherwise proceeds. Submit does not re-quote or alter any stored figure.
- AC-55: Given a submit, Then `WorkflowGate::evaluate()` is called once, inside the submit transaction, with entity type `purchase_order`, the order id, the actor as requester, the order's branch, `amount` = header `total` (exact string, D-20), and context fields `supplier_id`, `location_id`, `currency`, `line_count`.
- AC-56: Given `NotRequired`, When submit completes, Then the order is `approved` at once, one audit row `purchase_order.approved` records that approval was not required and who submitted it, and the approval outbox event is written (AC-97).
- AC-57: Given `Pending`, When submit completes, Then the order is `pending_approval`, `workflow_instance_id` is stored, a submit audit row `purchase_order.submitted` exists, and the order is locked (AC-60). A second submit returns the order and opens no second instance.
- AC-58: Given `evaluate()` throws `WorkflowEvaluationFailed`, When submit runs, Then the order stays `draft`, no instance id is stored, no audit row or event is written, and the caller receives `workflow_failed`. The module never treats an engine failure as "no approval needed".
- AC-59: Given a `pending_approval` order, When `SyncOrderApproval` reads the instance, Then `approved` makes it `approved` (event, AC-97); `rejected` makes it `draft` when `on_reject` is `return_to_requester` and `cancelled` when it is `stop`, instance id cleared on `draft`; `cancelled` or `expired` makes it `draft`; `pending` changes nothing. Re-applying an outcome already reflected is a no-op. The instance id of the order and the instance read must match, else `invalid_transition`.

### Purchase orders: amendment, reopen, cancel, close

- AC-60: Given a `pending_approval` order, When any header or line edit is attempted, Then it is refused `locked`. Cancel is permitted (AC-64).
- AC-61: Given an `approved` order with nothing received, When `notes`, `terms`, the header `expected_date` or a line `expected_date` is edited, Then it is applied (one audit row each). When **any other** field is edited (supplier, location, lines, quantity, unit, cost, discount, tax group, shipping, currency, rate), or a line is added or removed, Then it is refused `locked` naming the field, and the message names reopen (D-12).
- AC-62: Given an `approved` order whose every line has `received_base_quantity = 0`, When an employee holding `purchasing.orders.reopen` at its branch reopens it with a reason of 1 to 500 characters, Then it is `draft`, `workflow_instance_id` is cleared, one audit row `purchase_order.reopened` stores the reason and the old instance id, and a reopen outbox event is written. Re-submitting runs a **new** approval (AC-55). An order with any received base quantity is refused `already_received`; an order not `approved` is refused `invalid_transition`; a missing or overlong reason is `validation`.
- AC-63: Given a `partially_received` order, When `notes`, `terms` or the `expected_date` of a line that is not yet complete is edited, Then it is applied; any other edit is refused `locked`.
- AC-64: Given an order in `draft`, `pending_approval` or `approved` with nothing received, When it is cancelled, Then it is `cancelled`; a `pending_approval` instance is cancelled through `WorkflowGate::cancel()`; a reason (1 to 500 characters) is **required** to cancel an `approved` order and is optional otherwise; one audit row exists; cancelling an order that had been approved writes the cancel outbox event. An order with any received base quantity is refused `already_received` (close it instead). A second cancel is a no-op success. The row is never deleted and its number is never reused.
- AC-65: Given a `partially_received` or `received` order, When an employee holding `purchasing.orders.close` at its branch closes it with a reason (1 to 500 characters), Then it is `closed`, remaining quantity on open lines is abandoned (the stored line quantities and received columns are unchanged), one audit row exists and the close outbox event is written. Closing from any other status is refused `invalid_transition`; a second close is a no-op success.
- AC-66: Given an order in `received`, `closed` or `cancelled`, When any edit, line change, submit, reopen or receipt application is attempted, Then it is refused `order_closed` (or `invalid_transition` for a transition); the order and its lines are unchanged. Reads still work.
- AC-67: Given the order lifecycle, When any transition outside this set is attempted, Then it is refused `invalid_transition` naming the current status, with no change and no audit row: `draft -> pending_approval | approved | cancelled`; `pending_approval -> approved | draft | cancelled`; `approved -> draft (reopen) | partially_received | received | cancelled`; `partially_received -> received | closed | approved (reversal to all-zero only)`; `received -> partially_received (reversal only) | closed`. `sent` is in the stored enum and **no feature enters or leaves it** (D-2).

### The received-quantity rollup

- AC-68: Given an order line is created, Then it carries `received_quantity` and `received_base_quantity` as `DECIMAL(18,4)` both `0.0000`, and the header carries `received_value` `0.0000`. `received_value` is not written by this task (D-18).
- AC-69: Given an `approved` or `partially_received` order, When `ApplyReceivedQuantity` is called with a line id, a caller-supplied application id (ULID), a non-zero `received_base_delta` and a `received_quantity_delta` of the same sign, Then both columns on the line move by the deltas, the application is stored with its id, and the order's status is recomputed **from the stored `received_base_quantity` and `base_quantity` of every line, never from `received_quantity`**: some base received but at least one line incomplete gives `partially_received`; every line complete gives `received`; all lines at zero gives `approved`.
- AC-70: Given an order line of 10 cases at `unit_factor` 24 (`base_quantity` 240.0000), When a delivery of 10 cartons of factor 12 arrives (caller supplies `received_base_delta` `120.0000` and `received_quantity_delta` `5.0000`), Then the order is `partially_received`, **not** `received`, even though ten cartons were counted against ten cases ordered. When a further `120.0000` base arrives, it becomes `received`.
- AC-71: Given an order with two lines, When one line is complete and the other is not, Then the order is `partially_received`; when both are complete it is `received`.
- AC-72: Given a line with `base_quantity` `240.0000`, When `received_base_quantity` is `239.9999`, Then the line is **not** complete; at `240.0000` it is. The comparison is exact on the stored four-decimal base values.
- AC-73: Given a line, When received base exceeds ordered base, Then the delta is accepted, stored as given, the line counts as complete, and no refusal occurs (over-receipt is recorded; the owner is asked, Q-1).
- AC-74: Given a line with received base `120.0000`, When a negative delta (a cancelled receipt) is applied, Then the columns decrease and the status is recomputed (a `received` order returns to `partially_received`; all-zero returns to `approved`). A delta that would take either received column below zero is refused `out_of_range`.
- AC-75: Given an order in `draft`, `pending_approval`, `closed`, `cancelled`, or a line id that does not exist, When a receipt is applied, Then it is refused `order_not_open` or `not_found`, and nothing changes. A `received` order accepts only a negative (reversal) delta or a positive over-receipt.
- AC-76: Given application id A already applied with identical line and deltas, When replayed, Then the response is the same, no column moves, no audit row, no event. When A is replayed with different line or deltas it is refused `replay_conflict` naming A.
- AC-77: Given an apply, When a delta is not a `DECIMAL(18,4)` string, is zero, is a float, or the two deltas differ in sign, Then it is refused `validation`.
- AC-78: Given two applies for different lines of the same order arriving concurrently, Then neither update is lost and the final status is the one the final stored sums imply (the header row is locked first, D-22).
- AC-79: Given any rollup operation, Then no stock level, stock movement, GRN, journal or `quantity_incoming` value is read or written by this module. FP-250 learns through the events in AC-97.
- AC-80: Given the receipt application, Then one audit row `purchase_order.receipt_applied` is written per real application, carrying the application id and both deltas.

### Purchase orders: reads

- AC-81: Given `get order`, When the caller holds `purchasing.orders.view` at its branch, Then header and every line are returned: the unit quad, `description`, `unit_cost`, `discount_percent`, `tax_group_id`, `tax_amount`, `line_total`, received columns, header totals, `status`, `workflow_instance_id`, `request_id`, the three supplier snapshots, all money as four-decimal strings. A caller without the key at that branch is refused; an unknown id is `not_found`.
- AC-82: Given `list orders`, When called, Then only orders at branches where the caller holds `purchasing.orders.view` appear, newest first, 25 per page, maximum 100, filterable by status, supplier, branch, number and `order_date` range (a range whose end precedes its start is `validation`); no match is an empty list.
- AC-83: Given a read of a soft-deleted supplier's order, Then the order is returned with its snapshotted supplier name; the deletion does not hide or alter the order.

### Cross-cutting

- AC-84: Given every write and read slice (suppliers, requests, orders, lines, transitions, `ApplyReceivedQuantity` excepted, see AC-96), When called by an employee lacking the key, Then it is refused by the slice itself, carrying the access reason, with a test per slice (D-26).
- AC-85: Given a branch-scoped key, When tested, Then (a) a grant scoped to A is refused at B, (b) a company-wide grant is accepted at any branch, (c) a branch-scoped key asked with no branch is refused `BranchRequired`, (d) the branch asked is always the **document's stored branch**, never a caller-supplied one that differs from it.
- AC-86: Given an employee who is suspended, inactive or deleted, When they call any slice, Then it is refused with the resolver's reason and nothing is written.
- AC-87: Given any write, Then exactly one `AuditTrail::record()` row is written inside the same transaction (module `purchasing`, actor, action, subject type and id, before and after, `branch_id` where the subject has one); a refusal or an idempotent replay writes none; a rollback removes it. Action names are declared through `DeclaresAuditActions`.
- AC-88: Given the multi-tenant rule, Then no new table has a `tenant_id` or equivalent column; an id from tenant A is `not_found` when used in tenant B; every new table is added to the cross-tenant isolation suite (T-022).
- AC-89: Given the schema, Then it is created by per-tenant migrations run by the tenant runner against **every** tenant database, expand-only: new tables only, no change to an existing table, no drop, rename, truncate or data delete in any migration. Foreign keys point only at tables that exist (`products`, `units`, `tax_groups`, `branches`, `locations`, `employees`, `workflow_instances`); the deferred columns of D-3 are absent. `ON DELETE` is `RESTRICT` except order and request lines, which cascade from their header (no header is ever hard-deleted). Ids are `CHAR(26)` ascii binary and are folded to upper case on input (T-014 AC-61).
- AC-90: Given any write that fails at any step (resolver, pricing, numbering, workflow, audit, outbox, database), Then the whole operation rolls back: no partial order, no orphan line, no audit row, no event, and **no consumed document number**.
- AC-91: Given malformed input of any kind (non-ULID id, impossible date, wrong type, null where a value is required, an unknown status filter, an over-long string), Then the result is a named `validation` refusal, never an unhandled exception.
- AC-92: Given a refusal, Then it is one of the closed set of named reasons, each reachable by a test, with the foreign cause attached where one exists (AC-52).
- AC-93: Given the module source, Then a static test finds no read of another package's tables, no read of `unit_conversions` or `units.factor`, and no multiplication by a factor column (the existing Catalog boundary rule), and the boundary check passes with the module granted only the contracts namespaces it uses.
- AC-94: Given one operation touching several lines (conversion, a multi-line create), Then each distinct product's unit is resolved no more than once per line and each line's tax at most once; the QA report records the measured query count for adding one line and for converting a 50-line request (the known per-line cost is FP-426; this task must not worsen it).
- AC-95: Given the permissions, Then every key in D-26 is declared through `DeclaresPermissions`, registered with the permission registry, and visible to `SyncPermissionRegistry`; supplier keys are not branch-scoped, all others are.
- AC-96: Given `ApplyReceivedQuantity`, Then it is an **internal operation for FP-255's own transaction** and carries no actor permission check of its own; the calling slice (FP-255's receive) owns the permission and branch check. This is stated in its docblock and the architect confirms the shape (contract versus direct call).
- AC-97: Given the outbox, Then these events are written inside the same transaction, ids and base figures only, never a name, address or `bank_details`: `purchase_order.approved` (per line: product, location, `base_quantity`, `received_base_quantity`), `purchase_order.reopened`, `purchase_order.cancelled` (only if it had been approved), `purchase_order.closed`, `purchase_order.received_applied` (line, deltas, resulting sums, resulting status). A replay or a refusal writes none.
- AC-98: Given the stream's `ENGINE_HOLD`, Then the engine-touching tests (migrations, tenant database, concurrency AC-78, cross-tenant AC-88) are **written but not run**, pure-logic tests (state machine, arithmetic, validation) are written and run only when the single gate is free, and no report claims a green gate that was not run (D-30).

- AP documents, ageing, supplier balance, credit-limit enforcement, due-date computation (FP-265).
- Journal posting, accounts, `payable_account_id`, `default_expense_account_id`, `opening_balance` (FP-262, FP-265).
- Screens (FP-256) and HTTP routes (D-1); the OpenAPI document does not change.
- `product_suppliers`, `purchase_price_history` (FP-255).
- Restoring a deleted supplier; a "change order" document; the `sent` status; partial conversion of a request; splitting a request across suppliers.
- A workflow definition for purchase orders or requests (configuration, not code); who approves is the engine's rule.
- Approver notifications and escalation (T-020 D-9).
- Currency conversion, base-currency totals, exchange-rate lookup.
- Tolerance rules for over- or under-delivery beyond what AC-72 and AC-73 state.

## Non-functional requirements

- **Exactness**: money and quantities are exact decimals end to end; no float in code, JSON or storage (AC-46).
- **Security**: `bank_details` is returned only to managers and redacted from audit and logs (AC-15, AC-17); every slice checks its own permission (AC-84); no secret is logged.
- **Tenancy**: no tenant column; the connection is the boundary (AC-88).
- **Integrity**: gapless numbers survive rollback (AC-90); nothing is hard-deleted except draft lines (AC-49, AC-89).
- **Performance**: list reads are paged (maximum 100); per-line resolver cost is measured, not capped, and a 200-line limit bounds the worst case (D-25, AC-94).
- **Auditability**: one audit row per write (AC-87).
- **Delivery**: `ENGINE_HOLD` (AC-98).

## Questions for the owner

Each has a default that is **built**; none blocks work.

- Q-1: Should receiving more than was ordered be refused, accepted within a tolerance, or accepted freely? **Built default: accepted freely and recorded** (AC-73). Refusing a delivery that is physically on the dock is the unsafe choice.
- Q-2: May a purchase line cost zero (free goods, samples)? **Built default: yes** (D-28). Also decides whether a request line with no estimate may become an order line at `0.0000`.
- Q-3: Is the approval threshold judged on the order's document-currency total or on a base-currency figure? **Built default: document-currency `total`, with `currency` available as a condition field** (D-20). A base-currency threshold needs FP-262's rate handling.
- Q-4: What should a **supplier-facing printed order** show for the unit? **Built default: the unit's current code by join** (D-27), so renaming a unit code changes a reprint. Say if orders should snapshot `unit_code` like the three print-bearing lines.

## Assumptions

- A new purchasing module is created; its package name and layout are the architect's (D-1).
- No HTTP routes; slices are invoked by handler (D-1).
- A document's branch is its stored `branch_id`; suppliers are tenant-wide (D-4).
- A draft document is cancelled, never deleted, so the gapless sequence stays gapless (D-10).
- The caller supplies each created row's ULID, which doubles as the idempotency key (D-21).
- `order_date` is server-set, `expected_date` and `required_date` are client-supplied (D-19).
- Maximum 200 lines per document and 100 per list page (D-25).
- The status names are `docs/database.md`'s; "submitted" is `pending_approval` (D-2).
- The deferred columns of D-3 are added by expand migrations in the tasks that own them.
- The `entity_type` values `purchase_request` and `purchase_order` already exist in the workflow engine and need no change there.
- A line quantity is in the line's own unit, `unit_cost` is per that unit, and `base_quantity` is `ROUND(quantity x unit_factor, 4)` computed by the resolver, never here.
