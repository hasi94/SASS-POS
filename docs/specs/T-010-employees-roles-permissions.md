# T-010: Employees, roles and branch-scoped permissions

Backlog: FP-208 (carries FP-200's debt). Decisions: `docs/decisions/T-010-employees-roles-permissions.md` (D-1 to D-35, cited below as "D-n"; T-009's decisions are cited as "T-009 D-n"). Branch `ai/T-010-employees-roles-permissions`.

## Problem / goal

FP-208: "Tenant-local employees, roles, branch-scoped permissions, cashier PINs, the permission resolver."

T-009 let a person sign in and open a shop, but the token says nothing about what they may do there, and no employee exists. This task creates, **inside each tenant database**, the people who work in a shop, the roles and permissions that say what they may do, the cashier PIN, and the one resolver every module will ask "may this employee do this, here?". It then adds to the tenant token the claims T-009 refused to mint (T-009 D-10, FP-200).

**This is the first task whose tables live in a tenant database.** The database is the tenant boundary, so **no table here has a `tenant_id` column and no query here is scoped by tenant**. A criterion that scopes a tenant table by tenant is the error the architecture exists to prevent.

**Three rulings the rest of the spec rests on** (each argued in the decisions file):

1. **Branch scoping is built now, against branch ids that are not yet a table (D-1).** Branches are FP-209. The storage and the resolver are branch-aware from the first row, because a resolver's answer shape and the hash over it are published to every module, and changing them later redefines rather than adds. The branch columns are plain unguarded identifiers (the T-008 D-5 precedent); FP-209 adds the foreign keys. What T-009's D-10 rule does and does not carry over to a *column* is argued in D-1.
2. **Only claims whose meaning is final are minted (D-2).** `employee` stays a plain id (it is not turned into an object, D-3). New: `branch_ids`, `all_branches`, `perm_version`, `perm_hash`.
3. **Permission changes beat the 15-minute window (D-4, D-7).** The tenant database is authoritative on every request, and a token whose `perm_version` is behind is refused with a distinct reason until refreshed. This is deliberately stronger than T-009 D-2 and is stated as such.

## Users affected

- Shop owners and administrators: create employees, define roles, assign access, set cashier PINs.
- Branch and shop managers, cashiers, waiters: the people the resolver judges. A cashier has **no master login** (architecture decision 3); their only credential here is a PIN.
- Developers of every later module: they guard their operations with a permission key and ask the resolver; they never read the access tables.
- Platform staff: no bypass (T-009 D-18 stands). A staff login with no employee in a shop has no permission in it.
- Downstream: FP-206 (provisioning creates the first owner), FP-209 (branches, terminals, terminal tokens, the foreign keys), FP-211 (audit framework), FP-213 (plugin permissions).

## Current behaviour

- No employee, role or permission table exists. `modules/host/database/migrations-tenant/` holds the six baseline tables (`schema_meta`, `settings_registry`, `settings`, `number_sequences`, `audit_logs`, `outbox_events`).
- `settings.updated_by` exists as an unguarded `CHAR(26)`; T-008 D-5 and the `settings` migration's docblock say the **employees** module owes its foreign key.
- The tenant token (T-009 AC-39) carries exactly `sub`, `token_type=tenant`, `tenant`, `employee` (only when `tenant_users.employee_id` is non-null, passed through **unverified**), `iat`, `exp`, `jti`. Selection **does not open the tenant database** (T-009 D-9, AC-39 last sentence).
- Nothing checks a permission anywhere. A tenant token reaches any handler its tenant gate admits.
- `docs/database.md` section 5 and `docs/architecture.md` section 5 print a longer claim set than is minted; FP-200 tracks annotating them.

## Token claims after this task (the list for whoever updates the design documents, FP-200)

Names are the ones in the code. "Mint" means placed in the token at selection and again at every tenant-scoped refresh (never at platform login).

| Claim | Platform token | Tenant token, membership **with** an employee | Tenant token, membership **without** an employee | Meaning (final) |
|---|---|---|---|---|
| `sub`, `token_type`, `iat`, `exp`, `jti` | yes | yes | yes | unchanged (T-009 AC-28, AC-39) |
| `tenant` | no | yes | yes | tenant ULID, unchanged |
| `employee` | no | yes | **no** | `employees.id` as a **string**, unchanged in shape. Now **verified** against the tenant database (D-6). Not an object (D-3) |
| `branch_ids` | no | **new** | no | array of the distinct branch ids in the employee's `employee_branches` rows, sorted ascending, possibly empty. **Explicit attachments only**; never expanded to "all branches" (D-2) |
| `all_branches` | no | **new** | no | boolean: true when the employee holds at least one *allowing* assignment (role or per-person grant) with a null branch scope. Exists so an owner with `branch_ids: []` is not misread as "no branches" (D-2) |
| `perm_version` | no | **new** | no | integer, `employees.perm_version` at mint (D-4) |
| `perm_hash` | no | **new** | no | hex fingerprint of the employee's contributing grants and denials plus `perm_version` (D-23) |

**Not minted, and why:** `branch` (singular; `docs/database.md` section 5 prints it, `architecture.md` prints `branch_ids[]`, they contradict, and the plural was ruled for because one token must serve a person who works at several branches); `terminal_id` (FP-209); `employee_id` and `tenant_id` spellings (the code mints `employee` and `tenant`; the two design documents disagree with each other and with the code on these names too). The permission *list* is not in the token (size and staleness); a client reads it through the "my permissions" query (AC-60).

Either **all five** employee-derived claims (`employee`, `branch_ids`, `all_branches`, `perm_version`, `perm_hash`) are present or **none** is.

## User stories

- As a shop owner, I want to add my staff as employees, so that payroll, commission and the till later attach to real people rather than logins.
- As a shop owner, I want a cashier who has no web login to exist as an employee with a PIN, so that they can work the till and never reach the web application.
- As a shop owner, I want to define roles and give each person a role, in all my branches or just one, so that a branch manager cannot act in a branch they do not run.
- As a shop owner, I want to deny one permission to one person even though their role grants it, so that exceptions do not need a new role.
- As a shop owner, I want a revoked permission to stop working on the next request, not up to 15 minutes later, so that a dismissed person is not still acting.
- As a module developer, I want one question to ask ("may this employee do this key at this branch?") and one place to declare my keys, so that no module invents its own access check.
- As a security reviewer, I want a PIN to be impossible to read back from any log, response, URL or audit row, so that a till credential cannot leak through the places we inspect most.
- As the platform operator, I want a stranger who guesses PINs to be slowed down and every denial recorded, so that guessing and probing are visible.

## Acceptance criteria

Conventions. "Operation" means one named capability of this task; the transport (HTTP routes, console) is `architect`'s, **except** where a criterion says "over HTTP". Time is the injectable clock (T-009 D-22); no criterion may sleep. "Tenant fixture A / B" are two SQLite stand-in tenant databases as in T-009's tenant-request criteria. **Refusal reasons are a closed, named set** (D-26): `not_permitted`, `branch_required`, `unknown_permission`, `permissions_changed`, `employee_unavailable`, `last_owner`, `self_change`, `no_escalation`, `role_in_use`, `system_role`, `scope_not_applicable`, `not_attached`, `has_scoped_grants`, `validation`. A criterion that proves a refusal **names the state that survives it and the reason**, because many guards refuse with the same status class and "refused" alone proves only that something refused. Every refusal criterion carries a **positive control**: the single change that removes the cause makes the same request succeed.

Markers: **[ENGINE]** needs a real MySQL/MariaDB engine and is reported NOT VERIFIED while the engine hold stands. **(diff)** needs repository history, which `ba` cannot see; `qa` verifies. **Sweep** criteria must publish their domain (D-27): the test output lists every item it examined and asserts the list is non-empty, so a clean result and an empty one are distinguishable.

### A. Tenant schema and structure

The master database gains **no table and no column** from this task, and `modules/host/database/migrations/` gains no file (diff). Controls: the listing check fails against a database with one extra table and against one with one missing. **[ENGINE]** for the live listing on a real engine; the stand-in listing is provable now.
- AC-2: Given the new tables applied, When every column of every new table is listed (live) and every new migration file is read (source), Then no column is named `tenant_id`; and over a full run of this task's tests, **no query against a new table carries a tenant predicate** (query-log scan). Controls: T-008's AC-24 source check reports a fixture migration declaring `tenant_id`; the query-log scan reports a fixture query `where tenant_id = ?`. **Cross-tenant control:** with the same employee id seeded in fixture A and fixture B holding different roles, a tenant-A operation never reads or writes B's rows (row counts in B unchanged, B's `perm_version` unchanged).

### B. The permission registry and the owner role

- AC-14: Given the application's declared permissions, Then every declared key matches the key format (lower-case dotted segments, e.g. `employees.manage`, at most 80 characters), carries `module`, `group`, `description` and `is_branch_scoped`, and this task declares **at least** these six, all `is_branch_scoped = false`: `employees.view`, `employees.manage`, `employees.set_pin`, `roles.view`, `roles.manage`, `access.assign`. A malformed or over-long key, or the same key declared twice with different attributes, makes the sync fail as a whole with nothing written. Controls: a fixture declaring each defect fails once per defect; the valid set syncs.
- AC-15: Given an empty `permissions` table, When the registry sync runs, Then every declared key is inserted and the report states `inserted`, `updated`, `unchanged`, `orphaned` counts. Running it again reports `inserted 0, updated 0` and changes no row (including no `perm_version`). A changed description is `updated`. A changed `is_branch_scoped` on an **existing** key is refused for that key and reported (flipping it would silently change the meaning of every existing grant), and the rest of the sync proceeds.
- AC-16: Given a key present in `permissions` but no longer declared in code, When sync runs, Then it is reported as `orphaned`, **not deleted**, and every grant of it is untouched.
- AC-17 (owner role): Given the sync, Then a system role `owner` exists with `is_system = true` and holds **every** registered key. Given a newly declared key, When sync runs, Then it appears in `owner`'s permissions and `perm_version` of every employee holding `owner` (at any scope) increases by at least 1 in the same transaction; a second sync bumps nothing. Control: an employee holding a custom role is not bumped.
- AC-18 (sweep, domain published): Given the registry, Then a test enumerates the declared keys **from the registry's own declaration source** (not a hand-written list), syncs, and asserts the table's keys equal the declared keys; the output prints the keys and their count (non-empty; at least the six of AC-14). Control: a scratch declared key that was not in any list is picked up by the sweep; a key inserted directly into the table but not declared is reported as orphaned.

### C. Roles

- AC-19: Given an actor holding `roles.manage`, When they create a role with a valid new `key` and `name`, Then the role exists with `is_system = false`, `deleted_at` null, no permissions, and one audit row (AC-70). Refused with `validation` and nothing written: missing or blank `key` or `name`, a `key` that is not the role-key format (lower-case letter first, then lower-case letters, digits and underscores; not the dotted permission-key pattern, D-34), over the column width, or already used **including by a soft-deleted role**. Control: the valid request succeeds in the same test.
- AC-20: Given a custom role, When `roles.manage` sets its permissions to a list of registered keys, Then `role_permissions` holds exactly that set (replace, not merge) and the role's holders' `perm_version` is bumped (AC-52). Given a list containing one unregistered key, Then `validation`, **no** row changes (all or nothing), no bump. An empty list is valid and removes every permission.
- AC-21: Given a system role (`owner`), When anyone, including a holder of every permission, tries to rename it, change its permissions, or delete it, Then each is refused with `system_role` and the role is unchanged. Control: the same three operations on a custom role succeed.
- AC-22: Given a custom role assigned to at least one employee at any scope, When deletion is requested, Then `role_in_use`, the role and its assignments unchanged; Given no assignments, Then it is soft-deleted, its key stays reserved (AC-19) and it no longer appears in the role list.
- AC-23: Given the role list and the role detail queries, Then they return `key`, `name`, `description`, `is_system` and the permission keys, ordered by `key`, exclude soft-deleted roles, and require `roles.view`.

### D. Employees

- AC-24: Given an actor holding `employees.manage`, When they create an employee with `code` and `first_name`, Then the employee exists with `status = active`, `display_name` defaulting to the trimmed first and last names joined by one space, `perm_version` at its initial value, `pin_hash` null, `user_id` null unless supplied, `created_by` the actor, and one audit row. The response and every later read contain **no** `pin_hash` (AC-65).
- AC-25: Given invalid input, When create is attempted, Then `validation` and no row: blank or missing `code` or `first_name`; `code` over 20 characters, containing whitespace inside it, or already used (including by a soft-deleted employee); a `user_id` that is not a 26-character ULID; a `user_id` already held by another employee; a non-string value for any field; a `status` not in the allowed set. Controls: a 20-character code is accepted; a `user_id` of null is accepted and a second employee with null is accepted (AC-7).
- AC-26: Given an existing employee, When `employees.manage` updates `first_name`, `last_name` or `display_name`, Then they change and `perm_version` does **not**. A request that includes `code`, `user_id`, `pin_hash`, `perm_version` or `status` in that update is **refused with `validation`**, not silently ignored, and the stored values are unchanged (D-32). Reason (`architect`): a silent ignore is indistinguishable from a field that was never wired, so a test could not tell "protected" from "forgotten". Control: the same request without those fields succeeds. `code` is immutable in this task (D-14).
- AC-27: Given an employee, When `employees.manage` changes `status` to each of `active`, `probation`, `on_leave`, `suspended`, `resigned`, `terminated`, Then the status is stored; the **acting** statuses are exactly `active` and `probation` (D-15, one place, moving it moves the result as in T-009 AC-12); whenever a change **crosses** the acting boundary in either direction `perm_version` increases, and within one side it does not.
- AC-28: Given an employee, When `employees.manage` soft-deletes them, Then `deleted_at` is set, `perm_version` increases, the employee no longer appears in the employee list or resolves any permission, and their `code` stays reserved. Soft deletion is the only deletion; no operation hard-deletes an employee.
- AC-29: Given the employee list and detail queries (`employees.view`), Then the list is ordered by `code`, excludes soft-deleted rows, returns at most a configured page size (a request for more is clamped or refused, stated), and each item shows `id`, `code`, names, `status`, `has_pin` (boolean) and the assigned role keys with their scopes, **never** `pin_hash`, `pin_failed_attempts` or `perm_version`.

### E. Assigning access

- AC-30: Given an actor holding `access.assign`, When they assign a custom role to an employee with a null scope, Then an `employee_roles` row exists with `branch_id` null, `granted_by` the actor, `granted_at` now, one audit row, and the employee's `perm_version` increases. The same role assigned again at a null scope is refused with `validation` (duplicate) and nothing changes. Control: a different role, or the same role at a specific branch, is accepted.
- AC-31: Given an employee **attached** to branch X (AC-35), When a role is assigned at scope X, Then the row exists with `branch_id = X`. Given an employee **not attached** to X, Then `not_attached`, nothing written (D-11). A `branch_id` that is not a 26-character ULID is `validation`. A well-formed id for which no branch exists is **accepted**, because there is no `branches` table to check against (D-30); `qa` must not file that as a defect and must not claim branch existence is validated.
- AC-32: Given an employee, When `access.assign` sets a per-person permission `allowed = true` or `allowed = false` for a registered key at a null scope or at an attached branch, Then one `employee_permissions` row holds it (a second set for the same employee, key and scope **replaces** the first) and `perm_version` increases. Refused: an unregistered key (`validation`); a **non-branch-scoped** key at a specific branch (`scope_not_applicable`, since such a key can only be held company-wide, D-8); a branch the employee is not attached to (`not_attached`). Clearing a per-person row removes it and bumps.
- AC-33: Given an assignment or per-person row, When it is removed, Then the row is gone, `perm_version` increases, and removing a row that does not exist is `validation` (not a silent success) and bumps nothing.
- AC-34 (no self-change): Given an actor holding `access.assign`, When they assign, remove, grant, deny or clear anything **on their own employee record** (roles, per-person permissions, branch attachments), Then `self_change`, nothing written. Control: the same change made by a different actor succeeds. A PIN reset on oneself is **not** an access change and is allowed (AC-47).
- AC-35: Given `access.assign`, When an employee is attached to a well-formed branch id, Then a row exists with `is_default` false unless requested; attaching again is `validation`; requesting default makes it the only default for that employee (the previous default becomes false in the same operation); `perm_version` increases (the `branch_ids` claim changed). When detaching, Then if any `employee_roles` or `employee_permissions` row for that employee is scoped to that branch the detach is refused `has_scoped_grants` and nothing changes (D-11); otherwise the row is removed and `perm_version` increases. Detaching the default leaves the employee with no default.
- AC-36 (no escalation): Given an actor who does not hold, at the scope concerned, every permission of a role, When they assign that role, Then `no_escalation`, nothing written. "Holds at scope S" means the resolver answers *allowed* for each of the role's keys at S; for a null scope S it requires an allowing contribution with a null scope and no null-scope denial for each branch-scoped key. Likewise `roles.manage` adding a key to a custom role requires the actor to hold that key company-wide, and a per-person **allow** requires the actor to hold the key at that scope; a per-person **deny** needs no such check. Control: the owner (holds all) succeeds; an actor lacking exactly one of the role's keys is refused, and granting them that one key makes the same assignment succeed.
- AC-37 (last owner): Given exactly one acting, non-deleted employee holds `owner` at a null scope, When anyone (another employee, with the permission) removes that assignment, sets that employee's status to a non-acting one, or soft-deletes them, Then `last_owner`, nothing changes. Given two such employees, the same operation on one succeeds. Control: after a second owner is assigned the refused operation succeeds. **[ENGINE]** two concurrent removals each seeing the other as the remaining owner (the guard must hold under concurrency, so both cannot succeed).

### F. The resolver

The resolver answers one question: **may employee E do permission K, at branch B (or company-wide)?** It reads the tenant database, never the token's claims (D-4, D-8). The truth table below is the specification; each row is a criterion case.

- AC-38: Given an employee with **no** role assignment and no per-person row, When K is asked, Then refused `not_permitted`. Given the employee holds a role containing K at a null scope, Then allowed. Control: removing the role flips the result back.
- AC-39 (branch-scoped key K, branch B asked): allowed when an allowing contribution has a null scope **or** scope B; refused `not_permitted` when the only allowing contribution is scoped to a different branch Y (the case that matters: a manager of Y acting in B). Control: the same employee asked about Y is allowed.
- AC-40 (deny wins): Given an employee whose role grants K and who has a per-person **deny** of K with a null scope, Then refused `not_permitted` at every branch. Given the deny is scoped to branch Y only, Then K is refused at Y and **allowed** at every other branch the role covers. (A per-person allow and a per-person deny of the same key and scope cannot coexist: AC-32 replaces one with the other.) Given a deny at B and a role grant at a null scope, Then refused at B (deny at any scope that covers B wins; no "more specific allow beats a general deny"). **Mutation control (mandatory):** reversing the precedence in the resolver (allow beats deny) must turn this criterion red; `qa` runs the mutation, not just the green case.
- AC-41 (non-scoped key): Given K with `is_branch_scoped = false`, Then it is allowed only through an allowing contribution with a **null** scope; a role holding K assigned at a specific branch does **not** confer it (least privilege, D-8). A branch passed when asking about a non-scoped key is ignored. Control: the same role assigned at a null scope confers it.
- AC-42: Given K with `is_branch_scoped = true` and **no branch** supplied, Then refused `branch_required`, distinct from `not_permitted`; given K unregistered, Then refused `unknown_permission`, distinct from both (a typo in a guard denies everyone silently otherwise). Controls: supplying the branch, or registering the key, changes the reason. **Refusal order (D-33):** the resolver refuses in the order `unknown_permission`, then `branch_required`, then `employee_unavailable`, then `not_permitted`. Principle: the first two are properties of the question and the third is a property of the subject; a malformed question has no answer about any subject, so question-validity precedes subject-judgement. Consequently an unregistered key, or a branch-scoped key with no branch, asked about a non-acting, soft-deleted or missing employee is refused `unknown_permission` or `branch_required`, not `employee_unavailable`.
- AC-43: Given an employee whose `status` is not acting, or who is soft-deleted, or does not exist, Then every question is refused `employee_unavailable` regardless of grants. Control: restoring `active` restores the grants. Roles that are soft-deleted contribute nothing (cannot occur while assigned, AC-22; asserted by direct fixture).
- AC-44 (domain published): The truth table of AC-38 to AC-43 is a dataset the test **prints**: each row names the employee fixture, key, asked branch, expected result and reason, and the test asserts the dataset is non-empty, contains at least one row for every reason in the closed set that the resolver can produce (`not_permitted`, `branch_required`, `unknown_permission`, `employee_unavailable`), and contains both allowed and refused rows. It also contains the ordering rows of AC-42: **an unregistered key asked about a non-acting employee returns `unknown_permission`, not `employee_unavailable`**, and a branch-scoped key with no branch asked about a non-acting employee returns `branch_required`. A resolver that always refuses, or always allows, fails it.
- AC-45 (tenant isolation, with any cache present): Given fixture A and B seeded with the **same employee id** and different grants, When the same worker answers a question for tenant A and then for tenant B (and again for A), Then each answer is that tenant's own. If the resolver caches, the cache key includes the tenant. Control: a deliberately mis-keyed cache fixture (employee id only) returns A's answer for B and the test reports it.
- AC-46 (freshness): Given any change that bumps `perm_version` (AC-52), When the resolver is asked immediately afterwards, Then the answer reflects the change, with any cache or per-request memo enabled. Control: a fixture resolver that caches without keying by version returns the stale answer and the test reports it.

### G. Cashier PINs

A PIN is a credential. **Its secrecy is a criterion, not a hope** (AC-48).

- AC-47 (set): Given an actor holding `employees.set_pin`, When they set a PIN for an employee over HTTP **in the request body**, Then `pin_hash` holds an Argon2id hash (never the PIN), `pin_set_at` is now, `pin_failed_attempts` is 0 and `pin_locked_until` is null (setting a PIN also unlocks), and the response states success and contains neither the PIN nor the hash. `perm_version` does not change. An actor may set their **own** PIN. Refused `validation`, no change: a PIN that is not all digits; shorter than 4 or longer than 8 digits (D-16, configuration); all one repeated digit; strictly ascending or strictly descending (`1234`, `4321`, `0000`, `1111`); a non-string; an empty body. Controls: `7391` and an 8-digit PIN are accepted; `0000` is refused. The weak-PIN rule is one list in one place.
- AC-48 (PIN secrecy, the criterion that matters): Given a run that sets a PIN whose value is a known **sentinel** and then fails and succeeds a verification with it, Then the sentinel and the stored hash string are absent from **every** sink below, captured at runtime (not by searching source text):
  1. **Every column of every table in the tenant database and in the master database**, enumerated from the live schema at test time (so a table added later is scanned), with the single expected exception `employees.pin_hash` holding the hash and nothing holding the plain PIN. The test **prints the table and column count it scanned** (non-empty). This covers `audit_logs.before/after/changed_fields`, `access_log.detail`, `outbox_events.payload`, `login_history`, `security_events`.
  2. The application log, at every level, including the error level.
  3. Every exception message and rendered error page produced by these operations.
  4. Every HTTP response body and header of the PIN operations and of every employee query.
  5. Token claims.
  6. **The ingress channel, out of the application's reach** (the adjacent check): the request's URL, query string and path as the application itself records them, and the `Referer` it might forward. A PIN is accepted **only in the body**. A request that carries a `pin` (or `pin_hash`) in the **query string or path** is refused `validation` **before any state is read or written**, the value is not echoed in the response or the log, and no `access_log`, `audit_logs` or `employees` row changes. Control: the same PIN in the body succeeds. The application cannot erase what a reverse proxy or web server logs on its own; this criterion proves only that the application neither accepts the URL channel nor re-emits it, and the report must say so.
  **Controls (mandatory, each in the same test):** (i) the capture harness fed a sink that deliberately contains the sentinel reports it found, for **each** of the six sink kinds; (ii) a **digit-string sentinel can collide with unrelated digits** (ids, timestamps, counts), so the harness first captures a run with no sentinel and asserts the sentinel string appears nowhere in that baseline, then uses a sentinel of at least 8 characters formed so that it cannot be a substring of any baseline capture; (iii) the scan also looks for the sentinel in **URL-encoded, JSON-escaped and reversed** forms. **Residual, stated and not tested:** a PIN that equals other digits stored legitimately (a 4-digit PIN colliding with a count) is not distinguishable by the scan; the sentinel mitigates, it does not remove, this.
- AC-49 (verify, in-process only): Given an employee with a PIN and a correct `code` and PIN, When the verify operation runs, Then it returns the employee's id to its in-process caller, writes one `access_log` row of type `pin_login` with `employee_id`, `ip`, and no PIN, and clears `pin_failed_attempts`. **There is no network route that verifies a PIN in this task (D-16):** a till has no terminal identity yet (FP-209), and a public PIN-checking endpoint over a 4-to-8-digit space is a guessing surface with no per-IP throttling (FP-199 covers login only). Control: the route list contains no route that reaches the verify operation (domain published: the list of routes examined, non-empty).
- AC-50 (refusal is one result): Given each of: unknown `code`, wrong PIN, employee with no PIN set, locked employee, employee with a non-acting `status`, soft-deleted employee, When verify runs, Then the in-process result is **one** refusal value, identical across causes; and exactly one `access_log` row of type `pin_failed` is written with a closed `detail.reason` in {`unknown_employee`, `bad_pin`, `no_pin`, `locked`, `not_acting`}, `employee_id` set when the code matched, and **never the attempted PIN** (a near-miss is close to the real one). The password hasher is invoked **exactly once** in every case, including the unknown-code and no-PIN cases, against a fixed dummy hash (counting double; a double that counts zero for the unknown case is the negative control that must turn this red; T-009 AC-8). Control: the correct PIN for the same employee succeeds in the same test, so the comparison is a refusal against a success.
- AC-51 (lockout): Given an acting employee with a PIN, Then four consecutive wrong PINs leave them unlocked with `pin_failed_attempts = 4` and the fifth **correct** PIN succeeds and resets the counter (negative control for the next); five consecutive wrong PINs set `pin_locked_until` to clock-now plus 15 minutes and reset the counter to 0 (D-17); while locked the correct PIN is refused with reason `locked`, the counter stays 0 and `pin_locked_until` is **not extended**; at `pin_locked_until` minus one second the correct PIN is refused, at exactly `pin_locked_until` and later it is accepted (both sides of the boundary); after an expired lock the count starts afresh (four wrong do not lock). A different employee is unaffected. Setting a new PIN (AC-47) clears a lock. A lock does not change `perm_version` or the employee's status. **[ENGINE]** simultaneous wrong PINs increment atomically and apply the lock once (the update must be atomic, shown by diff review; the concurrent proof waits for the engine).
- AC-52a (offline limit, stated): The stored hash is what a till will later hold to verify offline (`docs/database.md` section 5). An Argon2id hash of a 4-to-8-digit secret **can be brute-forced offline in a short time by anyone who obtains the hash**; no lockout applies offline. This is accepted as inherent to the design and is not a defect to file against this task; it is raised to the owner (Open question 3).

### H. `perm_version` and `perm_hash`

- AC-52: Given `employees.perm_version`, Then it is bumped, **in the same transaction as the change**, by at least 1 and never decreased or reset, for each of: assign or remove a role (AC-30, AC-33); set or clear a per-person permission (AC-32, AC-33); attach or detach a branch (AC-35); `roles.manage` setting a role's permissions (**every** employee holding that role at any scope, AC-20); a registry sync adding a key to `owner` (AC-17); a status change crossing the acting boundary (AC-27); a soft delete (AC-28). It is **not** bumped by: a name change (AC-26), a PIN set, verify or lockout (AC-47, AC-51), a role rename or description change, a sync that changes nothing. A change that fails (`validation`, `no_escalation`, `last_owner` and the rest) bumps nothing: the transaction rolled back with the bump. The increment is a single atomic statement, not read-then-write. **[ENGINE]** two simultaneous qualifying changes raise the version by two, never one.
- AC-53 (sweep, domain published, mutation-checked): Given every operation of this task that writes `employees.status`, `deleted_at`, `employee_roles`, `employee_permissions`, `employee_branches`, `role_permissions` or `permissions`, **enumerated from the operations' own directory/registry**, not from a list in the test, Then for each, with a fixture of several employees, the test computes the effective answer of every registered key at null scope and at one attached branch for every employee **before and after**; and asserts that for every employee whose resolver answers or whose `branch_ids` / `all_branches` changed, `perm_version` increased. The output prints the operations examined (non-empty, at least the operations of sections C, D and E) and the number of (employee, key, scope) cells compared. **Mutation controls (mandatory):** (a) deleting the bump from one operation turns the sweep red naming that operation; (b) a scratch operation that writes `employee_roles` and was never listed anywhere is found by the enumeration and fails; (c) a bump added to an operation that changes nothing is **not** required by the sweep (it asserts only that a change implies a bump, not the converse; the converse is AC-52's "not bumped" list).
- AC-54: Given `perm_hash`, Then it is a lower-case hexadecimal fingerprint computed over `perm_version` and the employee's **contributing grants and denials**: each role-derived allow as (key, scope, allow), each per-person row as (key, scope, allow or deny), duplicates collapsed, with scope the branch id or a fixed marker for "all branches". The canonical form is deterministic and `architect` documents it (the till will need to reproduce it). **Properties (proved):** the same contributions give the same hash regardless of row order, row ids and the order the role or grant was created; changing, adding or removing any one contribution, or `perm_version`, gives a different hash; two employees with identical contributions and identical `perm_version` give identical hashes. **Property deliberately not claimed (D-23):** that two different configurations which *resolve identically* hash equally (an allow through a role and the same allow granted directly hash differently). Controls: a fixture that reorders rows leaves the hash unchanged; a fixture that flips one `allowed` flag changes it.
- AC-55: Given an employee with no contributions, Then `perm_hash` is still defined and `perm_version` is present (the five claims are present together, AC-58).

### I. Tokens

- AC-56 (selection mints the new claims): Given a user with an `active` membership in a selectable tenant whose `employee_id` is non-null, whose employee exists, is acting, is not deleted, and whose `employees.user_id` equals the user's id, When they select the tenant, Then the tenant token's claim names are **exactly** `sub`, `token_type`, `tenant`, `employee`, `branch_ids`, `all_branches`, `perm_version`, `perm_hash`, `iat`, `exp`, `jti` (set equality, not "contains", T-009 AC-28), where `employee` is a string, `branch_ids` is a sorted array of distinct strings from `employee_branches`, `all_branches` is true exactly when the employee holds an allowing null-scope contribution (AC-57), `perm_version` equals the stored value and `perm_hash` equals the AC-54 fingerprint recomputed independently in the test. Positive control: a token minted with an extra claim in the test is rejected by the same comparison; the platform token's claim set is **unchanged** from T-009 AC-28.
- AC-57 (`branch_ids` and `all_branches`, both senses): Given four employees, one with attachments {X, Y} and no null-scope allow; one with no attachments and an `owner` role at a null scope; one with attachments {X} and a role at X only; one with neither, Then their claims are respectively `branch_ids [X, Y] / all_branches false`; `[] / true`; `[X] / false`; `[] / false`. A null-scope **deny** alone does not make `all_branches` true. `branch_ids` never lists a branch the employee is not attached to, and is never expanded to every branch even when `all_branches` is true. Controls: the four cases are distinct from each other so a constant implementation fails.
- AC-58 (all or none): Given a membership whose `tenant_users.employee_id` is **null**, When the tenant is selected, Then the token has none of the five employee-derived claims and its claim set is T-009's AC-39 set; selection in this case does **not** open the tenant database (T-009 AC-39 last sentence still holds here: tenant connection stays at the placeholder stanza, no `tenant_databases` read). Positive control: the same user with the employee link set gets all five.
- AC-59 (selection now opens the tenant database for an employee-bearing membership, D-5): Given a membership with a non-null `employee_id`, When the tenant is selected, Then the tenant database is entered through the **existing** `Tenancy::enter()` (never a connection built by this task; T-009 AC-52 still holds) and the existing serving gate decides whether it may be served. Given a tenant database that is not `active` or is below the schema floor, Then selection is refused with the existing `tenant_not_servable` reason naming the status, **no token is issued and no refresh token is written**, and the same request succeeds once the tenant is made servable (control). **This supersedes T-009 D-9's first clause and the last sentence of T-009 AC-39 for employee-bearing memberships only;** the test that pins that sentence is the one sanctioned edit to a T-009 test and must be narrowed to the null-employee case (AC-58), not deleted (diff).
- AC-60 (my permissions): Given a valid tenant token with the employee claims, When the "my permissions" query runs, Then it returns the current `perm_version`, `perm_hash`, `branch_ids`, `all_branches` and the effective contributions (key, scope, allow or deny) read **live** from the tenant database; it needs no permission key beyond the token itself (the one declared `authenticated_only` route, AC-63); with no employee claim it returns an empty set and no `perm_*` values.
- AC-61 (employee link, fail closed, D-6): Given a membership with a non-null `employee_id` and each of: no employee row with that id, a soft-deleted employee, a non-acting `status`, an employee whose `user_id` is null or **is a different user's id**, When the tenant is selected, Then selection is refused with reason `employee_unavailable`, the HTTP status 403, no token issued, no refresh row written, and a `login_history` failure row with `tenant_id` set (T-009 D-15). Positive control for each: fixing the single cause makes the same request succeed. The response does not say which of the four causes applied (one body), and the cause is in the application log at warning level without personal data. The refusal does not consume or revoke an existing refresh token (T-009 D-24).
- AC-62 (tenant refresh re-reads): Given a tenant-scoped refresh token, When presented after the employee's permissions changed, Then the new access token carries the **current** `perm_version`, `perm_hash`, `branch_ids` and `all_branches` (never copied from the old token); after the employee became non-acting it is refused `employee_unavailable` and, as in T-009 D-24, **the refresh token is not consumed**; a platform refresh token is unaffected by any employee state. A refresh request that carries any `perm_*`, `employee`, `branch_ids` or `all_branches` field ignores it (T-009 AC-38 extended).

### J. Using the token on later requests

- AC-63 (sweep: every tenant route is guarded or marked; domain published): Given the application's router, Then every route that accepts a **tenant** token declares exactly one of (a) a permission key that exists in the registry, or (b) the explicit marker `authenticated_only`. The test enumerates the routes **from the router**, not from a list in the test, prints each route with its declaration (non-empty; includes the routes of sections C to G and those of every other module that registers tenant routes), and fails on any route with neither, on a key not in the registry (`unknown_permission` at runtime, so a typo is caught before a user hits it), and on two declarations. **Mutation controls (mandatory):** a scratch route with no declaration, a scratch route naming an unregistered key, and a scratch route registered by a module the test does not mention are each reported. `authenticated_only` routes are listed in the output so a reviewer sees which routes skip the check.
- AC-64 (each guard refuses for its own reason): Given every guarded route from AC-63, When called by an employee holding **every registered key except the route's own**, Then the response is 403 `not_permitted`, the **handler spy is never called**, nothing is written to the route's tables (row counts unchanged), and exactly one `access_log` row of type `permission_denied` exists with `employee_id`, `permission_key`, `ip` and `detail.reason`. Given an employee holding **only** the route's key, Then the guard passes and the handler spy is called once. The pair (everything-but-K refused, only-K accepted) is what makes the refusal attributable to K and not to a sibling guard, a status check or an expired token. Reasons in `detail.reason` are one of `not_granted`, `explicit_deny`, `out_of_scope`; the HTTP body says only `not_permitted` for all three. Control: the explicit-deny and out-of-scope cases are each produced by a fixture and each logs its own reason.
- AC-65: Given an employee query or "my permissions" or any response of this task, Then none contains `pin_hash`, `pin_failed_attempts`, `pin_locked_until` or `perm_version` for **other** employees. (A PIN's secrecy is AC-48; this closes the response sink for ordinary reads.)
- AC-66 (stale token, D-7): Given a valid tenant token with `perm_version = n`, When `employees.perm_version` has since become greater than `n` and the token is presented on any tenant route, Then the response is 401 with reason `permissions_changed`, **no handler runs** (spy), and `access_log` is not written (it is a stale credential, not a denial). The token is otherwise valid (not expired, signature good). Control: before the change the same token reaches the handler once; after refreshing (AC-62) the new token reaches it. A token whose employee row is missing or soft-deleted gets the same 401 `permissions_changed`. A token with **no** `employee` claim performs no version check and reaches only `authenticated_only` routes (every guarded route refuses it `not_permitted`).
- AC-67 (the window is closed for permissions, open for users): Given an employee whose permission was removed after the token was issued, Then the very next request is refused (AC-66), **not** after `exp`. Given instead a **master** user disabled after issue, Then the token still verifies until `exp` exactly as T-009 AC-48 states, and this task does not change that. The asymmetry is deliberate and recorded (D-31); `qa` must not file either half as a defect.
- AC-68 (guards are the existing gate plus one check): Given a tenant token for a tenant whose mapping is not servable, Then the existing gate refuses first (T-009 AC-47) and the permission check never runs (spy). No token ever names a tenant in the permission check; the tenant is the token's (T-009 AC-45). Platform tokens remain refused on tenant routes (T-009 AC-46).

The audit writer is minimal and replaced by FP-211's framework later (D-20); `qa` must not ask for retention, search or export.

## Non-functional requirements

- **Security.** PIN: Argon2id only, never logged, echoed, put in a URL or kept in clear (AC-48). Authorisation decisions read the tenant database (D-4); the token is a hint and a staleness signal, not the authority. No bypass flag for anyone (AC-72). Refusal responses disclose no more than a reason code; the finer cause is in `access_log` (AC-64). Argon2id runs at reduced work factors in tests as in T-009 D-30; the algorithm is unchanged.
- **Determinism.** Time from the injectable clock; no criterion sleeps.
- **Performance.** No figure was given and none is invented. The per-request staleness check adds one primary-key read of one `employees` row on a connection that is already open for the request (D-4). Whether resolver results are cached is `architect`'s; AC-45 and AC-46 are the conditions any cache must meet. `docs/patterns.md` allows a read model only where measured; none is asked for here.
- **Concurrency.** Counter and version updates are single atomic statements; the concurrent proofs are **[ENGINE]** (AC-37, AC-51, AC-52).
- **Accessibility.** None (no interface).
- **Data.** Employees and roles are soft-deleted, never hard-deleted. No tenant column anywhere.

## Assumptions

- The tenant database, not the token, is authoritative for permissions (ARCH.md section 6 / `architecture.md` section 6: "Authorization is evaluated against the tenant database").
- Employee ids are ULIDs; `employees.user_id` is the master `users.id`; both are unchecked across databases (no foreign key), and the link is verified only at token mint (D-6).
- `Tenancy::enter()` is the only way a tenant connection is built; this task adds none.
- The registry of permission keys is declared in code by each module (`docs/database.md` 6.2: "seeded at provisioning from the application's registry"). Only this task's six keys exist in production; no production key is branch-scoped yet, so the branch-scoped mechanism is proved with **fixture-registered keys** and `qa` must not file "no branch-scoped key exists" as a defect (D-13).
- Lockout figures for PINs (5 failures, 15 minutes), PIN length (4 to 8 digits), and page size are conventional, configurable, not owner-specified (D-16, D-17).
- Soft-deleted rows count as absent everywhere (as in T-009).
- Anything needing history (which tests were edited, commit order, whether a migration changed after release) is for `qa`; `ba` has no shell and no history.
