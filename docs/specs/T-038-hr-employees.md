# T-038: HR master data - employee profiles, departments, designations, documents

Backlog: FP-270. Decisions: `docs/decisions/T-038-hr-employees.md` (D-1 to D-32, cited below as "D-n"; T-010's are cited as "T-010 D-n", T-032's as "T-032 D-n"). Branch `ai/T-038-hr-employees`.

## Problem / goal

FP-270: "Employees, departments, designations, documents." Phase 4 (HR). Today a shop has an access-control `employee` (T-010: code, names, status, PIN, permission version) and nothing that says where that person works, what they are called, who they report to, or what paperwork the shop holds on them. Payroll (FP-280), leave (FP-272), attendance (FP-271), commission and the workflow engine's manager and department-head approvers (FP-358) all need that master data and cannot start without it.

This task builds the **HR master data backend** inside each tenant database:

1. **Departments** (a hierarchy, each with an optional head) and **designations** (job titles with a level).
2. **Employee profiles**: the HR facts about an access employee. A profile is a **separate row that points at the existing employee by id** (D-1). It does not copy, replace or re-create the identity T-010 owns.
3. **Employee documents**: metadata rows plus file bytes held behind a storage abstraction (D-9). No external service.
4. A **personal-data regime** (D-12 to D-16): which fields are sensitive, who may read them, what is never allowed into a log, an audit row, an event or a list.
5. A small **published read contract** other modules use to ask "who is this person's manager / department head" (D-18), which is what FP-358 needs.

**Four rulings the rest of the spec rests on** (each argued in the decisions file):

1. **Extend by reference, never duplicate identity (D-1).** `employees` stays the one identity table and stays owned by access. HR adds `employee_profiles` (one optional row per employee, keyed by `employee_id`). `docs/database.md` section 6.12 prints these columns on `employees`; this spec **deliberately places them in a sidecar table** and says so (see "Deviation from the schema document").
2. **Sensitive personal data is opt-in to read (D-12, D-13).** A directory view needs one key; anything personal needs a second key; confidential documents a third. Nothing sensitive appears in a list, a log, an audit value, an event payload or an error message.
3. **Documents are rows plus bytes behind a port (D-9, D-10).** The storage key is generated by the server, includes the tenant boundary, and is never client-supplied.
4. **Payroll-flavoured data is not built here (D-5):** salary, bank accounts, statutory numbers, commission plan, pay frequency, salary structure and employment history stay with FP-280 and neighbours.

**The database is the tenant boundary.** No table here has a `tenant_id` column and no query here is scoped by tenant. A criterion that scopes a tenant table by tenant is the error the architecture exists to prevent. The one place a tenant name legitimately appears is the **file storage key** (AC-70), because file storage is one shared root and not a database.

## Users affected

- Shop owners and HR staff: maintain departments, designations, employee profiles and documents.
- Managers: appear as department heads and as "reports to" targets; they gain no new access by that alone.
- Payroll, leave, attendance and workflow developers: consume the published read contract (AC-82 to AC-86) and reference `employees.id`, `departments.id`, `designations.id`.
- Security and compliance reviewers: the personal-data rules (section F) are written to be tested, not just stated.
- Employees themselves: no self-service in this task (D-14).
- Out of reach: the front end (FP-273 builds screens).

## Current behaviour

- `employees` (T-010, `packages/access`) holds identity and access only: `code`, `user_id`, `first_name`, `last_name`, `display_name`, `status`, PIN columns, `perm_version`, audit columns, soft delete. T-010 AC-3 pins "no HR column on `employees`" and T-010 D-14 deferred NIC, dates, salary, bank, department, designation, employment type, reporting line to "a later additive change".
- No `departments`, `designations`, `employee_profiles` or `employee_documents` table exists. `branches` exists (T-014) with its foreign keys.
- `employees.view` lets a holder list employees with `code`, names, `status`, `has_pin` and role keys. It exposes no personal data and stays that way.
- No file storage abstraction exists in the code base; the design documents mention attachment columns (`expense_attachments.file_path`) without a mechanism.
- `docs/backlog.md` FP-358 records that the workflow engine's `manager_of_requester`, `department_head` and `branch_manager` approver types are refused today because there is "no manager column" and "no `departments` table"; it waits for this task.
- The audit writer (T-017) refuses any `action` not in a declared catalogue; access declares its fifteen (`AccessAuditActions`).

## Deviation from the schema document

`docs/database.md` section 6.12 lists the employee columns (NIC, dob, department, designation, branch, reports-to, employment type, dates, contacts) **on `employees`**. This spec places the HR subset it builds on a **new table `employee_profiles`**, one row per employee, `employee_id` as the key. Same facts, different table. Reasons (D-1): it keeps one owner per table (access owns `employees`); it keeps T-010 AC-3 true and T-010's reads unable to leak personal columns by a careless `select *`; the authentication path reads `employees` on every request and should not drag personal data with it. `docs/database.md` needs the matching annotation (lead / `architect`; not edited here). The columns the document lists and this task does **not** build are named in "Out of scope".

## User stories

- As an HR administrator, I want to define departments in a hierarchy with a head, so that reporting and approvals can follow the organisation.
- As an HR administrator, I want to define designations with a level, so that each person has a title.
- As an HR administrator, I want to record where each employee works, their department, designation, manager, employment type and key dates, so that payroll, leave and attendance have one source for it.
- As an HR administrator, I want to store contracts, ID copies and certificates against an employee and be told when one is about to expire, so that nothing lapses unnoticed.
- As a shop owner, I want personal details (ID numbers, birth date, contacts, address) and confidential documents visible only to people I have explicitly allowed, so that staff data does not leak through a directory or a log.
- As a workflow developer, I want to ask "who is the manager of this employee" and "who heads this employee's department" without reading HR tables, so that FP-358 can enable the approver types.
- As a payroll developer, I want department and designation ids that never get reused or silently disappear while in use, so that historic records stay meaningful.
- As a security reviewer, I want a sentinel ID number to be provably absent from logs, audit rows, events, lists and errors, so that the personal-data rule is a test result, not a hope.

## Acceptance criteria

Conventions. "Operation" means one named capability of this task; the transport is `architect`'s except where a criterion says "over HTTP" (section J). Time is the injectable clock; no criterion may sleep. "Tenant fixture A / B" are two SQLite stand-in tenant databases as in T-010. Each operation is its own vertical slice (`docs/patterns.md` section 3).

**Refusal reasons are a closed, named set** (D-20): `not_permitted`, `validation`, `not_found`, `not_updatable_here`, `code_in_use`, `name_in_use`, `profile_exists`, `profile_not_found`, `reference_not_found`, `reference_inactive`, `self_reference`, `cycle`, `depth_exceeded`, `has_children`, `in_use`, `has_dependents`, `already_inactive`, `already_active`, `date_order`, `file_empty`, `file_too_large`, `file_type_not_allowed`, `document_limit`, `storage_unavailable`, `document_corrupt`, `page_size_invalid`, `cursor_invalid`. `validation` names the failing fields. A criterion that proves a refusal **names the state that survives it and the reason**, and carries a **positive control**: the single change that removes the cause makes the same request succeed.

Markers: **[ENGINE]** needs a real MySQL/MariaDB engine and is reported NOT VERIFIED while the engine hold stands. **(diff)** needs repository history, which `ba` cannot see; `qa` verifies. **Sweep** criteria enumerate their domain from its source of truth, print what they examined, assert it is non-empty and carry a mutation control (T-010 D-27).

Every handler checks its permission **first**, before any read or transaction, and refuses `not_permitted` without touching the store (T-032 D-24). Permission checks are company-wide (all keys are non-branch-scoped, D-8).

### C. Departments

- AC-15: Given an actor holding `hr.departments.manage`, When they create a department with a valid `code` and `name`, Then it exists with `is_active = true`, `deleted_at` null, `parent_id`, `manager_employee_id` and `branch_id` as supplied (null by default), and exactly one audit row `department_created` (AC-88). Control: the valid request succeeds in the same test.
- AC-16: Given invalid input, When create is attempted, Then `validation` naming the field and nothing written: missing or blank `code` or `name` (after trimming, D-19); `name` over 150 characters after trimming; a non-string value for a string field; a field not in the allowed set (the whole request is refused, naming it, D-21); `is_active` supplied (set only by the deactivate and reactivate operations). Controls: a 150-character name is accepted; a 151-character name is refused.
- AC-17 (code format): Given a `code`, Then it is 1 to 20 characters from upper-case ASCII letters, digits, `.` and `-`; lower-case letters are upper-cased on write; whitespace anywhere is refused (not trimmed); anything else is refused `validation`. A code already used **including by a soft-deleted department** is `code_in_use`. Controls: `fin-01` is stored as `FIN-01`; `FIN 01` is refused; a 20-character code is accepted and a 21-character one refused; a code matching a soft-deleted row is refused and a fresh one accepted.
- AC-18 (name uniqueness, D-22): Given a live department with a name under a parent, When another live department under the **same parent** (or both at the top level) is created or moved or renamed to the same name compared case-insensitively after trimming, Then `name_in_use` and nothing changes. The same name under a different parent is accepted; a soft-deleted department's name is free. **[ENGINE]** two simultaneous creations (the check is in the application, not a database key).
- AC-19 (parent rules): Given a `parent_id`, When create or re-parent runs, Then it is checked in this order and refused with the first failing reason: `reference_not_found` (no such row or soft-deleted), `reference_inactive` (parent inactive), `self_reference` (re-parent to itself), `cycle` (the new parent is a descendant of the department), `depth_exceeded` (the result would have more than 10 levels, counting the top level as level 1). Nothing changes on refusal. Controls: re-parenting to a sibling succeeds; a tree of exactly 10 levels is accepted and an 11th level refused.
- AC-20 (head rules): Given a `manager_employee_id`, When create or update runs, Then the employee must exist and not be soft-deleted (`reference_not_found` otherwise). A head with a non-acting status is **accepted** (D-23); an employee with no profile is accepted. One employee may head several departments. Null clears the head. Control: soft-deleting the employee afterwards leaves the department intact but and the employee's later soft delete is governed by AC-85.
- AC-21 (branch reference): Given a `branch_id`, When create or update runs, Then it must name an existing, non-soft-deleted branch (`reference_not_found`) that is active (`reference_inactive`). Null is accepted. Control: reactivating the branch makes the same request succeed.
- AC-22: Given an existing department, When `hr.departments.manage` updates `name`, `manager_employee_id` or `branch_id`, Then the changes are stored and `updated_at` moves; one audit row `department_updated` shows before and after. A request including `code`, `parent_id`, `is_active`, `id` or `deleted_at` is refused `not_updatable_here` and nothing is stored (D-21); `parent_id` changes only through re-parent (AC-19), `is_active` only through AC-24. A request that changes nothing succeeds, writes no audit row and does not move `updated_at`. Control: the same request without those fields succeeds.
- AC-23 (re-parent): Given a department, When `hr.departments.manage` moves it under a new parent (or to the top level with null), Then the rules of AC-19 and AC-18 apply, `parent_id` changes, and one audit row `department_moved` records old and new parent. Re-parenting to the current parent is a no-op, not a refusal, and writes no audit row.
- AC-24 (deactivate, reactivate): Given an active department, When deactivated, Then `is_active = false`, existing profiles and children keep pointing at it, one audit row `department_deactivated`; it is thereafter refused as a target for **new** assignments (AC-45, AC-19 as parent, AC-34) with `reference_inactive`. Deactivating an inactive department is `already_inactive`; reactivating an active one is `already_active`; reactivating requires that its parent (if any) is active, else `reference_inactive`. Controls: reactivation restores the ability to assign.
- AC-25 (delete, D-24): Given a department, When `hr.departments.manage` soft-deletes it, Then it is refused `has_children` while any **live** department has it as parent, `in_use` while any live designation has it as `department_id`, any live profile has it as `department_id`, or the usage port (AC-86) reports a referrer; and nothing changes. With none of those it is soft-deleted (`deleted_at` set), its `code` stays reserved, it disappears from lists and reads as `not_found`, one audit row `department_deleted`. Controls: after the last referrer moves away the same delete succeeds; a deactivated department with referrers is still refused.
- AC-26 (reads): Given an actor holding `hr.departments.view`, When the department list runs, Then it returns, excluding soft-deleted rows and ordered by `code`, each department's `id`, `code`, `name`, `parent_id`, `manager_employee_id`, `branch_id`, `is_active`, with page size 1 to 200 (default 50; outside the range `page_size_invalid`, never clamped, D-25) and an opaque cursor (a malformed or foreign cursor is `cursor_invalid`). Filters: `parent_id` (including top level), `is_active`, `branch_id`, and a case-insensitive `name` contains. A detail read returns the same fields plus child count and live profile count; an unknown or soft-deleted id is `not_found`.
- AC-27 (tree read): Given `hr.departments.view`, When the tree read runs, Then it returns every live department nested by `parent_id` in `code` order, in a response whose size is bounded by the 10-level limit; a live department whose parent is soft-deleted cannot exist (AC-25 refuses that delete) and a fixture that forces it is returned at the top level with a flag, not dropped.
- AC-28 (system seed): Given a new or existing tenant, Then **no** department and no designation exists after migration (D-26).
- AC-29 (concurrency; **[ENGINE]**): Two simultaneous re-parents that together would create a cycle cannot both succeed. Stated, not provable on the stand-in.
- AC-30: Given a failure forced mid-operation in any department write (a handler fixture that throws after the change and the audit row were prepared), Then neither the change nor the audit row persists (one transaction). Control: the same operation without the forced failure persists both.

### D. Designations

- AC-31: Given an actor holding `hr.designations.manage`, When they create a designation with valid `code`, `name` and `level`, Then it exists active with `department_id` as supplied (null by default) and one audit row `designation_created`. Code rules are AC-17's, applied to designations (own namespace: the same code may exist as a department code).
- AC-32: Given invalid input, Then `validation` naming the field and nothing written: blank `code` or `name`; `name` over 150 characters; `level` missing, non-integer, below 0 or above 255; unknown field (whole request refused); `is_active` supplied. Controls: levels 0 and 255 are accepted, 256 and -1 refused.
- AC-33 (name uniqueness, D-22): Given a live designation, When another live designation **in the same `department_id`** (null is its own group) is created or renamed to the same name, case-insensitive after trimming, Then `name_in_use`. The same name in another department group is accepted.
- AC-34 (department reference): Given a `department_id`, When create or update runs, Then it must name a live department (`reference_not_found`) that is active (`reference_inactive`); null accepted. Control: reactivating the department makes the request succeed.
- AC-35: Given a designation, When `hr.designations.manage` updates `name`, `level` or `department_id`, Then it is stored with one audit row `designation_updated` (before and after); `code`, `is_active`, `id`, `deleted_at` are refused `not_updatable_here`. A no-change request writes no audit row.
- AC-36 (deactivate, reactivate): As AC-24 for designations: `designation_deactivated` and `designation_reactivated` audit rows, `already_inactive` and `already_active`, a deactivated designation refused for new assignments with `reference_inactive`, existing profiles keep it. Reactivation requires the designation's department (if any) to be active.
- AC-37 (delete): Given a designation, When soft-deleted, Then `in_use` while any live profile references it or the usage port (AC-86) reports a referrer, nothing changed; otherwise soft-deleted, `code` reserved, `designation_deleted` audit row, `not_found` thereafter. Control: after the last profile moves away the same delete succeeds.
- AC-38 (reads): Given `hr.designations.view`, Then list and detail behave as AC-26 (ordered by `code`, page size 1 to 200, `cursor_invalid`), with filters `department_id`, `is_active`, `level` and a `name` contains; each item shows `id`, `code`, `name`, `department_id`, `level`, `is_active`.

### E. Employee profiles

An **employee** here means an access employee (T-010): a live, non-soft-deleted row of `employees`. Identity is never created, changed or read raw by HR (D-17).

- AC-39: Given an actor holding `hr.employees.manage`, When they create a profile for an existing, live employee with a valid `branch_id`, `employment_type` and `joining_date`, Then exactly one `employee_profiles` row exists with those values, every optional field null unless supplied, `created_by` the actor, and one audit row `employee_profile_created`. The employee's own row (`employees`) is **byte-identical** before and after (no column, including `perm_version`, `updated_at` and `updated_by`, changes). Control: the same request succeeds in the same test.
- AC-40: Given a create for an employee id that does not exist or is soft-deleted, Then `not_found` and nothing written. Given an employee that already has a profile, Then `profile_exists` and the existing row unchanged. An employee with no profile remains a valid access employee for every T-010 purpose (a cashier needs no profile).
- AC-41 (required fields): Given a create missing `branch_id`, `employment_type` or `joining_date`, or with `employment_type` outside the six values, or a non-date `joining_date`, Then `validation` naming the fields, nothing written. Dates are real calendar dates in `YYYY-MM-DD`; `2025-02-30` is refused; `2024-02-29` accepted.
- AC-42 (unknown fields): Given a create or update that includes any field outside the allowed set - including `code`, `first_name`, `last_name`, `display_name`, `status`, `user_id`, `pin_hash`, `perm_version`, any salary or bank field - Then the whole request is refused: `not_updatable_here` for the identity fields named (they change only through access's operations), `validation` for any other unknown field; nothing stored. Control: the same request without them succeeds.
- AC-43 (branch): Given `branch_id`, Then it must name an existing, non-soft-deleted, active branch (`reference_not_found`, `reference_inactive`). Control: reactivating the branch makes the request succeed.
- AC-44 (department and designation): Given `department_id` or `designation_id`, Then each must name a live row (`reference_not_found`) that is active (`reference_inactive`); null accepted. **No cross-check** between a designation's own `department_id` and the profile's department (D-27). Control: a deactivated designation already held by the profile is **not** refused when an unrelated field is updated, only when the designation field is set to it.
- AC-45 (reports to): Given `reports_to_employee_id`, Then it must be a live employee (`reference_not_found`); not the employee itself (`self_reference`); and following the chain of existing profiles' `reports_to_employee_id` from it must not reach the employee (`cycle`), with the walk bounded at 50 steps and a chain longer than 50 refused `depth_exceeded`. The manager need not have a profile. Null clears. Controls: a three-person chain is accepted; closing it into a loop is refused `cycle`; a status of `suspended` on the manager is accepted (D-23).
- AC-46 (date order, D-28): Given the dates, Then `confirmation_date`, `probation_end_date`, `resignation_date` and `last_working_date` must each be on or after `joining_date`, and `last_working_date` on or after `resignation_date` when both are present, else `date_order` naming the pair; `dob` must not be after the current UTC date (`validation`); `joining_date` may be in the future. The check runs on the **merged** result of an update (a change to `joining_date` alone that breaks an existing later date is refused). Controls: equal dates are accepted; one day earlier is refused.
- AC-47 (text and shapes): Given the text fields, Then each is trimmed, a blank value after trimming is treated as absent (null) on create and as a clear on update, lengths are the column widths (over-length `validation`), `personal_email` and `work_email` must be a syntactically valid address, `gender`, `marital_status`, `nationality` are free text with no closed list (D-29), `nic` and `passport_no` carry no format or uniqueness rule (D-30). `emergency_contact` is an object with keys `name`, `relationship`, `phone` only (strings up to 100 characters; `name` and `phone` required when the object is present). `address` is an object with keys `line1`, `line2`, `city`, `region`, `postal_code`, `country` only (strings up to 150). An unknown key, a non-object, a nested value or a non-string leaf is `validation`. Controls: each shape's valid example is accepted.
- AC-48 (update): Given a profile, When `hr.employees.manage` updates any allowed field, Then the change is stored, `updated_by` the actor, `updated_at` moves, `employees.perm_version` and every other `employees` column are unchanged, and one audit row `employee_profile_updated` is written (AC-89 for what it may contain). A request that changes nothing succeeds, writes no audit row and does not move `updated_at`. An update for an employee with no profile is `profile_not_found`. Setting an optional field to null clears it.
- AC-49 (soft-deleted or deleted employee): Given an employee soft-deleted after their profile was created, Then every HR read and write for that employee returns `not_found`, the profile and documents rows are **retained untouched** (D-31), and the employee's code stays reserved by access.
- AC-50 (directory list, D-13): Given an actor holding `hr.employees.view`, When the profile list runs, Then it returns, for employees that have a profile and are live, ordered by employee `code`, only the **directory fields**: `employee_id`, `code`, `first_name`, `last_name`, `display_name`, `status`, `branch_id`, `department_id`, `designation_id`, `reports_to_employee_id`, `employment_type`, `joining_date`, `work_email`. Page size 1 to 200 (default 50; `page_size_invalid` outside), opaque cursor (`cursor_invalid`). **No sensitive field and no key for one appears in any item**, even as null. It never contains `pin_hash`, `pin_failed_attempts`, `pin_locked_until`, `perm_version` or `user_id`.
- AC-51 (filters): The list filters by `branch_id`, `department_id`, `designation_id`, `reports_to_employee_id`, `employment_type`, `status` (the employee's) and a case-insensitive `name` contains over `display_name`, `first_name`, `last_name` and `code`. **There is no filter, sort or search over any sensitive field**: a request carrying `nic`, `dob`, `phone` or the like is `validation` (a filter would be an oracle for the value, D-12). Controls: each permitted filter narrows the result; a combination returns the intersection.
- AC-52 (detail, directory): Given `hr.employees.view` only, When the detail read runs for an employee with a profile, Then it returns the AC-50 fields and **no sensitive field**. For an employee with no profile it returns `profile_not_found`. For a soft-deleted or unknown employee `not_found`.
- AC-53 (detail, sensitive): Given `hr.employees.view` **and** `hr.employees.view_sensitive`, When the detail read runs, Then it additionally returns all sixteen sensitive fields and writes one audit row `employee_profile_sensitive_viewed` (AC-90). Given `hr.employees.view_sensitive` **alone** (without `hr.employees.view`), Then `not_permitted`: the second key adds to the first, it does not replace it. Given a request asking for sensitive fields without the key, Then the response is the directory shape, not a refusal and not partial sensitive data (a client may ask for the richer view by calling the one read; the server decides what it returns).
- AC-54 (department head and reporting reads): Given `hr.departments.view`, When the detail read of a department runs, Then the head is returned as an id only, never as a profile. Given `hr.employees.view`, a "direct reports of employee E" read lists live employees whose profile names E, in directory shape, page-limited as AC-50.
- AC-55 (no profile data on access reads): Given T-010's employee list and detail (`employees.view`), Then they return exactly what they returned before this task (shape and values), with no HR field added (T-010 AC-29 passes untouched).
- AC-56 (sweep, domain published): Given the sixteen sensitive fields, Then a test asserts the list of sensitive fields in code equals the list in this spec's "Closed value sets" (the set is printed), that **every** profile column is classified either sensitive or directory (no unclassified column: a new column added later without classification fails the test), and that the directory view contains no sensitive column. **Mutation controls:** a scratch column added to the table and unclassified is reported; moving `nic` into the directory view turns AC-50 and this sweep red.
- AC-57 (concurrent profile create; **[ENGINE]**): Two simultaneous creates for one employee produce one row and one `profile_exists`. Stated, not provable on the stand-in; the primary key on `employee_id` is the guard.

### F. Personal data

- AC-58 (two keys, three tiers): Given the five combinations of `hr.employees.view`, `hr.employees.view_sensitive`, `hr.documents.view`, `hr.documents.view_confidential`, Then the matrix is as stated in "Authorization matrix" below and each cell is a test: directory only; directory plus sensitive; documents only; documents plus confidential; none. The matrix is printed by the test (non-empty).
- AC-59 (sentinel, the criterion that matters): Given a run that creates a profile whose sensitive fields (`nic`, `passport_no`, `personal_email`, `phone`, `address.line1`, `emergency_contact.phone`, `notes`, `exit_reason`) each hold a distinct **sentinel** string of at least 12 characters, then updates and reads it through every operation, with success and with forced failures, Then no sentinel appears, captured at runtime, in any of these sinks: (1) **every column of every table in the tenant database and the master database**, enumerated from the live schema at test time, with the single expected exception of the `employee_profiles` columns that legitimately store it; the test prints the table and column count scanned (non-empty). This covers `audit_logs.before/after/changed_fields`, `access_log.detail`, `outbox_events.payload`, `login_history`, `security_events`. (2) The application log at every level including error. (3) Every exception message and rendered error response. (4) Every response body and header of the list, the directory detail and the filter operations (the sentinel is permitted only in the sensitive detail response, AC-53). (5) Token claims. (6) The request URL, query string and path as the application records them: a sensitive value in a query string or path is refused `validation` before any state is read and is not echoed. **Controls (mandatory):** (i) the capture harness fed a sink that deliberately contains a sentinel reports it, for each of the six sink kinds; (ii) a baseline run with no sentinel is captured first and the sentinel is asserted absent from it, and sentinels cannot be substrings of any baseline capture; (iii) the scan also looks for URL-encoded, JSON-escaped and reversed forms; (iv) the harness is shown to flag a deliberate leak into `audit_logs.after`. **Residual, stated and not tested:** a reverse proxy or web server logs a URL on its own; this proves only that the application neither accepts nor re-emits the URL form; and a short value that equals other legitimate digits cannot be told apart, which the 12-character sentinel mitigates.
- AC-60 (audit values redacted): Given an update to a sensitive field, Then the audit row's `changed_fields` names the field and its `before` and `after` hold the fixed marker `"[redacted]"` for that field, never the value; non-sensitive fields in the same update show real values. The same rule holds for create, for the sensitive-view row and for document metadata `notes` (AC-89).
- AC-61 (sensitive fields never in events): Given every operation of this task, Then no `outbox_events` row it writes carries a sensitive field value, and the events it does write (if any) carry ids and types only. Control: a scratch event carrying a sentinel is detected by the scan of AC-59.
- AC-62 (no export, no self-read): Given an employee reading their own profile, Then they need the same keys as any other (no self-service shortcut, D-14). No operation exports or bulk-downloads sensitive data; there is no "all employees with sensitive fields" read.
- AC-63 (storage form): Given the sensitive columns, Then they are stored as plain text in the tenant database, access-controlled, redacted from every log (AC-59, AC-60), and **not** application-encrypted (D-16). `qa` must not file the absence of column encryption as a defect; the owner question is Open question 5.
- AC-64 (platform staff and owners, no bypass): Given a platform staff user with no employee in the shop, Then every operation refuses `not_permitted` (T-010 AC-72 stands). Given an employee holding `owner`, Then they hold all ten keys by data (AC-12) and so read sensitive data; there is no code path that grants it by role name.

### G. Documents

Authorization tiers for a document: **non-confidential** needs `hr.documents.view`; **confidential** needs `hr.documents.view` **and** `hr.documents.view_confidential`.

- AC-65 (add): Given an actor holding `hr.documents.manage`, When they add a document to a live employee with `type`, `title`, the file content and optionally `issue_date`, `expiry_date`, `is_confidential`, `notes`, Then the bytes are written through the storage port (AC-69), one `employee_documents` row exists with `file_path` set to the **server-generated** key, `original_name`, `mime` (server-detected, AC-67), `size_bytes` (measured), `checksum` (SHA-256 of the stored bytes), `created_by` the actor, and one audit row `employee_document_added`. The employee need not have a profile. Control: the valid request succeeds.
- AC-66 (validation): Given invalid input, Then the matching refusal and **no row and no stored file**: `employee_not_found` as `not_found`; `type` outside the nine values, blank or over-150-character `title` after trimming, `notes` over 1000, non-date `issue_date` or `expiry_date`, `expiry_date` before `issue_date` (`date_order`), a non-boolean `is_confidential`, any unknown field including `file_path` and `checksum` (`validation`, client-supplied storage fields are refused whole, D-10). Controls: `expiry_date` equal to `issue_date` is accepted; a past `expiry_date` is accepted (already-expired paperwork is still paperwork).
- AC-67 (file rules, D-9): Given the upload, Then: an empty file is `file_empty`; a file over the configured maximum (default 10 MiB) is `file_too_large` (a file of exactly the maximum is accepted); a file whose **detected content type** (from the bytes, not the declared header or the file name) is not in the configured allow-list (default `application/pdf`, `image/jpeg`, `image/png`) is `file_type_not_allowed`; a file whose name extension disagrees with the detected type is `file_type_not_allowed`. `original_name` is stored as display text only after stripping path separators and control characters, truncated to 255, and never used to build a path. Controls: a PDF renamed `.png` is refused; an executable renamed `.pdf` is refused; a real PNG is accepted. Detection logic is **one list in one place**.
- AC-68 (limits): Given an employee with 100 live documents (configurable, D-9), When another is added, Then `document_limit` and nothing is stored; after one is soft-deleted the next succeeds.
- AC-69 (storage port, D-9): Given the HR module, Then every byte write, read and delete goes through one interface (`DocumentStore`), the module ships one local-disk implementation configured with a root directory **outside** any web-served path and a fake implementation for tests, and no HR code names a disk, bucket, SDK or external service. If the store throws on write, the add is refused `storage_unavailable`, no row remains; if the row write fails after the bytes were written, the bytes are deleted again before the operation returns (compensation). Controls: a forced failure after the store write leaves no row and no file; a store that fails to delete during compensation is logged at error level and the refusal is still returned. **No external service is called by any test** (spy on network access).
- AC-70 (storage key and tenant boundary, D-10): Given a stored document, Then `file_path` is a key of the form `<tenant-segment>/hr/employee-documents/<ulid>`: the tenant segment is derived **server-side** from the current tenant context, the ULID is generated by the server, no part comes from the request, and the key contains no `.`, `..`, `\`, drive letter, or user-supplied character. Given fixture A and B each holding a document with the same document id, When tenant A reads, Then it receives A's bytes and never B's; a forged `file_path` written directly into a row to point at B's key is refused at read (`document_corrupt`, the key's tenant segment does not match the current tenant) and nothing is returned. A path-traversal string in any request field (`../`, `..%2f`, an absolute path, a NUL byte) is `validation` and never reaches the store.
- AC-71 (download): Given `hr.documents.view` and a non-confidential document (or both keys and a confidential one), When download runs, Then it returns the bytes, `original_name`, `mime` and `size_bytes`, after verifying the SHA-256 of the bytes read equals `checksum`; one audit row `employee_document_downloaded` records document id, type and employee id and **no** name of the file beyond its id (D-32). A checksum mismatch is `document_corrupt`, no bytes returned, logged at error level. A missing file is `document_corrupt` as well (the row exists, the file does not). A soft-deleted document, an unknown id or a document of a soft-deleted employee is `not_found`. The response sets a download disposition and never inlines a stored file into a page (a stored HTML or SVG file is not rendered by the application; `mime` is the detected type from the allow-list only).
- AC-72 (confidential isolation): Given a confidential document and an actor with `hr.documents.view` only, Then the document does **not** appear in the list, a direct detail or download read is `not_found` (not `not_permitted`: existence is not disclosed), and no audit row of kind downloaded is written. Control: adding `hr.documents.view_confidential` makes the same reads succeed. The reverse is also tested: `hr.documents.view_confidential` alone is `not_permitted` (it adds to the view key).
- AC-73 (list): Given `hr.documents.view`, When the documents of an employee are listed, Then it returns for each visible document (AC-72) `id`, `type`, `title`, `original_name`, `mime`, `size_bytes`, `issue_date`, `expiry_date`, `is_confidential`, `created_at`, never `file_path`, never `checksum`, excluding soft-deleted rows, ordered by `created_at` then `id`, page size 1 to 200 (`page_size_invalid`), cursor (`cursor_invalid`); filter by `type`. The list for a soft-deleted or unknown employee is `not_found`. `notes` appears in the detail read only, and only to holders of `hr.employees.view_sensitive` as well (D-12; a document note is personal text).
- AC-74 (update metadata): Given `hr.documents.manage`, When updating `title`, `type`, `issue_date`, `expiry_date`, `notes` or `is_confidential` of a document **the actor can see** (confidential ones need `hr.documents.view_confidential`; an invisible one is `not_found`), Then it is stored and one audit row `employee_document_updated` shows before and after (AC-89 for `notes`). Changing a confidential document to non-confidential additionally requires `hr.documents.view_confidential`; the reverse (marking confidential) does not. A document of type `medical` cannot be set non-confidential (`validation`, D-33). The file, `file_path`, `checksum`, `size_bytes`, `mime`, `employee_id` and `original_name` are not updatable (`not_updatable_here`); replacing a file is delete plus add.
- AC-75 (default confidentiality, D-33): Given an add that omits `is_confidential`, Then the stored value is **true**. Given `type = medical`, Then `is_confidential = false` is refused `validation`. Control: an explicit `false` on a `contract` is accepted.
- AC-76 (delete): Given a document the actor can see, When `hr.documents.manage` deletes it, Then `deleted_at` is set, it disappears from lists and reads, one audit row `employee_document_deleted`, and the **file bytes are retained** in the store (no purge is built, D-31). The row is never hard-deleted by any operation. Deleting twice is `not_found` the second time.
- AC-77 (expiring documents): Given `hr.documents.view`, When "documents expiring within N days" runs (N from 1 to 365, default 30; outside the range `validation`), Then it returns live, non-deleted documents of live employees whose `expiry_date` is from today (clock) to today plus N inclusive, ordered by `expiry_date` then `id`, visible per AC-72, with employee id and directory name, page-limited as AC-73, and **already-expired** documents are listed only when `include_expired = true`. Controls: a document expiring exactly today is included; one expiring on day N+1 is not; a soft-deleted one is not; a confidential one is hidden from `hr.documents.view` alone. No notification is sent (out of scope).
- AC-78 (no hard dependency on a profile): Given an employee with documents and no profile, Then document operations work; given a profile and no documents, document reads return an empty list, not an error.
- AC-79 (atomic add): Given a failure forced after the row, audit row and stored file were prepared (handler fixture throws), Then no row, no audit row and no stored file persist. Control: without the forced failure all three persist.
- AC-80 (concurrency; **[ENGINE]**): Two simultaneous adds at the 99th document cannot both succeed past the limit of AC-68. Stated, not provable on the stand-in.
- AC-81 (unscanned content, D-34): Given an uploaded file, Then no malware scan is performed and none is claimed; the criterion is that the file is never executed, never served inline, never named by the client, and stored behind a non-public root. `qa` must not file the absence of a scan as a defect; it is an owner question (Open question 7).

### H. Published read contract and delete guard

- AC-82 (contract): Given the HR module, Then it publishes one read-only contract for other modules with exactly these questions, none returning sensitive data: `managerOf(employeeId)` returns the `reports_to_employee_id` of that employee's profile (null when none, when the profile is absent, when the employee is soft-deleted or when the manager is soft-deleted); `departmentHeadOf(employeeId)` returns the `manager_employee_id` of the employee's department (null when the employee has no profile, no department, the department is soft-deleted or has no head or the head is soft-deleted; **not** inherited from an ancestor department, D-18; the head may be the employee asked about); `departmentOf(employeeId)` and `designationOf(employeeId)` return the id or null; `directReportsOf(employeeId)` returns live employee ids in id order, bounded by a stated maximum (1000) with a `truncated` flag; `isLiveDepartment(id)` and `isLiveDesignation(id)`. It reads only HR's own tables and, for liveness, access's published contract (D-17). Controls: each answer flips when its cause is removed (clear the manager; delete the head).
- AC-83 (no wiring): Given the workflow engine, Then this task does **not** enable the `manager_of_requester`, `department_head` or `branch_manager` approver types and changes no workflow code; enabling them is FP-358, which now has its data source (D-18). `qa` must not file the still-refused approver types as a defect.
- AC-84 (contract has a default): Given a deployment without the HR module registered, Then a consumer that asks the contract through its published interface gets the documented "none" answer for every question rather than an unbound-interface failure (T-032 D-7 pattern; the null default lives with the interface).
- AC-85 (delete guard on access, D-35): Given the access employee soft-delete (T-010 AC-28), When the employee is the head of a **live** department or the `reports_to_employee_id` of any **live** profile of a live employee, Then the delete is refused `has_dependents` through a published guard (access defines the interface, HR implements it, the default answers "none"), nothing changes (no `deleted_at`, no `perm_version` bump, no audit row), and the refusal names the kind of dependent (`department_head` or `direct_reports`), never the ids. Control: clearing the head or moving the reports makes the same delete succeed. Changing the employee's `status` (including to `terminated`) is **not** blocked. This is the one sanctioned behaviour change to a T-010 operation; its tests gain the new refusal and nothing else is edited (diff). `qa` reports it as "T-010 AC-28, narrowed by a guard".
- AC-86 (usage ports): Given deleting a department or designation, Then HR consults a published usage port that other modules bind later (expense items, payroll, workflows), defaulting to "no referrers"; a test with a bound fake that reports one referrer sees `in_use` and the row unchanged. **Stated limit:** until those modules bind the port the guard only protects HR's own references; this is a forward dependency, not a defect.

| Sensitive profile detail (writes an audit row) | `hr.employees.view` **and** `hr.employees.view_sensitive` |
| Create, update a profile (all fields, sensitive included) | `hr.employees.manage` |
| List, expiring-documents (non-confidential) | `hr.documents.view` |
| Same, confidential documents | `hr.documents.view` **and** `hr.documents.view_confidential` |
| Download a document | the tier of the document, as above |
| Document `notes` in the detail | `hr.documents.view` (and tier) **and** `hr.employees.view_sensitive` |
| Add, update, delete a document | `hr.documents.manage`, and the tier of the document for update and delete; `hr.documents.view_confidential` additionally to declassify |
| Anything, with no employee link | refused `not_permitted` |

Writing sensitive fields needs only `hr.employees.manage` (D-13): a person who maintains records may need to type an ID number without being allowed to read it back.

## Out of scope

- **Any front end or HTTP screens** (FP-273). The thin routes of section J exist so the screens can be built; no screen, no menu, no form.
- **Salary, pay and statutory data:** `basic_salary`, `salary_structure_id`, `pay_frequency`, `commission_plan_id`, `is_sales_person`, `tax_id_no`, `epf_no`, `etf_no` (FP-280 and payroll tasks); **bank accounts** (`employee_bank_accounts`); **employment history** (`employment_history`); `default_location_id`; `photo_path` and photographs (D-5).
- **Attendance, shifts, leave, holidays, overtime** (FP-271, FP-272), including any automatic effect of `resignation_date` or `last_working_date` on the access `status` (D-28).
- **Creating, renaming, suspending or granting access to an employee** and any change to `employees`: those are T-010's operations. HR never writes an identity column, a PIN or a permission.
- **Cost centre linkage** (`departments.cost_centre_account_id`, D-6).
- **Enabling the workflow approver types** `manager_of_requester`, `department_head`, `branch_manager` (FP-358). A branch-manager data source does not exist and is not invented here.
- **Notifications and reminders** (document expiry, probation end).
- **Hard deletion, purge and data-subject erasure** of profiles, documents or stored files; retention schedules (D-31).
- **Column-level application encryption** of sensitive fields, malware scanning of uploads, optical character recognition, document versioning, signatures, templates, bulk import and export, e-signature.
- **Self-service** by the employee (read or edit own profile or documents) (D-14).
- **A cloud or object store implementation** of `DocumentStore`; only the interface and a local-disk implementation are built.
- **Default catalogues** of departments, designations or levels (D-26).
- **Plugin-contributed HR fields** (FP-213 era) and `custom_fields`.

## Non-functional requirements

- **Security and privacy.** Sensitive fields: AC-50 to AC-64. Document storage root outside web paths; server-generated keys with a tenant segment; no client-supplied path ever reaches the store; stored files never executed or served inline; checksum verified on read. Every refusal discloses only a reason code. Confidential documents are invisible (not "forbidden") to a holder of only the plain key (AC-72).
- **Auditability.** Eighteen declared actions, redacted values, sensitive reads audited (section I).
- **Determinism.** Time from the injectable clock; no criterion sleeps.
- **Performance.** No figure was given and none is invented. Bounds that protect the system are stated: page size 1 to 200, tree depth 10, reports chain walk 50, direct reports contract 1000, 100 documents per employee, default 10 MiB file. All are configuration except depth and the walk bound.
- **Concurrency.** Checks that need atomic guarantees (name uniqueness, cycles, document limit, profile create) are application checks plus the primary and unique keys the schema gives; concurrent proofs are **[ENGINE]** (AC-18, AC-29, AC-57, AC-80).
- **Accessibility.** None (no interface).
- **Data.** Soft delete only; no tenant column; no row hard-deleted.

## Open questions

None is BLOCKING. Every one was decided by `ba` under the TEAM PROTOCOL and logged. Items 1 to 9 are **owner-visible** with built-in defaults (also repeated in the decisions file); item 10 is for `architect`.

1. **Owner.** Should HR facts live on a separate profile row (default, D-1) or as extra columns of `employees` as `docs/database.md` prints? Default: separate row. Moving them later is a contract-phase migration.
2. **Owner.** Who may read personal data? Default: only holders of `hr.employees.view_sensitive` (with `hr.employees.view`), which `owner` has by data; HR managers can write but not read it back unless granted (D-12, D-13).
3. **Owner.** Should an employee be able to see their own profile and documents? Default: no (D-14).
4. **Owner.** Should reading personal data be recorded? Default: yes, one audit row per sensitive detail read and per document download, no values (D-15 / AC-90).
5. **Owner.** Should sensitive columns be encrypted by the application, not only protected by access control and platform disk encryption? Default: no (D-16). Search and backups are simpler; the risk is a database dump exposing plain text.
6. **Owner.** Retention and erasure of staff personal data: this task keeps everything (soft delete only, files retained, no purge). If a data-protection law applicable to the shop requires erasure on request or after a period, that needs its own task (D-31).
7. **Owner.** Uploaded file rules: 10 MiB maximum, PDF, JPEG and PNG only, 100 documents per employee, no malware scan (D-9, D-34). Which file types and size does the shop need? Is a virus scan required before the screens ship?
8. **Owner.** Should a national ID number (NIC) be unique per shop and format-checked? Default: neither (D-30); the format is country-specific and a wrong rule blocks real hires.
9. **Owner.** Deleting an employee who heads a department or has direct reports is refused until that is reassigned (D-35). Is that wanted, or should deletion always succeed and leave the department headless?
10. **-> architect.** (a) Confirm the sidecar placement (D-1) and the `docs/database.md` annotation owed. (b) How HR obtains identity data for lists (code, names, status, soft-delete) through access's published contract without a table read, and whether that contract needs additive reads (D-17). (c) How HR declares its eighteen audit actions to the writer (D-36). (d) Where the `DocumentStore` interface lives so a later module (expense attachments, leave documents) can reuse it without importing HR (D-9). (e) The guard for AC-85 needs an interface in access; confirm it is additive. (f) Whether the usage ports (AC-86) and the read contract (AC-82) share one registration point.

## Assumptions

- `employees` is the only identity table; an HR employee **is** an access employee (same id); an access employee may have no profile (a cashier).
- T-010, T-014 (branches), T-017 (audit writer) and T-021 (API foundation) are on the base; the worktree base contains their code.
- Cost centre, bank, salary and history tables are built by later tasks; this task builds nothing they need beyond stable ids.
- Soft-deleted rows count as absent everywhere (as T-009 and T-010).
- File storage root and the tenant segment are server configuration; the frontend never names a path.
- Numbers (page sizes, depth 10, 10 MiB, 100 documents, 50-step walk, 1000 reports) are conventional, not owner-specified, and configurable except where stated.
- Anything needing history (which tests were edited, commit order) is for `qa`; `ba` has no shell and no history. The worktree has no `docs/specs/` of its own for T-010 and T-032; those specs were read from the main checkout.
