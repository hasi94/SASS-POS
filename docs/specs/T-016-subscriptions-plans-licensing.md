# T-016: Subscriptions, plans and licensing

Backlog: FP-210. Decisions: `docs/decisions/T-016-subscriptions-plans-licensing.md` (D-1 to D-21, cited below as "D-n"). Branch `ai/T-016-subscriptions-plans-licensing`. Plan: `docs/plans/T-016-subscriptions-plans-licensing.md` (14 steps); this revision folds in `architect`'s plan-time rulings, relayed by the lead.

## Problem / goal

FP-210: "Plan limits actually enforced, subscription status gating access, feature flags per tenant."

T-008 shipped the master tables this task runs on — `plans`, `plan_features`, `plan_limits`, `subscriptions`, `licences`, `feature_flags`, `tenant_feature_flags` — migrated and empty (T-008 AC-11). T-009 built login and tenant selection and already gates both on `tenants.status` (D-8 of that task: the selectable set is `trial`, `active`, `past_due`). Nothing today reads `plans`, `subscriptions`, `licences` or either flag table, nothing enforces a limit, and nothing keeps a subscription's billing state and the tenant's commercial state in agreement. This task makes those four tables mean something: a plan's limits actually stop a tenant creating more of a resource than it is entitled to, a subscription's lifecycle drives the tenant status T-009 already gates on, a licence row (where one exists) can withdraw entitlement independently of billing, and a feature flag resolves to one effective answer per tenant that other modules can call.

It must be provable on the SQLite stand-in while the MySQL/MariaDB engine hold (`ENGINE_HOLD`) is on; anything that genuinely needs a real engine is marked **[ENGINE]**, same convention as T-008/T-009/T-010/T-014.

## Users affected

- Every tenant whose shop now has a plan, a subscription and (optionally) a licence — enforcement changes what they can create and whether they can sign in, without them taking any new action.
- Platform operators / billing staff, who change a tenant's plan or subscription state and expect the tenant's access to follow without a manual second step.
- Developers of other modules (branches, employees, terminals, catalog, …), who need one place to ask "does this tenant's plan allow one more of X" and one place to ask "is feature Y on for this tenant".
- Not affected directly: cashiers/waiters with no master login (T-009 D-18 family) — plan and licence gating is evaluated at the master/tenant-selection boundary, never at the till.
- Upstream: FP-207 (T-009, done) built the login/tenant-selection gate this task plugs into. FP-209 (T-014, done) explicitly deferred plan-limit enforcement for branches, locations and terminals to this task (T-014 D-25).
- Downstream: any later module (catalog/Phase 1 onward) that wants a plan limit or a feature flag uses the resolver this task builds rather than inventing its own.

## Current behaviour

- `plans`, `plan_features`, `plan_limits`, `subscriptions`, `licences`, `feature_flags`, `tenant_feature_flags` exist (T-008 migrations) and hold zero rows on a freshly migrated master; nothing seeds them.
- `tenants.plan_id` exists as a direct column on `tenants` (master ERD, `docs/database.md` §4.1) **and** `subscriptions.plan_id` exists on the `subscriptions` row for the same tenant (§4.2) — two columns carrying what should be the same fact, resolved in D-11 below.
- `tenants.status` already gates login and tenant selection (T-009 AC-12, AC-14, D-8): selectable for `trial`, `active`, `past_due`; not selectable for `pending`, `provisioning`, `suspended`, `read_only`, `closed`, `archived`. T-009 deliberately left subscription and licence checks out of scope (its own "Out of scope" list names FP-210 by number).
- `subscriptions.status` is a separate enum (`trial, active, past_due, paused, cancelled, expired`) that today has no relationship to `tenants.status` in any shipped code — nothing updates one when the other changes.
- No resource-creation code (branches, locations, terminals — T-014; employees — T-010) reads `plan_limits`, counts anything against it, or refuses a request on that basis (T-014 D-25, explicit deferral to this task).
- `tenant_usage_metrics` is designed in `docs/database.md` §4.2 as a nightly, per-tenant-database collector feeding reporting, but **`architect` found it was never actually built in T-008** — there is no such table in the shipped migrations, only the design document's description of one. AC-4 below is corrected for this (D-18); it is a documentation/reality gap, not something this task is asked to fix.
- No code reads `feature_flags`, `plan_features` or `tenant_feature_flags`; no module declares a flag key.
- No code reads `licences`.
- `subscriptions` has no column recording when its `status` became `past_due`; that timestamp is needed for the grace-period clock (AC-11, AC-16) and does not exist anywhere else to read it from (D-13).

## User stories

- As a platform operator, I want a tenant's plan to actually cap how many branches, locations, terminals and employees it can create, so that a shop on a small plan cannot silently use enterprise-tier resources.
- As a platform operator, I want a tenant whose subscription lapses to lose selectable access automatically, so that I do not have to remember to suspend them by hand.
- As a shop owner on a paid plan, I want my shop to keep working through a short billing hiccup, so that a late card does not stop me serving customers mid-day.
- As a platform operator, I want to grant or withdraw one feature for one tenant without changing their plan, so that I can run a pilot or handle a support exception.
- As a module developer, I want one call that tells me whether a feature is on for the current tenant, so that I do not reimplement the plan/override precedence myself.
- As a platform operator, I want a licence that is separate from billing to be able to withdraw a specific entitlement (e.g. a module) even while the tenant's subscription is paid up, so that licensing and billing can be managed independently when the business needs that split.

## Acceptance criteria

Conventions, following T-009/T-010/T-014: provable on the SQLite stand-in unless marked **[ENGINE]**, in which case it is deferred under the engine hold, not skipped. Time is the injectable clock already used by T-009 (D-22 there); no criterion sleeps. Where a criterion asserts an absence, its positive control is named in the same criterion.

### Plan limits — enforcement

- AC-1: Given a tenant on a plan whose `plan_limits` row for `employees` is 5, and the tenant already has 5 active (non-soft-deleted) employees, When a request creates a 6th, Then it is refused with a response naming the limit reached (e.g. `plan_limit_reached`, key `employees`) and no row is created. Control: the same request when the tenant has 4 employees succeeds.
- AC-2: The same shape as AC-1, independently, for `branches`, `locations` and `terminals` against each one's own `plan_limits` row (closes T-014 D-25). Each has its own positive control (one below the limit succeeds). Creating a branch also checks the `locations` limit, in addition to `branches`, because branch creation creates that branch's `branch_store` location as part of the same operation (`docs/database.md` §6.1: "every branch gets one `branch_store` location at provisioning") — one user action, two resources, two limits, both checked before either is created (D-20).
- AC-2a: Reactivating a soft-deleted or deactivated `branch`, `location`, `terminal` or `employee` is checked against that resource's plan limit exactly as creating a new one is (D-20) — it is the mirror case of AC-6's "deactivating frees quota": reactivating spends it again. Control: with the limit already at capacity from active rows alone, reactivating one more deactivated row is refused the same way a fresh creation would be.
- AC-3: Given a tenant's plan has **no** `plan_limits` row for a given key (e.g. a plan that does not cap `terminals`), Then creation of that resource is never refused on plan-limit grounds, however many already exist. Control: the same tenant moved to a plan that does carry a `terminals` limit is refused once at that new limit.
- AC-4: Given the limit count, Then it is a live count of the tenant's own rows at the moment of creation (e.g. `COUNT(*)` on that tenant's `branches`), never a value read from a usage-metrics table (D-3). **Correction (D-18): `tenant_usage_metrics` does not exist — it is documented in `docs/database.md` §4.2 but was never built in T-008.** Proof of "never the source of a refusal" is therefore a source scan (no code path in this task's handlers reads a metrics table at all) plus a live-count control (a fixture with no metrics table present — because none exists — still enforces correctly from the live count), not a "stale metrics row" fixture as originally worded.
- AC-5: Given the limit *value* (the number itself, from master `plan_limits`), Then resolving it for a tenant request never performs a live cross-database read from the tenant request path. **Mechanism (D-15):** one cached snapshot per tenant, read from the master once and cached for 300 seconds, cleared whenever this task's own code writes a value that changes the limit (a plan change, a `plan_limits` edit), mirroring the existing `tenant:conn:<tenant_id>` cache pattern T-008/§4.4 already uses for the connection mapping. Tests exercise it through the same stand-in config switch already used for the tenant-mapping cache, so no real cache backend is required to prove it on the stand-in. A master outage during normal operation does not stop a tenant creating a branch it was already entitled to create a moment before (mirrors T-014 D-25's concern about coupling branch creation to master availability).
- AC-6: Given a plan change that **lowers** a limit below the tenant's current count (e.g. moved from a 10-branch plan to a 5-branch plan with 7 branches already active), Then existing rows over the new limit are **not** deleted, deactivated or otherwise touched, and creation of a further row of that type is refused until the count is strictly **below** the new limit (D-17: a count exactly equal to the limit is still "at capacity" and still refused, matching AC-1's own "5 existing refuses a 6th" rule — "at or under" was wrong wording, corrected here). Control: with the limit at 5 and 7 branches active, deactivating **three** (down to 4, strictly below 5) is required before a new branch is accepted; deactivating only two (down to 5) must still refuse.
- AC-7: `plan_limits.limit_key` values `products`, `monthly_sales`, `storage_mb` and `api_calls_per_day` are **not** hard-enforced by this task (D-4): no catalog table exists yet for `products`, and the other three are continuously-varying metrics with no realtime metering path built (and, per AC-4's correction, no metrics table exists at all today). Stated here so QA does not file their absence as a defect.
- AC-8: Given the `users` limit key (seats on the master side, `tenant_users` rows for a tenant, not tenant employees), Then the check is proved at whatever single creation path exists today for a new `tenant_users` row, not end-to-end through an invite or access-grant flow — **neither exists yet** (D-19). This count is a master-local query (no cross-database read), consistent with D-3. QA should not expect, and must not file as a defect, the absence of an invite/access-grant handler to test this against; that handler belongs to whichever task builds invitations.

### Subscription status driving tenant status

- AC-9: Given a tenant's subscription transitions to `cancelled` or `expired`, Then in the same write `tenants.status` is set to `suspended` with `suspension_reason` recorded as a sentinel this task owns (e.g. `subscription_lapsed`), distinct from any reason an operator would type by hand (D-1, D-2, D-16), so the next login sees it through T-009's existing, unmodified selectable-set logic (no second gate is added at login — T-009's AC-12 continues to be the only runtime check).
- AC-10: Given a tenant's subscription transitions to `active` from `trial`, `past_due` or `paused`, Then in the same write `tenants.status` becomes `active` (unless it is already `closed`, `archived`, `pending` or `provisioning`, none of which this task's reconciler ever touches in either direction — D-1, D-16). Control: a tenant already `closed` whose subscription is reactivated stays `closed` until an operator explicitly reopens it.
- AC-10a: **The reconciler never lifts a suspension it did not itself impose (D-16).** Given a tenant was moved to `suspended` by an operator directly (any `suspension_reason` other than this task's own sentinels, e.g. `subscription_lapsed`, `licence_lapsed`, `past_due_grace_expired`), When that tenant's subscription later turns `active`, Then `tenants.status` stays `suspended` — the reconciler only reverses a suspension whose `suspension_reason` is one of its own sentinel values. Control, in the same test: a tenant suspended **by this task** for `subscription_lapsed` is returned to `active` once its subscription is `active` again, so the asymmetry is between the two causes, not a blanket refusal to ever reactivate.
- AC-11: Given a subscription transitions to `past_due`, Then `subscriptions.past_due_at` is set to the clock's now (D-13) and `tenants.status` becomes `past_due` — still selectable per T-009 AC-12, so a shop keeps working through a billing hiccup (matches the user story). Given it stays `past_due` for longer than the configured grace period, measured from `past_due_at`, Then `tenants.status` becomes `suspended` with `suspension_reason = past_due_grace_expired` (D-12: default 7 days, configurable via `platform_settings` key `billing.past_due_grace_days`). **Mechanism (D-14): this transition is evaluated by a scheduled job that runs every minute, not inline at login or any other request** — editing T-009's three reviewed login/selection/refresh handlers to add a time check was rejected. Consequence, stated so QA does not file it as a defect: a production tenant can remain selectable for **up to one minute** past the grace deadline, bounded by the job's own cadence. Test proof uses a fixed injectable clock and invokes the job directly, not a real one-minute wait; one second before the deadline the job leaves the tenant alone, at and after the deadline it suspends (same boundary-inclusive convention as T-009 AC-19).
- AC-12: Given a subscription transitions to `paused`, Then `tenants.status` becomes `read_only` (selling stops, matching the existing `read_only` semantics T-009 already treats as not selectable for write access — D-1's intent is to reuse existing states, not invent a new one).
- AC-13: Given a tenant with **no** `subscriptions` row at all (not yet billed, or a fixture predating this task), Then nothing in this task changes `tenants.status` on its own; the tenant's status is whatever it already was, and `tenants.plan_id` (if already set) is left as-is rather than cleared (D-11, informational: `architect`'s plan treats a pre-existing `tenants.plan_id` with no subscription row as the fallback display value until a subscription exists). Control: giving that same tenant its first subscription row at `active` sets `tenants.status` to `active` once.
- AC-14: Given more than one `subscriptions` row exists for a tenant (history is kept, never overwritten — §4.2 has no uniqueness constraint on `tenant_id`), Then the "current" subscription for every rule in this section is the row with the latest `current_period_start`, ties broken by the highest `id`. Proof: a fixture with three historical rows and one current row only reacts to the current one. A null `current_period_start` (a subscription not yet started) sorts behind every row that has one (informational, `architect`'s judgment call, not a spec change).
- AC-15: `tenants.plan_id` is a denormalised mirror of the current subscription's `plan_id` (D-11): any write that changes the current subscription's plan updates `tenants.plan_id` in the same transaction, and nothing else is ever allowed to write `tenants.plan_id` directly. **One class is the sole writer of `tenants.plan_id` and a separate class is the sole writer of `tenants.status`, both invoked inside the same transaction as the triggering subscription/licence write (D-16)** — named here as the structural rule a reviewer checks by diff, not a runtime-observable control. Control: a direct write to `tenants.plan_id` or `tenants.status` bypassing those two classes is the thing a future reviewer should reject on sight.
- AC-16: Given the grace-period clock of AC-11, Then it is the injectable clock, and the elapsed time is measured from `subscriptions.past_due_at` (D-13; not from `current_period_end`, which may predate it, and not read back from `platform_audit_logs`, which `architect` rejected as a source because SQLite and MySQL/MariaDB disagree on JSON query behaviour), so a tenant whose grace period started yesterday is unaffected by today's clock tick alone.

### Feature flags

- AC-17: Given a `feature_flags` key with `default_enabled = true` and a tenant with no `plan_features` entry for it and no `tenant_feature_flags` override, Then the flag resolves enabled for that tenant. Given `default_enabled = false` under the same conditions, Then it resolves disabled. (D-5, baseline of the precedence ladder.)
- AC-18: Given the same flag has a `plan_features` row for the tenant's plan with a boolean value, Then that value overrides the global default (D-5). Control: changing the plan to one without that `plan_features` row falls back to AC-17's default.
- AC-19: Given the same flag additionally has a `tenant_feature_flags` row for this specific tenant, Then the tenant row overrides the plan's value, which overrides the global default — all three layers exercised in one fixture so the precedence order itself is the thing under test, not just the top layer (D-5; `docs/database.md` §4.2 already states "Overrides the plan" for this table, so the ladder is not invented here, only implemented).
- AC-20: Given a `plan_features.value` that is a JSON object rather than a bare boolean (the column is typed `JSON` to also carry a config value, e.g. a numeric cap), Then the resolver returns the value as-is for non-boolean flags, and a module asking "is this on" treats a non-boolean, non-empty value as enabled (documented here as the only interpretation rule this task adds; a flag's own meaning for its JSON shape is that flag's owning module's business).
- AC-21: Given a `feature_flags` key that does not exist, When anything resolves it, Then the resolution is a programming error the resolver refuses loudly (an exception/false return distinguishable from "resolved disabled") rather than silently reading as disabled — so a typo'd flag key is caught rather than quietly behaving like an off switch. Control: a real key resolves normally in the same test.
- AC-22: One resolver call signature is the only way any module reads flag state in code written by this task (D-9): no module-local re-implementation of the three-layer precedence. Evidence is the diff: exactly one place computes the ladder.
- AC-23: This task builds the resolver and does **not** add route-level or feature-level gating to any existing module's endpoints (D-9) — no shipped feature today is named as flag-gated by any other module, so there is nothing yet to gate. Stated so QA does not look for a gated route that was never asked for.

### Licences

- AC-24: `licences` and `subscriptions` are distinct concepts (clarified for the record, not invented): a subscription is the billing relationship driving `tenants.status` (AC-9 to AC-16); a licence is a separate, optionally-present entitlement grant with its own `status` (`active`, `expired`, `revoked`, `suspended`) and validity window (`valid_from`/`valid_until`), independent of billing — the schema's own detached `signature` column exists so a licence can be verified without reaching the master database at all (§4.2), which a subscription row, tied to ongoing billing, structurally cannot be.
- AC-25: This task enforces `licences.type = 'platform'` rows only (D-6). Given a tenant has an active, unexpired `platform` licence, Then nothing changes (it is purely corroborating evidence today). Given a tenant has a `platform` licence whose `status` is `expired`, `revoked` or `suspended`, or whose `valid_until` has passed, Then `tenants.status` becomes `suspended` with `suspension_reason = licence_lapsed` (distinct from `subscription_lapsed`, so operators are not left guessing which one caused it, D-16). `status IN (revoked, suspended)` is checked whenever the licence is read; `valid_until` passing is checked by the same one-minute scheduled job as AC-11 (D-14), with the same up-to-one-minute lag stated as accepted, not a defect. Control: a tenant with an unexpired licence and a lapsed subscription is suspended for the subscription reason only, and (AC-10a) neither this nor AC-9's suspension is ever lifted except by the same cause reactivating.
- AC-26: Given a tenant has **no** `licences` row of type `platform` at all, Then this is not a restriction: absence of a platform licence is treated as licensed, not as a fail-closed refusal (D-7) — there is no provisioning step yet (FP-206 is still blocked by the engine hold) that would create one for every tenant, and failing closed with no seed path would lock out every tenant that exists today. Control, in the same test: giving that tenant an expired platform licence does suspend it, so the absence case is a deliberate "no row" branch, not a broken check that happens to pass.
- AC-27: `licences.type IN ('plugin', 'module')` is **not** enforced by this task (D-6): no plugin or module install/enable mechanism exists yet for such a licence to attach to (Phase 0's "Plugin framework" roadmap item and the whole `plugins`/`plugin_versions`/`tenant_plugins` machinery are unbuilt). Stated so QA does not look for plugin-licence enforcement that has nothing to gate.

## Non-functional requirements

- **Availability.** No enforcement path this task adds may make a tenant-scoped write depend on a live read of the master database at request time (D-3, D-5; mirrors T-014 D-25's concern directly).
- **Consistency.** Subscription/licence-driven changes to `tenants.status` are transactional with the triggering write (AC-29), never eventually-consistent via a queue or a nightly job. Time-based transitions (grace-period and licence expiry, AC-11/AC-25) are the one deliberate exception: they are evaluated by a one-minute scheduled job rather than at the moment the deadline passes (D-14), so a sub-minute lag is accepted there and nowhere else.
- **Determinism.** Time is the injectable clock already established by T-009 D-22; the grace-period boundary (AC-11) is inclusive/exclusive the same way T-009's lockout boundary (AC-19) is, so both sides of the boundary are testable without sleeping, by invoking the scheduled job directly in tests rather than waiting for it.

## Assumptions

- The four limit/flag/licence tables and their columns are exactly as T-008 shipped them (`docs/database.md` §4.2), **with two corrections found at plan time**: `subscriptions` gains a new nullable `past_due_at` column this task's own migration adds (D-13, AC-11), and `tenant_usage_metrics` — described in §4.2 but never actually migrated in T-008 — does not exist (D-18, AC-4). Where a limit this task's own stories wanted had no supporting column (`products`, the three continuous metrics), the gap is recorded as a scope decision (D-4), not papered over.
- "Current subscription" (AC-14) and the plan/limit resolution timing (AC-5) are conventional choices with no owner specification, logged as decisions (D-11, D-15) per the TEAM PROTOCOL rather than left as open questions.
- The grace period default of 7 days (AC-11, D-12) is a conventional industry default, not an owner figure; it is configurable from day one specifically because it is a guess. It is enforced on a one-minute cadence (D-14), not instantaneously.
- A manually-imposed suspension (any `suspension_reason` not one of this task's own sentinels) is never auto-lifted by this task's reconciler; only a suspension this task itself caused is reversible by the same cause reversing (D-16, AC-10a).
- Figures and shipped behaviour attributed to T-008, T-009 and T-014 above (table lists, AC numbers, D-numbers) were read from those tasks' own specs and decisions, not re-derived from code. Rulings attributed to `architect`'s plan (the new column, the scheduled job, the cache mechanism, sole-writer classes, the AC-6/AC-4/AC-8 corrections, the counting rules, the no-HTTP-surface scope) were relayed by the lead, not independently re-derived by `ba` from the plan document itself.
