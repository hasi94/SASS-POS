# T-014: Branches, warehouses, terminals

Backlog: FP-209 (carries the three branch foreign keys T-010 left opaque, and the T-010 D-39 PIN-reset prerequisite; closes the FP-309 fold). Decisions: `docs/decisions/T-014-branches-warehouses-terminals.md` (D-1 to D-45, cited below as "D-n"; T-010's are "T-010 D-n", T-009's "T-009 D-n", T-011's "T-011 D-n"; D-31 to D-45 record the architect's rulings in `docs/plans/T-014-branches-warehouses-terminals.md` section 0, which this spec now agrees with). Branch `ai/T-014-branches-warehouses-terminals`, cut from the T-011 tip. Criteria: AC-1 to AC-64.

**Tagging.** Every criterion is verifiable on the SQLite stand-in unless it carries **[ENGINE]**. An [ENGINE] criterion needs a real MySQL or MariaDB; while the engine hold stands, `qa` records it **NOT VERIFIED** with its reason and offers no green stand-in run for it. `(diff)` marks a criterion decided by reading the change, not by running code.

## Problem / goal

FP-209: "Organisation structure, terminal activation and revocation, devices, settings hierarchy." T-010 shipped who may do what, scoped to branch ids that are opaque `CHAR(26)` values with nothing behind them (T-010 D-1). This task creates, **inside each tenant database**, the things those ids name: branches, the locations stock will live in (including warehouses), the terminals a branch hosts, the devices behind them, the activation and revocation of a terminal, and the settings hierarchy that resolves a value for a terminal, a branch or the company. It then ships the foreign keys that make the branch ids real, as a contract-phase migration (possible since T-011), and closes the one security gap T-010 D-39 made a blocking prerequisite: anybody holding `employees.set_pin` can set the owner's PIN.

**This is tenant-database work.** No table here has a `tenant_id` column and no tenant-table query is scoped by tenant; the database is the boundary. The one master-database touch is the terminal's refresh-token family (`refresh_tokens`, principal type `terminal`, which T-009 left for this task).

## Users affected

- **Owner and shop administrators**: create branches, warehouses and terminals; issue activation codes; revoke a lost device; set options per company, branch or terminal.
- **Terminal (till device)**: activates itself once with a code, then refreshes its own token and reads its settings. It is a machine principal, not a person.
- **HR users holding `employees.set_pin`**: lose the ability to set the PIN of a more privileged colleague.
- **Later tasks**: FP-250 and FP-251 (stock per location), FP-216 (cross-tenant isolation suite), FP-241 (suspension reaching a till), FP-206 (provisioning seeds the first branch), the till app.

## Current behaviour

- No `branches`, `locations`, `terminals`, `devices` or `terminal_credentials` table exists. The tenant tree ends at T-010's tables and T-011's `settings.updated_by` key.
- `employee_roles.branch_id`, `employee_permissions.branch_id` and `employee_branches.branch_id` are unguarded `CHAR(26)`; `number_sequences.branch_id`, `audit_logs.branch_id`, `outbox_events.branch_id`, `access_log.branch_id` and `access_log.terminal_id` likewise. T-010 AC-31, AC-32 and AC-35 accept a well-formed branch id that names nothing.
- `settings` and `settings_registry` exist (T-008) with no resolution logic and no route.
- There is no terminal identity and no terminal token. `refresh_tokens.principal_type` allows `terminal` but only `user` is written (T-009 D-17 deferred "terminal tokens and the activation code").
- `PUT /api/v1/access/employees/{employee}/pin` lets any `employees.set_pin` holder set any employee's PIN. No route verifies a PIN (T-010 AC-49), so this is latent.
- `BranchScope` accepts a lower-case ULID (FP-309).

## User stories

- As an owner, I want to create branches and give each its own store location, so that a shop with several sites has a place for each.
- As an owner, I want warehouses that belong to a branch or to nobody, so that central stock is not forced into a shop.
- As an administrator, I want to create a terminal and get a one-time activation code, so that a new till can be enrolled without sharing a password.
- As a till device, I want to activate once with that code and then keep my session fresh, so that the shop can sell without a person signing the device in.
- As an owner, I want to revoke a terminal and have it stop working at once, so that a lost or stolen tablet is harmless immediately, not after its token expires.
- As an administrator, I want to set a value for the whole company, then override it for one branch or one terminal, so that each till behaves as that shop wants.
- As an owner, I want assurance that no lesser colleague can set my PIN, so that a cashier-level HR user cannot take over my identity.
- As a developer of later modules, I want branch ids to be real, so that a branch-scoped right or a numbering sequence cannot point at nothing.

## Data this task stores

New tenant tables, each with `id` a 26-character upper-case ULID unless stated, created and updated timestamps, and **no `tenant_id`**. Columns not listed are not created (D-10).

## Acceptance criteria

### A. Schema and the branch foreign keys

- AC-1 (shape): Given the tenant tree run to its end, When the live columns of `branches`, `locations`, `terminals`, `devices` and `terminal_credentials` are listed, Then each holds exactly the columns of "Data this task stores", none has a `tenant_id`, and none has `terminals.settings`, `terminals.invoice_prefix`, `terminal_credentials.secret_hash`, `branches.cost_centre_account_id` or any `[CF]` column (D-10, D-24). Control: a fixture table with one extra column, and one with one missing column, are each reported.
- AC-2 (constraints): Given the new tables, Then `branches.code` and `locations.code` are unique, (`terminals.branch_id`, `terminals.code`) is unique, a second `terminal_credentials` row for one terminal is refused, `terminals.branch_id` and `terminals.location_id` refuse an unknown id, and `locations.branch_id` refuses an unknown id but accepts null. A soft-deleted row (fixture) still holds its code. Controls: a distinct code, a different branch's same terminal code, and a null-branch location are each accepted.
- AC-3 (the four keys): Given the keys are in place, When a row is inserted **directly** into each of `employee_roles`, `employee_permissions`, `employee_branches` and `number_sequences` with a non-null `branch_id` that matches no `branches.id`, Then the insert is refused; with an existing branch id it is accepted; for the three tables whose `branch_id` is nullable (`employee_roles`, `employee_permissions`, `number_sequences`) a null is accepted. Control per table: the same insert before the key existed is accepted, shown on a fixture at the previous step. (D-1, D-2.)
- AC-4 (phase and ordering): Given the new migrations, Then the table-creating ones (one table per file) declare phase `expand`, **one** foreign-key migration declares `contract` and holds all six keys (the four of AC-3 plus `branches.default_location_id` -> `locations.id` and `terminals.current_device_id` -> `devices.id`, D-31, D-32), it sorts after every migration that creates a table it keys, and the static phase rule and the planner accept it. Given a fleet behind the version before the first key, Then the planner refuses a single run containing the key step and prints the two-run remedy (T-011 behaviour, no new rule here); a production fleet at the T-011 tip needs exactly two runs. Given a **fresh** tenant and a tenant seeded with T-010 data (employees, assignments, attachments) at the T-011 tip, When each is migrated to the end, Then both succeed and the seeded rows are unchanged.
- AC-5 (data-clean pre-check, each key; the two circular keys of AC-4 get the same pre-check on `default_location_id` and `current_device_id`; the migration runs every pre-check before it alters anything, D-31): Given a tenant whose `<table>.branch_id` holds a non-null value matching no `branches.id`, When that key migration runs, Then it refuses **before altering anything**, the message names the table, the column and the **number** of offending rows and **no value from the data**, the table and every row are unchanged, no value is deleted, nulled or repaired, and a second tenant in the same run still migrates (the failing tenant fails alone). After the data is corrected, re-running succeeds. Controls: a clean tenant and a tenant whose column is all null pass; a lower-case spelling of an existing upper-case id counts as offending (exact comparison, D-7).
- AC-6 [ENGINE]: Given a real MySQL or MariaDB tenant database, Then each key is added and enforced the same way as AC-3, the pre-check returns the same offending set as on the stand-in, and the pre-check statement has no engine-specific branch (shown by reading it). NOT VERIFIED while the hold stands.
- AC-7 (restrict): Given a branch referenced by any of the four keyed tables, When its row is deleted directly, Then the delete is refused. Control: an unreferenced branch row can be deleted directly (fixture), proving the refusal comes from the key.
- AC-8 (diff): No already-shipped migration file in the tenant tree is edited (their checksums move); the three T-010 docblocks that say "FP-209 owes its foreign key" and the baseline docblocks that say "owed" are left as written, and the new migrations' docblocks say where the key was delivered.
- AC-9 (deferred columns): Given `audit_logs.branch_id`, `outbox_events.branch_id`, `access_log.branch_id` and `access_log.terminal_id`, Then after this task they still carry no foreign key (D-2), and the lead is told a follow-up row is owed (report item). Control: the schema-shape test that lists unguarded columns names exactly these four.

### B. Branches

- AC-10 (create): Given an actor holding `branches.manage`, When they create a branch with valid input, Then one `branches` row exists with a 26-character upper-case ULID, `is_active` true, the folded-upper-case code; **exactly one** `locations` row of type `branch_store` exists for it with the D-11 defaults, `branch_id` = the new branch, and the **branch's code and name** as its own (D-39); if a location already holds that code, creation is refused `validation` and neither row is written; `branches.default_location_id` equals that location; one `audit_logs` row records it (AC-20); the response carries the ids. The two inserts are one unit: Given the location insert is made to fail (fault injection), Then no branch row exists. Control: without `branches.manage` nothing is written.
- AC-11 (create, invalid input): Given each of: blank or missing `code`, `name`, `timezone` or `currency`; a `code` over 10 characters, with a character outside `A-Z`, `0-9`, `-` after upper-casing, or already used (including by a soft-deleted row); a `name` over 100 characters; a `timezone` that is not an IANA zone; a `currency` that is not three letters; an invalid `email`; a `business_type` that is not null or one of `retail`, `restaurant`, `both` (D-39; also on update, AC-12); a non-string where a string is required; `is_active`, `default_location_id`, `id` or `deleted_at` supplied, When create is attempted, Then `validation` and **no** `branches` and no `locations` row. Controls: a 10-character code, `a1-b` (folded to `A1-B`) and `Asia/Colombo` with `LKR` are accepted.
- AC-12 (update): Given an existing branch, When `branches.manage` updates `name`, `address`, `phone`, `email`, `timezone`, `currency`, `tax_registration_no`, `business_type`, `opening_date` or `sort_order`, Then they change, `updated_at` and `updated_by` move, one audit row is written, and no employee's `perm_version` changes. A request that includes `code`, `id`, `is_active`, `default_location_id` or `deleted_at` is refused `validation` (not silently ignored) and stored values are unchanged; activation state changes only through AC-14. Control: the same request without those fields succeeds.
- AC-13 (read): Given `branches.view`, Then the list is ordered by `sort_order` then `code`, includes inactive branches with `is_active`, excludes soft-deleted rows, returns at most the configured page size (a larger request is clamped or refused, stated), and the detail returns the fields of the table plus the default location id. A branch id that does not exist, or is a well-formed id of another tenant's branch, is `not_found`. A lower-case spelling of an existing id resolves to that branch (AC-61).
- AC-14 (deactivate and reactivate): Given `branches.manage`, When a branch is deactivated, Then `is_active` is false and one audit row is written; it is refused `has_active_terminals` while any of its terminals is `pending` or `active` (an `inactive` or `revoked` terminal does not block), nothing changing; it is refused `last_branch` when it is the only active branch, nothing changing; reactivating sets `is_active` true. Deactivating or reactivating twice is `validation` (no state to change) and writes no audit row. No employee's `perm_version` or token claims change. Controls: a branch with only a revoked terminal deactivates; with a second active branch present the first deactivates; after deactivating the terminal the branch deactivates.
- AC-15 (effect of an inactive branch): Given an inactive branch, Then creating a terminal at it, attaching an employee to it, assigning a role or per-person grant scoped to it, creating a location under it, and writing a setting scoped to it are each refused `branch_inactive` with nothing written; **reading, detaching, removing a scoped assignment and clearing a setting are not blocked** (D-6). Control: after reactivation each succeeds.
- AC-16 [ENGINE]: Given exactly two active branches, When both are deactivated by two concurrent requests, Then at most one succeeds and one active branch remains (the guard holds under concurrency, as T-010 AC-37). NOT VERIFIED while the hold stands.
- AC-17 (no deletion, domain published): Given the registered route list, Then it contains **no** route that deletes or soft-deletes a branch, location or terminal (D-4); the test prints the routes it examined (non-empty). A fixture route that deletes a branch is reported by the same test.
- AC-18 (guards): Given each branch, location, terminal and settings route in this task, Then it declares exactly one of the eight permission keys (or `authenticated_only` where stated, or is the public activation route AC-29), and a token lacking that key is refused with the same refusal T-010 guards give. A platform token, a token with no employee, and a **terminal token** are refused on every employee-permission route; the test prints the route list and key per route (non-empty). Control: an owner passes each.
- AC-19 (tenant isolation): Given fixture tenants A and B, each with a branch of the **same code** and a terminal of the same code, When the same worker answers operations for A, then B, then A, Then each result is that tenant's own; an id from A presented under B is `not_found`; no query on these tables carries a tenant predicate, and no table has the column. Control: a deliberately mis-keyed cache fixture returns A's result for B and the test reports it.
- AC-20 (audit): Given any successful branch, location, terminal or setting mutation (create, update, deactivate, reactivate, deactivate-terminal, revoke, issue or re-issue a code, set or clear a setting), Then exactly one `audit_logs` row is written with the actor, the entity, `branch_id` where one applies, before and after values, and **no activation code, hash or secret setting value** (AC-27, AC-47); a refused or no-op request writes none. Activation writes one `access_log` row of type `terminal_login` (AC-29) and no `audit_logs` row with the code.

### C. Locations and warehouses

- AC-21 (create a warehouse): Given `locations.manage`, When a `warehouse` is created with a valid code and name and either no branch or an **active** branch, Then the row exists with D-11 defaults for unsupplied flags (negative stock false), `branch_id` as given, one audit row. Refused `validation` with no row: a duplicate or malformed code (D-13), a missing name, a `branch_id` that is not a 26-character id, a flag that is not a boolean, a `manager_employee_id` naming no employee. Refused `unknown_branch` / `branch_inactive` per AC-15. Controls: a null-branch warehouse and a branch warehouse are both accepted.
- AC-22 (other types): Given a create request of type `transit`, `consignment`, `damaged`, `virtual`, or `branch_store`, or an unknown type, Then `validation` and no row (`branch_store` exists only through AC-10; the other four are FP-251's, D-11).
- AC-23 (update): Given a location, When `locations.manage` updates `name`, `address`, `manager_employee_id`, the three flags or `sort_order`, Then they change and one audit row is written. A request including `code`, `type`, `branch_id` or `is_active` is refused `validation`, nothing changing. Control: the same request without them succeeds.
- AC-24 (deactivate and reactivate): Given `locations.manage`, When a location is deactivated, Then `is_active` is false, one audit row; refused `location_in_use` when it is the `default_location_id` of an **active** branch or the selling location of a `pending` or `active` terminal; reactivation of a location whose branch is inactive is refused `branch_inactive`. Stock on hand is not checked (FP-251 must add its refusal; this is stated, not tested). Controls: a warehouse no terminal sells from deactivates; the default store of an inactive branch deactivates.
- AC-25 (read): Given `locations.view`, Then the list is ordered by `code`, filterable by `branch_id` and by `type` (an unknown type filter is `validation`), includes inactive rows with their flag, is page-clamped as AC-13, and each item shows `type`, `branch_id` (null shown as null), the flags and the manager id. Control: filtering by a branch excludes null-branch warehouses.

### D. Terminals, activation and revocation

- AC-26 (create): Given `terminals.manage`, When a terminal is created for an **active** branch with a `location_id` that is an active location of that same branch with `is_sellable_from` true (D-30), a valid code (D-13, unique within the branch) and a name, Then a row exists with status `pending`, no device, an `activation_code_hash` that is 64 hex characters, `activation_expires_at` 24 hours after the clock's now (configurable), and the response carries the plaintext activation code **once**, in the form `<tenant code>-XXXX-XXXX` using only the 31-character alphabet of D-17 as amended by D-33 (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`; `0`, `O`, `1`, `I`, `L` never appear). Refused with no row: an unknown or inactive branch, a location of another branch, a null-branch location, a non-sellable or inactive location, a duplicate or malformed code. Controls: the same code under a different branch is accepted; two terminals receive different codes.
- AC-27 (activation-code secrecy): Given a run that creates a terminal (and separately re-issues a code) whose plaintext code is captured from the one response, Then that plaintext (also URL-encoded, JSON-escaped and reversed) is absent from **every column of every table in the tenant and master databases**, enumerated from the live schema at test time with the table and column count printed (non-empty), the application log at every level, every exception message, every later response and header of every terminal and device read, `audit_logs`, `access_log`, `outbox_events`, and token claims; the stored hash is not the plaintext. Controls: the harness fed a sink that deliberately contains the code reports it, for each sink kind; a baseline run with no code proves the sentinel is not a substring of any baseline capture. A code in a **URL path or query string** on any route is not accepted (the public route takes it only in the body) and is not echoed or logged.
- AC-28 (re-issue): Given a `pending` terminal, When `terminals.manage` re-issues, Then a new code and expiry replace the old, the old code now fails activation, one audit row is written. Given a terminal that is `active`, `inactive` or `revoked`, Then `terminal_not_pending` (revoked: `terminal_revoked`), nothing changing. An expired `pending` terminal can be re-issued. Control: the new code activates it.
- AC-29 (activate, public): Given a `pending` terminal with a valid unexpired code and a request body holding the code and a fingerprint (exactly 64 **lower-case** hex characters, D-36) and optional `platform`, `browser`, `os`, `screen`, When the public activation route is called, Then in one tenant transaction: the terminal is `active`; one `devices` row exists with the fingerprint and `revoked_at` null; `terminals.current_device_id` names it; one `terminal_credentials` row is `active` with `activated_by` the employee who issued the code in force (D-20), read from the actor of the newest `terminal_created` or `activation_code_issued` audit row for that terminal (D-34; no issuer column exists, AC-1) and `activated_at` now; `activation_code_hash` and `activation_expires_at` are cleared (single use); one `access_log` row of type `terminal_login` with `terminal_id` and the caller address; `last_seen_at` is set. The response carries an access token and a refresh token (a master `refresh_tokens` row, principal type `terminal`, `principal_id` the terminal, `tenant_id` the tenant, a **new** family) and no activation code. The tenant is resolved from the code's tenant part alone, with no authentication and no database name in the request. Control: the same code presented again is refused (AC-30).
- AC-30 (one refusal): Given each of: a malformed code; an unknown tenant part; an unknown, expired or already-used code; a code of a `revoked` or `inactive` terminal; a code for a terminal whose branch is inactive; a tenant that is not active (T-009's tenant-status rules); a missing or malformed fingerprint (including an upper-case or mixed-case one, or an over-length `platform`, `browser`, `os` or `screen`); a fingerprint that is the non-revoked device of another terminal (D-16), When activation is attempted, Then the response is **byte-for-byte identical** across all of them and nothing is written to any table except what AC-31 counts. A closed reason class is written to the application log, never the code. Positive control in the same test: the correct code and a fresh fingerprint succeed, so the comparison is a refusal against a success.
- AC-31 (guessing limit): Given 10 failed attempts (any cause) for one tenant part within 15 minutes (injected clock; numbers configurable, D-18), When an 11th is made with the **correct** code, Then it is refused with the same refusal as AC-30 and the terminal stays `pending`; once the window has passed the correct code activates. The same holds for 10 failures from one caller address across different tenant parts. An unknown tenant part is counted per address and consumes no tenant-keyed state. Controls: 9 failures then the correct code succeeds; failures by another address or against another tenant do not lock this one; the counters are keyed so that two tenants never share one (tenant-isolation of the limiter, a mis-keyed fixture is reported).
- AC-32 (device rules): Given a fingerprint, Then the device row stores it exactly, a terminal never holds two non-revoked devices (a second activation of the same terminal is impossible because the code is consumed, AC-29), and a fingerprint already the non-revoked device of terminal T cannot activate terminal U until T is revoked (AC-30), after which it can. No route modifies or deletes a device (domain published, as AC-17).
- AC-33 (terminal token): Given a terminal token minted at activation or refresh, Then it carries `tenant`, `terminal_id` and `branch_ids` holding exactly the terminal's one branch id (upper-case), its type/principal is `terminal`, access lifetime 15 minutes (T-009 default, configurable); and **none** of `employee`, `all_branches`, `perm_version`, `perm_hash` is present. Control: a tenant token for an employee still carries its five employee-derived claims unchanged (T-010's claim criteria re-run).
- AC-34 (request-time authority): Given a valid, unexpired terminal token, When the terminal is `active` with an `active` credential, Then a terminal request is accepted; When the terminal becomes `inactive` or `revoked`, or its credential is `revoked`, or the terminal row is missing, Then the **next request** with the same unexpired token is refused (no waiting for expiry), and the refusal reveals no reason. Each state is its own case. Control: the same token worked before the change; reactivating an `inactive` terminal makes the same token work again.
- AC-35 (route separation): Given a terminal token, Then every route requiring an employee permission refuses it (AC-18); given a tenant employee token, Then the terminal-only routes (AC-36, AC-50) refuse it; given a platform token, both refuse it. The test prints the routes in each class (non-empty).
- AC-36 (terminal refresh): Given a valid unused terminal refresh token and an `active` terminal, When it is presented, Then a new access and refresh token are issued in the **same family**, the presented row has `used_at` set, `last_seen_at` and the device's `last_seen_at` move, and the new refresh token expires 14 days after now (T-009 AC-33). Given the same token presented again (replay), Then the generic refusal, **every** row of the family gets `revoked_at`, and a `security_events` row of type `token_reuse` is written (T-009 AC-34); control: the newest token worked immediately before the replay and fails after. Given the terminal is `inactive` (paused), Then the generic refusal, the presented token is **not** consumed and the family is **not** revoked, so after resume (AC-37) the same token refreshes (D-35). Given the terminal is `revoked`, its row is missing or its credential is not `active`, Then refusal **and** the family is revoked. Controls: the same token worked before each state change; a token refused during a pause refreshes after the resume.
- AC-37 (pause and resume): Given `terminals.manage`, When an `active` terminal is deactivated, Then status `inactive`, one audit row, and AC-34 refuses its token at once while its refresh families stay intact, including when the paused till attempts a refresh (AC-36, D-35); When an `inactive` terminal is reactivated, Then `active` and the same unexpired token works again. A `pending` or `revoked` terminal cannot be paused or resumed (`terminal_not_active` / `terminal_revoked`), nothing changing; pausing twice is `validation`. Control: the active-to-inactive-to-active round trip leaves the credential and device rows unchanged.
- AC-38 (revoke): Given `terminals.manage`, When a `pending`, `active` or `inactive` terminal is revoked, Then in one tenant transaction its status is `revoked`, the credential `revoked` with `revoked_at` and `revoked_by`, every device `revoked_at` and `revoked_by` set, the activation hash cleared, and one audit row written; **then** every master refresh family for that terminal (principal type `terminal`, that `principal_id`, that tenant) gets `revoked_at`; and the **next** request with an unexpired access token is refused (AC-34). Other terminals, other tenants' terminals with the same id (fixture), and user tokens are untouched. Control: before the revoke the same token worked.
- AC-39 (revoke is safe to repeat): Given the master step fails after the tenant step committed (fault injection), Then the terminal stays `revoked`, the response states that the session-revocation step did not complete, and AC-34 still refuses the token; When the revoke is repeated, Then it succeeds, retries the master step, and writes **no** second audit row. Repeating a completed revoke is a success with no change and no audit row.
- AC-40 (revoked is final): Given a `revoked` terminal, Then re-issue, pause, resume and activation are all refused (AC-28, AC-37, AC-30), its old activation code fails, and no operation changes its status back (the route list contains none, domain published). Control: a new terminal with the same code in a different branch, and (after the old terminal is revoked) the same fingerprint, activate normally.

### E. Settings hierarchy

- AC-44 (resolution, domain published): Given a registered key K with a registry default, Then the effective value for a terminal is the first present of: that terminal's row, its branch's row, the company row (`scope_id` null), the registry default. The test **prints** a truth table (each row names the rows present, the asked terminal and the expected value and source layer) and asserts it contains at least: only default; company only; company and branch; branch override beaten by terminal override; another branch's override ignored; another terminal's override ignored; a terminal at branch X sees X's override and not Y's; and that after the terminal row is cleared the branch value returns. **Mutation control (mandatory):** reversing the precedence (company beats terminal) turns the dataset red; `qa` runs the mutation. A resolver that always returns the default fails it.
- AC-45 (write): Given `settings.manage` and a registered key, When a value is set at scope company (`scope_id` null), branch (an existing active branch id) or terminal (an existing, non-revoked terminal id), Then exactly one `settings` row exists for (scope type, scope id, key) holding the value, `updated_by` the actor (a foreign key to `employees`, T-011), one audit row; setting the same triple again **replaces** it (never two rows, including at company scope where `scope_id` is null). Control: the same value at a different scope creates a second row. Setting the same triple again with an **unchanged** value is still a replace (D-47): `updated_by` and `updated_at` are updated and exactly one audit row is written. The audit `before` and `after` hold `key`, `scope_type`, `scope_id`, then `value` (for a secret, `{is_set: bool}` instead of the value), and are identifiable on a clear too (D-46). No cap is placed on the size of a value (D-50, deliberate omission).
- AC-46 (write, invalid input): Given each of: an unregistered key; a registry row with an unknown `type` or `validation` key (fails closed, AC-64); a value failing the registry's `type` or `validation`; a JSON `null` value (D-23); a company scope with a `scope_id`; a branch or terminal scope with no `scope_id` or a malformed one; a branch or terminal id that does not exist (`unknown_branch` / `unknown_terminal`); a revoked terminal (`terminal_revoked`); a non-string `key`, Then `validation` (or the named refusal) and **no** row changes. Clearing: Given an existing override, When it is cleared, Then the row is gone, the next lower layer applies (AC-44) and one audit row is written; clearing a row that does not exist is `validation` and writes nothing. Registry rules (D-49): a rule outside its type (for example `max_length` on a boolean) fails closed like an unknown rule; a `json` key accepts arrays only; an `in` rule must be a non-empty list of scalars, else the registry row is invalid and fails closed.
- AC-47 (secret settings): Given a key whose registry row has `is_secret`, When it is set with a sentinel value and then read, listed, audited, logged and published, Then the sentinel (also URL-encoded, JSON-escaped and reversed) appears in **no** response, no `audit_logs` before or after, no `access_log`, no `outbox_events`, no application log, no exception message and no token claim; the one place it exists is `settings.value`; reads show the key with `is_set` true and no value; the audit `before` and `after` of a secret hold `{is_set: bool}` in place of the value (D-46). The harness controls of AC-27 apply (a sink containing it is reported; a baseline proves no collision). A value in a URL query or path is not accepted.
- AC-48 (read): Given `settings.view`, When the effective settings for a scope are listed, Then each item shows `key`, the value (omitted for secrets), and the **source layer** (`terminal`, `branch`, `company` or `default`), ordered by `key`; asking about a scope that does not exist is `not_found`; the employee layer is absent (AC-51). Reads succeed for an inactive branch and a revoked terminal; a malformed scope id is `validation` (D-48).
- AC-49 (tenant isolation and freshness): Given fixture tenants A and B with the same key and scope id and different values, When the same worker resolves for A, B, A, Then each is its own; if resolution caches, the cache key includes the tenant. Given any write or clear (AC-45, AC-46), When the value is resolved immediately afterwards, Then it reflects the change with any cache or memo enabled. Controls: a cache keyed without the tenant returns A's value for B, and one not invalidated on write returns the old value; the test reports both.
- AC-50 (terminal reads its own settings): Given a valid terminal token for terminal T in branch X, When it asks for its settings, Then it receives the effective values, resolved for T, of **exactly** the keys whose registry row has `sync_to_pos` true and `is_secret` false, with their source layer, and nothing about another terminal or branch; a key with both `sync_to_pos` and `is_secret` true is excluded (control with a fixture key). - AC-51 (employee layer): Given a write with scope type `employee`, or any unknown scope type, Then `scope_not_supported` (`validation` for an unknown type) and no row; given a pre-existing `employee`-scope row (fixture), Then resolution ignores it (D-23). - AC-52 (supersedes T-010, D-6): Given an attach, a role or per-person grant scoped to a branch, Then a branch id that names no branch is refused `validation` with reason `unknown_branch` and nothing is written; a branch that is inactive is refused `branch_inactive` (AC-15); an existing active branch is accepted as T-010 AC-31, AC-32 and AC-35 describe. ## Non-functional requirements

- **Security.** The activation code is a credential: random from a secure source, shown once, stored only as a hash, single use, expiring, never logged (AC-27, D-17). The public route has one refusal and a lockout (AC-30, AC-31). A terminal's revocation is effective on the next request, because the tenant database is consulted on every terminal request (AC-34). Secret settings never leave `settings.value` (AC-47).
- **Tenant isolation.** No tenant column and no tenant-scoped query on tenant tables; every cache, memo and limiter counter that exists is keyed by tenant (AC-19, AC-31, AC-49). FP-216 will add the generated cross-tenant attempts for these routes; this task's routes must be listed so it can.
- **Migrations.** Every schema change follows expand-and-contract and runs per tenant through the per-tenant runner. The one key step (six keys, AC-4) is `contract`, is forward-only (no `down()`), and may block writes to a small table while it runs; it claims no shop offline (as T-011). Two runs are needed against a fleet that is behind.
- **Compatibility.** Existing T-010 behaviour is unchanged except AC-52; existing tenant and master tokens are unchanged except that terminal tokens are new.
- **Defaults are configuration**, not constants: activation-code lifetime (24 hours), failure window and count (10 per 15 minutes), access lifetime (15 minutes), refresh lifetime (14 days), page size.
