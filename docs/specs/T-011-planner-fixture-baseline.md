# T-011: Give the planner corpus its own fixture baseline, and ship the `settings.updated_by` contract migration it unblocks

Backlog: FP-304, and T-010 AC-10 (owed since T-008 D-5, moved here from FP-209). Decisions: `docs/decisions/T-011-planner-fixture-baseline.md` (D-1 to D-15, cited below as "D-n"; T-010's are cited as "T-010 D-n"). Branch `ai/T-011-planner-fixture-baseline`.

**Authority for counts (FP-181).** The criterion range of this spec is **AC-1 to AC-26**, and the numbered criteria below are the only authority for how many there are. No other document (plan, QA report, backlog) may state a criterion total; each cites this range. The number of pre-existing test files or call sites edited is likewise not stated anywhere in prose: it is derived from the diff (AC-24).

## Problem / goal

**The planner's tests take the product's tenant migration tree as their baseline, so their meaning changes whenever the product ships a file.** Every FX (fixture) migration set is composed on top of the shipped tree, and the corpus deliberately maps its fixture tenants at schema version 0, because "a tenant that is behind" is the input the corpus exists to express. With a contract step anywhere in the shipped tree and a fleet at version 0, the shipped contract step always blocks first, so **no plan can reach any FX migration** and the corpus is dead for as long as that step exists. T-010 measured this (the red count is recorded in the T-010 plan, Ruling 3 correction (a)) and tried a bounded helper that a control killed: it stripped the contract step from exactly the FX-4 and FX-5 cases whose subject is a contract step. T-010 therefore withdrew its contract migration instead.

This task does two things, and the second is what makes the first provable:

1. **FP-304.** `runFixtureSet()` composes the FX sets onto a **fixture baseline tree that lives in the test-support tree**, not onto the product tree, so the corpus no longer changes meaning when the product ships a file. **One named case still measures the shipped tree**, so that coverage is named instead of silently lost.
2. **Ship the `settings.updated_by` to `employees.id` contract-phase migration.** FP-304's "done when" can only be proved with a contract step in the shipped tree, and this migration is the one owed. Its design is settled (T-010 plan, Ruling 3 corrections (a) to (d), section 3's withdrawn-migration row, step 3b): the data-clean pre-check runs first, then the key, with **no driver gate**, because step 3b measured all five table-rebuild properties green on a populated table. The file was never committed, so it is written afresh. T-010 recorded its AC-10 as "not done, and recorded"; **nothing here cites T-010 as having satisfied it**.

## Users affected

- Developers of every later task that ships a tenant migration: they can add a contract step without turning the planner corpus red or dead (FP-209's three branch keys queue behind this).
- Whoever runs the runner against a real fleet: the shipped contract step's two-run requirement and its printed remedy are now exercised, not just described.
- `qa` and reviewers: they need to tell a sanctioned edit to a pre-existing test from a weakening (AC-24).
- Shop operators: indirectly, the only new database rule is that `settings.updated_by` can no longer name a non-existent employee.

## Current behaviour

- `runFixtureSet(int ...$fx)` (`packages/kernel/tests/Support/migration-run-fixture.php`) starts from the shipped tenant tree (read from `schema.tenant_migration_path`) and appends each FX directory in the order given, so an FX migration's version is its position after the product's last file.
- The FX sets live under `modules/host/tests/Fixtures/TenantMigrations/FX1` to `FX6`, one directory each; their README describes them. FX-4 and FX-5 are contract steps (FX-5 destructive); FX-6 is wrong on purpose.
- `PlanMigrationRunHandler` refuses a plan containing a contract step at version V while any non-`provisioning` tenant in the fleet is below V - 1, and prints the remedy (`tenant:migrate --all --to=<V-1>` first). The existing printed-instruction test checks that the **argument guard** does not refuse the printed remedy using an FX-4 set; it does not run the remedy.
- The shipped tenant tree holds the six baseline files and eight T-010 files, all expand; it holds **no** contract step. `settings.updated_by` is an unguarded `CHAR(26)` and no table holds its foreign key. `APP_REQUIRED_SCHEMA_VERSION` in `modules/host/.env.example` equals the tree's highest version (T-008 AC-21).
- The engine-only tests (`modules/host/tests/Engine/*`, `packages/testing` `ThreeTenantFixture`) also compose from the shipped path; they are skipped while the engine hold (G-1) stands.

## User stories

- As a developer shipping a contract migration, I want the planner tests to be independent of my migration, so that adding a product file never reddens or silences the corpus.
- As a maintainer, I want exactly one named case that measures the shipped tree, so that "does the real tree plan and apply?" is a visible test and not a lost one.
- As a maintainer, I want every printed remedy proven by running it, so that an operator who copies it gets a working command.
- As a shop owner, I want a setting's `updated_by` to be a real employee, so that an audit trail never points at nobody.
- As an operator, I want a tenant whose data would break the key to fail alone and unchanged, so that one dirty shop cannot hold up the fleet or be left half-altered.
- As `qa`, I want the list of pre-existing tests this task may edit stated up front, so that I can tell a sanctioned edit from a weakening.

## Conventions used by the criteria

Markers follow T-010: **[ENGINE]** needs a real MySQL/MariaDB and is reported NOT VERIFIED while the engine hold stands; **(diff)** needs repository history, which `ba` cannot see, and `qa` verifies; **Sweep** criteria publish their domain (the output lists every item examined and asserts the list is non-empty, T-010 D-27). A *control* is a check that fails if the thing it protects is removed; each criterion that could pass vacuously names one. "Fixture baseline" means the tree of AC-1. "Shipped tree" means the product's tenant migration tree (`schema.tenant_migration_path`). "V" means the shipped contract migration's version, always **derived** from the shipped catalogue and never written as a literal in a test or in prose (FP-181). "B" means the fixture baseline's highest version, likewise derived. Time is the injectable clock; no criterion sleeps. "Stand-in" means the SQLite tenant databases the suite already builds.

## Acceptance criteria

### A. The fixture baseline and the composed sets (FP-304)

- AC-1: Given the repository, Then a fixture baseline tree exists in the **test-support tree** beside the FX directories (D-1), and it is not under the product tree: the product tree gains **exactly one** file in this task (AC-12) and the fixture baseline is not read by the product at any time (no product source, config or `.env.example` names it). (diff) Control: a scratch copy of the product tree placed at the fixture baseline's location is detected as "product code reads it" by the same check only if production code names the path; the check is shown red against a fixture that does.
- AC-2: Given the fixture baseline, Then it is **minimal and synthetic** (D-2): a small, fixed set of hand-written expand-phase files that create trivial tables, with **six files on purpose** (older corpus literals assume a six-file baseline; that coupling is a follow-up row, D-14), numbered consecutively, meaning the file-name sequence equals the catalogue version (file n is version n), **no contract step, no destructive step**, and no file copied from the product tree. A test reads its catalogue and asserts: non-empty; every entry expand and non-destructive; file-name sequence equal to the catalogue version, from 1; its highest version is B. The output prints the entries (domain published). Controls: a scratch baseline with one contract file is reported by the same check; a scratch baseline with a gap in its numbering is reported.
- AC-3: Given `runFixtureSet()` with no arguments, Then its catalogue (migration names, versions, checksums, phases) equals the fixture baseline's, **in full**; given `runFixtureSet(1, 4)`, Then the baseline comes first, FX-1 is at version B + 1 and FX-4 at B + 2, with the FX numbering unchanged from today's relative order. Controls: `runFixtureSet(4, 1)` yields the other order (the composition is positional, not by name); a set built from the baseline plus an FX directory that does not exist throws.
- AC-4 (independence, the control that matters): Given `schema.tenant_migration_path` pointed at a scratch tree that holds an extra file in the **contract** phase at its top, and again at a scratch tree that holds extra expand files, When `runFixtureSet(...)` is built for each of `()`, `(1)`, `(4)` and `(1, 5)`, Then each catalogue is **byte-identical** (names, versions, checksums) to the one built with the real path. Control: the same scratch trees do change the **shipped-tree** entry point `runFixtureShippedSet()`, so the test can tell "independent" from "never read anything". Because it must read the shipped tree, this check lives in the named file `ShippedTenantTreeTest.php` (group `shipped-tree`, D-3), not in the generic corpus.
- AC-5 (the corpus is alive again): Given a fleet mapped at schema version 0 (as the corpus does today) and the shipped tree containing its contract step, When the planner corpus plans `runFixtureSet(1)` to its top, Then a plan is written whose jobs run from 0 to B + 1, i.e. an FX-1 migration is **reached**. Controls: (a) the same request against the set from `runFixtureShippedSet()` is refused by the shipped contract step (the dead state this task removes; it is asserted, not assumed; this control also lives in `ShippedTenantTreeTest.php`); (b) fixture tenants stay at version 0, so the scenario "a tenant that is behind" is preserved.
- AC-6 (the guards still fire for their own reason): Given `runFixtureSet(4)` and a fleet with a non-`provisioning` tenant below the version before FX-4, Then planning is refused with the contract-step refusal, **naming FX-4's migration and version and the blocking tenant**, with zero run and job rows and zero tenant connections; the refusal does **not** name any product file. Given the same fleet where every tenant is at that version (or only `provisioning` tenants are behind), Then the plan is written (positive control). Given `runFixtureSet(5)` and a fleet that would apply FX-5, Then the destructive refusal still fires with backups unavailable and does not fire in the contract-only case FX-4 (the existing "contract but not destructive" control). `qa` must run the mutation: making the guard ignore a contract step turns this criterion red.
- AC-7 (nothing silently lost): Given the planner and runner corpus (every kernel test that composes a set through `runFixtureSet()` or through the migrate-tenant fixture), When the suite is compared with the tree before this task, Then **no test case is deleted, skipped or marked incomplete, no fleet's starting schema version is changed to make a case pass, and the set of case names is a superset** (diff). Sweep, domain published: a test enumerates the corpus files that call `runFixtureSet()` (from the directory, not a list in the test), prints them and asserts the list is non-empty and that none sets a starting version through the product tree's file count.
- AC-8 (sweep: only one reader of the shipped tree): Given `packages/kernel/tests/**` (the sweep's scope, D-15), Then the only code path that reads the shipped tree as a planner input is the named file `ShippedTenantTreeTest.php` (group `shipped-tree`), reached through the one entry point `runFixtureShippedSet()` in `packages/kernel/tests/Support/migration-run-fixture.php` (D-3). The sweep enumerates the callers of that entry point and of any direct reading of `schema.tenant_migration_path` inside the scope, prints them (non-empty) and fails on a second one. The only exclusion inside the scope is `MigrationSetTest` (its subject is the product path), excluded by name and printed. The other readers of the product tree lie **outside** the scope and are therefore **printed, not excluded**: the access package's tenant fixture, the engine-only tests (D-12), and the nine host product-tree readers (catalogue publish, migration-tree discipline and similar), listed in the plan. **Stated gap:** a reader added outside `packages/kernel/tests` is not caught by this sweep. Mutation control: a scratch kernel test that composes a set on the shipped tree is found and fails the sweep.

### B. The one named case that still measures the shipped tree

- AC-9 (precondition, fails rather than skips): Given the shipped tree, Then the named case derives from the **shipped catalogue** the version V of the highest contract-phase step, and **fails with a message saying the shipped-tree gate coverage has nothing to measure** if there is none; it never passes on an empty domain and never skips. Control: the same derivation against a scratch tree with no contract step reports "none" and the case's failure branch is shown to fire.
- AC-10 (the shipped contract step gates a fleet that is behind): Given the shipped set published, and active fixture tenants mapped at version 0, When the plan is requested to the top, Then it is refused with the contract-step refusal naming the shipped contract migration, V and each blocking tenant; zero run and job rows; zero tenant connections opened (the existing connection-use instrument). Positive controls, same test: (a) with the tenants at V - 1 the plan is written and every job targets V; (b) a tenant in status `provisioning` at 0 does not block.
- AC-11 (the printed remedy is run, not read; T-010 plan section 7's standing rule): Given the refusal of AC-10, When the remedy it printed is taken **from that message** (not retyped) and executed as the command it names against stand-in tenants with the real applier, Then the command's own argument guard does not refuse it, the fleet reaches **V - 1** (each tenant's recorded schema version equals the version in the message and the tables of the shipped tree up to V - 1 exist), and a second plan to the top is then written and applies V. The V - 1 in the message equals the derived V - 1. The whole shipped tree applies to the stand-in in a measured ~21 s (via `QaRealApplierOnStandInTest`'s fixture), so this is run for real, once (D-13). Controls: a remedy with a lower target leaves the second plan refused, checked **at plan level** with the fleet left at V - 2, not by a second real application; the existing argument-guard test remains and keeps its own subject (the FX-4 refusal), so the two do not stand in for each other. NOT VERIFIED on a real engine ([ENGINE] for the two-engine comparison only); the stand-in run is provable now.
- AC-12 (the shipped tree is publishable and the floor moved with it): Given the shipped tree after this task, Then the catalogue holds one more row than before in increasing version order, the committed catalogue fixture equals the table, **no baseline or T-010 migration file's checksum changed**, and the value `.env.example` ships for `APP_REQUIRED_SCHEMA_VERSION` equals the catalogue's highest version, which is V (T-008 AC-21 and its two moved-value controls still hold, and the floor value is **derived** in the test, not written). Control: with the fixture catalogue or the `.env.example` value one off, the equality test goes red.

### C. The `settings.updated_by` contract migration

- AC-13 (shape): Given the shipped tree, Then it gains **one** migration file, the highest-versioned and last in sort order, in the **contract** phase; its version is one above the previous highest (derived, D-6); it creates no table and alters only `settings`; T-008's static rules pass **without a new exemption** (the phase rule that permits a foreign key onto an existing table only in the contract phase, identifier-column rules, no engine/charset literal, no destructive call). Its docblock names the column, says T-008 D-5 / the employees module owed the key, states that the data-clean pre-check runs first and why, and states the two-run requirement and the printed remedy. (diff) Control: T-008's fixture `contract_step_adds_foreign_key` still passes and the expand-phase twin still fails, so the rule is not vacuous.
- AC-14 (clean data): Given a stand-in tenant carrying the tenant tree up to V - 1 whose `settings` holds only rows with `updated_by` null or equal to an existing `employees.id` (including an employee that is soft-deleted, D-8), When the migration runs, Then it succeeds, the tenant's recorded version becomes V, and the foreign key `settings.updated_by` to `employees.id` is reported by the schema inspection **alongside** the pre-existing `settings.key` to `settings_registry.key` key. Also succeeds with an empty `settings` table and with an empty `employees` table when every `updated_by` is null. Control: the same inspection before the migration reports no `updated_by` key.
- AC-15 (the five rebuild properties, carried from T-010 AC-10): Given a **populated** `settings` table, When the key is added, Then (1) every row and column is byte-identical before and after; (2) the stored generated column `scope_id_key` is still correct for every row; (3) the existing `settings_registry` key is still reported; (4) the new `updated_by` key is reported; (5) the null-scope duplicate (a second company-wide row for the same key) is still refused. There is **no driver gate** in the migration: it takes the same path on every driver (D-5). Controls: each property is shown red against a deliberately damaged fixture (one altered row, one missing generated column, one dropped existing key), so none passes by construction. The populated fixture holds rows with null scope and with a specific scope, so the generated column is exercised both ways.
- AC-16 (liveness, enforcement on): Given the migration applied and foreign-key enforcement **turned on in the test's tenant stanza** (the tenant stanza the application builds leaves it off, FP-305; this task does not change that, D-9), When a `settings` insert names an employee that does not exist, Then it is refused with a foreign-key failure and nothing is written; the same row naming a real employee is accepted. Control: with enforcement left **off** the first insert is accepted, proving the test can tell enforcement on from off; the report states that the production-stanza behaviour is FP-305's.
- AC-17 (dirty data fails that tenant alone, and unchanged): Given a stand-in tenant at V - 1 whose `settings` holds a row with a non-null `updated_by` that matches no `employees.id` (an unknown id), When the migration runs for it, Then the migration **fails for that tenant**: `settings` rows and columns are byte-identical to before, **no** foreign key was added, no temporary rebuild table is left behind, the tenant's recorded version stays V - 1, and the failure is recorded against that tenant only with the migration named. The failure message names the number of offending rows and **no** `updated_by` value from the data beyond what the runner's existing error recording already allows (D-10). Positive control: removing or nulling the offending value and re-running that tenant succeeds. **What is proved where (not overclaimed):** the "enforcement on" half is proved at **migration level** (the migration run directly on a stand-in with enforcement on); the **runner-level** failure recording (job failed, other tenants proceed, version stays V - 1) is proved with enforcement at the tenant stanza **default (off)**. `architect` read Laravel 12's SQLite table rebuild: it switches key checks off and never re-checks the data, and SQLite migrations are not transactional. If plan step 6's measurement confirms that, then on the stand-in the pre-check is the **only** guard in both enforcement states, and the criterion says so; if step 6 shows otherwise, the criterion is reworded to what was measured. Either way "unchanged" is asserted by the byte-identity and no-leftover checks above, not assumed from the engine.
- AC-18 (the pre-check really is first and really is the guard): Given AC-17's failing run, Then the statements issued on that tenant's connection contain the pre-check read and **no** schema-altering statement against `settings` (the statement list is captured and printed; non-empty). Mutation controls (mandatory, `qa` runs them): (a) deleting the pre-check turns AC-17 red with enforcement off, because the table rebuild then succeeds silently over dirty data, which is why the pre-check is the real guard on the stand-in; (b) moving the key-adding statement before the pre-check turns AC-18 red.
- AC-19 (isolation across tenants, T-008): Given three stand-in tenants at V - 1, A and C clean and B dirty, When one run is planned and executed for all three, Then A and C reach V, B stays at V - 1 with its job recorded failed, the run is recorded as having failures (not as success), and A's and C's tables are unaffected by B's failure. Control: with B cleaned and only B re-run (the existing retry route), B reaches V and A and C are not re-run.
- AC-20 (comparison is exact): Given `settings.updated_by` holding an id that differs from an existing `employees.id` only in letter case, Then it counts as unknown (AC-17 applies); given an `updated_by` equal to the id of an employee whose `deleted_at` is set, Then it counts as existing (AC-14 applies), because the key refers to the row, not to its being live (D-8).
- AC-21 (reversal): Tenant migrations are forward-only (T-008 D-8), so the migration declares no undo and no criterion expects one. Control: a source check that the new file declares no `down` while an existing baseline file's convention is the same, so the absence is the convention and not an omission.
- AC-22 [ENGINE]: Given a real MySQL/MariaDB tenant database, Then the key is added and enforced the same way (a bad insert refused, a good one accepted) and the pre-check query returns the same offending set on both engines. NOT VERIFIED while the engine hold stands; reported as such, with no test claimed green. The pre-check query is the same statement on every driver (no engine-specific branch), shown by diff review.

## Non-functional requirements

- **Safety.** No test of this task opens a connection to a real MySQL/MariaDB or to the local engine; the engine hold is respected. The migration's behaviour on dirty data is a fail-closed refusal that changes nothing (AC-17); it must never delete, null or "repair" an offending `updated_by` value (D-10).
- **Determinism.** Time from the injectable clock; no sleeping; every derived number (B, V, V - 1) comes from a catalogue, never from a literal.
- **Operational.** The two-run requirement (run `--to=<V-1>` fleet-wide, then the run that includes the contract step) is a standing property of any contract step and is documented in the migration's docblock (AC-13); a fresh `provisioning` database can still be migrated to the top in one run.
- **Performance.** None stated; the table rebuild on SQLite is proved on a populated table only (AC-15).

## Assumptions

- The tenant tree's versions are positions in one set ordered by file name (T-008); the new file must therefore sort after the last T-010 file, and the fixture baseline's order is its own.
- No tenant database exists outside tests; nothing here migrates or deletes real data (no escalation trigger).
- The runner records one failed job per tenant with the migration named (T-008); AC-17 and AC-19 rely on that existing behaviour and do not add to it.
- The SQLite stand-in adds the key by rebuilding the table through the schema builder (T-010 step 3b measured this and its five properties); `qa` must not re-derive that, and must not reintroduce a driver gate (D-5).
- The word "tenants at version 0" in the corpus is a deliberate input, not an accident to be corrected (T-010 plan, Ruling 3 (a)).
- Anything needing history (which tests were edited, whether a baseline migration file changed) is for `qa`; `ba` has no shell.
