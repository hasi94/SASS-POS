## Problem / goal

Modules that need to tell someone something (a receipt to a customer, a low-stock alert to a manager) have no way to do it. `docs/database.md` §6.16 documents the tables (`notification_templates`, `channel_configs`, `notifications`, `deliveries`) and nothing is built.

Goal of T-040: a Notification module in which (1) a calling module asks for "this template, this recipient, these variables" through one published contract; (2) the request is validated, checked against the recipient's consent, rendered with safe escaping, recorded as a `deliveries` row and queued through the existing outbox and event bus; (3) a consumer hands it to a channel driver behind an interface, with retry, back-off and idempotency; (4) every attempt and its outcome is recorded; (5) tenant admins (through in-process handlers, no HTTP yet) can configure channels (secrets stored encrypted), manage templates and record customer consent; (6) in-app notifications are written for employees; (7) deliveries can be listed, counted and retried. T-040b adds the inbox reads, retention, the owed column and the routes.

## Users affected

- Tenant admin / manager: configures channels, edits templates, records consent, reads deliveries, retries failed ones (via handlers; routes arrive in T-040b).
- Employee: in-app notifications are written for them (reading them is T-040b).
- Customer: is the recipient of customer messages; their consent and opt-out are honoured. Nothing real is sent to them in this task.
- Developers of later modules (sales receipts, AR reminders, payroll, stock alerts, notification rules, webhook, real providers): consume the published contracts.
- Not affected: cashiers at the till; no sale flow changes.

## Current behaviour

Measured on the worktree (base `81a9169`, the T-032 merge; plan section 0.1):
- The base holds the event bus, plugin SDK, access, kernel, organization, catalog, pricing, sales, workflow, platform, auth and finance packages **and the customers package** with `customer_communications` (no `delivery_id`; its migration defers it).
- No `notification_templates`, `channel_configs`, `notifications` or `deliveries` table exists. No Notification package exists.
- The outbox and event bus (T-018) exist: one outbox writer (it requires a 26-character ULID `aggregate_id`), a relay, consumer groups, idempotency left to the consumer, dead-letter handling, no HTTP surface.
- No published customers contract for contact data exists (`packages/contracts/src/Customers/` holds only credit-ledger and loyalty contracts).
- `employees` has no email or phone column (they arrive with T-038, not merged).
- `docs/database.md` §6.16 documents the four tables but no consent store: `customers` (§6.13) carries `phone` and `email` and no marketing or consent column.
- Tenant encryption: Laravel's encrypter keyed by `APP_KEY` exists (precedent: `plugin_settings`).
- No scheduler runs in production (backlog FP-319).

## User stories

- As a developer of another module, I want one published contract to request a notification by template key, recipient and variables, so that I never touch a channel, a driver or a provider.
- As a tenant admin, I want to configure which provider serves each channel and keep its credentials encrypted and unreadable afterwards, so that a leaked admin screen or log does not leak a secret.
- As a tenant admin, I want templates with variables per channel and locale, so that messages are consistent and editable without a release.
- As a customer, I want my opt-out respected before anything is sent to me, so that I am not messaged against my wishes.
- As a tenant admin, I want every attempt recorded with a status and reason, so that I can see what was sent, what failed and why, and retry what is safe to retry.
- As an employee, I want in-app notifications written for me, so that I see alerts without email (reading them: T-040b).
- As the owner of the platform, I want a log driver and no real sender, so that this task can be tested without credentials or cost.

## Acceptance criteria

Conventions for every criterion below. Refusals are whole-request: nothing is written, the response names the offending field and carries a stable snake_case reason code. "Live" means `deleted_at IS NULL` where the table has it. Timestamps are UTC and come from an injectable clock; no test waits in real time. Money does not appear in this task. Criteria marked `[ENGINE]` need a real MySQL or MariaDB engine (or real Redis) to prove and are recorded NOT VERIFIED until one runs them (T-018 D-1, T-028 D-15 precedent); everything else is provable on the SQLite stand-in and the in-memory bus. "Handler" means an in-process operation of the package; this task exposes no HTTP route (AC-105).

### A. Scope guard: nothing real is sent

- AC-1: Given the whole package and its tests, When the source is scanned, Then it contains no SMTP, mail-facade, HTTP-client, socket, cURL or provider-SDK call and no `composer.json` dependency on a mail, SMS or messaging SDK. A mechanical test fails the build on any such reference, naming it.
- AC-2: Given the application booted with default configuration and one end-to-end pipeline test (request, outbox, consumer, `log` driver, delivery `sent`) run with outbound HTTP blocked (stray requests refused) and the mail facility faked, When it runs, Then it completes and asserts zero HTTP requests and zero mails. Together with AC-1's source scan this is the proof that no code path opens a network connection. A run of the whole suite with the network physically unavailable is an environment property and is recorded NOT VERIFIED unless the lead runs one (D-49).
- AC-3: Given `channel_configs.provider`, When a config is created, Then the only accepted values are `log` and `null`, for the channels `email`, `sms`, `whatsapp` and `push`; any other value is refused `provider_not_available`. The refusal is by data, so no real send path can be switched on by configuration alone. (`in_app` is not a provider value: AC-113.)
- AC-4: Given a developer wanting a real provider, When they implement the driver interface (AC-6) and register it, Then no change to the delivery pipeline, the contracts or the schema is required; this task ships no such driver and no stub that pretends to be one.
- AC-5: Given the `webhook` value in the template channel enum, When a template or config is created for it, Then it is refused `channel_not_supported`. The value stays in the enum so a later task adds no enum migration (D-3).

### B. Channel drivers

- AC-6: Given the driver interface, When it is read by another module, Then it exposes only: the channel and provider it serves, the credential fields it declares, and one send operation that takes an immutable outbound message (delivery id as client reference, recipient address, subject or null, body, sender address or null) and returns an immutable result with an outcome (`accepted`, `transient_failure`, `permanent_failure`), an optional provider reference and an error code and message. It never exposes a model class or a table (module boundary; deptrac clean). Credentials reach a driver in an object that never reveals a value through a dump, a log context or serialisation (names only).
- AC-7: Given the driver registry, When a delivery needs a driver, Then it is resolved by (channel, provider) from the active channel config; a registered driver is selected by configuration only, never by business code. A (channel, provider) with no registered driver fails the delivery `driver_not_registered` (permanent). Two drivers registered for one (channel, provider) is a start-up error.
- AC-8: Given the `log` driver, When it sends, Then it writes exactly one structured log line carrying delivery id, channel, provider, template key and a masked recipient (email: first character, `***`, domain; phone: `***` plus the last two digits only), never the subject, the body, the credentials or the unmasked address, and returns `accepted` with provider reference `log:<delivery id>`.
- AC-9: Given the `null` driver, When it sends, Then it writes nothing anywhere and returns `accepted` with provider reference `null:<delivery id>`.
- AC-10: Given a driver that throws instead of returning, or returns an outcome outside the three allowed, When the pipeline handles it, Then the attempt is recorded as a `transient_failure` with error code `driver_error`, the stored error message is truncated to 500 characters and has any substring equal to a stored credential value replaced with `[redacted]`, and the exception never escapes to the queue consumer.
- AC-11: Given the in-app channel, When a delivery is for `in_app`, Then it is handled by the in-app writer (Group I), which writes a database row and calls no external system and no driver.

### C. Channel configuration and secrets

- AC-12: Given a valid `channel`, `provider`, optional `from_address`, `settings` (JSON object), `is_active` and `daily_limit`, When a channel config is created, Then a live row exists with a ULID id, `sent_today = 0`, and `is_active` default `false` (a new config is inert until explicitly activated, D-9). Only one config exists per (channel, provider); a second is refused `channel_config_exists` naming the first. A create body may carry `is_active`; later changes of it go only through activation and deactivation (AC-118).
- AC-13: Given `channel`, `provider` or `is_active`, When the value is not exactly one of the lower-case documented values, or `is_active` is not a JSON boolean, Then it is refused; `Email`, ` email`, `"true"`, `1` are all refused and never coerced.
- AC-14: Given `from_address`, When the channel is `email`, Then it must be a syntactically valid single address of at most 191 characters, with no display name, no comma, no CR/LF and no control character; for `sms`, `whatsapp` and `push` it is optional, 1 to 50 characters, with no control character. Violations are refused whole and never trimmed or truncated.
- AC-15: Given `daily_limit`, When it is supplied, Then it is null (unlimited) or an integer from 1 to 1,000,000; zero, negative, fractional, numeric string and over-range are refused.
- AC-16: Given `settings`, When it is supplied, Then it is a JSON object of at most 20 keys, each value a string up to 200 characters, a boolean or an integer, serialised at most 4,000 characters; a nested object or array value is refused `settings_invalid`. `settings` never holds a secret; a key whose name contains `secret`, `password`, `token`, `key` or `credential` (case-insensitive) is refused `secret_in_settings`.
- AC-17: Given at most one config active per channel, When a config is activated while another for the same channel is active, Then it is refused `channel_already_active` naming the holder; deactivating first is required. `[ENGINE]` for the two-connection race: of two simultaneous activations exactly one succeeds (a database-level uniqueness on the active channel is the backstop).
- AC-18: Given credentials, When they are supplied, Then they are accepted only as a JSON object whose keys are all in the driver's declared credential fields (AC-6); an undeclared key is refused `credential_field_unknown`; a missing required field is refused `credential_field_missing`. The `log` driver declares exactly one optional field, `sandbox_token`, which has no effect and exists so the encrypted-secret path is exercised without a real secret (D-8). The `null` driver declares none, and credentials supplied for it are refused `credentials_not_supported`.
- AC-19: Given credentials are stored, When the row is read from the database directly, Then `credentials` holds only ciphertext produced by the application's authenticated encryption (Laravel's encrypter with the existing `APP_KEY`, confined to one class, D-46), never the plaintext in any column. A test writes a clearly fake sentinel value, with a key generated inside the test, and asserts it is absent from the stored column.
- AC-20: Given a stored credential, When any read, list, audit row, log line, exception message, outbox payload, delivery row or handler result is produced, Then it never contains the plaintext or the ciphertext; reads expose only `has_credentials` (boolean) and `credentials_updated_at`. The same sentinel test scans all of these.
- AC-21: Given the stored ciphertext matches neither the current key nor any previous key (`APP_PREVIOUS_KEYS`), or no key is configured, When a driver needs the credential, Then decryption fails loudly with `credentials_undecryptable`, the delivery fails permanently with that code, and no partial or garbled value is passed to a driver. A credential encrypted under a configured previous key still opens. Rotating the key is out of scope (follow-up).
- AC-22: Given an update body, When it names credentials, Then the stored value is replaced whole (write-only) and `credentials_updated_at` is set; omitting `credentials` leaves it unchanged; an explicit `null` clears it; an empty object is refused. Any update naming `id`, `channel`, `provider`, `is_active`, `sent_today`, `sent_today_date`, `credentials_updated_at`, `created_at`, `updated_at` or an unknown key is refused naming every offending key (`is_active`: `not_updatable_here`, AC-118).
- AC-23: Given a config, When it is deleted, Then it is allowed only while inactive (`config_active`), it is removed whole including its ciphertext, and a second delete is refused `config_not_found`.
- AC-24: Given an outbound channel with no active config, When a send is requested for it, Then it is refused `channel_not_configured` and nothing is written. Given the config is deactivated after a delivery was queued, When the attempt runs, Then the delivery fails permanently `channel_not_configured`. `in_app` needs no config (D-10).
- AC-25: Given two tenants, When each configures a channel, Then each uses only its own tenant database's config and credentials; a send in tenant A never reads tenant B's row (verified with two tenant fixtures).

### D. Templates and variables

- AC-26: Given `key`, `channel`, `locale`, `subject`, `body`, `variables` and optional `is_active` (default `true`, D-47), When a template is created, Then a live row exists with a ULID id and `plugin_name = null`; (key, channel, locale) is unique, and a duplicate is refused `template_exists` naming the existing id. Proven on the stand-in and `[ENGINE]` on the real collation.
- AC-27: Given `key`, When it is submitted, Then it must match `^[a-z][a-z0-9_.]{0,79}$` exactly (lower case, never coerced, never trimmed), so a collation that ignores case cannot create two keys that collide; `Welcome`, `welcome ` and a 81-character key are refused.
- AC-28: Given `locale`, When it is submitted, Then it must match `^[a-z]{2}(-[A-Z]{2})?$` (`en`, `en-GB`); anything else is refused.
- AC-29: Given `channel`, When it is one of `email`, `sms`, `in_app`, `whatsapp`, `push`, Then it is accepted; `webhook` is refused (AC-5); anything else is refused.
- AC-30: Given `subject`, When the channel is `email` or `in_app` (where it is the title), Then it is required, 1 to 255 characters counted as characters, valid UTF-8, with no control character including CR and LF; for `sms`, `whatsapp` and `push` it must be null and a non-null value is refused `subject_not_supported`.
- AC-31: Given `body`, When it is submitted, Then it is required, valid UTF-8, 1 to 20,000 characters (`sms` and `whatsapp`: at most 1,600), not blank after trimming, with no NUL byte. Over-length input is refused, never truncated. The stored body is not trimmed or altered.
- AC-32: Given `variables`, When it is submitted, Then it is a JSON object (at most 30 entries) mapping a variable name matching `^[a-z][a-z0-9_]{0,39}$` to `{type, required, max_length}`, where `type` is one of `string`, `number`, `date`, `url`, `required` defaults to `true`, and `max_length` is an integer 1 to 1,000 (default 200) that applies to `string` and `url` only. Unknown keys inside an entry are refused.
- AC-33: Given the template syntax, When `subject` or `body` is stored, Then the only construct allowed is a placeholder `{{name}}` with optional spaces inside the braces. There are no expressions, no filters, no sections, no includes, no dotted names, no raw or unescaped form. Any other use of `{{` or `}}` (including `{{{x}}}`, `{{#x}}`, `{{>x}}`, `{{a.b}}`, `{{a|f}}`, an unclosed `{{`, a stray `}}`) is refused `malformed_placeholder` with the offending position. There is no way to write a literal `{{`. A consequence the owner should know: an email template holding nested CSS such as `@media{a{b:c}}` cannot be stored, because the closing `}}` is refused (D-12, D-55).
- AC-34: Given a placeholder naming a variable not in `variables`, When the template is stored, Then it is refused `undeclared_variable` naming each. A declared variable that is never used is allowed.
- AC-35: Given a template update, When it is submitted, Then `key`, `channel` and `locale` are immutable (refused `not_updatable_here`), as are `id`, `plugin_name`, `created_at`, `is_active` (AC-118) and any unknown key, all named. `subject`, `body` and `variables` are updatable and re-validated by AC-30 to AC-34 on the stored-plus-supplied values.
- AC-36: Given a template, When it is deactivated through the deactivation operation, Then it stays readable, is no longer used for new sends (`template_inactive`, AC-52), and queued deliveries are unaffected because they hold a rendered snapshot (AC-47). Reactivation through the activation operation is allowed. Deactivating an inactive template is refused `already_inactive`; activating an active one `already_active`.
- AC-37: Given templates, When listed, Then they filter by `key` prefix, `channel`, `locale` and `is_active`, ordered by `key`, `channel`, `locale`, with paging (default 25, maximum 100); a limit of 0, 101 or non-integer is refused `page_size_invalid`.
- AC-38: Given templates, When the operations of the package are read, Then there is no delete operation for a template (and so no route in T-040b): templates are deactivated only, because deliveries refer to a key by name (D-13).

### E. Rendering and escaping

- AC-39: Given a send request and a resolved template, When it is rendered, Then every required variable must be supplied (`missing_variable`), every supplied variable must be declared (`unknown_variable`, a typo is caught loudly), and each value must satisfy its declared type (`invalid_variable`). The whole request is refused naming every failing variable; nothing is written.
- AC-40: Given types, When a value is checked, Then `string` is a JSON string of valid UTF-8 within `max_length` characters, with no NUL; `number` is a JSON integer or a JSON string matching `^-?\d{1,18}(\.\d{1,4})?$` and never a JSON float (money and quantities stay exact, no float rule); `date` is a strict `Y-m-d` that is a real calendar date; `url` is an absolute `https://` URL of at most 500 characters with no user-info, no whitespace and no control character. Arrays, objects, null and booleans are refused for every type.
- AC-41: Given an `email` body, When a value is substituted, Then it is HTML-escaped (`&`, `<`, `>`, `"`, `'` to entities, UTF-8), so a value `<script>alert(1)</script>` appears as `&lt;script&gt;alert(1)&lt;/script&gt;` and never as markup. A value is escaped exactly once (no double escaping).
- AC-42: Given an `email` subject, or any `sms`, `whatsapp`, `push` body, or an `in_app` title or body, When a value is substituted, Then it is inserted as plain text: no HTML escaping is applied (so `&` stays `&`), but every ASCII control character is removed or, for tab, replaced by one space, CR and LF are removed, and the Unicode line and paragraph separators (U+2028, U+2029) and bidirectional override and isolate characters (U+202A to U+202E, U+2066 to U+2069) are removed. A value containing `\r\nBcc: x@y` therefore cannot add a header or a line.
- AC-43: Given a `url` variable inside an `email` body, When rendered, Then it passes AC-40 and AC-41, so `javascript:`, `data:`, `http://` and relative values are refused at validation, never emitted.
- AC-44: Given rendering, When a value itself contains `{{other}}`, Then it is inserted literally and never re-evaluated; rendering is a single pass over the template text only, so a value cannot inject a placeholder, and one request's values can never reveal another variable.
- AC-45: Given the template author's own markup in an `email` body (for example `<b>Hello</b>`), When rendered, Then it is emitted unchanged: template text is trusted content written by a holder of `notifications.templates.manage`; only variable values are untrusted (D-12). The spec states this plainly so no reviewer expects template text to be sanitised.
- AC-46: Given the same template, variables and clock, When rendered twice, Then the output is byte-identical (no random, no time-dependent content).
- AC-47: Given a send request, When it succeeds, Then the rendered subject and body are stored on the delivery as a snapshot at queue time and the driver sends the snapshot, so editing or deactivating the template afterwards cannot change a queued message (D-14).
- AC-48: Given a rendered result, When its length exceeds the channel limit (AC-31), Then the request is refused `rendered_too_long`; it is never truncated.

### F. Requesting a send, queueing through the outbox

- AC-49: Given the published contract `NotificationSender`, When another module calls it with `template_key`, `channel`, `locale` (optional), `recipient` (type and id), `category`, `variables`, `idempotency_key`, optional `source_event_id`, and the in-app-only optional fields `priority`, `data` and `action_url`, Then the module-boundary rule holds: it takes and returns plain immutable values and never a model, every enumerated field arrives as a string so a non-matching value is refused and never coerced, and it is the only way another module requests a notification. It returns a receipt with the delivery id, the delivery status, an error code (when the delivery is not queued) and whether the answer is a replay (AC-56). It joins the caller's open transaction or opens its own.
- AC-50: Given a request, When it is made, Then it carries exactly one `channel` (a list of channels is refused); one call produces one delivery for one recipient on one channel. Fan-out to several channels, roles or recipients is the caller's loop or a later rules task (D-5).
- AC-51: Given `recipient`, When it names an employee, Then that employee must exist and be live (`recipient_not_found`) and must be in the platform's acting set (status `active` or `probation`, the one authority `RoleHolders::actingAmong`; a list of statuses is not copied) otherwise `recipient_inactive`. Employees on leave, suspended, resigned or terminated therefore do not receive in-app alerts (D-40). When it names a customer, Then that customer must exist (`recipient_not_found`), not be merged into another (`recipient_merged`, checked before liveness because a merge soft-deletes the source) and be live. A raw address (an email or phone typed in the request) is refused `recipient_type_unsupported` (D-6). The same checks run again at attempt time (AC-73).
- AC-52: Given a `template_key`, `channel` and `locale`, When the template is resolved, Then the exact (key, channel, locale) is used; if absent and the locale is not `en`, the `en` template is used; otherwise the request is refused `template_not_found`. An inactive template is refused `template_inactive`. A customer recipient on `in_app` is refused `channel_not_supported_for_recipient` (customers have no inbox). An employee recipient is allowed **only** on `in_app`: any other channel is refused `channel_not_supported_for_recipient`, because employees have no email or phone until T-038 publishes contact data (D-41).
- AC-53: Given `category`, When it is one of `transactional`, `marketing`, `system`, Then it is accepted; anything else is refused. A customer recipient with `system` is refused `category_not_allowed_for_recipient`; an employee recipient with `transactional` or `marketing` is refused the same way (D-7).
- AC-54: Given a valid request that is neither suppressed (AC-66) nor failed for a missing address (AC-67), When it is accepted, Then in one database transaction exactly one `deliveries` row (status `queued`, `attempts = 0`, `next_attempt_at = now`, `dispatched_at = now`, a server-generated ULID `ref`) and exactly one outbox row are written, the outbox row through the one outbox writer (T-018 AC-5): `type = notification.delivery_requested`, `aggregate_type = delivery`, `aggregate_id = ref` (the outbox accepts only a ULID there, D-38) and `payload = {"delivery_id": <integer>}`. A test that rolls back the caller's transaction finds neither row (T-018 AC-6). A suppressed or failed-at-request delivery writes its row and no outbox row.
- AC-55: Given the outbox payload, When inspected, Then it contains the integer delivery id only: no recipient address, no subject, no body, no variable value and no credential; the consumer reads everything from the delivery row.
- AC-56: Given an idempotent request, When the same `idempotency_key` (1 to 100 characters, case-sensitive, ASCII printable) is submitted again with the same effective inputs, Then no second delivery and no second outbox row is written and the original receipt (delivery id and status) is returned with `replayed = true`. The stored key is compared by its SHA-256 digest (64 hex characters, unique), so `a` and `A` are different keys on any collation (D-39). "Same effective inputs" is a stored payload hash over every request field except `idempotency_key` and `source_event_id` (template key, channel, locale, recipient type and id, category, variables, priority, data, action_url, each in a canonical normalised form with sorted keys); with different inputs the request is refused `idempotency_key_conflict`. A missing or invalid key is refused `idempotency_key_required`. Replay is answered before any business check, so a replay returns the same answer even after a config was deactivated.
- AC-57: Given two simultaneous requests with the same key, When both run, Then exactly one delivery exists afterwards and the other returns it. `[ENGINE]` (unique index race).
- AC-58: Given a consumer in the consumer group `notifications` (the queue name already in `docs/architecture.md` §9), When it receives `notification.delivery_requested`, Then it processes the delivery by the id in the payload. Idempotency is the delivery's own status and `next_attempt_at`, read under a row lock, not a store of processed events (D-51): a redelivered message for a delivery that is no longer `queued`, or whose `next_attempt_at` is in the future, changes nothing and is acknowledged; a missing delivery id is acknowledged and logged, never retried forever; a malformed payload (non-integer id) is logged and acknowledged. A business outcome never throws; only infrastructure errors do.
- AC-59: Given a `queued` delivery whose event was dead-lettered or never relayed, or whose retry or deferral time has come, When the command `notifications:dispatch-due` runs, Then it finds due rows in bounded batches (default 100, ordered by `next_attempt_at` then `id`; never a cursor on a ULID, T-018 AC-14) and writes a fresh `notification.delivery_requested` outbox row for each, so a lost event recovers; running it twice before consumption is harmless because of AC-58 and AC-116. It reports how many it requeued and writes no audit row. This command is also what wakes transient-failure retries and daily-limit deferrals: the consumer acknowledges a not-yet-due row and nothing else re-delivers it. No scheduler runs in production (FP-319), so until one exists retries, deferrals and lost-event recovery fire only in tests and when the command is run by hand (Assumption 9).
- AC-60: Given the dispatch command's batch size, When configured, Then it is an integer 1 to 1,000; outside that range the command fails to start with a named error.

### G. Consent and opt-out

- AC-61: Given the consent store (new table `notification_consents`, D-15), When a consent is recorded, Then it holds one row per (customer, channel, category) with `status` `opted_in` or `opted_out`, `source` (1 to 50 characters, for example `staff`, `customer_request`, `import`), an optional `note` (up to 255 characters), `recorded_by` (employee), and timestamps; `channel` is one of `email`, `sms`, `whatsapp`, `push`; `category` is `transactional` or `marketing`. Recording again for the same triple updates the row (it never creates a second) and each change writes an audit row (AC-103). The customer must exist and be live (`recipient_not_found`).
- AC-62: Given a customer recipient and `category = marketing`, When a send is requested, Then it is allowed only if a consent row for that (customer, channel, marketing) is `opted_in`; no row, or `opted_out`, results in a delivery recorded as `suppressed` (AC-66) and nothing is sent (D-16, fail closed).
- AC-63: Given a customer recipient and `category = transactional`, When a send is requested, Then it is allowed unless a consent row for that (customer, channel, transactional) is `opted_out`; no row means allowed (D-16).
- AC-64: Given an employee recipient (`system` category), When a send is requested, Then consent rows are not consulted; an employee cannot be opted out through this store, and the `system` category is never offered to a customer (AC-53).
- AC-65: Given the consent check, When it runs, Then it runs twice: at request time (AC-62, AC-63) and again immediately before the driver is called (AC-73), so an opt-out recorded after a delivery was queued still stops it. The request-time read is advisory; the attempt-time read, under the delivery's row lock, decides.
- AC-66: Given a consent refusal, When it occurs at either time, Then the delivery is recorded (or moved) to status `suppressed` with `error_code` `consent_missing` or `consent_opted_out`, `attempts` unchanged, and the driver is never called. A `suppressed` delivery is terminal and is not retried by the dispatcher; it can be re-requested only by a new idempotency key after consent changes. At request time the call returns the suppressed delivery as a receipt (not an exception), so a caller can tell "refused by policy" from "invalid request".
- AC-67: Given a customer recipient, When the address for the channel is missing (`email` empty for `email`; `phone` empty for `sms`, `whatsapp` and `push`), Then the delivery is recorded `failed` with `error_code = recipient_address_missing`, `recipient` null, no attempt is counted, no outbox row is written and no driver is called. The address is read through the published `CustomerContacts` contract (AC-115, never the customers table) and a snapshot is stored in `recipient` at request time.
- AC-68: Given a customer in status `blocked` or `inactive`, When a `transactional` send is requested, Then it is allowed; a `marketing` send to such a customer is refused `recipient_not_eligible` (D-17).
- AC-69: Given consent records, When listed for a customer, Then every row for that customer is returned with channel, category, status, source, note and `updated_at`, with paging as AC-37. Inbound opt-out handling (a customer replying STOP, an unsubscribe link, a provider webhook) is out of scope (D-18).

### H. Delivery lifecycle, retry, back-off and idempotency

- AC-70: Given the `deliveries` status values, When a delivery moves, Then the only allowed moves are: `queued` to `sent`; `queued` to `failed`; `queued` to `suppressed`; `queued` to `delivered` (in-app only, AC-83); `sent` to `delivered`; `sent` to `bounced`; and, by the manual retry only (AC-79), `failed` to `queued`. Every other pair is refused `invalid_transition` and writes nothing; `suppressed`, `delivered` and `bounced` are terminal; `sent` is never moved back (D-19). The enum is `queued, sent, delivered, failed, bounced, suppressed` (`suppressed` is an addition to the documented enum, D-19).
- AC-71: Given a `sent` delivery, When nothing external can report back (this task builds no provider callback), Then it stays `sent`; `delivered` and `bounced` are reachable only through an internal transition operation that a future provider-callback task will call, and which this task exercises in tests and nowhere else.
- AC-72: Given a delivery attempt on a `queued` row whose `next_attempt_at <= now`, When it starts, Then the row is read under a row lock and every rule is evaluated on the locked values, so two workers on one delivery leave exactly one driver call and the other becomes a no-op (AC-58). `[ENGINE]` for the two-connection proof.
- AC-73: Given an attempt, When it starts, Then before any driver call it re-checks, in this order: the recipient is still live and eligible (AC-51, AC-68), the consent (AC-65), the channel config is active (AC-24), and the daily limit (AC-77); a failure of the first three ends the attempt without counting it (`suppressed`, or `failed` with the reason).
- AC-74: Given a driver call, When it returns `accepted`, Then the delivery becomes `sent` with `provider`, `provider_ref`, `sent_at = now`, `attempts` incremented, `error_code` and `error` cleared, and the channel's `sent_today` incremented, all in one transaction.
- AC-75: Given a driver call, When it returns `transient_failure`, Then `attempts` is incremented, `last_attempt_at = now`, `error_code` and a truncated `error` are stored, the status stays `queued`, and `next_attempt_at = now + min(cap, base x 2^(attempts - 1))` with default base 60 seconds and cap 3,600 seconds, so the delays are 60, 120, 240, 480 seconds for attempts 1 to 4, with no jitter in this task (D-20). Base and cap are configuration, integers 1 to 86,400, and the cap may not be below the base. The retry fires when the dispatch command (AC-59) next runs.
- AC-76: Given the maximum number of attempts (default 5, configuration integer 1 to 20), When a transient failure brings `attempts` to the maximum, Then the delivery becomes `failed` with `error_code = max_attempts_exceeded` and the last driver error code kept in `error`; a `permanent_failure` makes it `failed` at once with the driver's code. A `failed` delivery is never picked up by the dispatcher.
- AC-77: Given `daily_limit` is set and `sent_today` has reached it for the channel's current UTC day, When an attempt starts, Then the delivery stays `queued`, `attempts` is not incremented, and `next_attempt_at` becomes 00:00:00 UTC of the next day; `sent_today` resets when `sent_today_date` is not today's UTC date (D-21). A limit of null never defers. The deferred row is woken by the dispatch command (AC-59).
- AC-78: Given a provider reference, When any driver is called, Then it receives the delivery id as the client reference, so a real driver can de-duplicate. The spec records the known limitation: a worker that dies after the driver accepted and before the row is updated can cause one duplicate send on the next attempt; no exactly-once claim is made (T-018 AC-23 reasoning). The driver call runs inside the row-locking transaction (D-19); that is acceptable for `log` and `null` only (Owner-visible question 9).
- AC-79: Given a `failed` delivery, When a holder of `notifications.deliveries.retry` retries it, Then it becomes `queued` with `attempts = 0`, `next_attempt_at = now`, `dispatched_at = now`, `error_code` and `error` cleared (kept in the audit row), a new outbox event is written in the same transaction, and consent, recipient and config are re-checked at the attempt exactly as for a new delivery (a retry never bypasses consent). Retrying a delivery that is not `failed` is refused `invalid_transition`; retrying a `failed` delivery whose `error_code` is `expired` (set by the retention purge, T-040b) is refused `delivery_expired` (D-53).
- AC-80: Given retry timing, When tests run, Then the clock and the attempts are injected so the full retry ladder runs in milliseconds with no real wait (T-018 AC-17 convention).
- AC-81: Given a delivery row, When it is written, Then `recipient` holds the address snapshot (at most 191 characters) and is null for `in_app` deliveries (the employee is in `recipient_id`) and for `recipient_address_missing` (D-54); `provider` is the config provider at attempt time; `error` is at most 500 characters and never contains a credential (AC-10, AC-20); `sent_at` is set only on the move to `sent` (and on in-app delivery, AC-83); `delivered_at` only on `delivered`.
- AC-82: Given the lifecycle, When any status change is made, Then it happens only through the one delivery-state operation, which enforces AC-70; no handler updates `deliveries.status` directly. A source scan finds no second writer, the same one-writer rule as `audit_logs` and `outbox_events`. (The retention purge of T-040b deletes rows and is scanned for separately.)

### I. In-app notifications (written here, read in T-040b)

- AC-83: Given an in-app delivery to an employee, When the attempt runs, Then in one transaction a `notifications` row is written (`recipient_employee_id`, `type` = the template key, `title` = rendered subject, `body` = rendered body, `data` = JSON object or null, `priority` `normal` by default, `read_at` null, `action_url`, `delivery_id`) and the delivery becomes `delivered` with `delivered_at` and `sent_at` set and `attempts` incremented. The `priority`, `data` and `action_url` come from the request, carried on the delivery (`in_app` JSON) from request to attempt. No channel config row is needed (D-10).
- AC-84: Given `priority`, `data` and `action_url`, When supplied on a request for any channel other than `in_app`, Then the request is refused `field_not_supported_for_channel` naming each. For `in_app`, `priority` is one of `low`, `normal`, `high`; anything else is refused. `data` is a JSON object of at most 20 scalar entries and 4,000 serialised characters, containing no value that is another object or array; it is stored as given and never rendered as a template.
- AC-85: Given `action_url`, When supplied, Then it is either a path starting with exactly one `/` (not `//`), at most 500 characters, with no control character and no `\`, or an absolute `https://` URL; `javascript:`, `data:`, `http:` and protocol-relative `//host` values are refused `action_url_invalid`.
- AC-86: Given an in-app delivery that was already written (redelivered message, retry), When the attempt runs again, Then a unique reference from `notifications` to its delivery makes the second write impossible, so one delivery yields at most one in-app row (idempotent, T-018 AC-23).
- AC-89: Given in-app content, When the title and body are stored, Then they are stored as plain text (AC-42) and the contract is that consumers display them as text, never as markup; a stored `<b>` is returned as the same characters.

## Non-functional requirements

- Security: secrets encrypted at rest, write-only and absent from every output (AC-19 to AC-21); variable escaping per channel (AC-41 to AC-45); header and line injection blocked (AC-42); no URL scheme other than `https` or a local path (AC-40, AC-85); the permission split keeps secrets, content and retry separately grantable.
- Privacy: bodies and addresses are personal data; the log driver masks and never logs a body (AC-8); the outbox carries only an id (AC-55); delivery content needs its own permission (AC-92).
- Reliability: at-least-once delivery with idempotent consumers, a recovery command for lost events (AC-59, once a scheduler exists), and a documented duplicate window (AC-78).
- Performance: the consumer handles one delivery per message; the dispatch command runs in bounded batches; delivery list and counts use the documented indexes (AC-108); no unbounded select.
- Accessibility: not applicable (no UI).
- Observability: the dispatch command reports counts; the log driver line is structured.

## Owner-visible questions

Each has a built-in default already applied; none blocks work. The owner may change any of them later; all are reversible unless noted.

1. Consent and legal evidence. Default applied: marketing needs an explicit recorded opt-in (fail closed); transactional is sent unless opted out; a staff member records consent with a source and note. Does the business need double opt-in, proof of consent (timestamp, IP, wording) or jurisdiction-specific rules? The default is the safest, and the model can add columns later.
2. Which providers, and when. Default applied: none; only `log` and `null` exist. Which email and SMS providers should the first real drivers target, and who supplies the credentials?
3. Message retention. Default applied: 90 days for deliveries (built in T-040b), including the stored subject and body snapshot; in-app notifications kept indefinitely. Should customer message bodies be kept at all, or only metadata?
4. Blocked and inactive customers. Default applied: they still receive transactional messages but never marketing. Is that right?
5. Daily limit day. Default applied: UTC day. Should it follow the tenant's local time?
6. Automatic communication log. Default applied: sending to a customer does not create a `customer_communications` row by itself. Should every customer message appear in the customer's history automatically?
7. Who may read message content. Default applied: separate permission `notifications.deliveries.view_content`, not granted by default. Should managers see bodies by default?
8. No scheduler runs in production (FP-319). Until one exists, retries, daily-limit deferrals, lost-event recovery and the retention purge do not run by themselves. Accept, or raise FP-319's priority?
9. Real drivers and the row lock. The send call currently runs inside the transaction that holds the delivery's row lock (fine for `log` and `null`). Before a real provider driver ships, that call must move out of the lock (follow-up row 14). No action now.
10. Credential key. Credentials are encrypted with the existing `APP_KEY` (no new secret). Losing or replacing `APP_KEY` without listing the old one in `APP_PREVIOUS_KEYS` makes every stored credential unreadable (deliveries then fail `credentials_undecryptable`; the admin re-enters them). `docs/database.md` §4.4 keeps tenant database credentials under a separate key; if the owner wants provider credentials under a separate key too, that is a new secret and is a one-class change (follow-up row 8).
11. Nested CSS in email templates. Because any `}}` outside a placeholder is refused, a template with nested CSS like `@media{a{b:c}}` cannot be saved; write it with spaces (`} }`) or use a flat stylesheet. Accept?
12. Customer merge. Merging customers does not move consents (AC-119): the surviving customer must opt in to marketing again.
13. On-leave staff. On-leave employees do not receive in-app alerts (they are outside the platform's acting set). Should alerts queue for them instead?
