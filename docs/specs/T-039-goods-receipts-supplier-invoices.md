# T-039: Goods receipts and purchase returns (supplier invoices and payments split out)

Backlog row FP-255 ("Goods receipts, supplier invoices, returns and supplier payments"), **widened by T-006**: receive in a different unit from the order; price variance normalised per base unit; settle `grn_return`. Branch `ai/T-039-goods-receipts-supplier-invoices`. Decisions: `docs/decisions/T-039-goods-receipts-supplier-invoices.md` (cited as D-n). Written spec-ahead, documents only: `ba` has no shell and no git and claims nothing about history, any gate or any built code. Facts about T-031, T-033 and T-034 below are read from their **specs, plans and decisions in sibling worktrees**, none of which is in this branch's tree; the architect must confirm each against the tree this task is built on (section "Dependencies").

**The row is split (D-1).** This task builds **goods receipt notes (GRN) and purchase returns**, with the order rollup, the stock-ledger cost, the price history and the events a later posting task needs. **Supplier invoices (with the three-way match) and supplier payments are proposed as two follow-up rows** (section "Proposed follow-up rows"); the three-way match **rules** are pinned in D-14 so the follow-up does not re-decide them, and this task builds nothing that contradicts them.

## Problem / goal

A shop can order goods (T-034) and the stock ledger can hold stock (T-031), but nothing records that a delivery physically arrived, in what unit, at what price, or that part of it was sent back. This task builds the **goods receipt**: a numbered document that says "these goods, in these units, arrived at this location, from this supplier, at this price, optionally against this purchase order". Posting it (one transaction) writes the stock ledger through T-031's published contract, tells the purchase order how much of each line arrived (T-034's base-to-base rollup), records the price in the price history, and emits the event a later task posts to the journal. It also builds the **purchase return**, which sends goods back and takes them out of stock.

Two things the product owner asked for drive the design: goods may arrive **in a different unit from the order** (an order for 10 cases, a delivery of 240 singles), and a **price difference between order and delivery must be compared per base unit**, never per document unit, so a case price is never subtracted from a single price.

## Users affected

- **Receiving clerk / storekeeper**: records what arrived, in the unit on the delivery note.
- **Purchasing clerk / branch buyer**: sees what has arrived against orders and what was returned.
- **Branch manager / approver**: holds the key that posts a receipt or a return (stock and money change on post).
- **Owner / accountant**: needs exact money, a gapless numbered trail, an audit of every change, and the figures a later task posts to the journal without re-deriving them.
- **Developers of FP-250 (done as T-031), FP-262, FP-265, the follow-up rows, FP-256**: consume the tables, the events and the per-base-unit price figures.

## User stories

- As a receiving clerk, I want to record a delivery against a purchase order in the unit written on the delivery note, so that I do not convert cases to singles by hand.
- As a receiving clerk, I want to receive part of an order now and the rest later, so that a short delivery does not block the stock that arrived.
- As a receiving clerk, I want free bonus units on a line to enter stock at no cost, so that the stock quantity is right and the average cost is not overstated.
- As a receiving clerk, I want to receive goods that have no order, so that a walk-in delivery is not blocked.
- As a branch manager, I want a receipt to change stock and the order only when it is posted, and to be unchangeable afterwards, so that what was posted is what the books say.
- As a purchasing clerk, I want the order to show it is partly or fully received, counted in base units, so that a delivery in a different unit neither closes a half-empty order nor leaves a full one open.
- As an accountant, I want the price on the delivery compared with the price on the order per base unit, so that a case price is never booked against a single price as a variance.
- As a storekeeper, I want to return goods to a supplier, in a smaller unit than they came in if needed, so that one broken bottle out of a case is one bottle out of stock.
- As an owner, I want every change audited, every document numbered without gaps, and a user to act only inside their branches.
- As a finance developer (FP-262), I want one event per posted receipt or return carrying the values the stock ledger actually used, so that the journal can be posted without re-deriving them.

## Acceptance criteria

Refusals use a closed vocabulary of named reasons. T-030 / T-034 names are reused for the same cause: `validation`, `not_found`, `not_authorised`, `replay_conflict`, `out_of_range`, `unit_unresolvable`, `inherited_unit_mismatch`, `numbering_refused`, `number_too_long`, `pricing_refused`, `unknown_product`, `product_not_purchasable`, `unknown_tax_group`, `inactive_tax_group`, `no_default_tax_group`, `unknown_branch`, `unknown_location`, `unknown_supplier`, `supplier_inactive`, `too_many_lines`, `no_lines`, `locked`, `invalid_transition`, `order_not_open`, `currency_required`. This task adds: `order_item_mismatch`, `supplier_mismatch`, `product_mismatch`, `receipt_not_posted`, `over_return`, `tracking_not_supported`, `charges_unapportionable`, `ledger_refused`, `ledger_inconsistent`, `receipt_already_posted`, `order_application_refused`. A foreign refusal (unit, pricing, numbering, access, stock ledger, order rollup) is carried as the **cause** on a purchasing refusal that names the reason; `code()` reports the purchasing reason (T-030 D-67, T-034 AC-52). Every refusal leaves the database, the audit trail, the outbox and the stock ledger exactly as they were.

**Audit action names** (snake case, module prefix, as T-034): `purchasing_receipt_created`, `purchasing_receipt_updated`, `purchasing_receipt_line_added`, `purchasing_receipt_line_updated`, `purchasing_receipt_line_removed`, `purchasing_receipt_posted`, `purchasing_receipt_cancelled`, `purchasing_return_created`, `purchasing_return_updated`, `purchasing_return_line_added`, `purchasing_return_line_updated`, `purchasing_return_line_removed`, `purchasing_return_posted`, `purchasing_return_cancelled`. **Outbox event types are dotted**: `goods_receipt.posted`, `purchase_return.posted`.

**Ids:** every document and line id is caller-supplied (a ULID, folded to upper case on input), doubling as the idempotency key (D-5), as T-034 documents. Money, quantities, rates and percentages are strings or integers on input and four-decimal strings on output; never a float (T-034 AC-46).

### A. Goods receipt: header and lines (draft)

- AC-1: Given an employee holding `purchasing.receipts.manage` at the branch of location L, When they create a receipt with a caller-supplied id, an active supplier S, L, a `received_date`, and optionally an order O, `supplier_dn_no`, `currency`, `exchange_rate`, `other_charges` and `notes`, Then a `draft` receipt exists with a number from `DocumentNumbers::next('grn', branch)` (default prefix `GRN`, D-8), `supplier_id`, `order_id` (null for a direct receipt), `currency` (explicit, else O's currency when O is given, else S's, else the branch's currency; `currency_required` only if the branch has none), `exchange_rate` default `1.00000000`, `other_charges` default `0.0000`, every total `0.0000`, `posted_at` and `posted_by` null, `created_by` and `updated_by` set to the actor, and exactly one audit row `purchasing_receipt_created` carrying the location's `branch_id`.
- AC-2: Given a create, When L does not exist, is soft-deleted, is not `is_active`, is not `is_purchasable_to`, has **no branch** (a branch-less central warehouse, as T-034 D-40), or its **branch is not active** (T-034 AC-41; D-30 of this task), Then it is refused `unknown_location` and no number is consumed. When S is unknown or soft-deleted it is `unknown_supplier`; when S is inactive and **no order is given** it is `supplier_inactive`; **when an order is given, an inactive S is accepted** (T-034 AC-13: existing orders can still be received).
- AC-3: Given a create naming an order O, When O is unknown, Then `not_found`; When O's status is not `approved`, `partially_received` or `received` (that is `draft`, `pending_approval`, `sent`, `closed`, `cancelled`), Then `order_not_open`; When O's supplier is not S, Then `supplier_mismatch`; When L is not O's delivery location, Then `unknown_location` (D-6). A `received` order is accepted (an over-receipt or a late line, D-3). Nothing is written and no number is consumed.
- AC-4: Given a create, When `received_date` is missing, not a real calendar date, later than the branch's business date of the server clock, or (with an order) earlier than the order's `order_date`, Then it is refused `validation`. The date is client-supplied (a delivery can be entered the next day); the posting date later tasks use is this date (D-9).
- AC-5: Given a create or header edit, When `exchange_rate` is not a positive `DECIMAL(18,8)` string, `other_charges` is negative, a float or over `DECIMAL(18,4)`, `supplier_dn_no` is over 60 characters, `notes` over 2000, or `currency` is not three letters, Then it is refused `validation` (or `out_of_range` for an overflow). Text is trimmed; `currency` is folded to upper case.
- AC-6: Given a draft receipt, When a line is added with a caller-supplied line id, a product, a `unit_id`, a `quantity` (zero or more), a `free_quantity` (zero or more, default `0.0000`), a `unit_cost` (non-negative, **per line unit**), an optional explicit `tax_group_id`, an optional `order_item_id` and optional `notes` (at most 500 characters, else `validation`, D-26), Then the line stores the unit quad (`unit_id`, `quantity`, `unit_factor`, `base_quantity`) from the unit code (AC-8), the free quantity and its base equivalent (AC-9), the tax group (AC-14), the money (AC-12), and one audit row `purchasing_receipt_line_added` exists. A line with `quantity` and `free_quantity` both zero is refused `validation`.
- AC-7: Given a line add or edit, When the product is unknown, inactive or soft-deleted (`unknown_product`), or not purchasable (`product_not_purchasable`, the T-034 D-39 definition: active, `is_purchasable`, `track_stock`, type `simple`, `variant` or `composite`), or its `tracking_mode` is not `quantity` (`tracking_not_supported`: batch and serial receiving is FP-252), or the quantity is negative, a float, not a decimal, over `DECIMAL(18,4)` (`validation`, `out_of_range`), or the request carries `batch_no`, `expiry_date`, `mfg_date` or `serial_numbers` (`validation` naming the field, D-12), Then it is refused and the receipt is unchanged.
- AC-8 (receiving unit versus order unit): Given a line, Then its unit quad comes **only** from the unit code, never from arithmetic in purchasing: (a) a line with **no** `order_item_id`, or whose unit differs from the order line's unit, is resolved fresh with `UnitResolver::snapshot()`; (b) a line **with** an `order_item_id` whose `unit_id` equals the order line's `unit_id` is resolved with `snapshotInherited()` against the order line, so its `unit_factor` equals the order line's frozen factor even if the unit ladder has moved since the order (D-4). A failed resolution is `unit_unresolvable` or `inherited_unit_mismatch` carrying the resolver's refusal, and the line is not stored. `quantity` is rounded to the unit's precision by the resolver. Receiving in the **product's stock unit** against an order line in cases is case (a) and is always allowed.
- AC-9 (free quantity): Given a line with a `free_quantity`, Then it is in the **same unit** as `quantity` and converted with the **same frozen `unit_factor`**; its base equivalent (`base_free`) is obtained from the unit code, never by multiplying in purchasing, and is reconstructible from the stored row. A product whose stock unit has precision 0 and a free quantity or quantity whose base equivalent has a fractional part is refused `unit_unresolvable` (the ledger would refuse `fractional_base_quantity`; refuse it at the document).
- AC-10: Given an `order_item_id`, When it does not exist or belongs to a different order than the receipt's, Then `order_item_mismatch`; When the receipt has no order, Then `order_item_mismatch`; When the line's product differs from the order line's product, Then `product_mismatch`. Two lines of one receipt may name the same order line (for example 2 cases plus 3 loose singles), and the same product may appear on several lines in different units (D-3).
- AC-11 (over-receipt, partial receipt): Given an order line of 10 cases at factor 24 (base 240), When receipts totalling more than 240 base arrive over any number of receipts, Then **every one is accepted**, recorded and posted; there is no tolerance and no refusal (D-3, owner question Q-1, T-034 Q-1). When less than the ordered base arrives, the order is `partially_received`. A receipt result and a `get` expose, per line with an `order_item_id`, `ordered_base_quantity`, `received_base_quantity_before` and a boolean `over_received` that is true when the order line's received base after this line exceeds its ordered base; the flag is informational and never blocks.
- AC-12 (money): Given a line, Then money is exact decimal, half-up at four decimals at each step: the whole line is quoted by the T-034 `PurchaseLinePricing` contract with `quantity` (**paid** quantity only; free units carry no price), `unit_cost`, discount percent `0.00`, the resolved tax group, `base_quantity` and the **caller-supplied pricing date** `received_date` (the pricing engine must accept the date from the caller rather than read the clock, D-24); purchasing computes no tax itself. A paid `quantity` of zero (a free-only line) is quoted as a zero-quantity line and yields zero money (dependency, section "Dependencies"). The line stores `tax_amount` and `line_total` (net plus tax for an exclusive group; gross for an inclusive one). The **ex-tax line amount** is `line_total - tax_amount` in both cases and is the basis for inventory value (D-10). Worked example: 10 cases, `unit_cost` 4800.0000, a 0% tax group gives `line_total` 48000.0000, `tax_amount` 0.0000.
- AC-13: Given a receipt, Then header `subtotal` is the sum of line ex-tax amounts, `tax_total` the sum of line `tax_amount`, and `total` = sum of line `line_total` plus `other_charges`. An empty receipt has every total `0.0000` plus `other_charges`. Worked example: lines with `line_total` 48000.0000 and 120.5000, tax 0 and 10.0000, `other_charges` 200.0000 gives `subtotal` 48110.5000, `tax_total` 10.0000, `total` 48320.5000. (Other charges carry no tax in this task, D-10.)
- AC-14: Given a line with no explicit `tax_group_id`, Then its group is the product's `purchase_tax_group_id`, else `TaxGroupDirectory::defaultGroupId()`, else `no_default_tax_group`; an unknown group is `unknown_tax_group`, an inactive one `inactive_tax_group`; any other pricing failure is `pricing_refused` carrying the engine's refusal. The group id used is stored on the line. A line linked to an order line does **not** inherit that line's tax group unless none resolves (the delivery is taxed as the product is taxed today); the stored value is a snapshot.
- AC-15 (landed cost, stated before posting): Given a draft receipt with `other_charges` > 0, When it is read, Then `landed_cost` per line is **not yet stored** (null), because charges can still change; it is computed and stored at post (AC-24).
- AC-16: Given a receipt that is not `draft`, When any header or line add, edit or remove is attempted, Then it is refused `locked`. In `draft`, edit and remove work; a removed line is deleted and its before-image is in the audit row; removing the last line leaves a valid draft; a receipt with 200 lines refuses the 201st with `too_many_lines`. Edits re-quote the receipt totals in the same transaction.
- AC-17: Given a draft receipt, When `order_id` or `supplier_id` or `location_id` is edited while lines exist, Then it is refused `locked` naming the field (change them by cancelling the draft and creating a new one); when no lines exist the edit is validated as in AC-2 and AC-3.
- AC-18: Given a draft receipt, When it is cancelled, Then it is `cancelled`, one audit row `purchasing_receipt_cancelled` exists, **no stock, order or event effect exists**, and the number is never reused. A second cancel is a no-op success with no audit row. A **posted** receipt is refused `receipt_already_posted` (its correction is a purchase return, section D, D-7).

### B. Goods receipt: posting

- AC-19: Given a draft receipt with at least one line, When an employee holding `purchasing.receipts.post` at its branch posts it, Then **in one transaction**: every precondition in AC-21 to AC-23 is re-checked; landed cost is computed (AC-24); the stock ledger is written (AC-25); the order rollup is applied (AC-27); the price history is written (AC-29); the status becomes `posted` with `posted_at` (server time) and `posted_by`; one audit row `purchasing_receipt_posted` exists; and one `goods_receipt.posted` event is written (AC-30). If any step fails, **none** of it survives and the receipt stays `draft`.
- AC-20: Given a receipt with no lines, When posted, Then `no_lines`. Given a receipt already `posted`, When posted again, Then the receipt is returned unchanged with `replayed = true`, no second movement, no second order application, no audit row and no event (idempotent by outcome). A `cancelled` receipt is refused `invalid_transition`.
- AC-21: Given a post, Then the facts that can change between draft and post are re-checked with the same refusals as at entry: each product is still purchasable and quantity-tracked, L is still an eligible location, the order (if any) is still `approved`, `partially_received` or `received`, and the unit quad on each line is **not** re-resolved (snapshot, not recompute).
- AC-22: Given a line whose base quantity plus base free is zero after rounding, When posted, Then it is refused `validation` naming the line (it would write a zero-quantity movement, which the ledger refuses).
- AC-23: Given `other_charges` > 0 and every line's ex-tax amount zero, When posted, Then it is refused `charges_unapportionable` (D-10); with `other_charges` of zero, an all-zero-price receipt (free goods, D-11) posts normally.
- AC-24 (landed cost): Given a post, Then `other_charges` is apportioned across lines **pro rata to the line ex-tax amount** (AC-12), each share rounded half-up at four decimals, the rounding remainder added to the line with the largest ex-tax amount (the earliest on a tie) so the shares sum **exactly** to `other_charges`; each line's **inventory money** is its ex-tax amount plus its share; and `landed_cost` (per line unit) is stored as `ROUND(inventory money / quantity, 4)`, or `0.0000` when the paid `quantity` is zero. Worked example: lines with ex-tax amounts 48000.0000 and 12000.0000 and `other_charges` 600.0000 get shares 480.0000 and 120.0000, inventory money 48480.0000 and 12120.0000; the first line's quantity 10 gives `landed_cost` 4848.0000.
- AC-25 (cost into the stock ledger, through T-031's contract only): Given a post, Then each line becomes **one `grn` command** to the published `StockLedger` (batch, all lines of the receipt, input order), with: location L; the product; **quantity moved = `base_quantity + base_free`** in the product's stock unit (the only movement type that adds free units, `docs/database.md` section 6.5); `reference_type = grn`, `reference_id` = the receipt id, `reference_line_id` = the **receipt line id**; the money the ledger takes in = the line's inventory money (AC-24) **times the receipt's `exchange_rate`, rounded half-up once at four decimals** (the ledger is in company currency, D-10), supplied in a shape the contract permits that does **not** re-multiply a rounded per-unit cost (T-031 AC-26): the ledger's `unit_cost` is **the whole line's exact money** and `cost_quantity` is `"1"` (not the paid quantity that T-031's plan suggests, D-27); `employee_id` = the poster. Free units therefore move quantity and no money. Worked example (T-031 AC-25): 10 cases at 4800 with 2 free cases, factor 24, from an empty level gives movement quantity 288.0000, value 48000.0000, `avg_cost` 166.6667.
- AC-26: Given two lines of one product in different units on one receipt (2 cases plus 3 loose singles), When posted, Then two movements are written (two distinct `reference_line_id` values) and the level holds the sum. Given a line posted and the same post replayed after a crash, Then the ledger's replay (`replayed = true`) is accepted **only when the receipt is already `posted`**; a `replayed = true` result for a line of a receipt that was `draft` at the start of the post is refused `ledger_inconsistent` and the whole post rolls back (a caller must check the flag and never infer, T-031 AC-49).
- AC-27 (order rollup, base to base): Given a posted line with an `order_item_id`, Then `ApplyReceivedQuantity` is called **once per such line** inside the post transaction, with application id = **the receipt line id**, `received_base_delta` = the line's **`base_quantity` (paid only; free units are not counted against the order, D-3)**, and `received_quantity_delta` = that base amount expressed in the **order line's unit**, obtained from the unit code and never by multiplication in purchasing (zero is allowed when the base delta is non-zero, T-034 D-47). A line with `base_quantity` zero (a free-only line) applies nothing. A refusal is `order_application_refused` carrying it, and the post rolls back. The application's result exposes `replayed`; when it is `true` for a line of a receipt that was `draft` at the start of the post, the post is refused `order_application_refused` with detail `replayed_for_draft` and rolls back (D-28; the same principle as AC-26).
- AC-28: Given the order rollup, Then the order's status follows T-034 AC-69 to AC-72: receiving 120 base against a 240-base line (5 cartons of 12 against 10 cases of 24) leaves the order `partially_received`, not `received`; a further 120 base makes it `received`; two receipts may each arrive in a different unit. The order is **never** closed or cancelled by this task.
- AC-29 (price history): Given a posted line whose paid `base_quantity` is greater than zero, Then one `purchase_price_history` row is written in the post transaction with `product_id`, `supplier_id`, `grn_item_id`, `unit_cost` **per stock unit** = `ROUND(line ex-tax amount / paid base_quantity, 4)` (supplier price, excluding landed charges), `currency` = the receipt's, `quantity` = paid `base_quantity`, `effective_date` = `received_date`, `source = grn`. The row carries **no unit column** (it is below the document layer, D-13). A line with paid base zero writes none. A replayed post writes none. Worked example: 10 cases (base 240) at 48000.0000 gives 200.0000 per stock unit.
- AC-30 (event for the journal): Given a post, Then one outbox event `goods_receipt.posted` is written in the same transaction (idempotent with the post), carrying ids, base figures and money only (never a name, address or bank detail): `grn_id`, `number`, `supplier_id`, `order_id`, `location_id`, `branch_id`, `received_date`, `currency`, `exchange_rate`, `other_charges`, `subtotal`, `tax_total`, `total`, and per line `grn_item_id`, `product_id`, `order_item_id`, `base_quantity`, `base_free`, `unit_cost`, `landed_cost`, `tax_amount`, `line_total`, `inventory_money` (document currency), `ledger_value` (company currency, the figure the stock ledger actually used and returned, so a posting rule never re-derives it), `price_variance_per_base` (AC-32). A replay or a refusal writes none.
- AC-31 (what this task does not post): Given a post, Then no `journal_entries` or `journal_lines`, no `ap_documents`, no `batches` or `serials` row is read or written; no `quantity_incoming` value is written; ledger posting of a receipt is FP-262, consuming AC-30's event (T-033's `PostingService` is not called here, D-15).
- AC-32 (price variance per base unit, order versus delivery): Given a posted or draft line with an `order_item_id`, Then `price_variance_per_base` is returned as a four-decimal string: `received_cost_per_base - ordered_cost_per_base`, where each side is **its own ex-tax net amount divided by its own paid `base_quantity`** and rounded half-up at four decimals before the subtraction (the order side uses the order line's `subtotal - discount` net per T-034 AC-43, the receipt side the AC-12 ex-tax amount); a side whose paid base is zero makes the figure null, **and so does a receipt whose `currency` differs from its order's** (two currencies are never subtracted; D-19). A positive value means the delivery cost more per base unit than the order. It is **never refused, never blocked and has no tolerance** (D-14) and is computed from stored snapshots. Worked example (corrected, D-18): an order of 10 cases at `unit_cost` 480.0000 (net 4800.0000, base 240, 20.0000 per base) received as 240 singles at 20.0000 gives variance `0.0000`, **not** a 24x difference; received as 240 singles at 21.0000 gives `1.0000`. Counter-check: the same order at 4800.0000 per case (200.0000 per base) received as 240 singles at 20.0000 gives `-180.0000`. An order and a receipt in different currencies give null.
- AC-33: Given a post of a receipt in a currency different from the branch's currency, Then it posts with the receipt's `exchange_rate` applied once to the ledger money (AC-25); no rate is looked up; no total is expressed in a base currency anywhere else (T-034 D-20, D-10).

### C. Goods receipt: reads and rules of immutability

- AC-34: Given `get receipt`, When the caller holds `purchasing.receipts.view` at the receipt's branch, Then header and every line are returned (the unit quad, free quantity and its base equivalent, `unit_cost`, `landed_cost` once posted, tax, totals, status, `order_id`, `order_item_id`, AC-11's and AC-32's figures), all money as four-decimal strings; another caller is refused; an unknown id is `not_found`.
- AC-35: Given `list receipts`, When called, Then only receipts at branches where the caller holds `purchasing.receipts.view` appear, newest first by id, **keyset-paged** (`before_id`, T-028 `Pager`), default 25, an oversize `page_size` clamped to 100, filterable by status, supplier, order, location and `received_date` range (a range whose end precedes its start is `validation`); no match is an empty list; branch scoping is decided as T-034 AC-35 (once at a filtered branch, else per branch row including inactive and soft-deleted ones).
- AC-36: Given a posted receipt, When the product's unit ladder, a tax rate, a supplier's details or the order changes later, Then reading the receipt returns the stored `unit_factor`, `base_quantity`, tax, `line_total`, `landed_cost` and totals unchanged; a **posted receipt is never modified**: no HTTP route, handler or command edits or deletes a posted receipt row or line (a static test with a planted-violation control proves it).

### D. Purchase returns

- AC-37: Given an employee holding `purchasing.returns.manage` at the branch of location L, When they create a return with a caller-supplied id, a supplier S, L, a `return_date`, a `reason` (1 to 500 characters) and optionally a receipt G (`grn_id`), `debit_note_no` (the supplier's own document number, at most 60 characters), `currency`, `exchange_rate` and `notes`, Then a `draft` return exists with a number from `DocumentNumbers::next('purchase_return', branch)` (default prefix `PRN`, D-8), the other fields stored, and one audit row `purchasing_return_created` carrying the branch. L is validated as AC-2 (including the active-branch rule). The `return_date` rules are AC-63. A **deleted** or unknown S is `unknown_supplier`; an **inactive** S is accepted (goods go back).
- AC-38: Given a create naming G, When G is unknown (`not_found`), not `posted` (`receipt_not_posted`), for a different supplier (`supplier_mismatch`) or at a different location (`unknown_location`), Then it is refused and no number is consumed. `currency` defaults to G's; `exchange_rate` to G's. A return without G is a **direct return** (allowed; D-7); its `currency` is the explicit value, else S's currency, else the branch's currency, and `currency_required` only if none exists (D-20); `exchange_rate` defaults to `1.00000000`.
- AC-39: Given a draft return, When a line is added with a caller-supplied id, a product, a `unit_id`, a positive `quantity`, a `unit_cost` (the credit price per line unit, required, non-negative), an optional `tax_group_id` and, when G is set, optionally a `grn_item_id`, Then the line stores the unit quad and the money (as AC-12 with discount 0) and one audit row exists. Refusals as AC-7 for product, quantity and tracking.
- AC-40 (return in a different unit): Given a line with a `grn_item_id`, Then the unit quad comes from `snapshotInherited()` against that receipt line, so the line **inherits its frozen `unit_factor`** whether the return is in the receipt line's own unit or in the product's stock unit (one broken bottle out of a received case: quantity 1, stock unit); a unit that is neither is `inherited_unit_mismatch`. A line **without** `grn_item_id` is resolved fresh with `snapshot()`. The `grn_item_id` must belong to G, else `not_found`; its product must equal the line's, else `product_mismatch`. A line with a `grn_item_id` on a return that has no G is `validation`.
- AC-41 (tax on a return): Given a line, Then its tax group is the linked receipt line's `tax_group_id` when a `grn_item_id` is given, else the AC-14 chain; refusals as AC-14; the header totals are the sums as AC-13 (`subtotal`, `tax_total`, `total`, no `other_charges`), the credit the supplier owes.
- AC-42: Given a draft return, Then header and line edits, removals, the 200-line limit, the `locked` rule for non-drafts and the draft cancel behave exactly as AC-16 to AC-18 (cancelling a posted return is refused `receipt_already_posted`, the one name serving both documents, D-7).
- AC-43: Given a draft return with at least one line, When an employee holding `purchasing.returns.post` at its branch posts it, Then **in one transaction**: facts are re-checked; the over-return rule (AC-44) holds; one **`purchase_return` command per line** goes to the stock ledger (batch): the product, L, **quantity = the line's `base_quantity`**, `reference_type = purchase_return`, `reference_id` = the return id, `reference_line_id` = the return line id, **no cost supplied** (the ledger values every outbound movement at the location's average cost read under its lock, `docs/database.md` section 6.5 note 6; T-031 AC-28); the status becomes `posted` with `posted_at` and `posted_by`; one audit row and one `purchase_return.posted` event (AC-46) are written. Any refusal rolls everything back and the return stays `draft`.
- AC-44 (over-return): Given a return line with a `grn_item_id`, When the sum of `base_quantity` over this line and every **posted** return line against the same receipt line would exceed that receipt line's `base_quantity + base_free`, Then the post is refused `over_return` naming the line and the returnable base remaining; at exactly the limit it is accepted. Draft returns reserve nothing. The receipt line is locked for the check (D-7). A direct return line has no cap in this task (the ledger's own guard applies).
- AC-45: Given a post, When the location forbids negative stock and the return would take on-hand below zero, Then it is refused `ledger_refused` carrying the ledger's `insufficient_stock` (naming the on-hand figure) and nothing is written; given a replayed ledger result for a return that was `draft`, `ledger_inconsistent` (as AC-26). A return already `posted`, posted again, is returned unchanged with `replayed = true` and no further effect.
- AC-46 (event, and the variance a return creates): Given a post, Then `purchase_return.posted` carries ids and money only: `return_id`, `number`, `supplier_id`, `grn_id`, `location_id`, `branch_id`, `return_date`, `currency`, `exchange_rate`, `subtotal`, `tax_total`, `total`, and per line `return_item_id`, `grn_item_id`, `product_id`, `base_quantity`, `unit_cost`, `tax_amount`, `line_total`, and `ledger_value` (company currency, the signed outbound value the ledger used at average cost). The difference between the credit and the ledger value is the purchase price variance FP-262 posts; this task computes none.
- AC-47 (effect on the order): Given a posted return, Then **no purchase order column, status or application is changed** (D-7): returned goods were received, the order's received base is not reversed, and `ApplyReceivedQuantity` is not called with a negative delta by this task. A replacement delivery is a new receipt, accepted as a possible over-receipt (AC-11).
- AC-48 (`grn_return` settled): Given the movement type `grn_return`, Then **this task never writes it and defines no document for it**: a return of received goods is `purchase_return` against a return document (D-2); the stock ledger already refuses `grn_return` as `type_has_no_document`. A static test finds no producer of `grn_return` in the module.
- AC-49: Given `get return` and `list returns`, Then the read rules are AC-34 and AC-35 with the key `purchasing.returns.view` and the filters status, supplier, `grn_id`, location and `return_date` range.

### E. Cross-cutting

- AC-50: Given every slice of this task (create, edit header, add/edit/remove line, post, cancel, get, list, for receipts and returns), When the caller lacks the key at the document's branch, Then **the slice itself** refuses `not_authorised` carrying the access reason and writes nothing (no slice relies on the route layer, FP-452; reads check too, T-034 D-36). Keys: `purchasing.receipts.view`, `purchasing.receipts.manage`, `purchasing.receipts.post`, `purchasing.returns.view`, `purchasing.returns.manage`, `purchasing.returns.post`, all **branch-scoped**, asked with the **location's branch** at creation and the **document's stored branch** afterwards, never a caller-supplied different one; a grant scoped to branch A is refused at B; a company-wide grant is accepted anywhere; a branch-scoped key asked with no branch is refused `BranchRequired`. Each key is declared through `DeclaresPermissions` and visible to the registry sync.
- AC-51: Given a suspended, inactive or deleted employee, When they call any slice, Then it is refused with the resolver's reason and nothing is written. `received_by`-style attribution is the actor, never a caller-supplied value.
- AC-52 (idempotency): Given a create or a line add with a caller-supplied id, When replayed with an identical normalised payload, Then the original is returned with `replayed = true`, no second number consumed, no audit row and no event; the same id with a different payload is `replay_conflict` naming the id. Posting is idempotent by outcome (AC-20, AC-45). Edits of a draft are not replayed by id.
- AC-53 (document numbers): Given receipts and returns, Then each gets its number **at creation, inside the creating transaction, taken last among the locks**, in its own sequence (`grn`, `purchase_return`), gapless because drafts are cancelled, never deleted; a refusal, a replay or a rollback consumes none; a number over 30 characters is `number_too_long`, a numbering failure or a unique violation on the number is `numbering_refused`, never an unhandled error (T-034 AC-52, AC-90).
- AC-54 (audit): Given any write, Then **exactly one `AuditTrail::record()` row per write per subject** is written in the same transaction (module `purchasing`, actor, action, subject, before and after, the document's `branch_id`); a refusal, a replay or a rollback writes none; actions are declared through `DeclaresAuditActions`. The stock ledger writes no audit row of its own (T-031 AC-76), so the document's post row is its trail. T-034's `ApplyReceivedQuantity` writes its own audit row and event for the **order** (a different subject) per applied line; those are not counted against this task's one row for the receipt, and this task writes no row for the order (D-22).
- AC-55 (atomicity and lock order): Given a post, Then ledger, order application, price history, status change, audit and event are one transaction; the document header is locked first, then the referenced order header (inside `ApplyReceivedQuantity`), and the stock levels are locked by the ledger in its own ascending order; the order of these three is fixed by the architect and documented, and `UnitResolver`, pricing and permission reads happen **before** any lock (T-034 D-22). **[ENGINE; NOT VERIFIED]**
- AC-56 (concurrency, ENGINE_HOLD): Given two posts racing for the same receipt, or two receipts racing for one order line, or two return posts racing for one receipt line, Then exactly one effect is applied per receipt line, no update is lost, the over-return cap holds, and the loser of the same-receipt race is a replay. These tests are **written and skipped** under `ENGINE_HOLD` and reported **NOT VERIFIED**; the stand-in tests (schema, model, state machine, arithmetic, validation, cross-tenant) are written **and run** at each gate when the gate is free, and no report claims a green gate that was not run (T-034 AC-98).
- AC-57 (schema): Given the migrations, Then the five new tables (`grns`, `grn_items`, `purchase_returns`, `purchase_return_items`, `purchase_price_history`) are created by per-tenant migrations run against **every** tenant database, **expand-only** (new tables only; no change to an existing table, no drop, rename, truncate or data delete); foreign keys point only at tables that exist (`suppliers`, `purchase_orders`, `purchase_order_items`, `locations`, `products`, `units`, `tax_groups`, `employees`, `grns`, `grn_items`); no `tenant_id`; ids are `CHAR(26)` ascii binary; `ON DELETE` is `RESTRICT` except line tables cascading from their header (no header is ever hard-deleted); every quantity and money column is `DECIMAL(18,4)`, `unit_factor` `(18,6)`, `exchange_rate` `(18,8)`; **`purchase_price_history`, and every other table below the document layer, has no unit column**; `grn_items.free_quantity` is `NOT NULL DEFAULT 0`. The documented columns deferred to other tasks are **absent**: the `[GL]` columns (journal link), `batch_no`, `expiry_date`, `mfg_date`, `serial_numbers` on `grn_items` and `batch_id` on return lines (FP-252), `debit_note` linkage to an AP document (FP-265). The five tables join `tenantTreeTables()`.
- AC-58: Given the cross-tenant rule, Then an id from tenant A is `not_found` in tenant B for each root entity (receipt, return), and the price history is proven **at table level** (a row written in tenant A is absent from tenant B's table; no slice reads price history in this task, D-23); and the new tables are part of the shared tenant-table list T-022's sweeps read (T-034 AC-88).
- AC-59 (boundary): Given the module source, Then a static test finds **no write to another package's table** (including `purchase_orders`, `purchase_order_items`, `stock_levels`, `stock_movements`), **no read of** `unit_conversions`, `units.factor`, `units.base_unit_id`, tax tables, `number_sequences`, `workflow_*`, stock tables, journal tables or `ap_*` tables, **no multiplication by a factor column** and no percent arithmetic (the pricing scan); order state is changed **only** through `ApplyReceivedQuantity`, stock **only** through the published `StockLedger` contract (the boundary check passes with the module granted only the contract namespaces it uses). Read-only lookups of `products`, `locations` and `branches` for existence and facts follow the T-034 D-38 precedent.
- AC-60: Given malformed input of any kind (non-ULID id, impossible date, wrong type, null where a value is required, an unknown status filter, an over-long string, a float in a money or quantity field), Then the result is a named `validation` refusal, never an unhandled exception; a value that cannot fit `DECIMAL(18,4)` is `out_of_range`.
- AC-61: Given an operation touching several lines (a post of N lines, a multi-line create), Then each distinct product's unit and each line's tax are resolved at most once per line, the unit lookups happen before any lock, and the QA report records the measured query count for adding one receipt line and posting a 50-line receipt (the per-line resolver cost is FP-426; this task must not worsen it).
- AC-62: Given the ledger contract is called, Then **no field outside the contract's command shape** is sent (no `unit_id`, `unit_factor`, `base_quantity`; quantities are base only), `already_happened` is **not** set (a receipt is never "already happened"), and a ledger refusal (any reason) is carried as the cause of `ledger_refused`.

- AC-63 (`return_date`, D-21): Given a return create or header edit, When `return_date` is missing, not a real calendar date, later than the branch's business date of the server clock, or (with a receipt G) earlier than G's `received_date`, Then it is refused `validation` and no number is consumed. A direct return has no lower bound beyond a real date. A return dated the same day as G's `received_date` is accepted.

## Non-functional requirements

- **Exactness**: money and quantities are exact decimals end to end; no float in code, JSON or storage; rounding only where named (AC-12, AC-24, AC-25, AC-29, AC-32).
- **Integrity**: a posted receipt or return is immutable; stock, order and price history change atomically with the status; numbers are gapless (AC-53).
- **Security**: every slice checks its own permission (AC-50); posting is a separate key from editing (segregation); no secret and no personal data in events or logs.
- **Tenancy**: no tenant column; the connection is the boundary (AC-58).
- **Performance**: list reads paged (maximum 100); 200 lines per document; per-line resolver cost measured, not capped (AC-61); a 50-line receipt posts as one ledger batch, not 50 calls.
- **Auditability**: one audit row per write (AC-54).
- **Delivery**: `ENGINE_HOLD`: engine-only behaviour (locks, deadlock order, concurrent posts, the unique keys) is specified (AC-55, AC-56) and **NOT VERIFIED** until the engine gate lifts.

## Assumptions

- The tree this task is built on contains T-031, T-033 and T-034 merged; if T-031's table is held by FP-179, ledger-touching steps wait and the rest proceeds, as T-031 AC-77.
- A receipt's branch is its location's branch (the table has no `branch_id`); suppliers are tenant-wide.
- The company currency is the currency of ledger money; `exchange_rate` converts document currency to company currency (`docs/database.md` section 6.5, the money axis); the branch's currency is the default document currency.
- Input tax is recoverable and inventory is valued ex-tax; non-recoverable tax is not modelled (D-10).
- Other charges carry no tax and have no separate account in this task.
- Each line's `base_quantity` is `ROUND(quantity x unit_factor, 4)` computed by the unit code, never here.
- A receipt line `order_item_id` belongs to the receipt's order; a direct receipt has none.
- 200 lines per document and 100 per list page (T-034 D-25).
