### BUG-1 (minor) - claims, hash and "my permissions" count a soft-deleted role the resolver ignores
- **Failing test:** `packages/access/tests/Features/BuildEmployeeClaims/QaClaimsResolverAgreementTest.php` "lets a soft-deleted role contribute to none of the three (AC-43, AC-57, AC-54)"; its control case (a live role) is green.

## Notes (not defects; things nobody asked about)

- **A. `employee_branches.default_employee_id`.** AC-3 says the table holds "exactly" the columns of the spec's list; the list omits the stored generated column that carries AC-8's one-default rule. Plan section 4 declares it; QSS pins it by name. Not filed.
- **B. The employee list has no offset or cursor.** AC-29 asks for "at most a configured page size"; it delivers the first page and no way to the second. A shop with more than 100 employees cannot list the rest. Within the letter of the criterion; worth a backlog row before a real tenant exists.
- **C. Actorless writes.** `actor_required` (D-36) is raised only where a grant needs authority. A deny, a clear, a removal, a status change, a create or a role that confers nothing is accepted with a null actor and audited with `actor_id` null and `actor_type` employee. This is the "guard that permits whenever its input is missing" shape for every operation that has no authority check. Over HTTP the actor cannot be null; FP-206's system actor is the consumer to watch. ESC "does not consult the actor for a role that confers nothing" pins the empty-role case with an actor who holds nothing; the null-actor variant is not tested.
- **D. AC-37 under concurrency.** `LastOwner::requireAnother` is a select followed, in the caller, by a delete or update, inside a transaction, with no `lockForUpdate` anywhere in `packages/access/src` (grep: none). On MySQL's default isolation two concurrent removals of two different owners each see the other as the remaining owner and both commit, leaving zero owners. This is exactly what the [ENGINE] proof was deferred for, and it is a reading, not a test; the engine task should start there (T-009 Note A is the same shape).
- **E. Surrounding whitespace in a PIN.** The framework's `TrimStrings` runs before the policy, so a body of `"7391 "` is accepted and stored as `7391` (AC-47 says a PIN that is not all digits is refused). Harmless today (there is no network verify), consistent while every entry point goes through the middleware, and different for an in-process caller. Not pinned either way; `ba` may want a sentence.
- **F. `authenticated_only` is invisible to the dev refusal loops.** AC-63 accepts the marker and the dev AC-64 loops skip such routes, so re-declaring a sensitive route with it breaks nothing (H1r). QGI pins the skip-list to `GET /me/permissions`; a new entry needs a conscious edit there.
- **G. `detail.reason` is not always one of the closed three.** AC-64 says `not_granted`, `explicit_deny`, `out_of_scope`. For an unregistered key (a server defect, D-26) or a status that changed without a bump, the guard logs the refusal reason itself (`unknown_permission`, `employee_unavailable`). Sensible, documented in the middleware; outside the letter.
- **H. D-14 (case-sensitive `code`) on the engine.** The stand-in compares exactly; a MySQL 8.4 database created with the default `utf8mb4_0900_ai_ci` would treat `C001` and `c001` as one code. The migrations may not name a collation (T-008 rule), so provisioning (FP-206) decides it. Same family as T-009's collation half of AC-2.
- **I. The FP-297 caveat applies here.** `access_log.ip` and `audit_logs.ip` record `REMOTE_ADDR`, the proxy, until FP-297 lands.
- **J. Tests added and the clock.** The new tests add a measured amount to the gate (below); all use the SQLite stand-in; none reaches 127.0.0.1:3306; nothing under `E:` is written.
